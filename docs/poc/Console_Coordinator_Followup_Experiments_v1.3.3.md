## 2. Graphify의 최소 구현과 비교

고정 배포 이름은 `graphifyy`이며 버전·패키지 해시와 repo 커밋은 F01에서 수집 원본과 대조해 잠근다. 첫 구성은 **`--code-only`, LLM 단계 비활성, strict 모드 비사용**, 필요한 extra만 설치하는 방식이다. 명령 존재·LLM 비호출·색인 범위는 실행 로그와 실제 산출물로 확인한다. 그래프 메타데이터에 대상 repo의 build SHA를 남기고 현재 SHA가 다르면 쓰기를 중단하거나 다시 빌드한다. Guardrail은 동일 SHA에서 자기 그래프를 따로 만든다. `INFERRED`와 `AMBIGUOUS` 엣지는 사실/완료 근거로 인용하지 않는다. 추출 엣지도 현재 코드 원문과 대조할 수 있어야 한다.

**비교군:** 그래프 없음과 코드 전용 그래프 제공을 같은 repo·작업·모델·도구·권한·총예산에서 짝지어 비교한다. 그래프 구축/갱신/조회 비용을 포함하고 허용 품질 열화·최소 효과·반복/시간/토큰 상한을 결과 전에 고정한다. strict 모드로 원문 접근을 막는 변인은 첫 비교에 섞지 않는다. 고정 SHA 불일치·색인 누락·동명이인 기호·추론/모호 엣지 사례를 대조한다. 초기 카탈로그의 내용·모델 버전은 비교군에서 같다.

**결과/채택:** 정상 완료·숨긴 결함 발견·잘못된 완료·재질문·재작업·시간·입력/캐시/출력과 부모/자식 전체 토큰을 P20의 분모/계산식으로 기록한다. 기능/정확성을 유지하면서 사전 효과·예산을 충족한 범위만 채택한다. 효과 부족은 보류/기각할 수 있고 색인/계측/회귀 자산은 별도 검증 범위로 재사용한다. 그래프는 완료 판정의 독립 증거가 아니다.

다음 2.2절과 P29~P32는 원 v1.2 본문을 보존했다. 원 번호 T07/T08·5.5절은 원안의 근거 참조다. 현재 실행 번호/순서는 F01~F12와 위 진입 조건을 따른다. P30의 주 입력은 **실제 개발 기록**이며 모의 기록은 변환/거부의 보조 회귀에만 사용한다. 연구 평가 비용은 원본 확인·자료·어댑터·후보 생성/거부·검토/재실행·사용 시 비용까지 모두 포함한다.

### 2.2 연구 실험의 공통 준비·판정·비용 규칙

**도입 판단을 세 번 나눈다.** ① 고정 원본 또는 최소 방법을 실행할 수 있는가, ② 현재 방법보다 품질·진행·비용이 나은가, ③ 검증된 후보를 운영 기준으로 편입할 수 있는가를 따로 판정한다. ① 통과만으로 ②의 개선이나 ③의 운영 채택을 선언하지 않는다. 원본 실행이 안 되면 원인·필요 어댑터·재구현 비용을 남기고 해당 경로는 `INCONCLUSIVE`로 둔다. 범위를 명시한 방법 재구현을 별도 후보로 시험할 수 있으나 원 논문 재현으로 표시하지 않는다.

| 고정할 조건 | 실험 규칙 |
| --- | --- |
| 비교할 구현 형태 | 기존 수작업/고정 카탈로그, 공식 원본의 제한된 실행, 얇은 어댑터, 방법만 재구현을 구분한다. 가능한 경로만 실행하고 실행하지 않은 경로는 비워 둔다. Rust 이식 필요성과 공수를 결과로 판단한다. |
| 입력과 독립 평가 | T08에서 작업·실패 계열 단위로 작성용, validation, 최종 평가를 나눈다. 같은 기록의 변형이 양쪽에 섞이는지 확인한다. 후보 생성기와 대상 에이전트에는 최종 정답·결함 위치를 주지 않는다. validation을 반복 사용한 횟수를 기록하고, 최종 평가를 본 뒤 수정하면 새 평가 묶음으로 다시 시험한다. |
| 모델과 실행 환경 | 대상 모델·공급자 설정·도구·권한·이미지·repo 기준 SHA·제한 시간을 비교군마다 맞춘다. 제안·최적화 모델이 있으면 별도로 고정한다. 확률적 실행은 비교군 순서를 균형 있게 배정하고 같은 입력의 짝을 최소 3회 반복하는 초기안을 쓴다. 정확한 사례 수와 예산은 T01에서 동결한다. |
| 바꿀 수 있는 것 | 첫 범위는 재개 안내, 보고 지침, 개발·검토 절차의 문서와 카탈로그/스킬 후보다. 승인 권한, 필수 검사, 수용 기준, 정답·채점기, 보호 프로파일, 배포 권한은 후보가 바꿀 수 없다. 원본의 기본 권한 설정은 T05의 격리 실행 조건으로 대체해 시험한다. |
| 정상 진행과 오류 | 정상 입력의 실제 완료와 복구 가능 입력의 자동 재개를 함께 요구한다. 알려진 위반의 잘못된 완료·정답 누출·권한 밖 효과는 각 회차 0건이어야 한다. 전부 보류한 후보는 품질 유지나 성공으로 집계하지 않는다. |

### P32 · SkillOps 방식의 계약·관계·유지보수 가능성

**가설.** 개별 문서가 맞는 것뿐 아니라 스킬 계약·버전·관계를 점검하면, 단순 목록 조회로 남는 중복·구버전·검증 공백·입출력 불일치를 줄일 수 있다.

**선행 작업·구현.** R04의 T07, T08의 정상/오류 라이브러리와 독립 기대 그래프, T03의 대조·계측, P25 초기 문서 범위를 준비한다. 카탈로그를 선행조건·동작·산출물·검증기·실패 모드 계약으로 변환하고, 의존·호환·중복·대안·계보 관계를 기록하는 최소 어댑터를 만든다. 관계 표현을 위해 그래프 DB를 필수로 도입하지 않는다. 고정 파일이나 기존 DB로 비교할 수 있다.

**비교.** A는 같은 스킬의 평면 목록·키워드 조회, B는 계약·관계 검증만 적용, C는 진단 뒤 merge/repair/retire/add-validator/add-adapter의 유지보수 후보까지 적용한다. 제공 문서와 작업·도구·예산을 맞추고 유지보수 전후의 정상 실행을 같은 입력으로 비교한다. 실행 중인 버전을 수정하지 않고 새 라이브러리 버전으로 평가한다.

**사례.** 중복 스킬, 잘못 연결된 버전, 필수 validator 누락, 출력/입력 형식 불일치, 선행조건 미충족, 순환 의존을 각각 주입한다. 이름이 비슷하지만 적용 범위가 다른 정상 스킬과 승인된 대안도 포함한다. 자동 통합·폐기가 정상 기능을 지우는지 대조한다. 필수 선행이 없으면 필요한 준비를 제시하고, 준비가 주어지면 정상 실행으로 이어져야 한다.

**통과·채택.** 계약·관계·버전·유지보수 전후 결과를 외부 기대값과 대조할 수 있으면 최소 구현 가능성을 기록한다. 지정 오류의 미탐·잘못된 연결·정상 기능 파괴·필수 검증 누락 완료는 0건이어야 하고 정상 대조는 진행해야 한다. 후보 복원과 출처를 보존하며, 평면 목록보다 사전에 정한 품질·탐색·유지 비용 기준을 개선해야 도입 효과를 채택한다. 구조 검사 통과만으로 스킬 내용의 정확성(P25)이나 실제 활용(P20)을 대체하지 않는다.

**결과.** 공통 표에 오류별 검출/주입 수·정상 보존·스킬/관계 수·유지보수 조치·준비 제안/실제 후속 진행·복원 결과를 더한다. 재사용 후보는 계약 스키마·관계 검사기·라이브러리 diff·이전 버전 복원·회귀 사례다.

### P31 · SkillOpt 방식의 제한된 스킬 수정과 채택 가능성

**가설.** 고정 모델을 유지하고 스킬 문서의 변경 크기를 제한하며 별도 validation으로 채택하면, 무제한 자기 수정이나 고정 문서보다 안정적으로 개선할 수 있다.

**선행 작업·구현.** R03의 T07, T08의 작성/validation/최종 분리 자료와 독립 점수, T03의 사용량 계측, P25를 통과한 초기 스킬을 준비한다. 초기 스킬은 수작업 고정본으로 시작할 수 있고 P30의 통과를 필수로 요구하지 않는다. P30 산출물을 쓰는 추가 회차는 해당 버전의 준비 검증 증거를 요구한다. Console 실행·점수를 연결하는 어댑터, 제한된 add/delete/replace, 거부 후보 기록, validation 채택·기존본 복원을 최소 구현한다.

**비교.** A는 변경하지 않은 스킬, B는 같은 총 제안·실행 예산의 직접 수정, C는 변경 예산과 validation 채택을 갖춘 방법이다. 대상 모델·스킬 최초 버전·도구·권한을 고정한다. 수정 글자/토큰 상한·epoch·후보 수·재시도 예산을 먼저 정한다. validation은 후보 선택에 쓰고 최종 평가는 보고용으로만 사용한다.

**사례.** 실제 필수 적용이 빠지는 장황한 스킬을 개선하게 한다. 작성용 점수만 높이는 수정, 필수 조항 삭제로 짧아진 수정, 사용한 validation에 과적합한 수정, 변경 상한을 넘는 패치를 각각 대조한다. validation 실패·동점·정상 개선, 최적화 중단 후 재개와 기존본 복원도 확인한다.

**통과·채택.** 변경 한도·보호 조항·거부 기록·validation 채택 규칙이 지정대로 동작하고 올바른 기존본을 복원하면 최소 구현 가능성을 기록한다. validation 점수가 엄격히 좋아진 후보만 다음 독립 평가로 넘기며, 최종 품질·진행·전체 비용 기준도 만족해야 Console 도입 효과를 채택한다. 짧아졌다는 이유만으로 토큰 절감 성공이라 하지 않는다. 최적화 비용·거부 회차·검증 비용을 포함한 누적 회수 여부를 공개한다.

**결과.** 공통 표에 수정량·제안/채택/거부 수·validation/최종 점수·필수 조항 보존·복원 결과를 더한다. 재사용 후보는 문서 패치기·변경 한도 검사·후보 이력·평가 어댑터다. 모델 가중치 학습이나 제품 코드 자동 승격은 실험 범위가 아니다.

### P29 · Harness² 방식의 실행 지침 개선 가능성

**가설.** 고정된 실행 지침보다, 같은 사건에서 후보 지침을 비교하고 관측 차이로 조합하는 제한된 절차가 재개·보고의 정확성과 진행을 개선할 수 있다.

**선행 작업·구현.** R01의 T07, T08의 분리 자료·독립 판정, T03의 반복 실행·비용 계측, 사용할 P25 초기 문서 범위를 준비한다. 공식 demo/실행기를 연결할 수 있는지 먼저 시험하고, 불가하면 이유와 최소 어댑터 또는 방법 재구현을 별도 후보로 기록한다. 구현 범위는 후보 문서 생성→같은 사건의 비교 실행→행동 차이 기록→조합 문서 출력이다. 보호 정책은 편집 대상에서 제외한다.

**비교.** A는 현재 고정 지침, B는 Propose–Probe–Compose 1회, C는 B와 같은 총 생성·실행 예산에서 한 후보를 직접 수정·평가하는 단순 방법이다. B의 후보 수와 비교·조합 상한을 사전에 고정한다. B만 더 많은 재시도를 써서 좋아진 것인지 C로 구분한다. 원 방법의 정답 없는 내부 비교 점수와 Console의 독립 기대값을 모두 보존한다. 최종 채택은 독립 판정으로 한다.

**사례.** 결과 미확인과 미전송을 혼동하기 쉬운 재개 안내, 이전 SHA 승인만 남은 보고, 정상 완료, 정상적인 외부 대기를 사용한다. 작성용 사건과 다른 실패 계열·새 repo의 변형에서 평가한다. 더 그럴듯한 보고지만 실제 완료/미확인 사실을 왜곡하는 후보도 대조 입력으로 준다.

**통과·채택.** 동일 입력·버전에서 후보·probe·조합·결과를 재대조할 수 있으면 최소 구현 가능성의 근거가 된다. 정상 진행·보고 사실·승인 범위를 보존하고, 독립 평가에서 사전 품질/진행/비용 기준을 충족해야 도입 효과를 채택한다. 내부 점수만 오른 후보나 전부 보류하는 후보는 채택하지 않는다. 재사용 후보는 비교 실행기·패치/조합 기록·지침 어댑터다. 논문의 전체 재귀·도메인 벤치마크 재현이나 운영의 자동 자기 변경은 이 범위에 포함하지 않는다.

**결과.** 2.2절 공통 표에 후보 수·비교 횟수·내부/독립 점수 차이·조합 근거를 추가한다. 원본 코드 재사용/어댑터/방법 재구현 중 어떤 경로가 가능한지와 Rust 연동 수정량을 기록한다.

### P30 · Trace2Skill 방식의 개발 기록→재사용 스킬 생성 가능성

**가설.** 사람이 일일이 추가하지 않아도, 여러 성공·실패 기록에서 추출·통합한 절차가 고정 초기 카탈로그의 반복 누락을 줄이며 다른 repo의 같은 종류 작업에 적용될 수 있다.

**선행 작업·구현.** R02의 T07, T08의 정규화·비밀 제거·분리 자료, T03의 실행·계측, P25 초기 카탈로그를 준비한다. 개발·검토·복구 기록을 입력 계약으로 변환하는 코드, 기록별 개선 후보, 충돌 통합·출처 연결·스킬 디렉터리 출력을 최소 구현한다. 공개 spreadsheet 중심 실행과 Console 기록의 차이를 명시하고 필요한 입력·평가 어댑터를 별도 산출물로 남긴다.

**비교.** A는 고정 초기 카탈로그, B는 동일 기록을 매번 조회하는 방법, C는 같은 기록에서 생성·통합한 스킬을 제공하는 방법이다. B와 C의 원본 기록·대상 모델·도구·평가 예산은 같게 한다. 선택적으로 같은 예산의 순차 수정과 국소 후보 통합을 비교해 통합 자체의 기여를 분리한다. 생성에 쓰지 않은 작업·실패 계열·새 repo에서 평가한다.

**사례.** 옵션 누락, 실패를 성공으로 가린 CI, 현재 SHA 확인 누락, 자동 재개 실패의 반복 기록을 넣는다. 성공 기록과 실패 뒤 복구 기록을 구분한다. 상반된 도구 버전의 조언, 우연히 통과한 잘못된 절차, 승인 밖 우회를 제안하는 기록을 섞어 출처·적용 조건·충돌을 식별하는지 검사한다. 숨긴 최종 결함의 정답을 기록에 포함하지 않는다.

**통과·채택.** 원본 기록→국소 후보→통합 결과의 출처가 연결되고 실행 가능한 후보를 만들면 최소 구현 가능성을 기록한다. 생성 스킬은 별도 P25 검증 범위를 통과한 뒤에만 대상 에이전트에 제공한다. 최종 평가에서 필수 적용·결함 발견·정상 완료를 유지·개선하고, 기록 재조회 대비 비용을 포함한 사전 기준을 만족해야 도입 효과를 채택한다. 새 repo에 적용되지 않으면 확인한 repo 범위의 결과로 한정한다. 초기 자료를 자동으로 완전하게 만들었다고 해석하지 않는다.

**결과.** 공통 표와 P20 항목별 대조표에 기록 수·스킬 수·출처 연결률·충돌/오류·반려·교정 수, 새 repo의 실제 적용·실행 수를 더한다. 재사용 후보는 기록 정규화기·출처 매핑·후보 통합기·회귀 평가 자료다.

## 4. 결과에서 최종 스프린트로 연결

각 후보는 실행 가능성(PASS/FAIL/INCONCLUSIVE), 독립 효과와 전체 비용, 도입 결정(채택/부분 채택/보류/기각), 재사용 모듈의 repo 경로/SHA/계약/검증 범위, 남은 제품화와 재실험·대안·재개 조건을 남긴다. 반복은 원 계열의 누적 한도 안에서 진행하고 후보 이름을 바꿔 상한을 초기화하지 않는다.
