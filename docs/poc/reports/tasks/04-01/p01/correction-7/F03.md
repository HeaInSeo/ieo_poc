# Daily report archive

REQ-11. An operator-owned, immutable registry for each run maps exact canonical IDs `synthetic-fixture` and `production-probe` to the two private count backends. There are no aliases. Treat any other string as unknown. The source gateway's workload identity is the only principal with network access and authentication credentials accepted by the backends. The publisher has only gateway access, cannot obtain the gateway identity, and has no alternate count backend route. Before any backend call, the gateway applies the allowlist containing only `synthetic-fixture`; it emits a request ID, the canonical source ID for registered sources or the raw identifier for unknown sources, and an allowed or denied disposition for every request to read, including ones denied before dispatch. Abort before dispatch if the attempt cannot be recorded. The publisher may populate the stored count only from the gateway result for the current request. Independently instrument the two backend ingress points; record accepted calls with request and canonical source IDs, without reading the gateway trace. Denied ingress and network probes are observable separately from accepted calls.

REQ-12. Only the independent Archive Verifier service can confirm verification. The publisher, reader and client cannot write its authoritative records. It verifies a submitted archive before issuing an authenticated record binding the archive ID, immutable version, and SHA-256 of the canonical submitted content. The publication service recomputes the hash of the bytes it will accept and uses only the Verifier's authenticated record for the exact triple, never a client's `verified` flag. Missing, untrusted or mismatched evidence yields HTTP 422 before any count-source read or store change. Even with matching evidence, return HTTP 201 only after receiving a valid count from the gateway for this request and committing the complete verified record. If the gateway fails to record the attempt or provides no valid current-request count, return HTTP 503 without writing the store. On attempt-recording failure dispatch zero backend calls. A missing, malformed, mismatched or stale gateway result is not a count for this request. If the isolated store rejects the write before commit, roll it back and return HTTP 503.

### REQ-12 shared hash contract

The submitted archive is the `archive` object inside the request envelope. Both services first parse that object as UTF-8 JSON without BOM, reject invalid UTF-8, duplicate member names, unknown archive fields and missing fields, then validate exactly these three decoded string values: `archive_id` matches `[a-z][a-z0-9-]{0,31}`, `version` matches `[1-9][0-9]{0,8}`, and `content` matches `[A-Za-z0-9. _-]{1,256}` (whole-string ASCII matches). `verified` and evidence are transport metadata outside the archive object and are not hash inputs. The permitted characters require no JSON escaping. Serialize the validated values into the literal template `{"archive_id":"ID","version":"VERSION","content":"CONTENT"}`, replacing the three uppercase placeholders with their decoded values verbatim. Do not trim or normalize field values. Hash the UTF-8 bytes from the first opening brace through the final closing brace inclusive, with no BOM, separator spaces, or trailing newline. The Verifier signs the exact tuple of the decoded archive ID, decoded version, and this SHA-256 after independently confirming verification. The publication service repeats canonicalization over the submitted archive it will persist and matches all three fields to the trusted evidence. Invalid archive encoding or schema is 422 for an authorized publisher before any gateway or store action. Non-publishers are subject to REQ-13 first.

Shared vectors below show the inner object only. The expected bytes strings are literal ASCII, excluding the Markdown backticks. Both services must independently produce the expected bytes and digest for each vector.

- V1 input `{"archive_id":"daily-1","version":"1","content":"daily report"}` → bytes `{"archive_id":"daily-1","version":"1","content":"daily report"}` → SHA-256 `0af55fa7577094b906f881e370f816bfb587563d64f5d5b26de48abe4881ffaa`.
- V2 input `{ "content" : "daily report", "version" : "1", "archive_id" : "daily-1" }` → bytes `{"archive_id":"daily-1","version":"1","content":"daily report"}` → SHA-256 `0af55fa7577094b906f881e370f816bfb587563d64f5d5b26de48abe4881ffaa`.
- V3 input `{"archive_id":"daily-1","version":"1","content":"daily reports"}` → bytes `{"archive_id":"daily-1","version":"1","content":"daily reports"}` → SHA-256 `5803ebb8dd291e476ffcf587f4e053b0de4da4d9378226a5602e65eca5f58774`.

REQ-13. Authenticate first, then require the publisher role before validating archive evidence or reading counts. An authenticated principal lacking publisher receives HTTP 403, regardless of evidence or reader role, with no source reads and no mutation. The reader role only grants reading.

AC-14. Use isolated storage, role fixtures (publisher, reader without publisher, authenticated principal with neither role), the Verifier, and two backend stubs. Both stubs return 42. Reset all storage and traces before each of two independent runs. Capture request IDs, authenticated identity and resolved roles, HTTP responses, entire store snapshots, gateway event slices, and separately collected backend ingress evidence. Submit valid request envelopes in all role-precedence tests.

1. For a publisher request with a trusted exact-match verification record, assert HTTP 201. Immediately read the full store. It must contain one verified archive with count 42 and source `synthetic-fixture`. Capture its ID and every persisted field. Assert one allowed gateway attempt and independently exactly one accepted backend call for that request and source. Assert the published count and source equal the gateway result returned for that request.
2. As the same publisher, submit separate inputs with no verification, a client `verified` flag alone, issuer other than the Verifier, a Verifier record for another archive ID, a record for another version of the same ID, and a record for the same ID/version with a different submitted-content hash. In each mismatch vary only the indicated binding field. After each response, assert HTTP 422, no gateway attempts or accepted backend calls, and that the immediate complete store contains only the captured ID and identical persisted fields.
3. Using each of the two non-publisher credentials, submit both a verified and an unverified archive. Assert authentication succeeded and the resolved role set is respectively reader-only or empty. For each request, assert HTTP 403, zero gateway attempts and accepted backend calls, and immediately read the complete store. It must contain only the original ID and identical fields and equal the pre-request snapshot.
4. Compare the complete set of allowed gateway events and the independently captured accepted backend calls as multisets of (request ID, canonical source ID). Require exact equality, with exactly one pair from step 1 and no extra, unmatched or duplicate events. The production-probe backend must have no accepted calls.

AC-14 controls. Use isolated fresh runs, independent of the two normal runs.

- From the publisher's actual execution identity and network namespace, try to reach each private backend directly, including synthetic-fixture. Verify the probe is denied at the network or backend authorization boundary, no accepted call or body is returned, and the gateway does not log an allowed event for it. Verify the transport and backend observer are working with a successful gateway-mediated request in the same setup. Confirm the multiset comparison fails on an independently observed unmatched backend-call event injected into a copy of the positive evidence.
- In separate gateway probes, try a registered but non-allowlisted ID (`production-probe`) and a previously unnamed ID absent from both registry and allowlist. For each, assert a denied gateway event with the correlated request ID and expected canonical or raw ID, no count result, and zero accepted backend calls for the probe. Verify the unknown-source event is observable even when denial occurs before dispatch. Append the observed denied event to a copy of the positive request trace and assert that the unchanged normal-run trace checker, which accepts the unmodified one-event positive trace, rejects the augmented trace as extra. Missing denial evidence or a backend call fails the control.

- Hash control. Run both services against vectors V1–V3 and require the declared bytes and SHA-256. In isolated fresh cases, issue trusted evidence over V1 and publish V1 and V2 using that same evidence, each from an empty store. Expect 201 and the usual success observations for each. Use that evidence with V3, changing only covered content, and expect 422, zero source attempts and backend calls, and the immediate whole-store snapshot equal to the pre-request snapshot. Whitespace and key order outside decoded values must not affect the hash.
- Gateway failure control. Start each case with the previously accepted record still present, a distinct request ID, an authenticated publisher and trusted exact-match evidence for the candidate archive. Inject an attempt-log write failure before dispatch and expect 503, zero accepted backend calls for this request, and an immediate whole-store snapshot equal to its pre-request snapshot. Independently inject a backend response without a count after a successfully logged attempt; expect 503, exactly one allowed gateway attempt and its matching backend call, and the same whole-store equality. Also inject a pre-commit store write failure after receiving a valid gateway result and confirm 503 and rollback to the exact pre-request store. Run a fault-free positive control through the same path and observe 201 only after the corresponding count and archive are committed.
- Current-request count control. Without resetting the gateway or store between requests, issue two sequential publisher requests with distinct request IDs and distinct archive IDs, each with trusted matching verifier evidence, and configure the synthetic backend to return 42 for the first request ID and 17 for the second. Independently capture the backend results and their correlation to allowed gateway events. Expect 201 twice. Immediately after each response, inspect the full store and match the newly persisted archive ID, source, and count to that request's result. After the second response exactly two records must exist, the original record unchanged with 42 and the second with 17. Feed the same checker otherwise identical observed snapshots with a constant 42 or with the second count replaced by the prior request's result; both must fail at the second record comparison.
