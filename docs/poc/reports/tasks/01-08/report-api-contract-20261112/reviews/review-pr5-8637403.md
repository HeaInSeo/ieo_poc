## Findings

### F1 · P1 · Idempotency layer lets a draft be re-submitted as `executable` and get 200. This re-opens the F2 regression fixed in 01-07.
- **Violated condition:** §1.6 requires 422 for 등록 바인딩 오류. The accepted 01-07 contract and test `draft_registered_spec_is_not_idempotent_for_executable_intake` (crates/ieo-spec/tests/registration.rs:281) say "same content registered as draft must not short-circuit an executable request".
- **Contract text:**
  - The OpenAPI `registerSprint` says "Same Idempotency-Key + same body → 200 with the stored result; same key + different body → 409."
  - The 200 response is "Same sprint_id/revision/digest (or same Idempotency-Key + body) already registered."
  - `mode` is a query parameter, so it is neither the body nor the key.
  - CLI contract §4: "멱등 키를 주지 않으면 CLI가 요청 본문 digest로 만든다(같은 파일 재제출이 같은 키)".
- **Reproduction (contract walk-through):**
  1. `ieo sprint register spec.json` sends POST `?mode=draft` with key = digest(body) and gets 201.
  2. `ieo sprint register spec.json --executable` sends POST `?mode=executable` with the same key and the same body. The contract requires 200 with the stored (draft) result.
  - `RegistrationResult` has no `mode`/`registration_state`, so the client cannot tell. The 200 is `state: ALREADY_REGISTERED` and the CLI exits 0.
- **Expected:** 422 `UNBOUND_DRAFT`, or the idempotency fingerprint includes `mode` (key + body + mode). A different mode under the same key is a 409 `IDEMPOTENCY_KEY_CONFLICT`.
- **Observed:** the contract requires 200/exit 0. A 02-03 implementation that follows the OpenAPI literally reintroduces a defect that 01-07 already fixed.
- **Certainty:** supported. This is a specification reading. No server exists yet, but the rule is normative text in the bound contract and is the CLI's default path.
- **Raw ref:** contracts/ieo-api-v0.openapi.yaml lines 26–48. Report_API_Contract_v0.md §4 last paragraph. crates/ieo-spec/tests/registration.rs:281–295.

### F2 · P2 · `ieo-report` and `validate_contracts.py` disagree in both directions. The Rust timestamp parser has two real bugs.
- **Violated condition:** lib.rs:4–5 claims the "same rules as docs/poc/scripts/validate_contracts.py", and the REPORT claims parity.
- **Reproduction:** logs/parity.txt (44 cases, 10 DIFF).
- **Rust bugs:**
  - `parse_ts` reads offset hours with `i64::parse`, which accepts a sign. `next_check_at = "2026-11-12T09:00:00+-1:00"` or `"++1:00"`: Rust **ACCEPT**, Python REJECT. `next_check_at` has no `format`, so nothing else catches it. `+-1:00` is silently interpreted as UTC−1.
  - Fractional seconds are discarded before comparison.
    - Forecast `earliest .9Z > latest .1Z` within the same second: Rust **ACCEPT**, Python REJECT ("reversed forecast").
    - `late` with observed `00:00:00.9Z` after deadline `00:00:00.1Z`, which is genuinely late: Rust **REJECT** ("기한 전인데 지연"), Python ACCEPT.
- **Python-side divergences:**
  - Forecast/late comparisons call `datetime.fromisoformat` without the `t`/`z` normalisation, so valid lowercase timestamps crash into ValueError and are REJECTED. Rust ACCEPTs.
  - `next_check_at "+05:60"`: Python ACCEPT, Rust REJECT.
  - Year `0000` (RFC 3339-legal): Python REJECT, Rust ACCEPT. This affects observed_at, schedule.deadline_at, decision.deadline_at and next_check_at, because jsonschema-rs `date-time` also accepts year 0.
- **Agreements:** Feb 29 in leap years (2000, 2024) is accepted and in non-leap years (1900, 2023) rejected. Hour 24, `+24:00`, second 60, a space separator, `+0900`, a missing offset, full-width digits, trailing whitespace or newline, and `.Z` are all rejected by both.
- **Expected:** both reject the same set. At minimum, the Rust side rejects signed offset digits and compares fractional seconds.
- **Certainty:** reproduced.

### F4 · P2 · `render_human` omits confirmed facts and delay reason/impact, and the headline can read as completion for a mere claim.
- **Reproduction:** logs/render.txt.
- **(a) Headline from a claim:** a development_progress **claim** with phase 보고 and state 완료 renders the headline `**상태 변경 · fixture-repo FIXTURE-TASK · 보고/완료 · 사용자 결정 불필요**`. "claim" appears only in line 2. The design log requires the first line to say what changed. A claim headline should be marked as claim, since the agent's completion message is not the verdict (§1.5/§1.2).
- **(b) Delay reason and impact:** a verified late verdict with `delay_reasons=["quota 소진으로 3일 중단"]` and `schedule.affected_tasks=["07-03"]` renders only "상태 late". The delay reason and the impact are dropped. 01-08.accept requires 지연 사유/영향.
- **(c) Confirmed facts:** `body.evidence_comparison` ("main CI 실패 확인") is not rendered anywhere. The "확인한 사실과 영향" part shows no confirmed fact at all, only evidence level, unknowns and affected tasks. The same applies to guardrail verdict and findings and to development change_summary and internal_checks.
- **(d) Missing design-log elements:** "계속할 수 있는 작업" (no field), "시한이 지나면 생기는 일" and "승인 범위" are absent.
- **What works:** the 5-part order is correct, and "다음 확인 시각(해결 예상 시각 아님)" is correctly distinguished. Unknown facts render as "없음" only when the array is empty.
- **Certainty:** reproduced.

### F6 · P2 · Authorization holes in the agent paths.
- **(a) Stale or foreign assignment claims:** `authorize_claim` (lib.rs:283) binds only (repo_id, role).
  - A development credential can submit claims for any task, assignment_id or **stale generation** in its repo.
  - No 4xx/409 code exists for a stale generation. The Rejection enum has none. The repro path, by contrast, has `rejected_stale_generation`.
  - This conflicts with §1.2 ("권한 세대가 오래된 응답은 현재 상태를 전진시키지 않는다") and with design-log POC-05 (an old document version must be rejected with 0 changes).
- **(b) Agent read access to development claims:** nothing forbids an agent credential from holding `sprints:read`. The bearer scheme maps any kind to scopes.
  - A Guardrail credential with `sprints:read` would receive `latest_claims` containing the development agent's change_summary and progress narrative.
  - §1.2 forbids this ("개발자의 비공개 추론/요약을 검토 기억에 주입하지 않는다"). 01-02 §2 also restricts Guardrail inputs to approved spec, profile, fixed SHA and protected check results.
  - The contract should state that agent-kind principals cannot hold `sprints:read`, or that claims are redacted for them.
- **(c) Repro request lookup:** `GET /v0/agent/repro-requests/{request_id}` says only "Same credential scope as the submitter". It does not require the request's repo to match the caller's repo.
- **What works:**
  - Body names are ignored (test `claim_authorization`).
  - verified/coordinator reports from an agent are denied.
  - A development credential is denied on repro (403), at the text level.
- **Certainty:** supported.

### F7 · P2 · The CLI `register --human` contradicts "CLI uses only the API" and the 01-07 binding rule.
- **Contract text:** contract §4 says `ieo sprint register --human <input.json> --context <binding.json>` runs a "로컬 변환(01-07 규칙)".
- **What 01-07 conversion needs from the coordinator:**
  - The coordinator-assigned sprint number NN.
  - Registered task IDs, for TASK_ID_CONFLICT and `after` resolution.
  - The "위임·출처·사람 확인 블록은 코디네이터의 승인된 repo 바인딩에서 받고 사용자에게 쓰게 하지 않는다" rule.

- **Expected:** a server-side conversion endpoint, or an API to fetch the binding context.
- **Certainty:** supported.

- **Also:** the `verified` description says "or null before any verdict", but the type is a non-nullable array.
- **Expected:** `allOf` with `evidence_level: {const: verified}` / `{const: claim}` on the items.
- **Certainty:** certain (schema reading).
- **Raw ref:** contracts/ieo-api-v0.openapi.yaml, `SprintState`.
