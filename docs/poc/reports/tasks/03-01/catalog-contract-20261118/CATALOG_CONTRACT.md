# T02 카탈로그 작성 계약 v0.1.0

계획 v1.3.3의 `POC-REQ-03-01`과 `poc-acceptance-v1.3.3@4 / 03-01.accept`를 적용한다. [카탈로그 색인](catalog.json)은 항목별 상세, [원본 대응표](sources.json)는 같은 항목 ID와 버전별 근거를 제공한다. 두 파일은 함께 고정한다.

## 항목 작성 양식

| 필드 | 작성 규칙 |
| --- | --- |
| `id`, `version`, `title` | 항목 주소는 `id@version`이다. 내용이나 근거가 바뀌면 새 버전을 발행하고 기존 참조를 보존한다. |
| `requirements` | 명세의 요구 ID, 수용 항목 ID, 프로파일 ID와 revision을 한 묶음으로 참조한다. 필수 여부는 승인된 프로파일에서 읽는다. |
| `scope`, `roles`, `applies_when`, `excludes_when` | 범용·Go·Rust·저장소 전용 중 하나와 소비 역할을 지정한다. 저장소 전용에는 대상 repo를 고정한다. 권한과 적용 조건이 불명확하면 확인 필요로 둔다. |
| `purpose`, `expected_evidence`, `evidence_limits` | 문제, 확인할 산출물과 관측 방법, 증거의 한계를 쓴다. 결과에는 환경과 대상 commit 또는 artifact digest를 연결한다. |
| `execution` | 명령형은 명령과 중요한 옵션을, 정책형은 설정 절차와 기대값·실제값 대조 방법을 쓴다. 양쪽 모두 도구·버전·환경·권한을 지정한다. 미확정 값은 이유를 적고 실행 전에 채운다. |
| `verdicts`, `cost` | 기대 성공, 실패·불충분, 비적용 판정과 비용 근거를 남긴다. 비용은 미산정·추정·실측을 구분하고 시간·자원·토큰에서 해당 없음이나 미계측의 이유를 쓴다. |
| `readiness` | 작성 계약은 `contract`, 작성 후보는 `draft`로 관리한다. P25 준비 완료 여부는 대응 범위·버전의 별도 독립 판정에서 읽는다. |
| 원본 대응표 | `item_id@item_version`으로 결합한다. 각 연결에 `source_id`와 `relation`을 둔다. 원본별 경로·고정 revision·전체 파일 SHA-256·행 위치·해당 구절·사용 범위를 기록한다. |

## 조회와 적용

색인에서 명세 요구 ID와 프로파일 revision을 먼저 대조하고, 대상 role 및 범용/스택/저장소 조건에 해당하는 항목만 선택한다. 여러 버전이 있어도 승인 프로파일 또는 실행 기록이 지목한 정확한 버전을 사용한다. 항목과 원본 대응표가 양방향으로 연결되고 SHA와 인용 위치가 일치해야 한다. `candidate`는 이식 검토 후보이며 `observation`은 그 시점의 실제 관측이다. 정책 근거 `requirement`는 수용 항목별 승인 출처 집합과 파일 경로·절 위치·고정 구절을 대조한다. 초기 승인 집합은 T01 범위표, T02/P25 및 명세의 03-01 항목에서 고정했다. 새 수용 범위를 등록할 때 같은 승인 근거를 확인한 뒤 집합을 개정한다.

03-02는 공통 정책·역할·GitHub 항목을 작성하고, 03-03은 Go/Rust별 명령·중요 옵션·버전·실패/건너뜀·비용을 채운다. 03-04/P25는 승인된 T01 범위와 독립 기대값으로 적용·비적용·오류를 대조한다. 작성 후보에 들어 있는 기대 증거에는 실제 P25 판정이 필요하다. P21은 이식 범위, P23은 실제 설정의 효과를 검증한다.

[검사기](verify_catalog.py)는 버전·참조·필수 필드·원본 일치 여부를 검증한다. 작성 후보에 실행 권한은 없으며 운영 설정과 강제 검사 목록은 각자의 승인 계약을 적용한다.
