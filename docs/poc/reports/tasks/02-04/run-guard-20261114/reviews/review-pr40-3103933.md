## Findings

### 1. High: exit paths after `spawn` return `Err` and leave the process group running unsupervised

Several calls in `run()` can fail after the child has been spawned: `File::create(stdout_path)?` (line 154, after `spawn` on line 142), `writeln!(out, ..)?` (lines 171 and 206), and `child.try_wait()?`. Each one returns from `run()` before any `signal_group`. The child is then never signalled. No deadline, token cap or overage stop applies to it any more, and nothing kills its group.

- Probe P1: `stdout_path` in a missing directory. `run()` returned `Err`, and the fake leader (`sleep 30`) was still alive afterwards.
- `writeln!` failing on a full disk is a realistic trigger: the build host is at 94% full.
- Fix: create the stdout file before `spawn`. Make cleanup unconditional, for example with a drop guard that sends TERM, then KILL after the grace, then KILL to the group, and also calls `child.kill()`, on every exit path. Alternatively, turn I/O errors into a stop reason and run the normal stop path. Add a test for an uncreatable stdout path and for a failing write.

### 2. High: the post-exit drain has no bound, so a descendant holding stdout keeps the run alive past every limit

When the leader has exited but stdout is still open, the Timeout branch runs `while let Ok(line) = rx.recv_timeout(200ms)`. This loop has no deadline check and no cap. A descendant that keeps writing at least every 200 ms holds the guard in the loop forever. The final group kill comes only after the loop, so that descendant is never killed.

- Probe P2: the leader backgrounds `while :; do echo x; sleep 0.05; done`, then exits. The limit was 2 s plus 1 s grace. `run()` had not returned when the 12 s watchdog fired.
- Lines read during the drain are also never passed to `stream_stop` or the usage sum. A breaking `rate_limit_event` or the last usage in those lines is copied to the file but not reflected in `Outcome`. The pre-run `observation_check` would catch the event later, but the outcome under-reports it.
- Fix: bound the drain by the deadline, or by a short fixed budget after exit. Send TERM and KILL to the group before draining, or at least when the bound is reached. Run the drained lines through the same `stream_stop` and usage handling.

### 3. High (honesty, user-required limits statement): in-run `assistant` usage does not include final output tokens, and some usage never appears in the stream

The real data contradicts the limit as written in the PROGRESS note and the module doc. Both say usage appears "after the model request that produced it has completed". In fact the CLI copies the message-start usage snapshot onto each content-block `assistant` line, so `output_tokens` is not final.

| Stream | Observed billable / cache_read (per-id max) | `result.usage` | `modelUsage` |
|---|---|---|---|
| `r1-new.jsonl` | 1807 / 649 | 2414 / 649 | 2414 / 649 |
| `r1-new.jsonl` output tokens alone | 5 | 612 | |
| `n4a-resume.jsonl` | 1567 / 13364 | 1878 / 13364 | 2584 / 20878 |
| `l3-compact.jsonl` (compaction) | 0 / 0, no `assistant` lines | | 8035 / 26400 |
| `t23-child.jsonl` (with child) | 3780 | 3047 (parent only) | 3902 |
| 01-04 attempts 02, 04, 07, 09 | each 1 below `result` | | |

- The token cap is therefore a lower-bound signal. Output and thinking tokens of every request, and calls that never appear as `assistant` lines (compaction, and other model calls in `modelUsage`), are invisible until `result`.
- Decision 2026-11-14 §3 requires that values known only at the end are stated as limits. They are not stated, and the current sentence describes a measurement that is more complete than the real one.
- Requested:
  - Correct the module doc and PROGRESS §2: output tokens are known only at the end, compaction and other side calls are not visible in-run, and the observed sum can be far below the `result` and `modelUsage` share.
  - Optionally add a fixture-replay test that pins this undercount, so the limit is evidenced rather than asserted.
- The rest of the "observe then stop" framing is fine. The note does not claim a provider-side hard limit, and it keeps the pre-run check separate from in-run enforcement.

### 4. Medium: a non-UTF-8 line or a closed stdout silently blinds the guard (fails open)

`BufReader::lines()` returns `Err` on invalid UTF-8. The reader then breaks, drops the pipe and disconnects the channel. From then on no line is observed. The Disconnected branch waits until the deadline while the process keeps running, possibly making model calls (Node ignores SIGPIPE).

- Probe P3b: the fake ignores SIGPIPE, prints `\xff`, then an `assistant` line with 5000 input tokens, against a room of 1000. Result: `stop=RunTimeout` after 3.06 s, `observed=0`. Expected: TokenCap.
- Probe P3, without `trap PIPE`: the leader died of SIGPIPE and the outcome was `Exited` with observed 0. The over-room message was never seen.
- More generally, stdout closing while the leader is still alive means usage can no longer be observed.
- Requested:
  - Read bytes with `read_until(b'\n')`, keep the raw bytes for the copy, and parse lossily.
  - Treat a reader error, or Disconnected while the leader is still alive, as a stop with its own reason, such as `Stop::Unobservable`, rather than waiting out the deadline.
  - Add tests for both cases.

### 5. Medium: a missing or failing `kill` binary leads to an unbounded `child.wait()`

`signal_group` ignores spawn failure and exit status. If `kill` is not on `PATH` (minimal role images), neither TERM nor KILL is delivered, and `break child.wait()?` blocks forever when the leader ignores TERM.

- Probe P6: the test binary was run with `PATH=/nonexistent` and the fake given `/bin/sh` by absolute path. The guard had not returned 10 s after a 0.5 s limit and 1 s grace, and the leader was still alive. I killed it by hand afterwards.
- The `kill` invocation itself is robust in both environments: util-linux 2.32.1 here (100+ runs) and procps on ubuntu-latest CI (group-kill tests pass at this head). `kill -s SIG -- -PGID` is portable across both.
- Requested:
  - After the grace, also call `child.kill()` (std, no `unsafe`) so the leader at least is always killed.
  - Make an unspawnable `kill` an error or a loud report instead of silent.
  - Optionally use an absolute `/bin/kill` or `/usr/bin/kill` with a fallback.

### 7. Medium: `Limits::for_next` is not consistent with `budget::next`, and its doc overclaims

- `for_next` builds on `Spent` alone. It returns `Some` when `next` would return Stop or Hold:
  - unmeasured or unclassified records, whose tokens then count as 0 in `billable_room`, which conflicts with "unmeasured never counts as 0";
  - a failed observation check.
- It also returns `Some` with `billable_room == 0` or `cache_read_room == 0`.
- Its doc says "`None` when the budget allows no run", which is not true.
- The arithmetic is otherwise edge-safe:
  - `left` is guarded;
  - `checked_sub` returns `None` on an overrun;
  - the timeout equals `Decision::Start.timeout_seconds`.
- The difference from `next`, which reserves the largest run, is reasonable for an in-run room. It should be documented.
- Requested: derive `Limits` only from a `Decision::Start`, or have `for_next` call `next` itself, or at least return `None` on unmeasured or unclassified records and on a zero room. Fix the doc and add tests for these cases.

### 8. Low: grace and drain overrun of the time limits are not stated

After the deadline the group gets up to `grace` (10 s), plus polling and drain time. The total limit (14400 s) can therefore be exceeded by about the grace on the last run. Requested: state this in PROGRESS §2, or start TERM at `deadline - grace`.

### 9. Low: `assistant` messages without a `message.id` collapse into one key `""`

Probe P5: two id-less 600-token messages were counted as 600, with `messages: 1`. Missing `usage` counts as 0 in-run.

No real stream shows either case: every `assistant` line has an id and a usage object. Still, using a per-line key for id-less messages, or treating them as unobservable, would avoid an undercount.

Per-message-id max is otherwise correct for the real shapes:
- repeated ids per content block carry identical usage, and max neither double-counts nor undercounts;
- child messages (`parent_tool_use_id` set) have distinct ids and are included;
- no usage field is missed for the defined billable sum. `cache_creation.ephemeral_*` sums equal `cache_creation_input_tokens`, and `server_tool_use`, `service_tier` and `speed` are not tokens.

### 10. Low: stale doc in `budget.rs`

Line 17 still says "The adapter's in-stream stop on a cap crossing is a later 02-04 step." This PR adds that stop. Update it to point at `run::run`, together with the limits from finding 3.

### 11. Info: a failing test leaks its process group

When the `go` watchdog fires, for example under mutants R2 or R7, the fake process group is left running (`sh` and `sleep 300`) and its tmp dir remains. After mutation runs I found and killed such leftovers, all from my own runs. Unmodified code left nothing behind in 100 runs. Optional: record the pgid in the test and kill it from the watchdog's failure path.
