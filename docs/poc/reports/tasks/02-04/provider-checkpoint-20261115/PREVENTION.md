# 재발 방지 대응표 · 02-04 PoC에서 발견한 문제 → 정식 설계·개발 요구사항

2026-11-15 KST · 근거 결정: [사용자 결정 2026-11-15 §4](../../../../User_Decisions_2026-11-15_0204-acceptance.md) · 관련 기록: [진행 기록 9](PROGRESS.md)

**범위.** 이 표는 정식 설계·개발이 근거로 쓸 기준이다. 정식 제품 전체를 여기서 구현하지 않는다. “지금(PoC)” 열은 이미 구현했거나 이번에 구현한 것, “정식 설계로 넘김” 열은 후속 설계·개발의 몫이다. 이 표의 어떤 항목도 02-04의 새 선행 조건이 아니다.

**정식 설계 문서.** 이 저장소에는 아직 정식 설계 문서가 없다. 정식 설계를 시작하는 문서는 이 표를 근거로 인용하고, “추가 검증 필요” 열의 가정을 그 문서의 미확정 목록에 옮긴다.

### 1.3 재개 기준 오류

| 남은 한계·추가 검증 필요 | 개발 컨테이너 안의 같은 UID 문제(계약 §2.1). 체크포인트를 바꿀 수 있고 바꾼 사실은 드러난다 |

### 1.4 정정과 이력 훼손

| 단계 | 내용 |
| --- | --- |
| 발견한 문제 | 세 가지가 있었다. D3 정정에서 원본·최초 실패를 보존해야 했다. 정정의 상대 경로 문제가 있었다(N1). “잃음”을 “나중에 보존함”으로 고친 사례가 있다(빈 변수로 보존 복사가 실패) |
| 원인 | 정정을 덮어쓰기로 할 수 있는 구조였다. 정정 근거를 다시 측정하지 않았다. 보존 단계가 실패해도 조용히 지나갔다 |
| 정식 설계 요구사항 | 원본과 최초 판정은 추가 전용으로 둔다. 정정은 원본을 가리키는 별도 행으로 쓰고, 근거를 읽을 때마다 재측정한다. 같은 회차의 중복 차감과 횟수 초기화를 막는다. 보존 단계는 실패하면 중단한다(`set -u`, 결과 해시 확인) |
| 자동 검증·회귀 자료 (지금) | `tests/caller.rs`: `a_run_is_corrected_once_from_its_kept_records_and_not_counted_again`, `a_correction_must_match_the_run_it_corrects`, `a_correction_is_measured_again_when_read`, `reevaluation_checks_the_decision_the_kept_digest_and_the_base_session`. 코디네이터 추가 전용 트리거(`role_checkpoints` UPDATE·DELETE 거부 시험) |
| 담당·완료 조건 (정식 설계로 넘김) | 정식 원장·정정 모델(정정 행 스키마, 재측정 규칙, 이중 차감 검사) |
| 남은 한계·추가 검증 필요 | 비공개 보존소(`/opt/rust/ieo_poc_runs`)의 무결성은 `SHA256SUMS`를 사람이 대조한다. CI 밖이다 |

### 1.5 파일 위치 의존

| 단계 | 내용 |
| --- | --- |
| 발견한 문제 | 세 가지가 있었다. 정정에 상대 경로로 전사를 가리켰다(N1). 다음 기동의 정리가 자식 전사를 지운다. 보존 위치가 작업 디렉터리에 묶였다 |
| 원인 | 증거 참조가 “지금 이 위치의 파일”이었다. 위치·해시 계약이 없었다 |
| 정식 설계 요구사항 | 증거 저장 계약을 둔다. 참조는 절대 경로나 내용 주소(sha256)로 하고 해시를 함께 기록한다. 정리 전에 복사한다. 작업 디렉터리를 바꾸거나 원본을 정리한 뒤에도 해시로 검증할 수 있게 한다 |
| 자동 검증·회귀 자료 (지금) | 역할 서비스의 자식 전사 보존(`keep_child_transcripts`, `GET …/children/{agent}`). `reevaluate`의 절대 경로 사본(caller 시험). 이번 항목 9의 체크포인트 보관 사본(`/state/checkpoints/<seq>`)과 중앙 digest |
| 담당·완료 조건 (정식 설계로 넘김) | 정식 증거 저장소(내용 주소, 보존 기한, 접근 통제) |
| 남은 한계·추가 검증 필요 | PoC 보존소는 단일 호스트 디렉터리다 |

### 1.6 시험 기준의 모호함

| 단계 | 내용 |
| --- | --- |
| 발견한 문제 | D3 기대값은 3이었고 답은 4였다. Read 표시의 마지막 개행 뒤 빈 4행이 원인이었다(진행 기록 7 §4) |
| 원인 | 기대값을 실행 전에 실제 입력 바이트와 도구 표시 방식으로 계산해 확인하지 않았다 |
| 정식 설계 요구사항 | 실행 전 점검 단계를 둔다. 입력의 실제 내용, 도구가 보여 줄 형태, 기대값 계산 규칙을 기록하고 고정한다. 기대값은 실행 전에 동결한다. 실패는 사후에 기대값을 바꿔 없애지 않는다 |
| 자동 검증·회귀 자료 (지금) | D3 실패 기록 유지(RUN_PLAN의 기대값 그대로, 진행 기록 7 §4, 수용 기록). **자동 점검기는 없다** |
| 담당·완료 조건 (정식 설계로 넘김) | 정식 시험 하네스의 실행 전 점검기. 각 실제 회차 계획에 “입력 바이트·표시·계산 규칙” 필드를 둔다 |
| 남은 한계·추가 검증 필요 | 실행 전 점검기 구현은 후속이다. 다음 실제 회차 계획(04-05)에서는 사람이 이 필드를 채운다 |

### 1.9 런타임 갱신

| 남은 한계·추가 검증 필요 | 형 정의 비교는 지금 수동이다. 공급자 거부·인증 오류의 실제 출력은 관측하지 않았다(진행 기록 9 §5) |

### 1.10 시험 환경 간섭

| 단계 | 내용 |
| --- | --- |
| 발견한 문제 | 세 가지가 있었다. 시험 프로세스 안에서 `waitpid(-1)`이 다른 시험의 자식을 회수했다. 다른 곳에서 fork한 프로세스가 잠금 사본을 쥐었다. 공유 빌드 디렉터리가 지운 worktree 경로를 박아 넣었다. 디스크가 찼다 |
| 원인 | PID 1 전용 동작이 시험 프로세스에서도 돌았다. 시험 사이 자원이 격리되지 않았다 |
