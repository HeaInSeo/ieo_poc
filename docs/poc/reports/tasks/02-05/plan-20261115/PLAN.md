## 1. 범위와 이월 항목

### 1.1 범위

장부 행과 명세 v0, 검증 계획 §1.2의 정의를 합치면 02-05가 만드는 것은 다음 연결이다.

```
명세 revision(출처 sources[]·digest) → 배정(assignment_id·generation·target_sha·한도)
  → 전달(코디네이터가 supervisor start·reconnect를 부른 기록과 응답)
  → 실제 인수(supervisor가 그 배정·revision·digest로 takeover 체크포인트를 보고해 저장된 기록)
  → 첫 행동(런타임 stream에서 관측한 첫 실제 행동)
  → 체크포인트(after_run·error, 02-04 중앙 기록)
```

- **전달과 실제 인수를 나눈다**(검증 계획 §1.2 “역할 Pod 수신”, “요청 전달과 실제 인수의 구분”). 전달 응답(2xx)은 인수가 아니다. 인수는 supervisor가 같은 배정·세대·revision·digest로 takeover 체크포인트를 보고하고 코디네이터가 저장했을 때다. 첫 행동은 그 뒤에 따로 기록한다.
- **에이전트 기록은 claim이다.** 에이전트(모델)의 진행 보고는 지금처럼 보고 v0 claim으로 저장한다. supervisor가 보고하는 인수·첫 행동·세션 상태도 agent 자격으로 들어오므로 claim 수준이다. 코디네이터가 스스로 한 일(전달 요청과 받은 응답)만 verified다. 완료 판정(02-03 `judge`)은 이 claim을 입력으로 요구하지 않는다.
- **배정 통지 스트림과 사건 기반 즉시 인수는 02-08 범위다**(개정 A5). 02-05는 02-08이 쓸 시각과 실행 원인을 남길 자리만 만든다(§3 단계 4).
- **실제 GitHub 수집은 범위 밖이다**(02-04 수용 이월 1b: GH1~GH5 뒤 04-07·05-01~05-03·EARLY-01). 02-05는 GitHub 증거를 지금처럼 `evidence:ingest`로 받은 기록만 쓴다.

### 2.1 F4 · GitHub 검토 author 신원

- **문제.** 정책 G3는 “작성자와 다른 검토자”의 GitHub 검토만 센다. 지금 `author`는 증거 입력 서비스가 준 문자열이다(`api.rs`의 `body->>'reviewer' <> body->>'author'`). 정책 문장도 “GitHub 대조는 실제 수집기의 몫”이라고 적었다. 로그인 문자열은 이름을 바꾸면 달라지고, PR 작성자와 실제 push 주체가 다를 수 있다. 런타임 계약 §2.1에 따르면 개발 역할은 GitHub App 단기 토큰으로 push한다(GH1). 그러면 PR 작성자는 App 봇이 된다. Guardrail이 같은 App으로 검토를 남기면 자기 검토가 되고, 다른 신원이면 그 신원이 무엇인지 정해야 한다.
- **선택지.**
  - (가) 현행 유지: 수집기가 준 `author` 문자열.
  - (나) PR 작성자의 GitHub **숫자 user id**만 쓴다.
  - (다) (나)에 더해 “변경 작성자”를 집합으로 정의한다: PR 작성자 id, 그리고 그 repo 개발 역할에 등록된 GitHub 신원(App 봇 id 포함). 검토자 id가 이 집합에 있으면 독립 검토가 아니다. 개발·Guardrail은 서로 다른 GitHub 신원을 쓴다.
- **권고: (다).** 숫자 id는 이름 변경에 흔들리지 않는다. 집합 정의는 “개발 역할이 다른 이름으로 낸 승인”을 막는다. 더 엄격한 쪽이다. 역할별 신원 분리는 GH1·GH2가 이미 전제한다.
- **닿는 곳과 시점.**
  - 정책 G3 문장(새 버전과 digest, 독립 검토).
  - 증거 `review`에 `reviewer_id`·`author_id` 추가(OpenAPI·`evidence` 검사).
  - 코디네이터 설정에 repo별 역할 GitHub 신원.
  - 시점은 실제 수집을 연결하는 1b 작업이다. **02-05에서는 코드를 바꾸지 않는다.** 규칙만 확정해 1b 작업의 입력으로 남긴다.
- **권한: 사용자 결정.** G3의 “작성자”의 뜻을 바꾸므로 판정 정책의 새 버전이다. 승인되면 1b 작업의 `unresolved`에 규칙을 적는다(원장 갱신은 별도 PR).

### 2.2 N5 · 이전 SHA의 changes_requested와 GitHub PR 상태

- **문제.** 같은 PR에서 검토자 r2가 SHA1에 changes_requested를 남긴 뒤 새 push(SHA2)에 r1만 승인하면, 코디네이터는 G3(“다른 SHA의 검토는 세지 않는다”)대로 SHA2 검토를 승인으로 본다. GitHub의 PR `reviewDecision`은 r2가 승인하거나 dismiss될 때까지 `CHANGES_REQUESTED`다. 두 상태가 갈린다.
- **선택지.**
  - (가) 현행 유지, 차이는 보고에만 적는다.
  - (나) 같은 PR의 어느 SHA든 검토자별 마지막 changes_requested가 남아 있으면 막는다. GitHub와 같아지지만 G3의 “다른 SHA는 세지 않는다”를 바꾼다.
  - (다) G3는 그대로 둔다. PR 수준 미해결 changes_requested(수집기가 준 `reviewDecision`과 검토자 목록)를 **별도 입력**으로 받는다. 이 입력이 있으면 병합을 요청하지 않는다. 판정 문구에는 “외부 상태 불일치”로 표시한다. 해소는 그 검토자의 현재 SHA 승인이나 dismiss다.
- **권고: (다).** 현재 SHA 원칙(G2·G3, Guardrail의 옛 SHA reject 제외와 대칭)을 유지하면서, 코디네이터가 GitHub와 다른 상태로 병합을 요청하는 일을 막는다. 병합 전 “승인 철회·필수 검사 대조”는 검증 계획 §1.9가 이미 요구한다.
- **효과의 한계.** 새 입력은 판정의 `outcome`을 바꾸지 않고 G3의 검토 입력(a)·(b)에도 들어가지 않는다. 판정 출력에 “외부 상태 불일치” 표시만 더한다. 판정은 `evidence:ingest`로 들어온 `merge` 증거를 받으므로, 코디네이터 밖의 병합(예: `reviewDecision`이 `CHANGES_REQUESTED`인 상태의 관리자 병합)은 지금처럼 `accepted`가 될 수 있다. “GitHub와 어긋나지 않음”은 **코디네이터가 요청한 병합에만** 성립한다. 밖의 병합까지 막으려면 판정 규칙을 바꿔야 하고, 그것은 (나)와 같은 정책 변경이다.
- **닿는 곳과 시점.** 증거 입력에 PR 수준 검토 상태 종류 추가, 병합 요청 조건(02-06), 판정 문구(02-07). 실제 수집은 1b다. **02-05에서는 코드를 바꾸지 않는다.** 02-06·02-07로 넘기는 몫은 그 작업들의 원장 `unresolved`에 다음 원장 갱신에서 적는다(이 계획 PR의 원장 몫이 아님).
- **권한: 개발자 권한.** 정책 의미를 바꾸지 않고 기존 계획의 병합 전 대조를 구체화한다. 이 계획으로 정하고, F4와 같은 수집기에 걸리므로 F4 결정 요청에 함께 보고한다(§4.3). 사용자가 (나)를 원하면 정책 새 버전이 된다.

### 2.3 S1 · G1 `outputs` 비교를 필수 산출물로 좁힐지

- **문제.** G1은 선행 판정이 본 revision과 최신 revision의 작업 정의(outputs·acceptance·exit_condition·verification·requirement_ids)가 같아야 선행을 인정한다. `outputs`는 배열 전체를 비교한다. 그래서 순서나 선택 산출물 설명만 바뀌어도 선행 판정이 무효가 된다. 판정(G7)은 `required=true`의 artifact_id만 읽는다.
- **선택지.**
  - (가) 유지(정책 0.6.0).
  - (나) `outputs`를 `required=true` 항목의 artifact_id 집합으로 정규화해 비교한다(정책 0.7.0).
- **권고: (가) 유지.** 지금 동작은 닫힌 실패(더 엄격)다. 계획 작성자가 산출물 목록을 고치는 드문 편집에서만 드러난다. 바꾸면 정책 digest가 바뀐다. 그러면 기존 판정 행은 다른 digest가 되어 선행 조건을 채우지 못한다(G1 “다른 정책 digest의 판정은 선행을 채우지 않는다”). 02-05의 연결 작업은 이 규칙과 무관하다. 실제로 막히는 사례가 생기면 그때 (나)를 요청한다.
- **권한: 사용자 확인.** 판정 정책 버전에 관한 결정이다. “바꾸지 않음”도 이월 항목의 처분이므로 확인을 받는다. 원장의 “02-05 착수 전” 조건은 그대로다(§2.6).

### 2.4 U2 · 가져온 스프린트의 소유 검사 순서

- **문제.** `register`는 `guard_import_owned`(가져온 스프린트의 내용 소유, 409 `EVENT_CONTENT_CONFLICT`)를 01-07의 등록 검사보다 먼저 한다. 그래서 가져온 스프린트에는 01-07의 revision 오류(`REVISION_SUPERSEDED`·`REVISION_CONFLICT`)와 digest·참조 400보다 소유 409가 먼저 나온다. 같은 상황이 바뀐 필드에 따라 다른 코드를 받는다. OpenAPI의 순서 문장(“format → reference → binding”)에는 이 검사의 자리가 없다. 쓰기는 없다.
- **선택지.**
  - (가) 현재 순서를 OpenAPI에 적는다(“format → 가져오기 소유 → reference → …”).
  - (나) 소유 검사를 01-07 등록 검사(`check_registration`: 형식 → 참조 → revision·digest → 바인딩) 뒤로 옮긴다. 순서를 OpenAPI에 적는다.
- **위치(중요).** 소유 검사는 “저장 직전”이 아니라 `check_registration`의 결과가 나온 직후에 둔다. 그리고 01-07이 거부하지 않은 **모든** 결과에 적용한다: 새 revision(201로 저장될 것), 같은 revision·같은 digest 재제출(200 `AlreadyRegistered`), 낡은 revision의 같은 내용 재제출(200 `Superseded`). 저장 직전에만 두면 `Superseded`·`AlreadyRegistered`가 저장 없이 200으로 끝나 소유 검사를 건너뛴다. 예를 들어 최신 가져오기가 rev 2일 때 이전 가져오기의 저장된 rev 1을 그대로 다시 보내면 지금은 409 `EVENT_CONTENT_CONFLICT`인데 200이 된다. 위 위치에서는 지금처럼 409다. 가져오기 출처 대조(`notion_gate`, executable)는 소유 검사 뒤에 그대로 둔다. 같은 키 멱등 재조회(`idempotent_lookup`)는 지금처럼 맨 앞이다.
- **순서(새 문장).** 멱등 재조회 → 형식(400) → 01-07 참조·revision·digest·바인딩 → 가져오기 소유(409 `EVENT_CONTENT_CONFLICT`) → 가져오기 출처 대조(409 `IMPORT_GATED`·`IMPORT_INCOMPLETE`, executable) → 저장.
- **바뀌는 것.** 거부되는 요청의 집합은 같다. 지금 거부되는 요청은 여전히 거부되고(어느 검사가 먼저 거부하든), 지금 받아들여지는 요청은 같은 검사를 모두 통과해야 하므로 여전히 받아들여진다. 409가 200이 되는 경우는 없다. 바뀌는 것은 두 검사 이상에 걸리는 요청의 첫 코드뿐이다.

  | 입력 | 지금 | 바뀐 뒤 |
  | --- | --- | --- |
  | 가져온 스프린트, 작업·출처가 다른 **낡은** revision(최신보다 작음, 새 내용) | 409 `EVENT_CONTENT_CONFLICT` | 409 `REVISION_SUPERSEDED` |
  | 가져온 스프린트, 저장된 revision과 같은 번호·다른 digest | 409 `EVENT_CONTENT_CONFLICT` | 409 `REVISION_CONFLICT` |
  | 가져온 스프린트, 작업·출처가 다르고 01-07 참조·digest 오류가 있음 | 409 `EVENT_CONTENT_CONFLICT` | 01-07의 그 코드(400·422) |
  | 가져온 스프린트, 작업·출처가 다르고 executable 바인딩 미충족 | 409 `EVENT_CONTENT_CONFLICT` | 422 `UNBOUND_DRAFT` |
  | 출처 대조에 걸리고(executable) 01-07 참조·revision·digest 오류도 있음 | 409 `IMPORT_GATED`·`IMPORT_INCOMPLETE` | 01-07의 그 코드 |
  | 그 밖(형식 오류, 다른 repo, 01-07 통과 뒤 소유 불일치, 소유 통과 뒤 출처 대조) | 지금 코드 | 같음 |

- **X-01 시험의 기대 코드.** main 433ec4c의 `crates/ieo-coord/tests/coordinator.rs`를 읽은 범위에서는 바뀌는 기대가 없다. 소유 409를 기대하는 등록 시험(`an_import_owned_sprint_changes_only_through_imports`, `an_imported_draft_can_be_promoted_only_with_its_own_tasks_and_source`, `h2_every_reader_takes_the_same_latest_import`의 rev 2 파생)은 모두 01-07을 통과하는 새 revision을 보낸다. h2의 “출처 대조 전에 낡은 파생으로 거부” 순서는 소유 검사가 출처 대조보다 앞에 남으므로 그대로다. `IMPORT_GATED`·`IMPORT_INCOMPLETE` 기대 시험은 단계 1 PR에서 01-07 오류가 겹치지 않는지 다시 확인한다. 바뀌는 기대가 나오면 PR 설명에 시험 이름과 옛·새 코드를 적는다.
- **닿는 곳.** `api.rs` `register`(`register_spec`을 검사와 저장으로 나눠 그 사이에 소유 검사·출처 대조), 변환 경로도 같은 순서, OpenAPI registerSprint·import 설명. 회귀 시험: 위 표의 각 행, 이전 가져오기 rev의 같은 내용 재제출 → 409 `EVENT_CONTENT_CONFLICT`(200 아님), 최신 파생 재제출 → 200, 정상 파생 새 rev → 201. 모든 거부에서 행 수 불변.
- **권한: 개발자 권한.** 수용 결과·상태 변화는 바뀌지 않고, 수용된 01-07 계약의 순서와 코드를 가져온 스프린트에도 적용한다. 바뀐 코드 우선순위는 PR 설명과 F4 결정 요청의 보고에 함께 적는다.

### 2.5 T1 · 토큰을 쥐는 프로세스

- **결정.** 코디네이터 자격(`checkpoint:report`·`agent:report`, guardrail은 `agent:repro`)은 supervisor만 읽는다. 모델 프로세스 환경에는 넣지 않는다(이미 §4.3 허용 목록). 02-05의 새 supervisor 작업(§3 단계 2)은 새 범위를 만들지 않고 `checkpoint:report`를 “그 (repo, role)의 supervisor 범위”로 쓴다(gRPC 계약 §3 “새 범위는 만들지 않는다”). 같은 UID 프로세스는 이 파일을 읽을 수 있다는 한계는 런타임 계약 §2.1 그대로다. 그래서 supervisor가 보내는 기록도 claim이다.

- **권한: 개발자 권한.** 기존 계약 범위 안의 구현 선택이다.

### 3.2 단계별 내용과 수용 증거

**단계 1 · 등록 규칙 정리(모델 호출 없음).**
- U2(§2.4 (나)): 소유 검사 위치를 옮기고 OpenAPI에 순서를 적는다.
- C2(N2, §2 표): 코디네이터의 repo 바인딩(01-07 §3, `ctx.bindings`)이 이름 붙인 sprint_id는 그 repo 것으로 예약한다. 아직 등록되지 않은 예약 ID를 다른 repo가 등록·변환하면 409 `SPRINT_REPO_CONFLICT`다. X-01이 가져오기에 둔 예약 검사와 같은 규칙을 `/v0/sprints`·`/v0/sprint-inputs`에도 쓴다.
  - **이미 다른 repo가 가진 ID.** repo B가 이미 등록한 sprint_id를 repo A의 바인딩이 이름 붙이면, RG2(첫 등록 repo가 소유)로는 A가 거부되고 예약 규칙으로는 B가 거부되어 아무도 등록할 수 없게 된다. 그래서 X-01 U3처럼 **기동 검사**를 둔다: 바인딩의 sprint_id가 DB에서 다른 repo 소유이면 코디네이터가 기동을 거부한다. 실행 중에 RG2와 어긋나는 상태가 생기지 않는다. 운영자가 바인딩을 고친 뒤 재기동한다.
  - 바인딩에 없는 sprint_id는 지금 규칙(첫 등록 repo)을 유지한다. 존재 노출(409와 201의 차이)은 바인딩된 ID에서는 바인딩 자체가 공개 설정이므로 문제가 줄어든다. 바인딩 밖 ID의 노출은 남는 한계로 적는다.
- 증거: §2.4 표의 각 행과 재제출 회귀, 예약 ID 선점 시도 409와 원 repo 등록 201, 다른 repo 소유 ID를 이름 붙인 바인딩의 기동 거부, 거부 시 행 수 불변. 변이 시험(소유 검사 위치, 예약 검사 제거, 기동 검사 제거).

**단계 2 · 새 supervisor 작업(모델 호출 없음).**
- 자기 배정 조회·첫 행동 기록·세션 상태 보고를 작업 표에 넣고 HTTP·gRPC 어댑터를 단다. proto에 RPC·메시지 추가, `buf breaking` 통과.
- 세션 상태 보고는 지금 `GET /v0/role/status`의 §7 항목(lifecycle, session_id, `quota_group_id`, `provider_status_or_unknown`, `last_actual_action_at`, 체크포인트 순번·digest, `pending_external_requests`, `active_children`)을 그대로 싣는다. 코디네이터 쪽 이력에 쌓아 조회 때 supervisor에 닿지 못해도 마지막 보고와 그 시각을 보인다. 낡은 보고는 현재 값으로 쓰지 않는다(02-04 항목 4의 신선도 규칙).
- OpenAPI의 `checkpoint:report` 범위 설명을 새 작업에 맞게 고친다(§2.5).
- 증거: 인증·범위(다른 repo·역할 403, development의 guardrail 경로 403), 멱등(같은 키 200, 다른 내용 409), 거부 무상태, 두 전송의 같은 답(공통 회귀 표에 행 추가). gRPC 부분이 늦어지면 HTTP 시험만으로 이 단계를 병합하고 RPC는 뒤따른다(위 공통 규칙).

**단계 3 · 코디네이터의 배정 전달(모델 호출 없음, 첫 supervisor 변경 PR).**
- `deliverAssignment`: (1) 전달 요청을 기록한다(배정 머리와 같은지 확인, 아니면 409 `STALE_ASSIGNMENT`). (2) 기존 `compare`(`judge_resume`)로 판단한다. `no_checkpoint`이면 start, `resume_allowed`이면 reconnect를 부른다. `already_running`·`stale_generation`·`external_reconciliation_required`·`not_observed`이면 부르지 않고 그 판단을 기록해 돌려준다. (3) 요청 본문의 `coordinator` 기록(배정·세대·sprint revision·digest·이미지·프로파일)과 `limits`는 **DB에서** 만든다. 호출자가 넘긴 값을 쓰지 않는다. (4) 응답이나 결과 불명(`unknown`)을 기록한다. 결과 불명은 같은 request_id로 재조회·재전송하고, supervisor는 같은 `attempt_id`·같은 내용이면 저장된 결과를 돌려준다(새 실행 없음).
- supervisor: start·reconnect를 받으면 자기 배정 조회로 코디네이터 DB의 현재 배정과 요청의 `coordinator` 기록이 같은지 확인한다. 다르면 실행하지 않는다(`STALE_GENERATION` 또는 `EXTERNAL_RECONCILIATION_REQUIRED`). 그 뒤 지금처럼 `central::compare`를 한다.
- C1: 전달 기록과 매핑 레코드에 논리 이름을 저장하되, reconnect는 체크포인트·중앙 기록의 session_id로만 한다. 시험: 논리 이름만 바꾼 reconnect가 같은 session_id로 재개되고, 이름이 같고 session_id가 다른 기록은 재개되지 않는다. 코드 검토 기록을 보고에 남긴다.
- C12(비차단): 빈 `projects/*/memory` 디렉터리의 digest 처리(f73ac13 P3)와 정리 코드가 범위 밖의 읽을 수 없는 파일을 열지 않는 시험(bc55edf R5)을 이 PR에 함께 넣는다.
- start·reconnect의 같은 `attempt_id`·같은 내용 재조회는 런타임 계약 §7(“같은 `request_id`·다른 내용”만 `ID_CONTENT_CONFLICT`)에 코드를 맞추는 교정이다. 뜻 변경이 아니며 revision 10에 그렇게 적는다.
- **예산 검사의 위치.** 02-04의 호스트 쪽 호출자(`caller.rs`)는 실제 회차의 예산 권한이다. 전달 경로가 실제 회차를 부를 때도 같은 검사(기록 판독, 추가 결제 없음 3중 확인, 한도 계산, 회차 뒤 계측·과금 기록, `stop_required`)를 **같은 코드로** 거쳐야 한다. 그래서 그 검사를 라이브러리로 묶어 전달 경로와 호출자가 같이 쓴다. 권한 있는 검사는 **역할 컨테이너 밖**(코디네이터 또는 호스트 쪽 호출자)에서 돈다. supervisor는 모델과 같은 UID로 돌아 그 안의 기록과 설정을 개발 코드가 바꿀 수 있기 때문이다(런타임 계약 §2.1). supervisor의 `config.budget`·`share`는 지금처럼 보조 상한으로만 남는다.
- **X-08과의 관계.** 이 라이브러리는 X-08이 고치는 `caller.rs` 위에 있어야 X-08 교정이 두 경로에 같이 적용된다. 그래서 라이브러리 묶기는 X-08 병합 뒤에 하고, **단계 8 전에 반드시 끝낸다.** 그 밖의 단계 3(전달 기록, `compare` 판단, supervisor 쪽 확인, 가짜 런타임 시험)은 X-08에 기대지 않는다. 같은 파일(`serve.rs`·`central.rs`)을 고치므로 X-08이 먼저 병합되면 충돌이 적어 그 순서를 **선호**하지만, X-08이 늦으면 기다리지 않고 진행한다.
- 증거(가짜 런타임·실제 DB): 체크포인트 없음 → start, 정상 after_run → reconnect(같은 session_id), 실행 중 → 부르지 않음, 낡은 세대·digest 불일치·중앙 앞섬·로컬 앞섬 → 부르지 않음, supervisor 무응답 → `not_observed`, 호출 뒤 응답 유실 → `unknown` 기록 후 재조회로 같은 결과(실행 1회), 다른 배정 기록을 넣은 start → supervisor 거부. 코디네이터와 supervisor 재시작 뒤 같은 판단. 모든 경로에서 실행 수와 체크포인트 행 수를 센다.

**단계 4 · 인수·첫 행동 연결과 연결 조회(모델 호출 없음).**
- 인수: takeover 체크포인트에 `delivery_id`를 싣는다. 코디네이터는 체크포인트 저장 조건(02-04 (a)~(c))에 더해, 그 전달이 같은 (repo, role, 배정, 세대)의 것이고 결과가 기록됐거나 `unknown`인지 확인한다. 저장과 같은 트랜잭션에서 인수 행(delivery_id, 체크포인트 순번, session_id, 적용 revision·digest, 수신 시각)을 만든다. 전달 없는 takeover는 409로 거부하고 행을 남기지 않는다.
- 적용 버전: 인수 행의 revision·digest는 supervisor가 실제로 적용한 값(체크포인트의 값)이다. 배정의 revision과 다르면 저장 조건 (b)가 이미 거부한다. 발행(배정)·전달·적용을 따로 남기므로 P02(04-02)가 대조에 쓸 수 있다.
- 첫 행동: supervisor는 회차 stream에서 첫 실제 행동을 찾는다. 정의는 `init` 다음의 첫 `assistant` 사건 중 `tool_use` 또는 텍스트 출력이 있는 것이다. 사건 오프셋과 관측 시각(supervisor 시계, 사건에는 시각이 없음)을 `recordFirstAction`으로 보낸다. 실행 중 보고가 실패해도 회차를 멈추지 않는다. after_run 체크포인트에 같은 값을 넣어 다음 보고로 채운다. 행동 없이 끝난 회차는 “첫 행동 없음”으로 남기고 0이나 시작 시각으로 채우지 않는다. 세션 상태의 `last_actual_action_at`도 이 관측으로 갱신한다(C14).
- 02-08 준비: 전달 행에 `cause`(지금은 `operator`만, 02-08이 `event`·`periodic`을 더함)와 요청·응답 시각을 둔다. 조건 충족·사건 수신 시각은 02-08이 더한다.
- 연결 조회: (sprint_id, revision, digest, `sources[]`) → 배정(세대·target_sha·한도·발급자·정책 digest) → 전달(요청·판단·응답·시각, verified) → 인수(체크포인트 순번·digest·session_id, claim) → 첫 행동(오프셋·시각, claim) → 이후 체크포인트·변조 사건 → 같은 배정의 에이전트 보고(claim, 별도 필드).
- claim 보존과 판정 분리: 에이전트 보고가 하나도 없어도 연결과 완료 판정이 진행되는 시험(02-03 `judge`는 GitHub·실행 증거만 입력). 에이전트 보고가 있으면 claim으로 저장되고 판정 입력에 쓰이지 않는다. 인수·첫 행동 claim이 없거나 늦게 와도 판정 결과는 같다.
- 증거: 정상 연결 전체, 전달만 있고 인수 없음(“요청만으로 인수 인정 0건”, 검증 계획 P21 행), 전달 없는 takeover 거부, 낡은 세대 전달 뒤 새 세대 인수, 첫 행동 중복·내용 충돌·유실 뒤 after_run으로 채움, 재시작 뒤 연결 조회가 같음.

**단계 5 · 배정 수준 시간·토큰 한도, 1a(모델 호출 없음).**
- 배정 요청에 선택 필드 `limits {elapsed_seconds, total_tokens}`를 더한다. 없으면 명세 revision의 `limits`를 쓴다. 명세 값을 넘으면 422로 거부한다. 숫자를 새로 정하지 않는다(정책 “numeric_values”).
- 소비량: 전달한 각 회차가 끝나면 코디네이터가 역할 서비스의 회차 stream을 받아 02-01 계측기로 회차 몫을 계산한다(재개는 누적 차분, 자식은 전사 기준, 런타임 계약 §11·§12). 배정(모든 세대) 합계를 DB에 기록한다. 미계측 회차가 하나라도 있으면 그 배정의 다음 전달을 멈추고 0으로 세지 않는다.
- 집행: 다음 전달의 `limits`(회당 시간 창, 토큰 여유)는 배정 남은 양, 승인된 모델 예산의 남은 양, 역할 몫 중 가장 작은 값이다. **역할 몫**은 승인된 예산을 역할별로 나눈 상한이다. 02-04에서는 실행 계획([RUN_PLAN](../../02-04/real-sessions-20261115/RUN_PLAN.md))이 개발 8회·9,600초·1,000,000·10,000,000, Guardrail 4회·4,800초·500,000·5,000,000으로 정했고 합이 승인 예산과 같았다. 역할 설정의 `share`가 그 값이다. 02-05 예산이 승인되면 그 결정의 역할별 회차(§4.3)로 같은 방식으로 정한다. 승인된 예산이 없으면(모델 호출 없는 시험) 이 항은 시험 고정값이다. 이 계산도 컨테이너 밖에서 한다(단계 3). 남은 양이 없으면 전달하지 않고 거부 사유와 기록을 남긴다(409 `LIMIT_REACHED`와 같은 계열의 코드, 상태 불변). 운영 상태는 “사람 결정 대기”다.
- 사람 결정 요청(decision_request)을 자동으로 만들려면 정책 G5의 범위를 넓혀야 한다. 그것은 정책 새 버전이므로 02-05에서는 하지 않는다. 거부와 사건 기록까지만 하고, 결정 요청 연결이 필요하면 근거와 함께 사용자에게 묻는다.
- 증거: 시간 한도 도달(가짜 런타임이 창을 다 쓰고 정지), 토큰 한도 도달(가짜 stream 사용량), 재개 회차의 누적 차분, 미계측 회차 뒤 정지, 여러 세대에 걸친 합산, 예산이 배정보다 작을 때 예산 쪽 적용, 거부 무상태, 재시작 뒤 같은 합계.

**단계 6 · 외부 요청 추적, 3(모델 호출 없음).**
- 추적 대상과 정의를 먼저 적는다. 02-05가 추적하는 외부 요청은 역할이 supervisor를 거쳐 보낸 요청이다: 코디네이터 보고·체크포인트·재현 요청 중 답을 받지 못한 것(대기 사본 포함), 그리고 전달 경로의 결과 불명. 모델이 Bash 등으로 직접 낸 네트워크 요청은 관측할 수 없다. 이것은 `not_observable`로 따로 보고하고 “없음”으로 쓰지 않는다. push 단기 토큰 경로(GH1)는 05-03 범위다.
- supervisor는 `pending_external_requests`를 `not_tracked` 대신 실제 목록(요청 id·종류·보낸 시각·대상)으로 보고하고 체크포인트에도 쓴다. 답을 받거나 재조회로 반영을 확인하면 지운다. 목록이 비어 있지 않으면 reconnect는 외부 대조로 멈춘다(런타임 계약 §5-1·§6).
- repo 범위 정지: 외부 요청 목록이 실제 목록이 돼도 `active_children`은 04-05 전까지 `not_tracked`다. 그래서 `safe_shutdown_confirmed`는 계속 `false`이고 사유에 자식 미추적이 남는다. 사용자 결정 항목 3 그대로다.
- 증거: 답 유실된 보고가 목록에 남고 재조회 뒤 지워짐, 목록이 있는 상태의 reconnect 거부, 정지 보고에 외부 요청이 사유로 나타남, 외부 요청 0이어도 자식 미추적 때문에 미확인 유지.

**단계 7 · GitHub SHA·CI 대조를 재개의 최종 근거로(모델 호출 없음).**
- 근거: 개발 컨테이너의 체크포인트는 같은 UID의 개발 코드가 바꿀 수 있다(런타임 계약 §2.1). 그래서 재개 판단의 최종 근거는 GitHub의 브랜치 head·CI 기록이다.
- 입력: 실제 수집이 없으므로 `evidence:ingest`로 받은 기록만 쓴다. 새 증거 종류 `branch_head`(sha, 브랜치 ref, source_ref)를 더한다. CI는 기존 `ci_run`. 둘 다 서비스 주체가 넣는 신뢰 입력이며, 시험에서는 고정 입력이다(02-03과 같은 구분).
- 규칙(`judge_resume` 확장, 개발 역할):
  - supervisor가 after_run 체크포인트에 `worktree_head`(작업 디렉터리 `HEAD`)와 push한 SHA를 기록한다. 지금은 추적하지 않는다(C14).
  - 배정 브랜치의 최신 `branch_head`가 체크포인트의 push SHA와 같아야 재개한다. 아직 push가 없으면 배정 `target_sha`와 같아야 한다.
  - 다르면 `external_reconciliation_required`이고, GitHub 기록이 없으면 `not_observed`다. 어느 쪽도 재개하지 않는다.
  - CI는 그 head SHA의 `ci_run`만 본다. 다른 SHA의 CI는 쓰지 않는다. 결과(성공·실패·없음)는 재개 판단 기록과 전달 본문에 싣는다. 체크포인트나 에이전트 보고의 CI 주장과 GitHub 기록이 다르면 GitHub 기록을 쓰고 불일치를 기록한다.
- Guardrail: 검토 대상 SHA가 현재 개발 배정의 `target_sha`가 아니면 재개하지 않는다(새 검토 배정이 필요, 계획 §1.9).
- 남는 것: 실제 GitHub에서 head·CI를 가져오는 수집기, 신원(F4)·PR 수준 상태(N5)는 1b 작업이다. 그 작업은 이 입력 자리에 실제 수집 결과를 넣는다. 수용 보고는 C10 옆에 “대조 대상은 증거 입력으로 받은 기록이며 실제 수집이 아니다”를 다시 적는다.
- 증거: head 일치 → 재개, push 뒤 head 불일치(로컬 체크포인트 변조 포함) → 외부 대조, GitHub 기록 없음 → `not_observed`, 다른 SHA CI 무시, CI 주장 불일치 기록, Guardrail 대상 SHA 낡음 → 재개 안 함.

**단계 8 · 실제 회차 확인(실제 모델 호출 필요, 선택).** §4.

**단계 9 · 수용 보고(모델 호출 없음).** 수용 기준 문장별 대응, 이월 C1~C14의 처분, 실제·모의·저장 기록·문서 구분, 남은 한계, 독립 검토. 02-04처럼 수용 판단은 보고 검토와 사용자 결정 뒤에만 상태를 바꾼다.

## 4. 실제 모델 호출 부분

### 4.1 무엇이 실제 호출을 필요로 하는가

수용 기준의 연결(출처·digest·revision → 전달 → 인수 → 첫 행동 → 체크포인트)은 가짜 런타임과 실제 DB로 모두 시험할 수 있다. 실제 Claude가 꼭 필요한 확인은 둘뿐이다.
1. **첫 행동 판별이 실제 stream에서 맞는지.** 가짜 stream은 CLI 2.1.322의 형 정의를 따르지만, 실제 첫 `assistant` 사건의 모양과 순서는 실제로만 확인된다.
2. **전체 경로를 실제로 한 번 지나는지.** 02-04의 실제 7회는 중앙 체크포인트 경로(항목 4·9)를 지나지 않았다(수용 기록 §2). 코디네이터 전달 → supervisor → 실제 `claude` → takeover 체크포인트·인수 → 첫 행동 → after_run → 코디네이터 경유 reconnect를 실제로 지난 기록이 없다.

장부의 수용 기준이 이 실제 확인을 요구하는지는 문장만으로 정해지지 않는다. “실제 인수”는 검증 계획 §1.2에서 “전달 응답과 구분되는 작업자의 인수 기록”이다. 실제 에이전트·PR 연결의 검증은 04-03(P03)과 EARLY-01이 따로 맡는다. 그래서 두 가지 길이 있고 사용자가 정한다(§4.3).

## 5. 위험·한계와 X-08과의 순서

- **X-08과의 순서.** X-08은 모델 호출 없는 교정이고 첫 실제 호출 전에 병합된다. **X-08 병합이 필요한 것은 단계 8(실제 회차)뿐이다.** 02-05의 모델 호출 없는 단계 3~7(코디네이터 start·reconnect 호출, 한도 집행 등)은 X-08을 기다리지 않는다(개정 A6, 재개 지시 §6). X-08은 `caller.rs`·`serve.rs`·`central.rs`를 고치고 단계 3·5도 같은 파일을 바꾸므로, 충돌을 줄이려고 X-08을 단계 3 전에 병합하는 순서를 **선호**한다. 이것은 선호이지 조건이 아니다. X-08이 늦거나 사용자 결정으로 멈추면 단계 3~7은 먼저 진행한다. 공유 예산 검사 라이브러리만 X-08 병합 뒤에 그 위에서 만들고, 단계 8 전에 끝낸다.
- **예산 권한의 위치.** 실제 회차의 예산 권한은 역할 컨테이너 밖(코디네이터·호스트 쪽 호출자)이다. supervisor는 모델과 같은 UID여서 보조 상한일 뿐이다. 전달 경로가 실제 회차를 부르면 같은 검사를 같은 코드로 거쳐야 한다(단계 3). 둘이 다른 코드가 되면 X-08 교정이 한쪽에만 적용된다.
- **claim의 한계.** 인수·첫 행동·세션 상태는 같은 UID 프로세스가 바꿀 수 있는 supervisor의 보고다(런타임 계약 §2.1). 판정과 재개의 최종 근거로 쓰지 않는다. 판정은 GitHub·실행 증거, 재개는 GitHub head·CI 대조(단계 7)다.
- **외부 요청의 관측 범위.** 모델이 직접 낸 네트워크 요청은 추적하지 못한다(단계 6). 안전 종료는 04-05의 자식 추적 전까지 미확인이다.
- **GitHub 입력은 고정 입력.** 단계 7의 GitHub head·CI는 증거 입력 서비스가 준 기록이다. 실제 수집(1b)과 신원 규칙(F4)이 붙기 전에는 “GitHub 대조”가 신뢰 서비스 입력의 대조라는 점을 보고에 적는다.
- **계약 변경.** OpenAPI 0.9.0(추가), proto RPC 추가, 런타임 계약 revision 10(체크포인트 `delivery_id`·`worktree_head`·첫 행동·외부 요청 목록, 어댑터 멱등 재조회). 모두 추가이며 뜻 변경이 아니다. 뜻 변경이 필요해지면 구현 전에 사용자에게 보고한다. 정책 파일(`judgment-policy-v0.json`)은 02-05에서 바꾸지 않는다(F4·S1 결정과 단계 5의 결정 요청 연결은 별도).
- **영속 DB.** 스키마 변경(새 표, `evidence.kind`의 CHECK 확장)은 영속 PoC DB에 이관이 필요하다. 시험은 일회성 DB로 하고, 영속 DB 적용은 병합 뒤 별도로 기록한다.
- **일정.** 02-05의 추정은 `unestimated`다. 비교 가능한 실측이 없다.
