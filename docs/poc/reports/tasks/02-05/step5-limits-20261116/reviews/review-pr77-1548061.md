## Analysis

### M-1 (review 1): fixed

- **Ordering and recovery.**
  - `seq bigserial` replaces the `(delivery_id, record_sha256)` PK, and the newest row is chosen by `seq` (`limits.rs:240`, LATERAL in `settle`).
  - `ON CONFLICT DO NOTHING` is gone, so a record that returns inserts a new newest row.
  - S5-C4 kills the old behaviour.
- **Missing records.**
  - A sent call whose record is absent, or a record settled before and absent now, becomes `missing`.
  - `missing` keeps the last known counts. It is counted with `unmeasured`, so the delivery gets 409 `ASSIGNMENT_USAGE_UNMEASURED` (S5-C1, S5-C2, my N2).
  - The only ways back are a returning record, a correction (new digest), or an explicit `model_request: false` entry that names the attempt and role, which gives `withdrawn` (S5-M9).
  - Because `find` takes the first matching record, a withdrawal entry only takes effect after the original record is removed. That is consistent with how the budget library behaves (`budget::spent` skips `model_request: false`, and the original record still counts for the budget while it is present). Fail-closed.
- **Empty ledger.** No records at all while rows exist means "says nothing" (`limits.rs:79`). A truncated, moved or unmounted file can no longer erase consumption (S5-C3). A partially truncated file gives `missing` rows, which is fail-closed.
- **Ledger identity.**
  - Rows carry `<budget>@<ledger_dir>` (`limits.rs:32`).
  - `settle` refuses to continue rows that came from another ledger.
  - `room` refuses with 409 when `ledger_mismatch` is set.
  - This is fail-closed on any change to the string, including a cosmetic path change.
  - REPORT §8 states the consequence for the budget (나) switch: existing assignments stop until the old ledger is configured again or a new assignment id is issued. That is honest.
  - `getAssignmentChain` passes `ledger = None`, so its `operational_state` can read `open` while deliveries are refused for a mismatch (I-2).
- **Concurrency.** `seq` is assigned at insert, not at commit. Two concurrent settles holding different ledger views could make an older view the newest row. In every combination I worked through, the result is either fail-closed (a transient `unmeasured`/`missing` row) or corrected by the next settle. Info only.
- **Interaction with the budget library.**
  - `records_when_idle` only reads.
  - The ATTEMPT_ID_CONFLICT pre-check uses the idle view. When the ledger is busy, admit's own "attempt already recorded" check still refuses the delivery, which ends as `budget_refused` with no digest and is therefore never matched.
- **Restart.** Covered by e2e steps 4b(d) and 6.

## Findings

### N-M1 (Medium): a sent call whose result transaction was lost is never charged to its assignment

- **Where.**
  - `crates/ieo-coord/src/limits.rs:101`: `if !sent { continue; }`, where `sent` means "a result with `sent_sha256`".
  - `limits.rs:107`: `started` covers only `accepted`/`unknown`.
  - `crates/ieo-coord/src/delivery.rs` `replay`: when the delivery has no stored result, the re-query records `unknown` with `sent_sha256 = NULL` ("the supervisor holds an accepted attempt, but this delivery has no recorded request digest to compare").
  - `REPORT.md:187` (§8 "보내지 않았다고 본 전달").
- **Failure scenario.** Reproduced in `r77b-probe-result-lost.log`. Assignment A1/0 has `total_tokens` 40 and a role share of 120.
  1. The delivery of a1 sends its start. The supervisor accepts it, and the ledger gets a1's record. The result transaction then fails. In the probe, a test connection held `delivery:repo-a:development` for 15 s, so the HTTP 10 s statement bound turned it into a 500. A coordinator stop between the call and transaction 2 has the same effect.
  2. While a1's record is unmeasured (here: "stdout not available"), `getAssignmentChain` shows `runs 0`, `operational_state: open`. Only the budget library stops the next call. The assignment-level "unmeasured never counted as 0" rule does not apply.
  3. After 120 s the replay records `unknown` with no digest.
  4. A person then reconciles a1 to measured (20 billable).
  5. The next delivery is accepted with `billable_room 40`; the correct value is 20.
  6. The chain still shows `total 0, runs 0, usage_runs []`.
  7. Nothing later can fix this. The delivery never gets a digest, so it is skipped on every settle.
- **Impact.**
  - Permanent under-counting of a real run at the assignment level, on the exact failure path (a stop or lost transaction after a call) that the replay code is built to handle.
  - Version 97ff0bc matched by attempt and counted it, so the M-1/I-2 correction introduced this.
  - The budget and role share still bound the run, which is why I rate it Medium rather than High.
- **Fix.**
  - Treat a delivery as "may have sent its call" when either of these is true:
    - its newest result has a digest;
    - its newest result is `unknown`, or it has no result at all, and it is older than `IN_FLIGHT` (120 s). Below that age it may still be in progress, so skip it for now.
  - For such deliveries, match the ledger record by attempt and role. The I-2 risk is already handled for new deliveries by the record-time `ATTEMPT_ID_CONFLICT` check and admit's "attempt already recorded".
  - With no record, mark it `missing`, so it blocks. This also fixes N3 below.
  - If such a delivery later receives a result that shows nothing was sent (`not_accepted`, `budget_refused`, `refused`, `not_called`) and its newest usage row is `missing` with no ledger record, add a row that closes it (for example `withdrawn` with the reason "the delivery sent nothing").
  - Add an e2e case: hold the `delivery:` advisory lock during the result transaction, or stop the coordinator after the start is accepted, then check that the run is charged after reconciliation.
  - Update REPORT §8.
