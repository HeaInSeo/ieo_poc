## Analysis

### 1. The shutdown code (`crates/ieo-coord/src/delivery.rs:43-88,521-529,860-866`; `crates/ieo-coord/src/bin/ieo-coord.rs:110-141`)

- **FINISHING counting.** `Finishing::start()` runs in the worker after `start_with` returns `Accepted`. The guard moves into the spawned closure (`let _g = g;`), so the count drops when the finishing thread ends, including on unwind. If `thread::spawn` itself panics, the closure and the guard are dropped. The count cannot leak or go negative. `FINISHING` is a process-global static. Only the one unit test increments it in the lib test binary, and the integration tests run separate processes, so it does not make tests flaky.
- **No lost record on graceful stop.** The signal thread calls `begin_stop`, then `wait_finishing(limit)`, then `server.unblock()`. The HTTP workers keep serving during the wait, so the role's `after_run` report and any first-action or checkpoint report are accepted. gRPC is stopped only after `serve` returns. The e2e shows this end to end: SIGTERM during R2, a 503 during the wait, R2's record written, no `inflight.json`, and after restart the next delivery is judged normally ("planned runs are used"), not held.
- **No deadlock.** The wait is a sleep-poll on an atomic and holds no lock. The finishing thread needs the ledger lock, which it already holds, and the role service. Neither depends on the signal thread.
- **Deliveries refused while stopping record nothing.** The `STOPPING` check runs right after `need_compare`, before the key, body, transaction 1 or the budget. The e2e asserts that the `role_deliveries` count is unchanged. A replay of an existing key also gets 503, not its stored answer. That is acceptable, and the contract says "records nothing".
- **The bound.** `IEO_COORD_SHUTDOWN_WAIT_SECS` defaults to 720. See L-3: `After::finish` can legitimately take timeout + grace + 2 × 60 s margin, plus fetches and the record write.
- **Race probe** (`r82b-race.log`). SIGTERM came 20 ms and 60 ms into a delivery, while no run was finishing. The wait returned at once and the workers were unblocked mid-delivery. The role's start then could not complete its own call back to the coordinator. The delivery took about 10 s and ended `refused`, with no run, no record and no `inflight.json`. At 150 ms the delivery was already accepted (102 ms) and was counted, and R2's record was present after exit. So a delivery in progress at the signal fails closed in practice, because the role cannot take over without a reachable coordinator (`serve.rs:1192-1199`). The residual case is described in L-4.
- **Behaviour change.** It is listed in REPORT §3 item 3 (02-04 accepted shutdown: "stop accepting, finish requests, exit 0" becomes "serve until accepted runs are recorded, deliveries 503"), with the `podman stop -t` caveat.
