# X-05 · 기본 kind gRPC 시험 기준

기준 브랜치는 `task/x05-kind-grpc`, 출발점은 `b3846434a46c3d0f89ae08feb1fc2ab8edeb1ad6`이다. 진행 원장의 X-03·X-04 검수 완료와 [계획 §5~§7](../../../Plan_gRPC_Internal_API_v0.md)을 착수 근거로 삼는다. [진행 원장](../../../progress/STATUS.md)

## 토폴로지와 호출 경로

- 전용 rootless Podman kind 클러스터에 control plane 1개와 worker 3개를 둔다. 기본 kind 네트워크를 사용한다. 복제본은 처음 2개이며 서로 다른 worker에 둔다. 증설·교체·롤아웃 완료 시 worker마다 1개씩 둔다. 우선순위가 있는 분산 배치로 롤아웃 시 일시적인 네 번째 Pod를 허용한다. 클라이언트는 한 Pod 안에서 시험 시작부터 종료까지 같은 tonic 균형 채널을 보유한다.
- Ready 주소만 공개하는 IPv4 Headless Service를 사용한다. 클라이언트는 FQDN을 1초 주기로 조회하고, 조회에 성공하면 주소 집합 차이를 IP:port 키의 `Insert`·`Remove`로 보낸다. 조회 제한은 1초이며, 조회 오류에는 마지막 정상 집합을 보존한다. Connect timeout 1초, HTTP/2 keepalive interval 2초·timeout 2초·idle 활성, 일반 단항 호출의 클라이언트 제한 2초로 구성한다.
- 동일 키를 가진 읽기 재요청은 명시적으로 한 번만 수행한다. 시험용 읽기는 쓰기 상태가 없고 Pod마다 같은 의미 값을 준다. 제품 쓰기·재조회·멱등의 상태 판정은 X-06에서 다룬다. 시험 스트림은 결정적인 순번으로 구성하고, 새 스트림은 전달받은 마지막 순번의 다음 항목에서 시작한다.

## 동결한 판정

| 단계 | 기준 |
| --- | --- |
| 준비 | 기본 CNI와 노드 4개 Ready, 시작 서버 2개가 서로 다른 worker, 클라이언트 1개, EndpointSlice의 Ready Pod UID·IP가 서버 집합과 일치. 초기 2개 UID가 모두 30초 안에 응답 |
| 정상 분산 창 | 초기·3개 증설·스트림 Pod 교체·롤아웃·단항 Pod 교체 뒤 각각 연속 300건을 100ms 간격으로 발행한다. 첫 요청~마지막 요청 발행 29~31초, 첫 발행~마지막 결과 33초 이내. 300건 성공, 요청 ID 일치 및 중복 0, 기대한 Pod UID/세대만 응답, 각 Pod의 성공 비율이 균등 기대치의 ±10%p 이내 |
| 증설 | 2→3으로 변경. 120초 이내에 원래 두 UID를 포함한 세 서버가 Ready이며 EndpointSlice에 나타나고 서로 다른 worker에서 실행. 그때부터 30초 안에 새 UID를 포함해 현재 서버 모두 정상 단항 응답 |
| Pod 삭제·교체 | 스트림에 선택된 서버와 보류된 단항 읽기에 선택된 서버를 각각 별도 단계에서 grace 0으로 삭제한다. 단계별 120초 안에 삭제 UID가 사라지고 기존의 다른 두 UID와 새 UID 하나가 Ready 및 EndpointSlice에 나타나야 한다. 그때부터 30초 안에 세 UID 모두 정상 단항 응답 |
| 롤링 업데이트 | 3개 서버를 v1→v2로 바꾼다. `maxUnavailable: 0`, `maxSurge: 1`. 120초 안에 이전 UID 전부 교체되고 v2 세 UID가 Ready 및 EndpointSlice에 나타나야 한다. 그때부터 30초 안에 v2 세 UID 모두 정상 단항 응답 |
| 변경 중 새 단항 RPC | 네 변경 동안 일반 단항 발행을 10건/초로 계속한다. 명령 전 마지막 성공부터 해당 변경 뒤 정상 분산 창의 첫 성공까지 연속 성공 사이 간격은 10초 이하. 이 구간에는 일시 오류를 집계해 기록한다 |
| 열린 스트림과 명시적 재개 | 처음 5개 항목의 순번 1~5, 요청 ID와 서버 UID가 동일해야 한다. 해당 UID 삭제 명령부터 10초 안에 기존 호출은 전송 오류 또는 EOF로 끝나야 한다. 읽기 관측 제한 만료만으로는 실패 감지 증거가 되지 않는다. 이 호출에서 관측한 마지막 순번으로 같은 균형 채널에서 별도 RPC를 한 번 열고 10초 안에 다른 서버 UID에서 순번이 연속인 5개 항목을 받는다. 열린 호출 안에서 UID가 바뀌거나 재개 후 관측한 순번이 중복·누락되면 실패 |
| 응답 전 끊긴 단항 읽기 | 고유 ID로 보류 읽기를 1회 호출한다. 서버 로그에서 대상 UID의 처리 시작을 확인한 뒤 그 서버를 삭제한다. 삭제 명령부터 10초 안에 원래 호출에서 전송 실패를 관측해야 한다. 로컬 타이머 만료만으로는 부족하다. 명시 재요청 전까지 생존 서버 및 교체 서버에서 해당 ID를 재실행한 로그는 0건이어야 한다. 교체 확인 후 동일 채널·동일 ID로 명시 재요청 1회, 2초 안에 다른 UID에서 동일 의미 값 응답. 현재 서버 전체에서 같은 ID의 처리 시작을 합계 1건 확인 |

300건에서 균등 배정의 기준 표준편차는 비율로 약 2.7~2.9%p다. ±10%p는 임의 선택의 변동을 허용하면서 한 Pod로 고정되거나 일부 Pod가 누락되는 경우를 검출한다. 30초 유입과 2초 호출 제한은 고정 부하에서 비교할 수 있게 잡았다. 연결 감지 설정은 4초(keepalive 주기 + 대기)를 목표로 하며, 장애 중 10초 제한은 관측·연결 준비 여유를 포함한다. Ready 집합을 기준으로 한 30초는 DNS 캐시 및 전파와 여러 차례의 주소 조회에 여유를 둔다. 120초는 Deployment와 스케줄러의 수렴 시간에 대한 별도 제한이다. 이 수치는 시험 수용 값이다.

모든 필수 단계와 시간·정확성 조건을 충족하면 PASS다. 실행된 단계에서 한 조건이라도 위반되면 FAIL이며 분모를 줄이거나 실패를 표본에서 빼지 않는다. 환경·권한 문제로 필수 장면을 실행할 수 없으면 전체는 미실행 범위가 명시된 INCONCLUSIVE로 기록한다. Kubernetes 자원 스냅샷·변경 시점, DNS 주소 갱신, 각 시도의 시간·요청 ID·Pod 이름/UID·세대·결과, 스트림 순번 및 단항 서버 로그를 증거로 보존한다.
