## 1. C1 · Notion 원문을 옮겨 적지 않고 수집 (이슈 A, 결정 ⑤)

- **수집 경로.** 이 터미널의 Claude Code에 이미 연결된 Notion MCP 서버(`https://mcp.notion.com/mcp`, HTTP, 인증은 Claude Code가 보유)를 그대로 썼다. `claude mcp list`에서 Connected로 확인했다. 환경 변수에는 API 토큰이 없고, 기존 자격을 꺼내거나 새 인증을 만들지 않았다.
- **방법.** 세션에서 `notion-fetch`를 호출하면 Claude Code가 응답 원문을 세션 기록(JSONL)에 남긴다. `tools/notion_from_transcript.py`는 그 `tool_result` 텍스트를 그대로 비공개 파일(0600)로 복사하고 메타데이터를 남긴다: 기록 줄, tool_use_id, 기록 시각, 바이트 수, SHA-256, `page_last_edited_at`, 잘림 표지(`truncated`, `unknown_block_count`, 닫는 태그). 모델이 내용을 다시 쓰는 단계가 없다.
- **결과.** OC08 페이지를 두 번 수집했다(X-01 당시 호출과 이번 호출). 두 응답 원문은 같았다(17,203바이트, SHA-256 `0c2c7e82…`). 잘림 표지는 없었고 본문·페이지 닫는 태그가 모두 있었다. [c1-collection.txt](evidence/c1-collection.txt)
- **기존 사본과 비교.** 정규화 digest가 원문 두 건과 X-01 사본(옮겨 적고 뒷부분을 덧붙인 것) 모두 `3f8a300f…`로 같다. 속성 43개와 본문 5,034자도 같다. 목표·수용 기준(OC08-01~03)·선행조건·차단 사유·원 작업 ID도 같다. 따라서 **X-01 결과는 “당시 사본 기준 시험”으로 그대로 유효**하고, 다시 수행한 변환·등록·판정 시험은 없다. 기존 사본과 X-01 증거는 바꾸지 않았다.
- **한계.** 수집한 형태는 연결 도구가 그려 준 표현이다. REST API의 블록 JSON이 아니다. 두 경로의 digest는 원래 다르다(X-01 R5). REST 경로로 수집하려면 통합 토큰이 필요하지만 요청하지 않았다. 연결 경로가 동작하므로 결정 ⑤에 따라 새 발급을 요구하지 않는다. 기록 파일은 이 터미널의 세션 기록에 의존하므로, 다른 서버나 세션에서는 같은 도구를 해당 세션의 기록 경로로 돌려야 한다.

## 2. C2 · 등록자가 차단 사유를 지우는 경우의 실행 통제 (이슈 B, 결정 ③)

### 2.1 현재 한계 재현(교정 전 main 82c7db9)

큐 선행이 남은 가져오기 작업에서 일반 등록자가 미해결 사유를 모두 지우고 한도를 채운 파생 명세를 내면 이렇게 됐다. executable 등록 201, 의미 검토 201, 배정 201(`issued`). 서버가 강제한 것은 작업·Notion 출처의 동일성뿐이었고, 실행 허가는 등록자와 의미 검토자에게 달려 있었다: [c2-limit-reproduction.txt](evidence/c2-limit-reproduction.txt)

### 2.2 보완(최소, 기존 역할·범위 모델 재사용)

| 요소 | 동작 |
| --- | --- |
| 신뢰된 수집 기록 | `POST /v0/imports/notion`은 service 전용 범위 `notion:import`가 있어야 한다. 일반 등록자는 가져오기 기록이나 해제 기록을 쓸 수 없다(403). 가져오기 도구는 **큐 선행·차단(gates)**과 **필수 정보 누락(missing)**을 따로 보내고, 서버가 가져오기 행에 저장한다 |
| 실행 판정 | executable 등록과 배정을 판정할 때 명세 문구는 보지 않는다. 대상 페이지는 셋이다. ① 그 스프린트로 가져온 페이지. ② 명세의 출처 어느 필드에든 가져온 페이지 ID가 있는 페이지다. 출처 `kind`나 digest와 무관하고, 대시 표기와 URL 안의 ID도 찾는다. ③ 출처가 인용한 digest와 내용 digest가 같은 페이지다. 단, 그 출처가 가리킨 페이지의 **최신** 가져오기가 그 digest이면 ③은 더하지 않는다(같은 내용의 다른 페이지 과차단 방지). 과거에 그 digest였던 것만으로는 빼지 않는다(검토 aa38041 I1). 판정은 각 페이지의 최신 가져오기 행으로 한다. "최신"은 모든 검사에서 같은 순서다: revision이 먼저다(등록 잠금 아래 부여되므로 시계와 무관). 그다음이 가져온 시각이다(잠금 뒤 `clock_timestamp()`로 기록). 한 페이지를 두 시험 ID로 가져온 이전 데이터는 revision을 비교할 수 없으므로 그 페이지를 인용한 실행을 거부한다(닫힌 실패, 검토 6352413 K1). 새 가져오기는 두 번째 시험 ID를 거부하고(검토 7afd4d1 G3), 페이지 ID는 정규형(소문자 16진수 32자, 대시 없음)만 받는다(검토 f571d1e L3). [영속 DB 확인](evidence/persistent-db-checks.txt)에서 그런 페이지와 비정규 ID는 0건이다. 따라서 다른 sprint_id로 만든 사본도 판정 대상이다. 출처 종류를 바꾸거나, digest만 바꾸거나, 참조를 다른 가져온 페이지로 바꾼 사본도 마찬가지다. missing이 있으면 409 `IMPORT_INCOMPLETE`이고 예외로 풀리지 않는다. gates가 있으면 409 `IMPORT_GATED`이다. 이를 푸는 것은 둘뿐이다. 하나는 가져오기 자신의 시험 스프린트에 대해 그 행의 페이지와 내용 digest로 승인된 사용자 예외다. 다른 하나는 gates가 빈 새 가져오기(신뢰된 해제 기록)다. 한 페이지는 한 시험 ID에만 속한다(다른 시험 ID로 가져오면 409) |
| 재조회와 되돌림 | 같은 내용의 재조회는 그 페이지의 **최신** 가져오기일 때만이다. 내용이 이전 상태로 돌아가면(A→B→A) 새 revision이 되어 그 차단이 다시 적용된다 |
| 사용자 승인 예외 | user 전용 범위 `exceptions:approve`로 기록하고 추가 전용으로 보관한다. 적용 범위는 정확히 시험 ID, repo, 그리고 승인 시점 최신 가져오기의 페이지와 내용 digest다. 같은 내용을 가진 다른 페이지에는 적용되지 않는다. 이후 차단 내용이 다른 가져오기가 오면 다시 승인해야 한다. 큐 선행만 풀고, 형식·바인딩·한도·의미 검토·필수 정보 검사는 그대로 적용된다 |
| 이전 행 | C2 이전 가져오기 행은 gates/missing이 NULL이다. 가져오기 서비스가 저장한 응답을 가져오기 도구의 고정 사유 문형으로 나누고, 모르는 사유는 missing으로 본다(닫힌 실패) |

### 2.3 서버가 강제하는 범위와 등록자·의미 검토에 남는 범위

| 범위 | 강제 주체 |
| --- | --- |
| 가져온 작업을 executable로 등록하거나 배정할 때의 큐 차단·필수 정보 판정. 대상은 같은 스프린트, 그리고 출처가 차단된 페이지의 ID나 그 가져온 내용 digest 중 하나라도 인용하는 다른 스프린트다. 출처 `kind`나 digest를 바꾼 사본, 참조만 다른 가져온 페이지로 바꾼 사본도 포함한다 | **서버**(가져오기 기록·예외 기록 기준) |
| 해제 기록과 예외 기록을 쓸 수 있는 주체(service 가져오기, user 승인) | **서버**(범위·주체 종류) |
| 되돌린 내용의 차단 재적용, 내용이 바뀐 차단에 대한 예외 무효 | **서버** |
| Notion 출처를 **빼거나**, 페이지 참조와 digest를 **둘 다** 바꾸고(다른 가져온 페이지의 ID·digest로 바꾸는 경우 포함) 같은 작업을 새 스프린트로 등록하는 경우 | 서버가 원본을 알아볼 수 없다. **등록자와 독립 의미 검토**에 남는다. 의미 검토자는 원 Notion 페이지를 가리키지 않는 출처를 보게 된다. 시험 `g1_…`, `h1_…`이 이 한계를 고정한다 |
| 예외 기록의 `scope`(브랜치, 기준 SHA, 기본 브랜치 병합·배포 금지) | **기록만 한다.** 서버는 배정 SHA나 브랜치를 이 값과 대조하지 않는다. 병합·배포 금지는 대상 repo에 PR·병합 권한을 쓰지 않는 운영 규칙(결정 ③·④)으로 지킨다 |
| 승인 자격을 사람만 가진다는 보관 분리 | **미검증.** 같은 호스트·계정에 보관되므로 04-07에서 다룬다 |

### 2.5 영속 DB에 적용(OC08 시험)

배포 전 `pg_dump`로 백업했다. 아래는 교정 1(9cb0e3a) 빌드를 적용한 기록이다. 그때 이관은 열 추가, 기본 키를 (page, revision)으로 변경, 예외에 승인 내용 digest 추가였다. 교정 2는 기본 키를 (test_id, revision)으로 바꾸고 예외에 페이지를 묶는다. 이 변경은 병합 뒤 영속 코디네이터에 다시 적용한다. 그때 기존 예외 행(페이지 없음)은 닫힌 실패로 효력을 잃는다. 결정 ③의 예외는 같은 결정 근거로 페이지가 묶인 새 행으로 다시 기록하고, 그 결과는 보고 PR에 남긴다. C2 이전 OC08 행 2건은 그대로 두었다. 결과는 [c2-live.txt](evidence/c2-live.txt)와 검토 반영 뒤 재확인 [c2-live-r2.txt](evidence/c2-live-r2.txt)에 있다.
- 예외 없이 사유를 지운 파생 executable 명세는 409 `IMPORT_GATED`이고 행은 바뀌지 않았다.
