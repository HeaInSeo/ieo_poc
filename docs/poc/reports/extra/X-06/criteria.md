# X-06 · 제품 코디네이터 gRPC 시험 기준

시작점은 X-05 병합 `d27fa96504b568fd3156d6c5ac21e7d2f333ff9e`다. X-04 수용과 X-05 병합 SHA의 main CI를 확인한 뒤 시험한다. [gRPC 계획 §5~§7](../../../Plan_gRPC_Internal_API_v0.md), [제품 계약 §5·§6·§10](../../../../../contracts/ieo-internal-v0.md), [X-05 결과](../X-05/REPORT.md)

## 환경과 관측

- 일회용 표준 Ubuntu 러너에서 별도 rootless Podman kind 클러스터를 만든다. 기본 kindnet, control plane 1개와 worker 2개를 사용한다. 서버와 클라이언트는 서로 다른 worker에 배치한다. kubeconfig, namespace, PostgreSQL 및 시험 자격은 이 클러스터 전용이다.
- 출시와 동일한 바이너리 진입점 `ieo-coord serve --grpc-listen`을 실행한다. 같은 바이너리와 구성으로 서로 다른 빈 PostgreSQL DB를 바라보는 두 서버를 띄운다. 시험 클라이언트는 제품에 정의된 tonic stub을 사용한다. HTTP 대조군과 제품 gRPC 경로에는 같은 의미의 요청을 보낸다. 코디네이터의 관리 작업은 계약에 정의된 HTTP 경로로 준비한다.
- coordinator Headless Service에는 해당 실험 Pod만 들어간다. 클라이언트가 서비스 DNS를 해석하고 결과 및 Pod IP·UID·노드 배치를 기록한다. gRPC 정상 비교 창에는 같은 채널을 재사용한다. 각 호출의 업무 ID 또는 시나리오 이름과 순번을 기록한다. X-05에서 측정한 다중 Pod 분산과 스트림 재개는 별도 증거로 연결한다.

## 사전 고정 판정

| 구간 | 표본·한계·판정 |
| --- | --- |
| 준비 | 역할별 Pod, DB, Service를 생성하고 180초 안에 Ready. gRPC 네트워크 호출과 HTTP 및 DB 대조가 가능해야 한다. |
| HTTP/gRPC 동등성 | X-04에서 재사용하는 157개의 대응 요청을 각 전송에 한 번씩 발행한다. 전체 120초 이내, 각 정상 gRPC 응답·거부 5초 이내. HTTP 상태·본문과 gRPC 상태·상세 trailer의 대응, 각 요청 직후 정규화한 PostgreSQL 스냅샷에서 차이 0건. 인증 없음·다른 역할/저장소 거부를 포함하고 거부 전후 업무 상태가 같아야 한다. 멱등 재생은 원래 영수증과 상태를 보존해야 한다. 옛 세대 보고는 `preserved_late`이며 현재 `latest_claims`에 나타나는 횟수 0. |
| 배정 중복 | 정상 시나리오 초기 배정 시 각 DB에서 기존 배정과 같은 요청이 200 및 `already_issued`, 이전 머리를 보지 못한 별도 요청이 409 `OWNERSHIP_CONFLICT`. 각 DB의 두 호출 전후 배정·머리·업무 스냅샷 차이 0. 배정은 HTTP 전용이며 gRPC 자기 배정 조회로 관측한 머리는 원래 배정과 일치해야 한다. |
| 커밋 전 롤백 | 정상 비교 창 뒤 새로운 개발 체크포인트 키를 준비한다. PostgreSQL 자문 잠금으로 해당 키 쓰기를 막고 제품 gRPC에 1회, 600ms 기한으로 호출한다. 5초 안에 서버가 롤백한 `DEADLINE_EXCEEDED`, 잠금 해제 뒤 업무 스냅샷 차이 0. 같은 채널에서 확인 조회를 한 번 호출해 기존 체크포인트 머리가 그대로여야 한다. |
| 커밋 뒤 응답 유실·재요청 | 정상 연결을 먼저 확인한 투명 TCP 릴레이에서 서버→클라이언트 전달만 차단한다. 고유 `request_id`의 재현 요청을 1회 보낸다. 2초 안에 응답 유실을 관측하고 독립 DB 조회에서 새 키 1건이 있어야 한다. 원래 제품 채널에서 `GetReproRequest` 1회로 키와 반영 결과를 확인한 뒤 같은 요청만 명시적으로 1회 보낸다. 각 확인은 5초 이내, `REPLAYED`(HTTP 대응 200), 행·업무 스냅샷 차이 0, 같은 키의 최종 행 1건. 제품 요청 자동 재실행 0. |

요청 수는 잠긴 X-04 공통 회귀 픽스처의 호출 개수와 두 장애 장면의 고정 호출 횟수를 따른다. 업무 판정과 상태 비교에는 오차를 허용하지 않는다. 5초와 120초는 runner 스케줄링·소켓 처리 여유를 포함한 관측 한도이며, 600ms는 X-04의 기존 잠금 대기·서버 롤백 판정을 재사용한다. 전체 시험은 한 번의 동일 클러스터 실행에서 위 기준을 모두 충족해야 PASS다. 비교·상태·관측 한도 위반은 FAIL이다. 환경 제약으로 장면이 시작되기 전에 차단되면 INCONCLUSIVE와 근거를 남긴다. 실행 전 이 문서를 커밋하며 관측 결과에 맞춰 개정하지 않는다.
