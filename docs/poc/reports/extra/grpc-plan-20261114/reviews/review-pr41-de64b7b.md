## Findings

1. **[Medium] X-05 acceptance (ledger §7 and A4 json) leaves out user constraints that only the plan carries.** Missing from the binding text: (a) "폴백에서도 gRPC를 유지한다" (keep gRPC in the fallback too); (b) state the balancing path and settings in the deployment config; (c) do not assume an existing stream moves to another Pod (the text only says to judge the two separately); (d) no real Claude calls (only in state.json `unresolved` and the plan); (e) check host resources and run the default and Cilium setups sequentially if needed. (b) and (a) are deliverable requirements in the user decision §3 and must be checkable at acceptance. Add them to the X-05 acceptance; put (e) in X-05 and/or X-07.

2. **[Medium] The X-06 and X-07 acceptance texts are weaker than the decision.** X-06 lists "재전송 중복 반영 방지" but drops the decision §5 clauses "연결 실패만 보고 작업 전체를 무조건 재실행하지 않는다" and "전송 성공 여부와 서버의 실제 반영 여부가 다른 경우 포함", which X-04 keeps. The user's rule to commit the criteria (observation time, request count, allowed deviation, recovery limit, failure criteria) in advance, with reasons, and not change them after seeing results applies to the kind tests. Plan §7 applies it to X-05 and X-06, but only X-05's acceptance includes it. X-07 says "X-05와 같은 기능·정확성 기준" but does not say the Cilium setup must not touch the existing dev cluster or production DB; scope_limit covers that only in general terms. Add these clauses to X-06 and X-07.

3. **[Medium] Plan §2 overstates how much existing code covers the coordinator↔execution-management-service API.** `handle` and `Credentials` are transport-independent (confirmed: `Req{method,path,query,idempotency_key,body}`, one transaction per request with rollback on `Err`, Bearer→digest lookup). But the actual supervisor-facing operations do not exist yet. The OpenAPI paths and router have no checkpoint, session status, delivery or acceptance endpoint, and crates/ieo-supervisor has no coordinator client (its deps are hex, serde_json and sha2). `auth.rs` has no principal kind or scope for a supervisor or execution-management service. Agent credentials are bound to one repo and role with only agent:* scopes, and client scopes are user- or service-oriented. The table row "인증·역할 권한 → 기존 구현" therefore implies coverage that does not exist. The table also lists every business area (registration, Notion import, user exception approval) as reused over gRPC without saying which operations form the internal API. Add to the "추가 필요" column: (i) which existing operations the gRPC surface carries and which it does not; (ii) the supervisor principal, scopes and per-role permissions, to be defined in X-03; (iii) the new supervisor operations planned for 02-05, and whether they also get an HTTP/JSON form, since the user said to keep HTTP and add gRPC.

4. **[Low] The placement makes X-04 a de facto gate on 02-05 without saying so.** Plan §6, TASKS next_action and state X-03/X-04 say "02-05 전에 완료", and plan §3 says "gRPC 전환은 X-04·02-05에서 한다". The ledger keeps 02-05's prerequisites at 02-03·02-04, and A4 only says X tasks are not prerequisites of "02-04 등". Placing the work before 02-05 is a reasonable reading of the dependency instruction, since 02-05 is where coordinator↔supervisor calls start. But the plan should say explicitly that this is an ordering preference: 02-05's acceptance criteria and prerequisites are unchanged, and if X-04 is not ready, 02-05 proceeds over HTTP/JSON rather than being blocked. The user said to continue current work absent a real blocker and to track new scope separately, not fold it into 02-05.

5. **[Low] Plan §3 calls http.rs a thin adapter but omits its adapter-level behaviour that a gRPC adapter must reproduce.** That behaviour is: the 1 MiB body limit with a 400 SCHEMA_VIOLATION rejection (gRPC needs a max-message-size equivalent and a mapped error); reconnecting a dropped DB connection per worker with a 500 "database unavailable"; and the unauthenticated `/v0/health` route that runs outside the transaction. X-03/X-04 should list these, or the HTTP and gRPC paths can diverge outside `handle`.

6. **[Low] Stale or incomplete progress fields.** Plan §6 step 1 says "진행 중: PR #40 … 검토·병합", but PR #40 was merged as ccf7291, which is this branch's base and is reflected in the resume next_action. `resume.plan_and_spec` still reads "v1.3.3-A1·A2·A3" and should include A4. The decision requires the next regular report to include placement and order; next_action names the PR #40 report PR but does not record that it must carry the gRPC placement and order.

7. **[Info] Accurate items, no change needed.** User_Decisions_2026-11-14_grpc.md matches the decision text: the CNI principle sentence is verbatim; scope exclusions, budget, no-auto-retry, counts and the kind-wording limit are all present, and no authority is added. Plan §4.3 lists 503→UNAVAILABLE, although the coordinator emits no 503 today; that is harmless as a reserved mapping. The statuses actually emitted are 200, 201, 202, 400, 401, 403, 404, 409, 422 and 500. Library support (tonic `balance_channel`, tower P2C, DNS polling, keepalive) is clearly marked "아직 확인 안 함" or as a candidate. Nothing claims implementation or verification: every X task is 미착수 / unverified and the event says "구현 전 계획 단계, 라이브러리 지원 미확인". The pre-separation claims are true: routing is a single `match (method, segs)` in `handle`, status is `u16`, and the runtime is synchronous (tiny_http, a sync postgres client, one connection per worker thread).
