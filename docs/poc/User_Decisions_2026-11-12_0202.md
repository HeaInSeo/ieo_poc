# 사용자 결정 — 02-02 범위 조정 (2026-11-12)

배경: 02-02 수용 기준의 “숨긴 평가” 분리를 위해 같은 서버의 별도 계정 봉인안을 준비했다([계획](reports/tasks/02-02/eval-vault-plan-20261112/PLAN.md)). 읽기 전용 확인에서 개발 계정 heain에 비밀번호 sudo와 `kind` NOPASSWD 규칙이 있어, 그 규칙을 바꾸지 않으면 이 서버의 별도 계정이 개발 에이전트로부터 봉인되지 않는다는 점을 보고했다. 사용자는 처음에 방안 1(별도 계정/호스트)을 채택했다가 아래와 같이 변경했다.

## 원문

> 앞서 선택한 ‘동일 서버의 별도 계정으로 강한 봉인 환경 구축’ 지시를 변경할게. **3번에 해당하는 범위 조정, 즉 강한 봉인을 후속으로 이월하는 것을 승인해.**
>
> 현재 PoC에서는 판정기의 정확성과 실행 증거 검증에 집중하자. 아래 방향으로 02-02를 진행해줘.
>
> 1. **이번 작업 범위**
>    기존 kind·sudo·클러스터 설정은 유지해줘. 별도 계정 생성, sub-UID/GID 변경, 추가 서버·VM 준비는 이번 범위에서 제외해줘. 작성한 봉인 구축안은 이력으로 보존하고 ‘이번 단계에서는 보류’라고 처분을 남겨줘.
>
> 2. **02-02에서 완료할 검증**
>    기존 수용 기준 중 강한 봉인과 직접 관련 없는 항목은 유지해줘. 수집기 이월 결함 교정, 공개·작성·검증 세트, 독립 담당자가 근거를 갖춰 작성한 기대값과의 대조, 현재 범위에서 가능한 정답 누출 검사를 진행해줘.
>
>    기대값과 평가 기준은 첫 평가 전에 동결하고, 기대값이 불명확한 사례는 미확정으로 구분해줘.
>
> 3. **완료 기준과 보고 범위 개정**
>    비공개 평가 세트의 강한 봉인 및 OS 권한으로 개발 계정의 접근을 차단했다는 실증은 이번 02-02 완료 조건에서 제외해 후속으로 이월해줘. 영향받는 계획·수용 기준·명세·원장에 이 사용자 결정을 일관되게 반영하고 독립 검토를 받아줘.
>
>    결과에는 ‘개발 계정의 정답 접근 차단은 미검증’이라고 명시해줘. 공개 시험이나 독립 기대값 대조의 통과를 강한 봉인 검증 또는 실제 개발 전체의 정확성 보장으로 보고하지 말아줘.
>
>    이번 조정은 02-02의 평가 환경 준비 범위에 한정해. 제품 런타임의 개발·Guardrail 역할 및 자격 격리 조건은 유지해줘.
>
> 4. **후속 조건 관리**
>    이월 항목은 담당 작업과 처리 시점을 정해 원장에 연결해줘. P07 등 비공개 평가가 실제로 필요한 실험은 해당 선행 조건을 충족한 뒤 착수해줘. 그때 평가 목적과 위협 범위에 맞는 최소 구성을 검토하고, 기존 개발 서버의 권한 개편을 당연한 전제로 삼지는 말아줘.
>
>    기존 보고의 ‘sudo가 없다’는 오류도 수집된 근거에 따라 정정해줘.
>
> 5. **검수와 후속 진행**
>    개정된 수용 기준으로 검증·독립 검토를 진행하고, 승인된 head의 필수 CI 확인 → 해당 SHA 조건부 병합 → main CI 확인 → 원장·STATUS 갱신 순서로 마무리해줘.
>
>    계획 변경이나 환경 준비는 완료 수에 넣지 말고, 02-02가 검수 완료된 경우에만 완료 수를 올려줘. 기존 예산과 검토 상한을 준수하면서 진행 가능한 작업은 계속 이어가줘.
