# Console 코디네이터 PoC 계획 v1.3.2 확인과 표준화 검증 변경 요청

Nov 12, 2026 · @필요없어.

이 문서는 PoC 계획을 작성한 설계 에이전트에게 전달한다. 검토 대상은 `Console_Coordinator_v1_3_2_2026-11-11` 묶음이다. 수행할 일은 "변경 요청" 절에 있다.

## 결론

**v1.3.2는 여섯 지시를 전부 반영했고 검산 수치가 검토자의 재계산과 일치한다. v1.3.2를 기준선으로 확정한다.**

그 위에 변경 요청 하나를 더한다. 사용자가 2026-11-12에 물은 것은 이렇다. 스프린트 문서의 형식과 개발·Guardrail 에이전트의 보고 형식을 표준화할 수 있는가. 그 표준이 사람의 결정을 쉽고 빠르게 하는지 평가하는 시험이 계획에 있는가.

확인한 답은 "형식은 정의돼 있고 기계 검사는 시험하지만, 사람이 쉽게 쓰고 빠르게 결정하는지는 거의 시험하지 않는다"이다. 이 문서의 변경 요청은 그 공백을 메운다. 다른 부분은 고치지 않고 01-01부터 실행한다.

항목별로 본문도 확인했다. "단일 컨테이너" 문구, 전체 84 합산, 5분·30분 보고 규칙은 남아 있지 않다. 스크립트 두 개는 읽기만 했고 실행하지 않았다.

지시보다 낫게 된 곳이 세 군데 있다. 유지한다.

- **무허가 push의 처리.** 1.9절의 "새 SHA 검토만으로 그 위반을 소급 승인하지 않는다".
- **병합 조건.** 병합 직전 재조회로는 경쟁을 막았다고 보지 않고 GitHub의 서버 측 head SHA 조건을 쓴다.
- **기술 근거의 해석 범위.** Restricted가 모든 단일 컨테이너 격리의 불가능을 증명하지는 않으며, 두 Pod도 노드 장애까지 독립은 아니라는 정정. 검토자의 설명이 과했던 부분이고 정정이 맞다.

P05-Q를 P26의 선행으로 넣지 않고 "한도로 인한 정지" 분류를 택한 판단에도 동의한다.

## 현재 계획이 시험하는 범위

| 대상 | 정의된 것 | 시험하는 것 |
| --- | --- | --- |
| 스프린트 명세 | 1.4절의 필드 표, `SprintSpec_v0.schema.json`, 등록 API | 필드 누락·없는 선행·순환·없는 프로파일 항목의 거부(01-07). 요구의 모순을 적대적 검토가 찾는가(P01) |
| 진행 보고 | 1.5절의 필드 표, `ProgressReport_v0.schema.json`, 5부 구성, 결정 요청 필드 | 참가자 1명이 4문항(현재 단계, 미확인 사실, 다음 행동, 결정 필요 여부)을 맞히는가(04-09). CLI가 구조만 읽고 맞게 표시하는가. 중복 발송이 없는가(P13) |
| 제품 단계의 사람 평가 | 07-04 | "T01에서 정한 기준으로 평가한다"만 있고 내용이 비어 있다 |

04-09의 크기(1명, 4문항)는 S0를 막지 않으려고 작게 잡은 것이고 그 판단은 유지한다. 다만 이 크기로는 "치명적 오해가 없다"만 확인된다. "쉽고 빠르다"는 말할 수 없다.

## 빠진 것

1. **스프린트를 누가 어떻게 쓰는지 시험하지 않는다.** 명세 v0는 digest와 프로파일 항목 ID가 들어가는 JSON이라 사람이 손으로 쓸 형식이 아니다. 지금의 9개 명세도 에이전트가 썼다. 사람이 쓰는 입력 양식, 작성에 드는 시간, 등록 거부 사유를 보고 고칠 수 있는지를 보는 시험이 없다. P26이 작성 시간을 재지만 결과로 기록할 뿐 형식을 평가하지 않는다.
2. **일정이 비어 있다.** 명세의 일정 필드는 "시간대, 착수 조건, 기한 또는 미확정 이유"이고 9개 명세 모두 미확정이다. 보고 스키마에는 기한 대비 상태나 예상 완료가 없다. 사용자가 가장 먼저 묻게 될 "언제 끝나나, 늦어지고 있나"에 답하는 표준이 없다.
3. **결정의 속도와 질을 재지 않는다.** 04-09는 결정이 필요한지 알아봤는지를 묻는다. 그 결정을 얼마나 빨리, 맞게 내렸는지는 묻지 않는다.
4. **비교 대상이 없다.** 표준화의 효과를 보이려면 같은 사실을 표준 형식과 자유 서술로 비교해야 한다. P12 본문에 "보고 문안 두 가지를 비교하는 경우"라는 문장은 있지만 그 비교를 하라는 작업은 없다.
5. **개발 에이전트의 보고와 Guardrail의 보고가 구분되지 않는다.** 보고 스키마는 하나이고 보낸 쪽은 문자열 하나(`actor`)다. Guardrail의 보고는 판정과 발견 목록이고 발견마다 위반 조건·재현 방법·기대값과 실측값·심각도가 붙는다. 설계 로그와 P07에 글로는 있는데 형식으로 고정돼 있지 않다.
6. **표본이 작다.** 평가자가 한 명이면 사람 수 대신 시나리오 수를 늘리고 정답을 사전에 고정해야 한다.

## 변경 요청

v1.3.2 기준선에 대한 변경이다. 기준선 변경 절차(원 분모, 변경 분모, 이유)로 기록한다. 아래 외에는 작업 ID, 선행, 통과 기준을 바꾸지 않는다.

### 1. 사람용 스프린트 작성 양식

01-07의 산출물에 추가한다.

- 사람이 쓰는 입력 양식(필드, 예시, 필수와 선택)과 그것을 명세 v0로 변환하는 규칙을 정한다.
- digest, 프로파일 항목 ID처럼 사람이 쓰지 않는 값은 변환이 채운다.
- 등록 거부 응답은 사람이 고칠 수 있게 필드 위치와 고칠 내용을 적는다.
- 누가 양식을 쓰고 누가 변환을 검토하는지 적는다.

### 2. 일정 표준

01-07과 01-08에 추가한다.

- **명세.** 작업별 예상 범위(근거가 있을 때만), 스프린트 기한, 기한이 없는 경우의 표시.
- **보고.** 기한 대비 상태(정상, 지연 위험, 지연), 남은 작업 수, 지연 사유와 영향받는 작업.
- 예상 완료는 근거(이전 작업의 실측)가 있을 때만 범위로 적고, 없으면 "미산정"으로 둔다. 다음 확인 시각을 예상 완료로 쓰지 않는 기존 규칙은 유지한다.

### 3. 역할별 보고 형식

01-08에 추가한다. 보고 v0의 공통 필드는 유지하고 본문 유형을 나눈다. `actor`는 문자열 하나가 아니라 역할과 이름으로 나눈다.

| 유형 | 보내는 쪽 | 본문에 들어갈 것 |
| --- | --- | --- |
| 개발 진행 | 개발 에이전트 | 단계, 변경 요약, 대상 SHA, 내부 검사 결과, 막힌 이유 |
| Guardrail 검토 | Guardrail 에이전트 | 판정(승인, 반려, 추가 확인), 대상 SHA, 발견 목록. 발견마다 위반한 조건, 재현 명령과 입력, 기대값과 실측값, 심각도, 근거의 확실성, 원본 로그 참조 |
| 코디네이터 판정 | 코디네이터 | 증거 대조 결과, 영향받는 작업, 다음 담당 |
| 결정 요청 | 코디네이터 | 질문 하나, 선택지별 영향, 권고와 이유, 기한, 미응답 시 기본 조치 |

앞의 두 유형은 주장(claim)이고 뒤의 두 유형은 판정(verified)이라는 기존 구분은 그대로다.

### 4. 새 실험 P36 · 표준 형식의 작성과 결정 지원

장부에 작업을 추가한다. 위치는 04-09 뒤, P26 전이다. S0의 선행으로 넣지 않는다. 평가자는 사용자 본인 한 명이다(2026-11-12 결정).

**가설.** 표준 양식과 표준 보고가 자유 서술보다 스프린트 작성과 사람의 결정을 빠르고 정확하게 한다.

**(a) 작성.** 사용자가 양식으로 실제 스프린트 3건을 작성한다. 대상은 P26 표본에 쓸 NodeKit 또는 Sori의 실제 작업으로 하고 결과를 07-01의 입력으로 재사용한다.

- 기록: 작성 시간, 등록 거부 횟수와 사유, 거부 응답만 보고 고친 비율, 에이전트에게 되물은 횟수.
- 대조: 같은 요구를 자유 서술로 준 경우 에이전트가 명세로 바꾸며 되묻는 횟수.

**(b) 결정.** 시나리오 12건 이상을 실행 전에 고정한다.

- 정답 결정은 Guardrail 역할 또는 별도 세션이 원본 증거로 정한다. 개발 에이전트가 시나리오와 정답을 모두 만들지 않는다. 사용자는 평가 전에 정답과 시나리오 목록을 보지 않는다.
- 포함할 유형: 결정이 필요 없는 상태 변경, 범위 결정, 일정 결정, Guardrail 반려의 수용 여부, 한도 대기, 외부 결과 미확인, 지연 위험, 개발 주장과 판정이 다른 경우.
- 같은 사실을 표준 보고와 자유 서술 보고로 만든다. 한 사람이 같은 시나리오를 두 형식으로 모두 보면 두 번째는 답을 아는 상태가 된다. 시나리오를 난도가 비슷한 두 묶음으로 나눠 한 묶음은 표준, 다른 묶음은 자유 서술로 보여 준다. 묶음의 배정과 제시 순서는 실행 전에 정한다.
- 기록: 결정까지 걸린 시간, 정답과의 일치, 원본 증거를 다시 열어 본 횟수, 추가로 물은 횟수, 결정이 필요 없는 건을 필요한 건으로 오인한 수와 그 반대, 사용자가 남긴 불편 사항.

**(c) 판정.** 치명적 오해 0건은 필수다. 그 위에 실행 전에 고정한 기준(결정 일치율, 시간, 추가 질문 수)을 표준 형식이 충족하고 자유 서술보다 나빠지지 않아야 채택한다. 기준 수치는 01-03에서 정한다. 결과에 따라 형식을 고친 경우 새 버전으로 새 시나리오에서 다시 시험한다.

### 5. 07-04의 내용

P26의 실제 실행에서 나온 보고로 P36(b)와 같은 측정을 한 번 더 한다. 합성 시나리오와 실제 보고의 결과를 따로 적는다.

## 산출물과 순서

**산출물**

- 바뀐 절과 스키마, 변경 요약표
- 장부의 추가 작업과 선행, 기준선 변경 기록(원 분모 72, 변경 분모, 이유)
- 의존관계 재검산 결과와 명세 JSON의 새 revision·digest
- "결정 필요" 목록. 근거가 없는 곳은 추측으로 채우지 않는다

동의하지 않는 항목이 있으면 고치지 말고 항목 번호와 근거를 보고한다.

**순서**

1. 이 변경을 반영한 뒤 문서는 더 개정하지 않고 01-01부터 실행한다.
2. 01-02에서 런타임 후보를 비교해 하나를 제안하고 사용자 결정을 받는다. 후보별로 무인 기동, 이름으로 세션 재개, 세션 기록 위치 지정, 자식 에이전트, 사용량 조회, 한도 신호의 지원 여부를 문서 근거와 함께 표로 낸다. 문서로 확인되지 않는 항목은 "probe 필요"로 표시한다.
3. 01-04의 probe는 다음 두 항목부터 실행한다. 둘 중 하나라도 불가하면 다음 작업으로 넘어가지 말고 영향과 대안을 보고한다.
   - 같은 계정으로 세션 둘을 동시에 실행할 수 있는가
   - 개발과 Guardrail의 자격과 한도를 나눌 수 있는가
4. 01 스프린트가 끝나면 산출물과 probe의 원본 로그를 묶어 독립 검토에 넘긴다. 지원함, 지원 안 함, 관측 불가를 구분한다.

## 한계

- **평가자가 한 명이고 형식 설계에 관여했다.** 처음 보는 사람보다 잘 읽을 수밖에 없다. P36의 결과는 "이 사용자에게 쓸 만한가"까지만 말해 준다. 결과에 이 한계를 적고 다른 사용자에게 일반화하지 않는다.
- **사용자의 시간이 든다.** 스프린트 3건 작성과 시나리오 12건 판독으로 반나절 정도를 예상한다. 실제 소요 시간도 결과에 적는다.
- **검토자가 확인하지 못한 것.** 런타임의 실제 기능(probe 15개 항목 미실행), 스크립트의 실행 결과, 실험 상세의 P 본문 전체, NPG의 현재 서버 상태, P26의 백로그 후보.
