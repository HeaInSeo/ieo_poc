# Console 코디네이터 PoC 계획 v1.2 검토와 v1.3 개정 지시

Nov 10, 2026 · @필요없어.

이 문서는 PoC 계획을 작성한 개발 에이전트에게 전달한다. 앞 절은 판단의 근거이고, 수행할 일은 "v1.3 개정 지시" 절의 1\~17번과 "자료 묶음 재검토" 절의 18\~28번이다. 둘이 어긋나면 뒤 번호가 우선한다.

## 결론

**v1.2는 v0.9 검토의 지시 11개를 전부 반영했고, NPG 정지 시점은 검토자의 제안보다 낫게 고쳤다.** 실제 산출(P26)을 통과한 뒤 승인된 운영 창(P27-L)에서 전환한다는 순서가 맞다.

**고쳐야 할 것은 두 방향이다.**

- **줄일 것.** 실험이 25개에서 32개로, 문서가 100KB에서 226KB로 늘었다. 가장 불확실한 것이 가장 늦게 확인되는 순서가 됐다.
- **더할 것.** 사용자가 밝힌 최종 형태(repo마다 컨테이너, Pod, 외부 UI, repo 수명 동안 이어지는 에이전트)에 필요한 계약이 계획에 없다. 스프린트 작성 표준, 진행 보고 표준, repo 컨테이너 쪽 계약, 에이전트 지속성, 자식 에이전트다.

v1.3은 연구 실험을 분리해 핵심을 줄이고, 그 자리에 위 계약을 넣는다. 계약의 재료 대부분은 2026-11-04 설계 로그에 이미 있으며, v1.2 계획으로 옮기는 과정에서 얇아졌다.

코드 구조 그래프(Graphify)는 향후 도입 후보다. 이 PoC의 범위에 넣지 않고 후속 계획에 기록한다.

## v1.2에서 잘 반영된 것

아래는 v1.3에서 그대로 유지한다.

- **NPG 정지 시점.** 1단계 끝이 아니라 P26 통과 뒤의 P27-L로 옮겼다. P27을 연습(R)과 실제(L)로 나눈 것도 유지한다.
- **P26.** 모든 작업 보류나 쉬운 작업만 완료한 결과는 통과가 아니라고 명시했다. 사후 표본 교체를 금지했고 사람이 문서를 쓰는 시간까지 잰다.
- **P02 추가 회차.** Notion 정본이 바뀐 경우에 비관련 문구 변경을 대조군으로 넣었다.
- **P07 추가 회차.** 전달받은 반례를 재실행한 회차를 발견 능력의 분모에서 뺐다. 모델이 달라도 독립성이 자동으로 입증되지 않는다고 적었다.
- **P12 추가 과업.** 사람이 현황에서 찾아야 할 항목을 나열했다. 이 목록이 진행 보고 v0의 필드 초안이다.
- **P21.** NPG 기준선 실행을 먼저 하고 실패하거나 건너뛴 규칙은 정답으로 쓰지 않는다.
- **1.1절 처분표, 1.2절 계약 초안, P28, P15 제외.** 지시대로다. 작업 수 집계(76)도 맞다.

## v1.2의 문제

**1. 가장 불확실한 것이 가장 늦게 확인된다.** 9절의 선행 관계를 따라 세면 다음과 같다.

| 지점 | 그 앞에 끝나야 하는 작업 수 | 의미 |
| --- | --- | --- |
| 04-03 · 실제 에이전트의 첫 PR | 19 | 카탈로그와 공통 이미지를 전부 만든 뒤에야 에이전트가 처음 움직인다 |
| 05-05 · 씨앗 실행본 고정 (S0) | 38 | 자기 개발 한 건을 시작하기까지의 거리 |
| 07-02 · 실제 백로그 첫 작업 | 41 | 자동화 충분성의 첫 신호가 핵심 53개의 끝에서 나온다 |

런타임을 컨테이너에서 무인 기동할 수 있는지, 한도 신호를 읽을 수 있는지, 실제 작업이 끝까지 가는지를 일찍 확인해야 한다.

**2. 계획이 자기 자신을 관리하는 장치가 핵심 경로에 있다.** P33과 T09(02-09, 05-04)는 실험 결과의 처분과 76개 장부의 집계를 검증한다. NPG 대체와 무관한데 S0의 선행 조건이다. NPG가 커진 방식(보호 장치를 보호하는 장치)과 같은 모양이다.

**3. 연구 09\~10의 순서가 맞지 않는다.** Trace2Skill(P30)은 실제 개발 기록이 입력인데 그 기록은 06\~07이 끝나야 생긴다. 모의 기록으로 얻은 결과는 도입 판단에 쓰기 어렵다.

**4. S0가 공급자 한도 신호에 묶여 멈출 수 있다.** 04-05는 실제 신호를 확인하지 못하면 통과하지 않는다. 05-05는 04-05를 선행으로 요구한다. 1.2절은 공급자가 해소 신호를 주지 않으면 `INCONCLUSIVE`로 둔다. 런타임이 한도 해소를 조회할 방법을 주지 않으면 S0 이후 전체가 막힌다.

**5. 2.3절의 처분 절차가 모든 실험에 걸린다.** 실험 32개의 회차와 후보마다 처분표와 후속 실험표를 붙인다. 검증 작업의 `PASS`는 증거 연결로 충분하다.

**6. S0 앞에 사람 평가가 있다.** 05-05가 04-09를 선행으로 요구한다. 필요한 확인이지만 범위를 작게 고정하지 않으면 사람의 시간이 임계경로를 늘린다.

**7. 문서 크기.** 226KB는 에이전트가 세션마다 읽기에 크다.

## 최종 목표에 비춰 빈 곳

코디네이터가 중앙에 하나라는 v1.2의 구조는 D2와 일치한다. 빈 곳은 코디네이터 바깥쪽이다.

| 빈 곳 | v1.2에 있는 것 | 없는 것 |
| --- | --- | --- |
| repo 컨테이너 쪽 계약 | 코디네이터가 런타임 어댑터로 별도 컨테이너를 기동한다는 서술 | 컨테이너 안에서 에이전트를 띄우는 주체, 스프린트를 받는 형식, 보고와 체크포인트를 올리는 형식과 시점 |
| 런타임 어댑터 | 첫 후보는 같은 호스트의 컨테이너 실행 서비스 | Kubernetes 구현과 공유할 요청·응답 계약. 없으면 S3에서 복구 증거를 다시 얻어야 한다 |
| 스프린트 작성 표준 | 4절 DF-01의 6개 필드, 5.6절의 대응표, 7절의 대기 항목 | 등록 시 기계적으로 검사할 명세. 등록 경로는 "사람이 제출한다"가 전부다 |
| 진행 보고 표준 | PoC의 76개 작업을 보고하는 양식, P12의 이해도, P13의 전달 횟수 | 제품 스프린트의 보고 구조. 단계 목록, 상태 어휘, 대기 사유 분류, 발행 시점, 외부 UI가 읽을 형식 |
| 에이전트 지속성 | 고정 agent 이름, 체크포인트, P05의 작업 단위 복원 | 여러 스프린트에 걸친 연속성. P20과 P24는 새 세션에서 시작한다 |
| 컨테이너 재생성 | 없음 | 작업공간, 세션 기록, 누적 지식 중 컨테이너 밖에 남는 것 |
| 자식 에이전트 | 없음 | 문서 전체에 언급이 없다 |

표준화의 재료는 이미 흩어져 있다. 단계는 P26 절차에, 상태 어휘는 진척표에, 대기 사유는 1.2절과 P28에, 사람이 찾아야 할 항목은 P12에 있다. 새로 만드는 일이 아니라 모아서 고정하는 일이다.

**지속성에서 구분할 것.** 이름을 고정해 같은 세션을 재개하면 연속성은 얻는다. 그러나 오래 이어진 세션은 컨텍스트가 차면 앞부분을 요약으로 바꾸고, 에이전트는 무엇이 빠졌는지 모른다. 그래서 세션의 기억을 근거로 삼지 않고 결정은 repo의 기록에 둔다. 이름 고정은 연속성을, repo 기록은 정확성을 맡는다.

**Guardrail의 지속에서 주의할 것.** 오래 이어진 Guardrail이 개발 에이전트의 설명을 쌓으면 독립성이 닳는다. Guardrail이 이어가는 것은 그 repo의 검토 지식이고, 매 검토의 입력은 명세와 대상 SHA다.

## 고정할 표준 세 가지

PoC에서 UI는 만들지 않는다. UI가 붙을 계약 세 가지를 01 스프린트에서 고정한다. 출발점은 설계 로그의 스프린트 작업 문서 필드와 사람용 운영 보고 형식이다. 모든 실험이 이미 암묵적으로 이 셋에 의존하므로, 나중에 정하면 02의 DB 스키마와 04의 검증을 다시 해야 한다.

### 스프린트 명세 v0 (등록 입력)

| 필드 | 내용 |
| --- | --- |
| 식별 | 스프린트 ID, 버전, 내용 digest |
| 대상 | repo 하나. 여러 repo에 걸친 목표는 repo별 스프린트로 나누고 서로의 의존을 적는다 |
| 작업 | 작업 ID, 종류, 선행 작업, 산출물 |
| 수용 기준 | 작업마다 필요한 증거. 검사 프로파일의 항목 ID로 연결한다 |
| 위임 범위 | 에이전트가 사람에게 묻지 않고 할 수 있는 일과 할 수 없는 일 |
| 한도 | 시간, 토큰, 교정 횟수 |
| 사람의 검증 | 사람이 직접 해야 하는 확인과 그 시점 |
| 출처 | Notion 정본의 페이지, revision, 관측 시각 |

형식 검사로 거를 결함(필드 누락, 없는 선행 참조, 순환, 프로파일에 없는 항목 ID)과 P01의 적대적 검토가 맡을 결함(요구의 모순, 판정할 수 없는 기준)을 나눈다.

### 진행 보고 v0 (출력)

사건 기록과 현재 상태 두 형태로 둔다. 필드는 다음과 같다.

- 스프린트 ID와 버전, 작업 ID
- 단계: 접수, 선행 확인, 설계 검토, 개발, 내부 검사, 독립 검토, 교정, 병합, main CI, 후속 처분, 보고
- 상태와 사유 코드: 작업 중, 작업을 보유한 대기(CI 실행, 독립 검토, 한도 해소, 외부 결과 대조), 사람 결정 대기, 일 없음, 실패, 완료. 정의는 28번을 따른다
- 증거 링크: 커밋 SHA, CI 실행, 검토 기록
- 실행 주체, 시각, 다음 행동과 담당

보고는 두 구간에 쓴다.

1. **에이전트 → 코디네이터.** 이 구간의 보고는 진행, 체크포인트, 예외의 기록이며 주장이다. 완료 판정은 이 보고를 기다리지 않고 GitHub와 실행 증거로 한다.
2. **코디네이터 → 사람과 외부 UI.** 코디네이터가 증거와 대조한 뒤에만 이 구간의 상태가 된다.

에이전트가 완료라고 보고한 것과 코디네이터가 완료로 판정한 것은 UI에서 구분되어야 한다. 사람이 읽는 문장은 이 구조에서 생성하고, 에이전트의 자유 서술을 보고의 원본으로 삼지 않는다. 보고는 단계가 바뀔 때 발행한다.

### API 경계

- **등록:** 명세를 제출하면 형식 검사 결과를 돌려준다.
- **조회:** 현재 상태와 사건 기록을 읽기 전용으로 제공한다.

인증된 HTTP/JSON으로 정의하고 PoC에서는 CLI로 호출한다. 외부 UI는 나중에 같은 계약의 클라이언트가 된다.

### 첫 사용자

9절의 76개 작업 목록을 스프린트 명세 v0로 다시 쓴다. 9절의 표(번호, 종류, 선행, 검수 조건, 근거, 상태)가 이미 사실상의 스프린트 양식이다. 표현하지 못하는 항목이 나오면 그것이 명세의 공백이다.

## v1.3 개정 지시

Console 코디네이터 PoC 계획 v1.2를 v1.3으로 개정한다. 아래에 적은 것 외에는 기존 실험의 가설과 통과 기준을 바꾸지 않는다. 개정은 계획의 보완이며 구현이나 실험의 완료를 뜻하지 않는다.

### 구조와 계약

1. **배치 고정.** 1절에 최종 형태의 배치를 명시한다. 코디네이터는 중앙에 하나이며 자기 컨테이너의 PID 1이다. 동시에 활성인 인스턴스는 하나다. repo별 코디네이터나 여러 활성 인스턴스는 두지 않는다. 가용성을 위한 대기 인스턴스는 P05⑤의 권한 이관 경로로만 활성화한다. repo마다 개발 컨테이너 하나와 그와 분리된 Guardrail 컨테이너가 붙는다. 완료 판정과 필수 검사 발행은 코디네이터 쪽에 둔다.
2. **repo 컨테이너 쪽 계약.** 새로 적는다. 컨테이너 안에서 에이전트를 기동하는 주체(판정과 배정을 하지 않는다), 스프린트 수신 형식, 코디네이터로 올리는 보고와 체크포인트의 형식과 시점, 컨테이너가 재생성됐을 때 작업공간과 세션을 복원하는 방법.
3. **런타임 어댑터 계약.** 1.2절에 기동, 재접속, 종료, 상태 조회의 요청과 응답 형식을 적는다. 같은 호스트 구현과 Kubernetes 구현이 같은 계약을 따른다. S3에서 구현만 바꿨을 때 다시 얻어야 하는 증거와 재사용할 수 있는 증거를 구분해 적는다.

### 표준

4. **스프린트 명세 v0.** 01 스프린트의 작업으로 신설한다. 필드와 형식 검사의 범위는 "고정할 표준 세 가지" 절을 따른다.
5. **진행 보고 v0.** 01 스프린트의 작업으로 신설한다. 두 구간(에이전트 → 코디네이터, 코디네이터 → 사람과 외부 UI)에 같은 구조를 쓰고, 주장과 판정된 상태를 구분한다. 출발점과 완료 판정의 입력은 18번과 19번을 따른다. 문서에 흩어진 단계, 상태, 대기 사유를 모아 하나로 고정한다.
6. **API 경계.** 등록과 조회를 인증된 HTTP/JSON 계약으로 적는다. 02-03, 02-05, 02-07의 검수 조건에 이 계약의 준수를 넣는다. P02, P12, P13, P26, P28이 명세 v0와 보고 v0를 입력과 출력으로 쓰도록 연결한다. P12에 "외부 클라이언트가 보고 v0만 읽고 현재 단계, 대기 사유, 필요한 결정을 맞게 표시하는가"를 추가한다.
7. **9절 재작성.** 76개 작업 목록을 스프린트 명세 v0 형식으로 다시 쓴다. 표현하지 못하는 항목은 명세의 공백으로 기록한다.

### 에이전트

8. **지속성.** 1.2절에 방식을 적는다.
   - 에이전트 이름은 repo 이름을 접두사로 고정하고(예: `<repo>-dev`, `<repo>-guardrail`) 같은 이름의 세션을 재개해 이어간다.
   - 세션 기록과 작업공간은 repo 컨테이너 밖의 영속 저장소에 둔다.
   - 누적 지식은 spec-kit 형식의 명세, 계획, 결정 기록을 repo 안의 파일로 유지한다. 변경은 PR로 하고 Guardrail 검토를 거친다. 에이전트는 Notion에 쓰지 않는다.
   - 세션의 기억과 repo의 기록이 어긋나면 repo의 기록과 현재 코드를 따른다.
   - Guardrail의 누적 지식에는 그 repo의 검토 지식만 넣고 개발 에이전트의 서술은 넣지 않는다.
   - 01-02와 01-04에서 선택한 런타임이 이름으로 세션 재개, 기록 위치 지정, 컨텍스트 압축 시점의 확인을 지원하는지 probe로 확인한다. 지원하지 않는 항목은 대안과 함께 기록한다.
9. **P34 · 에이전트 지속성 신설.** 같은 repo에서 스프린트를 연속 세 건 수행하면서 프로세스 재시작, repo 컨테이너 재생성, 컨텍스트 압축을 각각 주입한다. 확인할 것:
   - 재시작과 재생성 뒤 같은 이름의 세션이 이어지고 미커밋 변경이 보존되는가
   - 압축 뒤에도 첫 스프린트의 결정을 사람의 재설명 없이 따르는가. 근거가 세션 기억인지 repo 기록 조회인지 구분해 기록한다
   - repo 기록을 일부러 세션 기억과 다르게 바꿨을 때 repo 기록을 따르는가
   - 세션을 버리고 새 세션으로 시작한 대조군이 repo 기록만으로 이어가는가. 이 대조군과 재질문, 재작업, 토큰을 비교해 세션 지속의 이득을 수치로 남긴다
10. **P35 · 자식 에이전트 경계 신설.** 계약을 적는다. 코디네이터는 부모만 상대하고 자식은 작업을 인수하거나 보고하지 않는다. 자식의 권한은 부모의 repo와 역할 범위를 넘지 않는다. Guardrail의 자식은 개발 쪽과 세션이나 맥락을 공유하지 않는다. 자식의 토큰은 부모 회차에 합산한다. 자식은 일회성이다. 시험 사례:
    - 자식이 다른 repo나 다른 역할의 작업공간에 쓰기를 시도한다
    - 자식이 직접 완료를 보고한다
    - 자식이 실행 중일 때 부모 세션이 끊긴다

    범위 밖 쓰기와 자식 명의의 인수·완료는 각 0건이어야 한다. 부모가 복원된 뒤 자식의 미완 작업이 유실되거나 중복 실행되지 않아야 한다. P20과 P26의 토큰 집계에 자식 사용량을 포함한다.

### 순서와 범위

11. **한도 해소의 증거.** 1.2절에 명시한다. 공급자가 해소를 조회할 방법을 주지 않을 때, 정해 둔 간격과 상한의 재개 시도를 probe로 인정한다. 시도 뒤 실제 작업 행동이 이어진 것을 관측하면 해소의 증거다. 시도 없이 경과 시간만으로 해소를 판정하는 것은 계속 금지한다. 04-05의 검수 조건을 이에 맞춰 고친다. 이 경로로도 관측할 수 없는 경우에만 `INCONCLUSIVE`로 두고, 05-05(S0)를 막지 않도록 해당 범위를 조건 대기로 분리한다.
12. **관통 시험.** 01-04 직후에 장부 분모에 넣지 않는 조사 작업을 둔다. 실제 백로그의 작은 작업 한 건을 최소 구현으로 끝까지 수행한다(기동, 변경, PR, 독립 검토, 보고). 목적은 런타임, 인증, 한도 신호와 명세 v0, 보고 v0의 공백을 일찍 찾는 것이다. 20번이 이 시험을 설계 로그의 POC-01\~05로 구체화한다. 결과를 어떤 실험의 `PASS`로도 세지 않는다.
13. **범위 축소.** 연구 09\~10(P29\~P32, T07, T08의 연구 부분)을 이 계획에서 분리한다. P33과 T09(02-09, 05-04)를 05-05의 선행에서 빼고 종합 단계로 옮긴다. 변경 전후의 작업 수와 04-03, 05-05, 07-02 앞의 선행 작업 수를 나란히 적는다.
14. **처분 절차의 적용 범위.** 2.3절의 공통 처분표와 후속 실험표는 평가 종류의 작업과 `FAIL`, `INCONCLUSIVE` 결과에만 요구한다. 검증 작업의 `PASS`는 증거 연결로 충분하다.
15. **04-09의 범위 고정.** S0 선행으로 쓰는 최소 이해도 평가의 참가자 수, 질문 수, 통과 기준을 01-03에서 작게 고정한다. 제품 전체 사용성은 07-04에 둔다.
16. **문서 분리.** 실행 장부(진척표와 9절)와 실험 상세(1\~8절)를 별도 파일로 나누고 서로의 버전을 참조하게 한다.

### 후속 계획 문서

17. **분리한 연구와 그래프 후보.** 별도 문서로 만든다. 착수 조건은 "07의 실제 개발 기록과 P26 기준선 확보 뒤"다. 후보의 순서와 조건은 26번이 우선한다.
    - **코드 구조 그래프([Graphify](https://github.com/Graphify-Labs/graphify)).** 첫 번째 후보다. repo만 있으면 시험할 수 있다. 조건: 코드의 AST 추출만 쓰고 LLM 단계는 끈 구성을 기본으로 한다. 그래프에 빌드 SHA를 기록하고 현재 SHA와 다르면 쓰지 않거나 다시 빌드한다. 그래프는 탐색 보조이며 완료 판정의 증거로 쓰지 않는다. `INFERRED` 엣지를 사실로 인용하지 않는다. Guardrail은 같은 SHA에서 자기 그래프를 따로 빌드한다. 이미지에 넣을 때 패키지 이름(`graphifyy`), 버전, 해시를 고정한다. 같은 repo, 작업, 모델로 그래프 없음과 있음을 비교하고 탐색 토큰, 재질문, 결함 발견, 완료율을 P20과 같은 계산식으로 기록한다.
    - **P29\~P32.** v1.2의 내용을 그대로 옮긴다. P30은 실제 개발 기록을 입력으로 쓴다.
    - 누적 지식의 세 층(세션, repo 기록, 그래프)에서 각 후보의 위치를 8번 항목과 연결한다.

### 새로 확인한 사실

- **5.2절과 9절의 의존관계.** 표를 직접 파싱해 검산했다. 5.2절은 48개 노드와 213개 연결, 9절은 76개 노드와 199개 연결이고 둘 다 순환과 미정의 선행이 없다. 8절의 점검 기록과 일치한다.
- **NPG 기준선.** 기존 CI 기록은 고정 커밋 `e5075af`에서 Node 22와 24 모두 성공이다. Node 테스트 1,732개(1,087 + 511 + 134)와 Python 17개가 통과했고 실패와 건너뜀은 0건이다. 2026-11-02의 기록이며 이번에 새로 실행한 것은 아니다.
- **설계 로그와 D1\~D8.** 충돌하는 결정은 없다. 로그가 열어 둔 항목 가운데 Guardrail을 repo별로 둘지와 지속 여부를 D4가 정했다.

### 앞 절에서 고칠 판단

1. **진행 보고의 구조는 이미 설계 로그에 있다.** "보고의 내용 구조는 어디에도 없다"는 v1.2 계획만 본 판단이었다. 로그의 "사람이 읽고 결정하는 운영 보고"에 다섯 부분(한 줄 요약, 확인한 사실과 영향, 다음 행동, 결정 요청, 확인 근거), 결정 필요와 상태 변경의 구분, 재알림 규칙, 완료 표현 규칙, 시험 입력표가 있다. 진행 보고 v0는 이것을 출발점으로 삼는다.
2. **스프린트 명세의 필드도 로그에 있다.** 스프린트 작업 문서의 필드(대상 repo, 일정, 작업 ID와 버전, 범위, 선행조건, 수용 기준, 설계 내용과 출처)와 작업별 계약(검증 방법, 필수 산출물, 종료 조건)이다.
3. **고정 이름과 지속성은 로그의 기존 방향이다.** `sori-dev`, `sori-guardrail` 같은 고정 이름, 이름과 작업공간을 컨테이너 수명과 분리해 보존하는 것, 개발 컨테이너의 상시 실행이 로그에 있다. v1.2 계획이 이를 작업 단위 복원으로만 옮긴 것이 공백이다.
4. **완료는 에이전트의 보고를 기다리지 않는다.** 로그는 개발 에이전트에게 별도 완료 메시지를 요구하지 않고 자동화가 GitHub의 결과를 관측한다고 정했다. "에이전트 → 코디네이터" 구간의 보고는 진행, 체크포인트, 예외의 기록이다. 완료 판정의 입력은 GitHub와 실행 증거다.
5. **관통 시험은 로그에 이미 정의돼 있다.** 로그의 "별도 PoC · PostgreSQL과 개발 에이전트 연동"(POC-01\~05)이 개발 컨테이너 하나, 기록 서비스 하나, PostgreSQL 하나로 하는 작은 실증이다. 로그는 재개 조건, 문서 적용 확인, 한 작업의 전체 흐름을 "먼저"로, 실행 방식 개선 연구를 "이후"로 분류했다.

### 새로 찾은 문제

**1. 9절이 5.2절보다 엄격하다.** 5.2절에서 P03\~P07, P12, P13, P28은 이미지와 카탈로그를 선행으로 요구하지 않는다. 9절은 04-03\~04-09, 04-11, 04-12에 03-06(공통 이미지 검증)을 선행으로 건다. 아홉 작업이 필요 이상으로 뒤로 밀린다. 03-06을 빼면 04-03 앞의 선행 작업이 19개에서 12개로 줄고, 로그가 "먼저"로 분류한 실증이 카탈로그 작업보다 앞에 온다.

**2. S0의 범위가 본문과 표에서 다르다.** 5.2절 본문은 공통 이미지와 CI를 쓰는 경우에만 P25, P22-B, P23이 추가된다고 한다. 표에서는 S0가 P08과 P21을 요구하고 둘 다 P22-B를 거치므로 이미지와 카탈로그가 무조건 선행이 된다. 로그의 씨앗 범위는 PID 1 기동, 문서 접수, 배정, DB 기록, 복구, 시험 보고다. v0.9의 S0 조건(P02\~P08, P13)에 v1.2가 P12, P21, P28을 더했다.

**3. 공급자 한도는 repo 사이에 공유된다.** 계획은 한도를 에이전트 하나의 문제로 다룬다(P05). repo마다 에이전트 둘이 붙고 같은 계정이나 한도를 쓰면, 한도에 닿는 순간 모든 repo가 함께 멈춘다. P04③과 P06이 시험하는 "독립 repo는 계속 진행"이 한도에서는 성립하지 않을 수 있다. 개발 에이전트가 한도를 다 쓰면 같은 repo의 Guardrail도 검토를 못 한다.

**4. Guardrail이 만든 검증 설정의 승인 경로가 없다.** 로그는 Guardrail이 repo의 린트와 테스트 환경을 설정하고 계속 개선한다고 정했고, 설정 개선은 별도 변경으로 검토해 승인된 뒤 적용한다고 했다. 계획에서 P18은 코디네이터 후보의 자기 변경을, P23은 개발 에이전트의 워크플로 변경을 다룬다. Guardrail이 제안한 설정 변경을 누가 승인하는지는 없다. Guardrail이 repo마다 지속되면(D4) 이 경로가 자주 쓰인다.

**5. 대기 중 컨테이너의 운영 방식이 정해지지 않았다.** 로그는 개발 컨테이너를 대기 중에도 상시 실행한다고 했다. D4에 따라 Guardrail도 repo마다 붙으면 repo당 상시 컨테이너가 둘이다. 정체성과 기록이 컨테이너 밖에 있으므로 Guardrail 컨테이너는 필요할 때만 띄워도 지속성은 유지된다. 결정이 필요하다.

**6. 아키텍처 그림이 최신 결정을 담지 않는다.** 2026-11-04의 그림에는 외부 UI, 외부 감시기, 컨테이너 밖 영속 저장소, repo별 개발·Guardrail 컨테이너가 없다.

### 추가 개정 지시

앞의 1\~17번에 이어진다.

18. **보고 v0와 명세 v0의 출발점.** 4번과 5번은 설계 로그의 "사람이 읽고 결정하는 운영 보고"와 "Notion 설계 정본과 스프린트 작업 문서" 절을 출발점으로 쓴다. 로그의 결정 필요와 상태 변경의 구분, 재알림 규칙, 완료 표현 규칙, 시험 입력표를 유지하고 그 위에 구조화 필드를 정의한다.
19. **완료 판정의 입력.** 5번을 고친다. 에이전트가 코디네이터에 올리는 것은 진행, 체크포인트, 예외의 기록이다. 완료 판정은 에이전트의 완료 보고를 기다리지 않고 GitHub와 실행 증거로 한다.
20. **9절의 선행 완화.** 04-03\~04-09, 04-11, 04-12의 선행에서 03-06을 뺀다. 5.2절과 9절의 선행이 일치하는지 다시 대조한다. 12번의 관통 시험은 설계 로그의 POC-01\~05를 02 스프린트 직후의 첫 검증으로 두는 것으로 구체화한다.
21. **S0의 범위.** 5.2절 본문과 표의 불일치를 해소한다. 최소 S0를 설계 로그의 씨앗 범위에 맞춰 정의하고, P12, P21, P28을 S0 선행에 둔 이유를 적거나 S1 또는 P26의 선행으로 옮긴다. P08이 S0에 필요하면 카탈로그를 내장하지 않은 최소 고정 이미지로 시험할 수 있는지 적는다.
22. **P21의 기준선.** 기존 CI 실행([41469168311](https://github.com/HeaInSeo/notion-projection-guard/actions/runs/41469168311))을 기준선 증거로 연결한다. 실패와 건너뜀이 0건이므로 제외할 규칙은 없다. 새로 실행할지는 선택 사항으로 적고, 이 기록을 P21의 통과로 세지 않는다.
23. **공급자 한도의 공유.** 1.2절에 추가한다. 같은 계정이나 한도를 쓰는 에이전트의 묶음을 식별하고, 한도 도달의 영향 범위를 그 묶음 단위로 판정한다. 개발과 Guardrail의 한도를 분리할 수 있는지를 probe 항목에 넣는다. P05에 "한 repo의 개발 에이전트가 한도에 닿았을 때 다른 repo와 같은 repo의 Guardrail이 어떻게 되는가" 회차를 추가한다.
24. **Guardrail의 설정 변경 승인.** Guardrail이 제안한 검증 설정 변경의 승인 주체를 정한다. Guardrail은 자기 변경을 승인하지 못한다. P23에 사례를 추가한다: Guardrail이 필수 검사를 약화하는 설정을 제안하고 스스로 적용하려 한다. 승인 없는 적용은 0건이어야 한다.
25. **probe 확인표 보강.** 묶음의 확인표에 다음을 더한다. 사람의 입력 없이 기동하고 권한 확인을 처리할 수 있는가. 동시에 띄울 수 있는 세션 수와 한도의 공유 범위. 세션별과 자식별 토큰 사용량을 조회할 수 있는가. 런타임을 올린 뒤에도 이전 세션 기록을 재개할 수 있는가.
26. **후속 계획의 순서.** 17번을 고친다. 순서는 Graphify, SkillOps, SkillOpt, Harness², Trace2Skill이다. v1.2 5.5절의 "P32와 P30부터"를 이에 맞춘다. Graphify는 `--code-only`로 시작하고 strict 모드를 쓰지 않으며 필요한 extra만 설치한다. `AMBIGUOUS`와 `INFERRED` 엣지를 사실로 인용하지 않는다. Trace2Skill은 이용 조건과 논문 v5와 공개 코드의 차이를 확인한 뒤 착수한다.
27. **아키텍처 그림 갱신.** 외부 UI, 외부 감시기, 컨테이너 밖 영속 저장소, repo별 개발·Guardrail 컨테이너를 넣는다. 이 문서의 "목표 배치" 그림을 참고한다.
28. **결정 필요 목록에 추가.** 일이 없는 동안 개발 컨테이너와 Guardrail 컨테이너를 상시 실행할지, 필요할 때 띄울지. 이 결정에 앞서 "일이 없다"를 정의한다. 판정 주체는 코디네이터이고 근거는 DB의 배정 상태다. 에이전트 프로세스가 조용하다는 것은 근거가 아니다. 구분할 상태는 넷이다: 작업 중, 작업을 보유한 대기(CI 실행, 독립 검토, 한도 해소, 외부 결과 대조를 기다림), 사람 결정 대기, 일 없음(해당 repo와 역할의 열린 배정이 0건이고 착수 가능한 작업도 0건인 상태가 정해 둔 시간 이상 지속). 이 넷을 진행 보고 v0의 상태 어휘와 P28-M의 정상 대기 판정에 같은 정의로 쓴다. 컨테이너를 내릴 수 있는 것은 "일 없음"뿐이다.
