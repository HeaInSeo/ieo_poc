## 먼저 볼 실행 계획과 진척표

**이 계획의 끝:** 승인된 PoC 범위의 정책·실행 기반을 구현하고, 정상·장애·실제 작업·연구 비교의 증거를 모아 채택/보류/기각을 판정한 뒤, 재사용할 코드와 남은 개발을 연결한 최종 스프린트를 인계한다. 필수 기능·실제 전환의 성공 여부는 실험 보고 완료와 별도로 판정한다.

**고정 목록 v1.2:** 11개 실행 스프린트·76개 검수 작업이다. 실험은 P01~P33 중 P15를 제외한 32개이며, 실험 수·검수 작업 수·테스트 회차 수는 서로 다른 집계다. 기존 T·P·S 번호는 원 설계의 참조로 보존한다. 9절의 01-01~11-05가 개발 에이전트가 배정·보고할 작업 번호다.

**현재 위치:** 실행 전이다. 이 계획에 연결된 검수 완료 증거는 0/76이며, 기본 초기 장부는 전 작업 미착수다. 다음 작업은 01-01, 전체 마지막 작업은 11-05다. 이번 문서 개정이나 기존 NPG/제품 개발의 성과를 76개 실행 작업의 완료로 세지 않는다. 이번 개정에서는 GitHub·서버의 실제 구현/인수 상태를 새로 감사하지 않았다. 기존 증거를 재사용하려면 해당 작업의 버전·범위·완료 조건에 맞춰 연결하고 독립 검수를 받아 초기 장부를 갱신한다.

### 번호·완료·범위 변경 규칙

- **실행 번호:** 앞 두 자리는 스프린트, 뒤 두 자리는 그 안의 작업이다. 번호는 고정한 수행 목표를 식별한다. 가장 큰 완료 번호를 전체 진행률로 환산하지 않는다. 한 작업 안의 정상/실패 사례나 재시험은 작업 번호에 회차·후보 버전을 붙여 기록하고 76개 분모에 중복 추가하지 않는다.
- **배정 순서:** 기본은 선행 조건이 충족된 작업 중 작은 번호부터다. 독립적인 병행은 기존 승인·역할·repo 소유권·자원 조건 안에서 한다. 선행을 통과하지 못한 작업은 조건 대기로 두고 담당·원인·다음 행동을 기록한다. 같은 repo의 수정 PR 제한 등 기존 프로파일을 번호 때문에 바꾸지 않는다.
- **작업 검수:** 설계/준비/구현은 지정 산출물·계약·외부 확인을, 필수 검증/연결 검수는 해당 범위의 실제 PASS 증거를 모두 갖춰야 검수 완료다. 테스트 일부 성공이나 코드 작성만으로 임의의 부분 완료율을 주지 않는다.
- **평가 작업:** 목적이 가능성·효과의 판정인 평가 작업은 유효한 비교·증거·독립 확인·처분 보고가 수용 기준이다. 효과 없음의 기각도 평가 작업은 끝낼 수 있다. 미실행, 근거 없는 보류, 판정 불가능을 기록했다는 이유만으로 완료하지 않는다. 실행 제약을 조사해 도입 불가를 판단한 경우에는 확인 범위·제약 근거와 승인된 평가 종료 조건을 제시한다. 기능 성공이나 실험 PASS로 바꿔 집계하지 않는다.
- **실패와 보류:** 필수 기능 검증이 FAIL이거나 필수 관측이 부족하면 그 기능 작업은 미충족이다. 평가 보고가 끝났더라도 제품 기능/전환 완료로 올리지 않는다. 2.3절의 한도에 도달하면 종료 미충족 또는 조건 대기로 남기고 후속·대안·필요한 결정을 보고한다.
- **기준선 변경:** 작업을 추가·분할·제외할 때 원래 76개와 변경 후 수량·이유·승인/위임 근거를 나란히 기록한다. 완료 뒤 소급 분할하거나 재시험마다 분모를 늘리지 않는다. 재검증에서 기존 인수 근거가 무효화되면 관련 작업의 인수 상태·영향을 명시해 갱신한다. 유효한 과거 버전의 결과는 삭제하지 않는다.

작업 상태는 미착수·준비됨·진행·검수 중·검수 완료·조건 대기·종료 미충족으로 기록하며, 각 작업은 한 시점에 한 상태만 가진다. 검수 완료와 나머지 상태의 작업 수 합계는 현재 기준선 분모와 같아야 한다. 범위 제외는 작업 상태를 완료로 바꾸는 방법이 아니라 별도 기준선 변경이다. 공수 가중 진행률은 전체 작업의 기준 공수 w와 인수 여부 a(0/1)를 고정한 뒤 sum(w×a)/sum(w)로 계산한다. 미산정 작업을 0공수로 넣거나 분모에서 빼지 않는다. 설계/준비/구현/검증/연결 검수/평가/종합의 인수 수량도 나눠 보고한다. 일정은 01~02의 실제 실행·검토·보정 기록을 확보한 뒤 범위와 불확실성을 붙여 예측하고, PoC 착수 전에 임의의 완료일을 약속하지 않는다.

### 문서 범위와 개정 맥락

이 문서는 PoC의 설계·구현·실험·결과 인수를 위한 실행 계획이다. 아래 통과 기준과 수치는 제안이며, 실제 측정 결과는 실행자가 별도로 기록한다. 전체 배치와 증거 흐름은 별도 그림 `Console_Coordinator_Architecture.png`에 있다. 설계 결정과 논의 이력은 [Console 설계 로그](https://chatgpt.com/library?file_id=libfile_0a245f9f7f888191af60f0773da23507&account_id=personal)에 있다.

v1.0은 [v0.9 독립 검토](https://chatgpt.com/library?file_id=libfile_fde3_f-398ecfb03a988191aaa559deff22f5fb_f08d5e8b68808191a6076e2e659f2fdc&account_id=personal)를 참고해 책임 이전, 실제 산출, 전환, 후속 처리와 정지 감지를 보완했다. Harness²·Trace2Skill·SkillOpt·SkillOps의 도입 가능성을 각각 작은 구현과 비교 실험으로 평가하는 P29~P32를 추가했다. 초기 카탈로그 작성·검증·활용과, 실행 기록으로 스킬을 개선하는 실험을 구분한다.

v1.1은 모든 실험의 결과를 채택·부분 채택·보류·기각으로 처분하고, 재실험·대안 탐색과 최종 스프린트 작성으로 연결하는 공통 절차를 보완한다. 실험 결과와 도입 결정을 분리하고, 필수 기능의 미해결과 선택적 방법의 기각을 구분한다. T09·P33은 결과 처리·코드 자산 등록·스프린트 변환 자체를 구현하고 검증하기 위한 추가 계획이다.

v1.2는 실행 스프린트 01~11과 검수 작업 01-01~11-05를 추가하고, 기존 T·P·S 참조를 보존한다. 전체 76개 작업의 범위·완료·대기·평가 종료와 공수/일정의 산정 기준을 앞쪽 진척표와 9절에 연결한다.

이 문서 개정에서 완료한 것은 계획 작성과 문서 구조 점검이다. NPG 기준선 테스트, 연구 코드 실행, 코디네이터 구현, 이미지 빌드, 실험, 운영 전환은 아직 수행하지 않았다. 모든 결과표의 —는 실측 전 빈칸이다. 기존 운영의 현재 상태는 이 계획으로 단정하지 않는다. 이번 보완 범위는 앞쪽 실행 진척표·P33 추가 회차·5.7절·6~9절에서 확인할 수 있다. 새 실행 목록은 PoC 수행 계획이며, 실험 결과로 만들 최종 제품 개발 스프린트와 구분한다.

## 1. 검증하려는 최종 목표

사람이 승인된 스프린트 문서를 제출하면, 시스템이 선행조건을 확인하고 개발·내부 테스트·린트·독립 적대적 검토·교정·수용 판정·최종 보고를 이어간다. 토큰 소진이나 시스템 장애가 해소되면 확인된 지점부터 재개한다. 자동화 권한을 넘어서는 결정이나 사람이 직접 해야 할 검증은 해당 범위와 이유를 보고한다.

Spec Kit의 명세·계획·작업·구현·수렴 흐름을 참고한다. 승인된 요구사항과 수용 기준을 개발과 검토의 공통 입력으로 삼고, 실행 단계에서 생긴 증거를 해당 작업과 연결한다. 구현 전 요구사항·설계에 대한 적대적 검토, 구현 후 독립 코드 검토, 실제 실행 증거 수집, 사람의 사용성 평가는 각기 다른 질문에 답한다. [Spec Kit](https://github.github.io/spec-kit/) · [ASDLC 적대적 코드 리뷰](https://asdlc.io/patterns/adversarial-code-review/)

### 1.1 Notion 경계와 NPG 책임 처분

### 1.2 에이전트 실행·인증·사용량 계약 초안

코디네이터 PID 1은 승인된 실행 설정을 런타임 어댑터에 전달해 개발·Guardrail의 별도 컨테이너와 세션을 생성·재접속한다. 첫 시험은 같은 호스트의 외부 컨테이너 실행 서비스를 쓰는 후보로 잡는다. 실제 CLI·SDK·세션 복원·사용량 조회 지원 여부는 T05·T06에서 확인하고 실행 전에 고정한다. 코디네이터 컨테이너에 무제한 호스트 제어 권한을 넘기는 것을 기본 구현으로 삼지 않는다. 어댑터가 요청한 역할·이미지·repo·작업공간만 기동할 수 있는지 허용·거부 대조를 수행한다.

| 계약 | 구현·시험에서 남길 것 |
| --- | --- |
| 실행 식별 | 고정 agent 이름, 역할, repo, 작업·스프린트 버전, 배정 세대, 실행 인스턴스, 모델·런타임 버전, 이미지 digest, 체크포인트 위치 |
| 인증 주체 | 코디네이터의 배정·DB 자격, 개발자의 소스 쓰기 자격, Guardrail의 검토 자격, 독립 필수 검사 발행 자격, 게시·승격 자격을 구분한다. 실제 GitHub 주체를 조회해 자기 승인이 아님을 확인한다. 비밀 값은 문서·로그에 넣지 않는다. |
| 기동과 인수 | 기동 응답·요청 전달만으로 작업 중이라 하지 않는다. 배정을 DB에 확정하고 실제 인수·첫 행동·체크포인트를 연결한다. 동일 작업의 중복 기동은 같은 배정을 조회하거나 거부한다. |
| 한도 분류 | 컨텍스트 한계, 공급자 사용량 한도, 일시적 rate limit, 인증·과금 오류를 구분한다. 실제 공급자 상태·오류 코드·재시도 가능 시각 등 관측 가능한 근거를 저장한다. 모델의 자기 보고만으로 해소를 판정하지 않는다. |
| 재개를 깨우는 주체 | 코디네이터의 재개 스케줄러가 저장된 `next_check_at`에 읽기 전용 상태 조회 또는 제한된 probe를 수행한다. 재시도 간격·상한을 T01에서 정한다. 해소를 확인한 뒤 현재 권한·문서·GitHub·미확인 요청을 재대조하고, 새 인스턴스가 기존 체크포인트에서 이어간다. |
| 공급자 해소 관측 불가 | 해소 신호·안전한 probe가 지원되지 않으면 해당 경로를 `INCONCLUSIVE`로 기록하고 필요한 결정을 보고한다. 고정 시간 대기만으로 한도 해소나 자동 복구 성공을 주장하지 않는다. |
| 코디네이터 자체 정지 | 컨테이너 런타임이 PID 1 재기동을 담당하고, 외부 감시기가 heartbeat·기한 초과를 관측한다. 감시기는 새 쓰기 소유권을 임의로 획득하지 않는다(P28). |

T06의 산출물에 이 계약의 실행 명령·요청 형식·종료 신호·오류 분류·재개 조건을 포함한다. 실제 런타임과 인증 공급자 선택은 7절의 확정 대기 항목이다. 이를 정하지 않은 모의시험의 통과를 실제 공급자 복구 성공으로 바꾸지 않는다.

### 1.3 네 연구의 도입 가능성 판단과 출처 대응

**판단.** 네 방법을 작게 구현해 Console에 도움이 되는지 확인하는 실험은 추가할 수 있다. 공개 구현은 별도 실행 도구나 어댑터로 시험하고, Rust 코디네이터는 고정된 요청·결과 형식으로 연결하는 후보를 먼저 비교한다. 처음부터 모든 코드를 Rust로 옮기거나 네 프레임워크를 한 번에 결합할 필요는 없다. 다만 공개 코드가 실제 Console 런타임·개발 기록에 맞는지와 비용 대비 이득은 아직 확인하지 않았다.

## 2. 공통 실험 규약

- **격리 환경과 고정 입력.** 테스트 repo A·B, 설계·스프린트 문서 v1/v2, 정상 및 결함 후보 커밋, 허용·금지 시험 서버, 전용 자격 증명을 쓴다. GitHub·DB·보고 수신기·클러스터는 실증용으로 분리한다. 주입한 결함과 기대 결과는 실험 담당자가 먼저 고정하고, 독립 검토자는 필요한 명세와 후보를 받는다.
- **독립 재현.** 각 실험은 초기 상태를 별도로 준비한다. 선행 단계가 필요한 실험은 명시한 검증용 상태에서 시작한다. 비교에서는 명시한 변인만 바꾸고 동일한 데이터·버전·부하·권한을 사용한다. 장애 시험은 최소 3회 독립 재현을 제안한다. 각 회차와 사건 순서를 기록한다. 표본이 작은 결과는 해당 사례의 재현성에 한정해 해석한다.
- **증거 연결.** 모든 결과에 스프린트·작업 ID, 적용 문서 버전 또는 digest, 실행 ID, 역할과 실행 주체, UTC 시각을 남긴다. 코드 결과에는 PR·커밋 SHA와 검사 프로파일 버전, 컨테이너 시험에는 이미지 digest를 추가한다. 보안 시험에는 관측기·커널·정책 버전, 적용 대상, 관측 구간과 원본 이벤트를 추가한다. Pod UID는 필요한 경우 이벤트의 노드·네임스페이스·Pod·컨테이너 식별자를 실행 시점의 Kubernetes 기록과 대조해 연결한다.
- **완료 판정.** 필수 항목의 `PASS`만 해당 조건을 충족한다. 반례나 기준 위반이 재현되면 `FAIL`, 권한·관측 범위·증거가 부족하면 `INCONCLUSIVE`로 기록한다. `N/A`는 실행 전에 문서가 해당 항목을 적용 범위에서 제외한 경우에만 쓴다. 전체 작업의 완료와 보고의 전달 확인은 별도 상태다.
- **비교 지표.** 분자·분모, 단위, 반복 횟수, 실패와 건너뜀 수를 함께 기록한다. 시간 또는 비용이 채택 기준인 비교는 허용 예산과 측정 방법을 실행 전에 고정한다. 핵심 경로의 잘못된 완료·중복 효과·권한 밖 전이처럼 표에서 0건을 요구한 항목은 개별 회차마다 판정한다.

### 2.1 선행 작업과 준비물의 통과 조건

실험 번호는 식별자이며 실행 순서가 아니다. 각 실험은 **필요한 자료 작성·구현 → 그 준비물의 검증 → 고정 버전의 활용 실험 → 통합 실증**으로 연결한다. 작성 작업의 산출물과 그 산출물이 유효하다는 증거를 따로 남긴다. 카탈로그가 부실한 상태의 결과만으로 에이전트가 카탈로그를 활용하지 못한다고 결론 내리지 않는다.

T02의 최초 범위에는 테스트·린트의 목적과 옵션, 실패·복구 검증, GitHub Actions·저장소 설정, 역할별 작업·인계 정책을 포함한다. 범용·Go·Rust 및 저장소 전용 기준의 적용 범위를 표시한다. 필요한 전체 목록은 T01의 요구 기준에서 먼저 정하며, `-shuffle` 같은 몇 가지 예시만으로 충실도를 판정하지 않는다. Go 범위의 작성·검증으로 양식을 먼저 교정하고 Rust를 채울 수 있다. 이후 두 스택 비교는 두 스택 모두 필요한 범위가 통과한 뒤 시작한다.

각 카탈로그 항목에는 **ID·버전, 해결할 문제, 적용·제외 조건, 얻는 증거와 확인하지 못하는 범위, 필요한 도구·버전·환경·권한, 명령과 중요한 옵션, 기대 결과·실패/건너뜀 판정, 예상 시간·자원·토큰 비용의 근거, 공식 자료나 고정 원본 규칙**을 적는다. 바로 실행할 수 없는 정책 항목은 설정 절차와 기대값·실제값을 확인할 방법을 적는다. 필수 여부는 대응하는 승인 기준·프로파일에 연결한다. 비용 추정과 실측은 표시를 달리한다.

카탈로그 작성자는 설명과 사용 예를 만들고, 별도의 검증 담당자는 T01의 기준 및 원본 근거로 충실도와 기대값을 대조한다. 카탈로그 자체에서 필수 목록과 정답을 모두 만들어 그 카탈로그를 통과시키지 않는다. 공개 설명용 사례, 작성 중 교정에 쓴 사례, P20·P24의 평가 사례를 구분하고, 숨겨 둔 결함과 기대 판정은 에이전트가 읽는 이미지에 넣지 않는다.

#### 모든 실험에 적용하는 착수·변경 규칙

- **착수 기록.** 각 회차에 실험 ID, 선행 작업·실험 ID, 필요한 산출물과 버전, 선행 통과 증거, 사용할 환경·권한, 기대 판정과 중단 조건을 기록한다. 구체적인 연결은 5절의 의존관계표를 따른다. 선행 실험은 이번 회차가 사용하는 범위와 버전의 통과 증거가 있어야 한다.
- **준비와 결과의 분리.** 준비 중·선행 미충족은 실행 관리 상태 `WAITING_FOR_PREREQUISITE`로 표시하고, 실험 결과는 `미실행`으로 둔다. 실행 후 위반이 확인되면 `FAIL`, 필수 관측이 불충분하면 `INCONCLUSIVE`다. 준비 부족 회차를 에이전트 활용 실패나 토큰 절감 성공으로 집계하지 않으며, 준비에 든 비용은 따로 공개한다.
- **의도적 누락 시험.** P20 A의 카탈로그 미제공, P23의 잘못된 워크플로, P24의 문서 누락처럼 의도한 변인은 사례에 미리 적는다. 이 경우에도 정상 기준본과 독립 판정·관측 도구의 준비는 확인한다. 시험을 위해 변형한 입력은 정상 준비 완료본과 다른 식별자로 보존한다.
- **변경과 재검증.** 카탈로그·정책·도구·프로파일을 바꾸면 영향을 받는 준비 검증부터 다시 확인하고 해당 입력을 쓰는 후속 결과의 재사용 여부를 판정한다. 진행 중인 비교군에는 같은 버전을 유지하고, 교정본은 새 비교 회차로 실행한다. 같은 버전·범위의 유효한 증거는 재사용하고 관련 없는 실험은 계속할 수 있다.
- **부트스트랩.** T03·T06과 P25의 첫 검증은 버전을 고정한 외부 절차에서 수행한다. 후보 코디네이터가 준비물이나 자신의 완료를 단독 승인하게 하지 않는다. P22·P23은 만들어진 후보를 검증하므로 자신의 통과를 자신의 착수 조건으로 삼지 않는다.

| 실험 ID·회차 | 필요한 선행 산출물·버전 | 선행 통과 증거 | 준비 상태·미충족 이유 | 실행 결과·후속 영향 |
| --- | --- | --- | --- | --- |
| 예시 · P20 / 준비 | P25 카탈로그 통과본, P22 기본 실행 통과본, P23 공통 CI 통과본 | 미확보 | `WAITING_FOR_PREREQUISITE` | 미실행 · 해당 버전의 활용 비교를 시작하지 않음 |

### 2.2 연구 실험의 공통 준비·판정·비용 규칙

**도입 판단을 세 번 나눈다.** ① 고정 원본 또는 최소 방법을 실행할 수 있는가, ② 현재 방법보다 품질·진행·비용이 나은가, ③ 검증된 후보를 운영 기준으로 편입할 수 있는가를 따로 판정한다. ① 통과만으로 ②의 개선이나 ③의 운영 채택을 선언하지 않는다. 원본 실행이 안 되면 원인·필요 어댑터·재구현 비용을 남기고 해당 경로는 `INCONCLUSIVE`로 둔다. 범위를 명시한 방법 재구현을 별도 후보로 시험할 수 있으나 원 논문 재현으로 표시하지 않는다.

| 고정할 조건 | 실험 규칙 |
| --- | --- |
| 비교할 구현 형태 | 기존 수작업/고정 카탈로그, 공식 원본의 제한된 실행, 얇은 어댑터, 방법만 재구현을 구분한다. 가능한 경로만 실행하고 실행하지 않은 경로는 비워 둔다. Rust 이식 필요성과 공수를 결과로 판단한다. |
| 입력과 독립 평가 | T08에서 작업·실패 계열 단위로 작성용, validation, 최종 평가를 나눈다. 같은 기록의 변형이 양쪽에 섞이는지 확인한다. 후보 생성기와 대상 에이전트에는 최종 정답·결함 위치를 주지 않는다. validation을 반복 사용한 횟수를 기록하고, 최종 평가를 본 뒤 수정하면 새 평가 묶음으로 다시 시험한다. |

| 정상 진행과 오류 | 정상 입력의 실제 완료와 복구 가능 입력의 자동 재개를 함께 요구한다. 알려진 위반의 잘못된 완료·정답 누출·권한 밖 효과는 각 회차 0건이어야 한다. 전부 보류한 후보는 품질 유지나 성공으로 집계하지 않는다. |
| 전체 비용 | 원본 확인·어댑터 개발·자료 준비, 후보 생성·거부·최적화·검토·재실행, 사용 시 조회·실행·교정을 각각 기록한다. 입력·캐시 입력·출력 토큰과 집계 가능 범위를 표시하고 모든 모델의 실패·중단 회차도 포함한다. 공급자 사용량을 얻지 못하면 토큰 효과는 `INCONCLUSIVE`다. |
| 채택 기준 | 정상 완료율과 결함 발견을 유지·개선하고, 사전 지정한 품질·시간·토큰 목표 중 하나를 충족하며 나머지는 허용 범위를 지켜야 한다. 최소 개선량·허용 열화·시간/토큰 상한을 결과 확인 전에 고정한다. 수치가 미정이면 탐색 결과만 보고하고 도입 가치는 판단 보류한다. |
| 재사용과 편입 | 후보·패치·기록·어댑터는 버전과 출처를 보존한다. 채택한 문서는 P25의 새 버전 검증→P22의 새 이미지/입력 확인→영향 받는 P23·P20·P24 회차를 통과해야 편입할 수 있다. 후보 생성 성공만으로 현재 이미지를 수정하지 않는다. |

### 2.3 모든 실험의 결과 처분과 후속 실험

이 절은 연구 실험뿐 아니라 P01~P33 중 실행 대상인 각 범위·후보·회차에 적용한다. P15의 명시적 실행 제외는 유지한다. T01에서 요구사항 ID별 필수 기능과 선택적 구현 방법을 먼저 구분한다. 실행자는 증거와 원인 가설을 제출하고, 독립 검증 담당자는 기대값·실측값·증거의 유효성을 대조한다. 채택과 후속 배정은 기존 승인·위임 범위에서 확정하고, 목표·수용 기준·권한·총예산을 바꾸는 결정만 권한자에게 올린다. 승인된 보정과 재시험마다 사람의 새 지시를 요구하지 않는다.

**실험 판정과 도입 결정.** `PASS/FAIL/INCONCLUSIVE/N/A`는 고정한 기대값에 대한 결과이며, `채택/부분 채택/보류/기각`은 특정 후보를 사용할지에 대한 결정이다. 의도적으로 넣은 결함을 기대대로 차단하면 해당 시험은 `PASS`다. 최소 실행 시험이 `PASS`여도 효과·비용·편입 조건이 부족하면 도입을 보류하거나 기각할 수 있다. 환경·계측·평가 자료 부족은 확인한 원인과 함께 `INCONCLUSIVE`로 두고 후보의 효과 없음으로 단정하지 않는다. 사후에 필수 항목을 `N/A`로 바꾸지 않는다.

| 관측과 판단 근거 | 도입 결정 | 후속 처리 |
| --- | --- | --- |
| 선언한 범위의 품질·효과·비용 조건을 충족 | 채택 | 검증 범위와 자산 버전을 고정하고 필요한 제품화·통합·편입 작업을 생성한다. |
| 독립적으로 사용할 일부 범위만 충족 | 부분 채택 | 통과/미통과 범위와 의존을 분리한다. 필수 선행이 미충족인 기능을 부분 채택만으로 완료하지 않는다. |
| 증거·환경·비용 관측이 부족 | 보류 | 부족한 근거, 담당, 재개 신호·조건과 재확인 기한을 기록한다. 해당 조건이 충족될 때 재배정한다. |
| 원인 가설이 있고 승인 예산 안에서 교정 가능 | 보류 후 재실험 | 바꿀 변수·새 버전·대조군·통과/중단 조건을 정하고 다음 회차를 연결한다. |
| 유효한 평가에서 효과 부족·비용 초과 또는 한도까지 개선 없음 | 기각(현재 방안 폐기) 또는 근거 있는 보류 | 도입 대상에서 제외하고 이유·비용·증거를 보존한다. 향후 재개 조건이 없다면 막연한 대기로 남기지 않는다. |
| 현재 방안이 필수 기능을 충족하지 못함 | 현재 방안 보류/기각, 필수 목표는 미해결 | 검증된 기준선을 유지하거나 대안 탐색을 배정한다. 목표 축소는 별도 승인으로만 반영한다. |

기각은 해당 방안의 편입을 중단한다는 뜻이다. 소스·원본 로그·실패 사례·계측 코드의 삭제를 뜻하지 않는다. 선택적 연구의 기각은 의존하지 않는 기본 개발을 막지 않는다. 필수 기능이 미해결이면 관련 범위는 완료되지 않으며, 다른 구현 방법을 찾거나 승인된 범위 변경을 받아야 한다. 조합 실패는 해당 조합과 의존 범위에 연결하고 유효한 단독 결과를 지우지 않는다.

**모든 실험의 공통 결과·처분표.** 기존 실험별 상세 결과표에 아래 요약을 붙인다. 후보가 여러 개면 후보별로 나누고, 실패·중단·보류도 최초 표본과 총비용에 남긴다. 결과와 처분은 수정 이력으로 연결하며 이전 회차의 사실을 덮어쓰지 않는다.

횟수·시간·토큰 상한은 T01에서 원 요구사항·실험 계열별 누적으로 관리한다. 후보나 실험 ID를 바꿔 한도를 초기화하지 않는다. 상한 또는 기한에 도달하면 자동 반복을 끝내고 기각/보류와 필요한 결정을 보고한다. 대안도 같은 필수 요구와 평가 기준으로 시험하며, 기준을 낮춘 결과는 기존 후보의 개선으로 집계하지 않는다. 기준 변경을 승인받으면 별도 비교군으로 표시한다. 승인된 범위에서 완료 보고까지 자동으로 이어지는지는 P28, 이 결과 처리 규칙 자체는 P33에서 검증한다.

## 3. 독립 실험

각 절의 기대 결과는 시험의 합격 조건이다. 실제 관측값과 발견 사항은 결과표에 작성한다.

### P01 · 요구사항·설계 오류 발견

- **가설.** 구현 전에 별도의 적대적 검토를 두면 모순된 요구사항과 확인 불가능한 수용 기준을 작업 배정 전에 발견할 수 있다.
- **절차.** 정상 설계, 허용 대상과 금지 대상이 충돌하는 설계, 권한 주체가 빠진 설계, 판정 방법이 없는 수용 기준을 준비한다. 개발·검토를 분리하고 검토자에게 결함 정답을 숨긴다. 각 판정 후 같은 결함을 교정한 문서를 다시 제출한다.
- **통과와 증거.** 지정한 차단 결함마다 위반한 요구 ID, 반례, 영향과 수용 기준의 수정안을 남긴다. 결함 문서의 구현 배정 0건, 정상 문서와 교정본의 착수 가능 상태를 확인한다. 고정 문서, 독립 판정, 배정 이력을 보존한다.
- **해석.** 알려진 결함의 발견과 배정 차단을 검증한다. 실제 설계의 발견율은 별도 표본이 필요하다.

### P02 · 문서 버전 적용과 전달 누락

- **가설.** 발행 버전과 에이전트 적용 버전을 따로 기록하면 변경 누락과 구버전 완료를 구분할 수 있다.
- **절차.** v1로 착수한 뒤 필수 계약 테스트를 추가한 v2를 발행한다. 첫 전달을 누락시키고 정기 대조를 실행한다. 사전에 정한 전환 지점에서 에이전트가 v2를 적용한 뒤, 늦은 v1 결과와 유효한 v2 결과를 순서대로 제출한다.
- **통과와 증거.** 사전에 정한 대조 기한 내에 발행과 적용의 차이를 찾고 v2 적용 확인을 남긴다. v1 결과로 v2가 완료되는 건 0건이다. v2 적용 확인과 v2 필수 테스트가 연결된 정상 결과는 진행한다. 문서 digest·전달·적용·판정 이력을 보존한다.

**추가 회차 · 정본→실행 계약.** Notion의 요구 조항 r1에서 스프린트 v1을 만든 뒤 원본을 r2로 바꾸되 스프린트는 그대로 둔다. 요구 ID별 원본 페이지·관측 시각·내용 digest와 스프린트의 출처를 대조해 영향 있는 변경을 기한 안에 찾는지 확인한다. 비관련 문구 변경도 대조군으로 둔다. 영향을 받는 v1 작업은 사전에 정한 전환 지점에서 보류하고, r2를 반영한 승인 스프린트 v2를 적용한 뒤 재개한다. 승인 전 스프린트 내용을 에이전트가 임의 변경하지 않는다. 누락·이전 정본 근거로 새 요구를 완료한 건은 0건이고, 관련 없는 작업은 계속 진행해야 한다. 원본 접근 불가·부분 읽기는 최신 확인으로 인정하지 않는다. 원본과 스프린트 변환 책임·수정 승인·재개 이력을 보존한다.

### P03 · 실제 개발 에이전트와 외부 DB 연결

- **가설.** 실제 에이전트가 작은 변경을 끝내고 작업 근거를 코디네이터와 PostgreSQL에 일관되게 남길 수 있다.
- **절차.** 테스트 repo A의 작은 변경을 승인 문서로 배정한다. 에이전트가 클론에서 변경·테스트를 수행하고 PR을 올린다. API 기록, DB 상태, 실제 코드와 원본 테스트 결과를 비교한다.
- **통과와 증거.** 작업 ID·적용 버전·실행 주체·PR/커밋·검사 결과가 일치한다. 완료 판정 전에는 개발 단계만 전진한다. API 기록·DB 스냅샷·PR·검사 로그를 보존한다. 기존 로그의 POC-01과 함께 검증한다.

### P04 · 트랜잭션, 재시도, repo 간 동시성

- **가설.** 외부 DB가 부분 기록과 중복 전이를 막고 독립 repo의 쓰기를 계속할 수 있다.
- **절차.** 별도 초기 상태에서 네 경우를 시험한다. ① 상태 변경 후 이력과 보고 대기 기록이 확정되기 전에 실패를 주입한다. ② 커밋 직후 응답을 끊고 같은 사건 ID와 같은 내용으로 재요청한 뒤, 같은 ID에 다른 내용도 제출한다. ③ repo A의 행을 갱신하는 트랜잭션을 열어 둔 동안 독립 repo B를 갱신한다. ④ A의 자격으로 B에 쓰고, A의 구버전 작업에도 새 결과를 쓰려 한다.
- **통과와 증거.** ① 관련 DB 변경이 모두 롤백된다. ② 동일 요청의 상태 전이·이력·보고 대기 항목은 각 1건이고 내용 충돌은 거부된다. ③ B가 A 잠금 해제 전에 커밋된다. ④ 범위 밖 쓰기와 구버전의 현재 상태 변경이 0건이고 정상 요청은 성공한다. 커밋 순서·잠금 범위·API 응답·이력 건수를 보존한다. 기존 POC-02~05에 대응한다.
- **해석.** 이 결과는 시험한 DB 스키마와 쿼리의 동작이다. 외부 보고 수신의 중복 억제는 P13에서 확인한다. [PostgreSQL 잠금](https://www.postgresql.org/docs/current/explicit-locking.html)

### P05 · PID 1과 에이전트 장애 복구

- **가설.** 코디네이터 프로세스, 개발 에이전트, Guardrail의 수명과 작업 상태를 분리하면 중단 뒤 이어갈 수 있다.
- **절차.** ① PID 1 확인 후 배정이 DB에 커밋됐지만 응답을 보내기 전에 코디네이터를 강제 종료한다. 런타임이 컨테이너를 재기동한 뒤 에이전트를 재접속시킨다. ② 정상 종료 신호를 보내 신규 배정 중단과 진행 기록의 상태를 확인한다. ③ 개발 세션의 토큰 소진을 재현하고 저장된 미커밋 변경을 복원한다. ④ Guardrail을 중단하고 고정 SHA에서 복원한다. ⑤ 실행 권한을 새 인스턴스에 이관하고 이전 인스턴스의 늦은 결과를 제출한다.
- **통과와 증거.** ① 원래 배정을 찾고 같은 작업의 중복 활성 배정 0건이다. ② 종료가 시작된 뒤 신규 배정 0건이며, 종료 직전 요청은 확정 또는 재대조할 수 있게 남는다. ③ 체크포인트에서 이어가고 미커밋 변경의 내용을 대조한다. ④ 저장한 검토 대상과 적용한 프로파일을 복원한다. ⑤ 이전 인스턴스가 현재 상태를 전진시킨 건 0건이다. PID·종료 이벤트·실행 ID·작업공간 및 DB 이력을 보존한다.
- **해석.** 토큰 소진을 테스트 오류로 모의한 회차와 실제 에이전트 한도를 사용한 회차를 구분한다.

**추가 회차 · 한도 해소 감지와 자동 기동.** 1.2절의 실제 런타임 어댑터로 공급자 한도 도달을 감지하고 체크포인트·대기 이유·다음 확인 시각을 저장한다. 한도를 해소한 뒤 재개 스케줄러가 공급자 상태 또는 제한된 probe로 이를 확인해야 한다. 사람의 재지시 없이 사전에 고정한 기한 안에 한 실행만 다시 인수하고 실제 구현·테스트 행동을 이어가는지 확인한다. 한도가 유지되는 회차와 인증 오류를 함께 넣어 무한 기동이나 잘못된 해소 판정을 검사한다. 모의 오류·모의 시계 회차와 실제 공급자의 한도/해소를 확인한 회차를 따로 기록한다. 실제 신호를 확인하지 못하면 해당 범위의 자동 복구는 `INCONCLUSIVE`다.

### P06 · 외부 요청 결과 유실과 격리된 자동 재개

- **가설.** 결과를 모르는 외부 요청과 그 의존 작업만 멈추고, 증거가 확보되면 한 번 이어갈 수 있다.
- **절차.** 두 분리된 회차에서 A의 외부 작업을 호출하기 전에 권한을 만료시키거나, 시험 수신기가 요청을 반영한 뒤 응답을 유실시킨다. 결과가 불확실한 동안 독립 repo B를 실행한다. 이후 A 원요청의 상태를 수신기에서 확인할 수 있게 한다.
- **통과와 증거.** 미전송 건은 권한·전제 재확인 후 정책 범위에서 호출할 수 있다. 결과 미확인 건의 무근거 재전송은 0건이고 B는 끝난다. A의 원요청 반영을 확인하면 정해 둔 대조 기한 내에 후속 단계로 1회 진행한다. 원요청 ID·수신기 기록·호출 수·차단 범위·재개 시각을 보존한다.

### P07 · 현재 커밋의 필수 CI와 독립 적대적 검토

- **가설.** 작성자와 분리된 검토자가 고정된 후보를 검토하고, 이전 승인이나 자기 승인이 현재 후보를 통과시키는 경로를 막을 수 있다.
- **절차.** A 커밋을 승인한 뒤 B를 올린다. B의 CI만 통과시켜 이전 승인과 동일 작성자 자격의 판정을 제출한다. 검토자가 정상 CI에 드러나지 않는 고정 반례를 B에서 재현한다. 교정한 C의 필수 CI 및 독립 승인으로 다시 판정한다. 완료 확정 전에 해당 승인이 철회되는 변형도 시험한다.
- **통과와 증거.** B의 잘못된 통과 0건이다. 검토는 위반 조건·재현 입력·기대값과 실측값·심각도·원본 로그를 남긴다. C의 유효한 승인과 CI가 있을 때 코드 검증 단계가 전진한다. 철회된 승인은 완료 조건을 충족하지 못한다. 실제 GitHub 작성·검토 주체, 현재 SHA, 리뷰의 커밋 ID와 CI 원자료를 보존한다. [GitHub PR 리뷰 API](https://docs.github.com/en/rest/pulls/reviews)

**추가 회차 · 숨긴 결함 발견.** T08의 독립 담당자가 후보와 정상 대조를 만들고, 검토자에게 결함 위치와 재현 정답을 숨긴다. 상태·동시성, 실패 복구, 권한, 필수 검사 누락 등 승인 범위의 결함 계열을 구분한다. 발견 수/주입 수, 재현 성공, 오탐, 놓친 결함과 심각도, 검토 시간·토큰을 기록한다. 지정한 차단 결함의 발견과 정상 후보 진행을 모두 요구하고, 단순히 전달받은 반례를 재실행한 회차는 발견 능력의 분모에 넣지 않는다. 같은 모델의 개발·검토를 기본 비교로 기록하며 모델이 달라도 독립성이 자동으로 입증된다고 보지 않는다. 다른 모델 비교를 하면 같은 후보·권한·예산의 별도 회차로 둔다.

**추가 회차 · 검토 정지와 늦은 결과.** 시험 프로파일은 우선 30분 경고·60분 초과·대체 배정 최대 1회를 제안하며 T01에서 확정한다. 실제 기다림 대신 모의 시계로 경계를 시험한 결과와 실제 런타임의 경과시간 시험을 구분한다. 인수하지 않은 요청, 인수 후 무응답, 계속 진행 중이지만 기한 초과인 요청을 각각 넣는다. 대체 전 기존 배정의 쓰기 권한을 회수하고 실행 세대를 바꾼다. 경계 전 중복 요청 0건, 대체 2회 이상 0건, timeout만으로 승인한 건 0건이어야 한다. 뒤늦은 결과는 원래 요청·SHA·세대에 연결해 보존하되 새 배정을 덮어쓰지 않는다. 대체 검토의 유효한 결과로 진행하거나, 한도에 도달하면 필요한 결정과 재개 조건을 보고한다.

### P08 · 이미지와 품질 프로파일의 재현성

- **가설.** 승인된 이미지와 검사 프로파일을 사용하면 후보 PR이 필수 검사를 빼거나 중간 재생성에서 검사가 달라지는 일을 발견할 수 있다.
- **절차.** 정상 후보와 필수 계약 테스트가 실패하는 후보를 준비한다. 실패 후보에는 해당 검사를 검사 목록에서 빼는 변경도 넣는다. 후보가 제공한 설정과 별도로 승인된 설정을 각각 사용해 차이를 확인한다. 컨테이너를 재생성해 승인 이미지·프로파일·테스트 데이터로 반복한다.
- **통과와 증거.** 승인된 실행에서는 계약 테스트가 실행되어 실패하고, 정상 후보는 통과한다. 재생성 후 도구·검사 목록·실행 데이터 식별자가 일치한다. 필수 검사 건너뜀은 통과에 포함되지 않는다. 이미지 digest·프로파일 버전·검사 명령과 통과/실패/건너뜀 수를 보존한다. 통합·실환경·장애 검증 단계는 repo 계약의 적용 범위로 기록한다.

신규 저장소에서 검사 기준을 찾아 첫 셋업과 PR에 적용하는 경로는 P20에서 검증한다.

### P09 · eBPF 관측과 출처 확인

- **가설.** 에이전트의 자기 보고와 별도로 Kubernetes에서 실제로 실행한 행동을 식별할 수 있다.
- **절차.** 개발 에이전트 Pod와 제품 후보 Pod를 별개로 시험한다. 허용·금지 시험용 TCP 목적지로 한 번씩 연결을 시도하고, 보조 사례로 알려진 실행 파일과 고유한 시험 파일 접근을 재현한다. 네임스페이스·Pod·컨테이너를 식별할 수 있는 기준을 고정한다. 관측기 중단, 적용 대상에서 빠진 Pod, 서로 다른 Pod의 이벤트를 각각 주입한다.
- **통과와 증거.** 각 필수 행위의 시도 또는 결과를 선택한 훅의 의미대로 기록하고 올바른 실행에 귀속한다. 관측기는 각 시험 구간 전후의 알려진 신호를 잡고 해당 정책 적용 상태와 사용할 수 있는 손실 지표를 남긴다. 적용·관측이 불충분한 회차와 다른 Pod의 이벤트를 근거로 한 통과는 0건이다. 원본 이벤트·대상 Pod 기록·정책·관측기 상태·시험 서버 로그를 보존한다.
- **해석.** 설정한 훅과 재현한 경로의 증거다. 이벤트 0건만으로 정책 준수를 확정할 수 없다. TCP 연결 훅의 이벤트는 그 훅에서 확인한 동작을 뜻한다. 원격 서비스 수신 여부는 서버 기록으로 대조한다. [Tetragon 정책](https://tetragon.io/docs/concepts/tracing-policy/) · [Tetragon 관측 지표](https://tetragon.io/docs/reference/metrics/)

### P10 · 보안 위반 탐지와 실제 차단

- **가설.** 금지된 시도는 완료 판정을 바꿀 수 있고, 차단을 요구하는 정책은 시험용 서버 관측으로 효과를 검증할 수 있다.
- **절차.** 통제한 IPv4/TCP 경로와 전용 수신기를 사용한다. 먼저 경로가 실제로 열린 상태에서 금지 주소에 연결이 가능한지 확인한다. 탐지 회차에는 CI와 코드 검토를 통과한 후보가 금지 주소로 연결을 시도하게 한다. 차단 회차에는 CNI가 집행하는 네트워크 정책이나 해당 커널에서 지원되는 차단 정책 중 하나를 고정해 같은 시도를 반복한다. 허용 주소와 정책 미적용 대조군도 실행한다.
- **통과와 증거.** 탐지 회차에서 금지 시도는 위반으로 기록되고 해당 필수 조건의 통과 및 완료 보고는 0건이다. 차단 회차에서 금지 연결은 실패하고 시험용 수신기의 연결 수락은 0건이다. 허용 주소와 미적용 대조군은 정상 연결된다. 적용 정책·시도 로그·클라이언트 결과·수신기 접속 수·완료 판정을 보존한다.
- **해석.** 차단의 근거는 시험한 프로토콜과 경로에 한정한다. 관측 이벤트와 실제 차단은 별개 결과로 남긴다. [Tetragon 적용 예시](https://tetragon.io/docs/getting-started/enforcement/) · [Kubernetes NetworkPolicy](https://kubernetes.io/docs/concepts/services-networking/network-policies/)

### P11 · 선언 정책과 애플리케이션 권한 경계

- **가설.** Kubernetes 배포 정책과 애플리케이션 권한은 각 경계에서 검증할 수 있다.
- **절차.** 검증용 네임스페이스에 Pod Security Admission의 Restricted 정책을 enforce 모드로 적용하고 정책 버전을 기록한다. 다른 조건을 충족한 Linux Pod 명세와 `allowPrivilegeEscalation`을 `true`로 바꾼 변형을 제출한다. 별도 회차에서 정상 Pod의 낮은 권한 사용자로 다른 사용자의 시험 리소스에 접근하고, 승인된 사용자로 같은 동작을 수행한다.
- **통과와 증거.** 배포 정책 위반 명세는 거부되고 정상 명세는 수용된다. 앱의 범위 밖 접근에서 데이터 노출·변경이 각 0건이며 허용된 접근은 성공한다. Kubernetes 입장 제어 응답과 애플리케이션 응답·데이터 상태를 각각 보존한다. [Kubernetes Pod Security Standards](https://kubernetes.io/docs/concepts/security/pod-security-standards/) · [Kubernetes 보안 체크리스트](https://kubernetes.io/docs/concepts/security/security-checklist/)

### P12 · 사용자 과업과 보고 이해도

- **가설.** 사람 대상 검증은 코드와 실행 정책이 통과해도 남을 수 있는 사용성 결함을 드러낼 수 있다.
- **절차.** 대표 사용자가 수행할 과업과 성공 상태, 도움 허용 범위, 치명적 오류를 미리 정의한다. 예를 들어 완료 보고를 보고 현재 막힌 단계와 필요한 결정을 판단하게 하거나, 제품에서 정상 작업과 오류 복구를 수행하게 한다. 자동 시나리오 결과와 사람의 실제 행동을 따로 수집한다. 보고 문안 두 가지를 비교하는 경우 같은 사실을 제공하고 제시 순서를 균형 있게 배정한다.
- **통과와 증거.** 계획서가 정한 과업 성공 기준을 충족하고, 참가자가 완료 단계·미확인 사실·자기 결정 필요 여부를 원본 증거와 일치하게 답한다. 예비 실험의 기준은 치명적 오해 0건이며, 제품별 성공률·시간·도움 횟수의 수용 기준은 모집 전에 확정한다. 표본 수, 과업별 완료/실패·오류·시간과 익명 관찰 기록을 보존한다. 사람 평가가 필수인 작업에서 평가가 빠지면 `INCONCLUSIVE`로 남긴다.

**추가 과업 · Notion 현황 화면의 대체.** DB의 읽기 전용 현황 조회에서 현재 작업·owner·적용 문서·SHA·대기 사유·다음 행동·최근 관측 시각을 찾게 한다. 새 이벤트가 없는 장기 대기도 화면에서 확인할 수 있어야 한다. 최소 보고·현황 이해도는 S0/1단계와 전환 전부터 확인하고, 제품 전체 사용성 평가는 해당 제품 단계에서 수행한다. 수신 채널·최소 조회 화면과 접근 주체는 T05에서 고정한다. 알림만 제공해 현재 상태를 다시 찾을 수 없는 구성을 대시보드 대체 완료로 인정하지 않는다.

### P13 · 완료 판정과 보고 전달

- **가설.** 완료를 정확히 판정하고, 재처리 중에도 수신한 보고 수를 확인할 수 있다.
- **절차.** 필수 증거를 하나씩 제거한 상태, 전부 갖춘 상태, 이벤트 중복·역순 상태를 각각 실행한다. 테스트 수신기가 보고를 저장한 직후 응답을 끊는다. 같은 보고 ID의 대조와 수신기 중복 제거가 지원되는 회차, 원요청을 대조할 수 없는 회차를 분리한다.
- **통과와 증거.** 조건이 빠졌을 때 완료 보고 0건이다. 모든 조건이 갖춰졌을 때 DB의 완료·보고 대기 항목 각 1건이고, 중복 제거 또는 원요청 조회가 가능한 시험 수신기에서 실제 수신 1건이다. 원요청을 대조할 수 없는 회차는 전달 미확인 상태를 유지하고 추측에 따른 재전송은 0건이다. 요구사항별 증거표·DB·보고 본문·수신기 원본 기록을 보존한다.
- **해석.** 보고 한 건의 보장은 해당 수신 경로의 계약에 의존한다. 운영 채널에 적용하기 전 같은 경계에서 별도로 확인한다.

### P14 · 종단 실증

- **가설.** 독립 실험을 통과한 구성요소가 한 스프린트의 개발·검증·재개·보고로 연결된다.
- **절차.** 테스트 스프린트 문서에 필수 작업 두 개와 선후 관계를 넣는다. 하나는 현재 SHA의 CI·Guardrail을 요구하고, 다른 하나는 Kubernetes 실행 증거도 요구한다. 중간에 코디네이터를 재시작하고 GitHub 이벤트 하나를 누락시킨다. 독립 Guardrail이 찾은 결함을 개발 에이전트가 교정하고 새 커밋으로 재검증한다. 같은 스프린트에서 필수 런타임 증거를 뺀 변형을 별도로 실행한다.
- **통과와 증거.** 대조가 누락 이벤트를 발견하고 복구 조건이 충족된 뒤 사람이 재지시하지 않아도 선후 순서대로 진행한다. 완료 판정은 현재 문서 버전과 각 대상 SHA·이미지의 증거를 근거로 한다. 성공 회차의 최종 보고 수신은 1건, 증거가 빠진 회차의 완료 보고는 0건이다. 시작부터 보고까지 사건 순서와 원본 증거 링크를 남긴다.

**추가 회차 · 병합 이후와 후속.** PR의 코드 검증 이후 병합 커밋의 main CI를 조회한다. PR CI가 성공해도 main CI가 실패하거나 조회되지 않은 경우 산출물·후속 단계의 완료를 막고 필요한 교정으로 연결한다. 프로파일이 요구한 산출물·실제 인수까지 확인한다. 직접 후속 이벤트를 누락시킨 변형에서는 P28의 정기 대조가 후속 처분을 복구해야 한다. 코드 검증·병합·main CI·산출물·인수·보고를 구분한 사건 순서를 남긴다.

### P15 · Rust 언어 비교 실험의 처분

**실험에서 제외하고 ID는 보존한다.** Rust는 1절의 구현 방향으로 유지한다. 소유권 오류를 컴파일러가 거부하는 작은 예제만으로 Go 대비 유지 비용·운영 이득을 판단하지 않는다. 대체 목표를 위해 별도의 Go 코디네이터를 병행 구현할 근거도 현재 부족하므로 v0.9의 언어 우위 비교 실험은 실행 대상에서 제외한다.

이 처분은 Rust가 업무 규칙 오류·교착·외부 요청 중복을 막는다는 뜻이 아니다. P04~P07과 실제 산출·정지 감지 시험은 그대로 필요하다. 같은 계약의 Go 구현을 비교할 필요가 생기면 작업량·예산을 정한 별도 실험으로 제안한다. P15는 `N/A` 통과 항목이나 S0의 선행조건으로 집계하지 않는다.

### P16 · eBPF의 추가 발견과 Aya 구현 가치

- **가설.** 실행 증거를 추가하면 기존 검증으로 발견하지 못한 정책 위반을 찾을 수 있으며, 관측기에 남는 구체적인 기능 공백이 있을 때 Aya 구현의 가치도 별도로 평가할 수 있다.
- **절차.** 동일 후보와 시나리오에서 기존 CI·독립 리뷰 판정을 먼저 고정하고, 여기에 eBPF 증거만 추가해 다시 판정한다. 정상, 알려진 금지 행동, 관측 불충분 회차를 포함한다. 공백이 확인되면 기존 도구의 지원 설정으로 해결 가능한지 먼저 확인하고, 필요한 경우에만 그 행위 하나를 다루는 Aya 실험을 같은 환경에서 비교한다.
- **통과와 증거.** PoC의 추가 발견 기준은 사전에 지정한 금지 시나리오를 기존 층보다 1건 이상 더 발견하고, 정상 대조군 오탐이 0건인 것이다. 추가 발견·오탐·미탐·미확정의 건수와 분모를 따로 기록한다. 미확정 회차의 잘못된 통과는 0건이어야 한다. Aya 후보는 구체적인 공백을 재현해 해소하고, 대상 커널에서 로드·귀속·재현에 성공하며, 사전에 정한 권한·이벤트 손실·운영 부담 기준을 충족해야 채택 후보가 된다. 후보별 정책·원본 로그·이벤트 처리량과 손실·CPU와 메모리·설정 및 유지 작업을 기록한다.
- **해석.** 새 관측이 없거나 기존 도구 설정으로 공백이 해소되면 기존 관측기를 우선하는 근거가 된다. 커널 verifier 통과는 로드 시 안전 검사 결과이고, 보안 정책의 탐지 정확도와 차단 효과는 P09·P10으로 입증한다. [Linux eBPF verifier](https://www.kernel.org/doc/html/latest/bpf/verifier.html) · [Aya](https://aya-rs.dev/book/)

### P17 · 도그푸딩으로 코디네이터의 다음 변경 구현

- **가설.** 고정한 코디네이터가 자기 repo의 실제 변경을 배정하고 독립 검증을 조율하면, 운영에 투입하기 전에 문서·인계·보고의 결함을 발견할 수 있다.
- **절차.** 아래 S0에서 만든 실행본 v0를 고정하고, S1 작업 문서를 같은 repo에 제출한다. 개발 에이전트가 후보 v1을 만들고 별도 CI·Guardrail이 해당 SHA와 이미지 digest를 검증한다. 시험 도중 작업을 한 번 끊고 재개한다. 고정 v0의 배정·판정과 외부 시험 수신기의 보고를 대조한다.
- **통과와 증거.** 사람의 개입은 사전 승인과 외부 승격 판정으로 기록된다. 정상 진행·복구에 필요한 새 사용자 지시는 0건이다. v0가 판정한 범위, v1의 변경과 검증, 독립 리뷰, 보고 수신 1건을 같은 작업에 연결한다. 후보 실행본의 배정 권한·검증 설정·승격 권한 변경은 각각 0건이다. 수동 개입 횟수와 이유, 단계별 대기 시간, 발견 결함과 재현 시간을 남긴다.

### P18 · 자기 변경의 권한 분리와 복구

- **가설.** 후보가 자신의 검증을 약화하거나 승격 권한을 얻으려 해도 기존 실행본과 검증 근거는 보존된다.
- **절차.** 별도 회차에서 후보에 필수 검사를 빼는 변경, 검토나 승격 권한을 요구하는 요청, 시작에 실패하는 이미지를 각각 넣는다. 기준 프로파일·권한·배포 승인 경로는 후보에 쓰기 권한이 없는 별도 보호 영역에 둔다. 정상 후보로 격리된 전환을 수행한 뒤 직전 실행본으로 복귀를 연습한다.
- **통과와 증거.** 부적격 후보의 승격과 자기 승인 각 0건이다. 후보를 시험하는 동안 기준 프로파일이 그대로 적용된다. 이전 실행본 또는 외부 절차로 복귀한 뒤 DB·GitHub를 대조하면 기존 완료·배정·보고에 중복 효과가 없어야 한다. 실행본·프로파일·승격 기록, 접근 거부 기록, 전환 전후 실행 ID와 DB 상태를 보존한다.

### P19 · GHCR 게시, 고정 digest 배포, 승격

- **가설.** 코디네이터 후보를 GHCR에 게시하고, 독립 검증이 확인한 바로 그 이미지를 Kubernetes에서 실행하고 승격할 수 있다.
- **절차.** 검토 대상으로 고정한 Git SHA에서 단일 플랫폼 OCI 이미지를 빌드한다. 빌드 환경은 후보 코드 실행과 패키지 쓰기 권한을 분리한다. 제한된 권한의 게시 작업이 결과 이미지를 실증용 GHCR 패키지에 올리고, 레지스트리에서 확인한 매니페스트 digest와 SHA·빌드 실행 ID를 연결한다. GitHub Actions에서 게시할 때는 대상 패키지에 권한이 있는 게시 작업에만 `packages: write`를 부여한다. 검증용 Pod는 `ghcr.io/<owner>/<image>@sha256:<digest>`로 가져온다. 비공개 패키지는 `imagePullSecrets` 등 읽기 전용 pull 자격으로 접근한다. 별도 승격 권한자가 같은 digest를 롤아웃 설정에 지정한다.
- **반례.** ① 동일 태그를 다른 내용의 이미지로 이동시킨다. ② 다른 SHA에서 빌드한 digest를 제출한다. ③ 게시 오류와 읽기 권한이 없어 pull에 실패한 경우를 각각 재현한다. ④ 후보 실행 환경의 자격으로 패키지 게시나 롤아웃 설정 수정을 시도한다.
- **통과와 증거.** 빌드에 사용한 SHA가 검토 SHA와 일치하고, 검증 Pod 명세와 승인 롤아웃이 같은 GHCR 매니페스트 digest를 참조한다. 런타임 이미지 식별자가 매니페스트와 다른 형식이면 같은 이미지로 매핑되는 근거를 남긴다. 태그를 옮겨도 digest로 고정한 이미지는 바뀌지 않는다. 다른 SHA, 게시 실패, pull 실패 회차의 승격은 0건이다. 후보 실행 환경의 범위 밖 쓰기도 0건이다. 빌드와 게시 기록, 레지스트리 조회, Pod 상태·이벤트, 독립 승인과 롤아웃 이력을 보존한다.
- **해석.** GHCR 게시와 배포 승격은 별도 사건이다. 이미지가 레지스트리에 있어도 필수 CI·독립 검토·필요한 실행 증거가 맞을 때만 승격한다. 멀티아키텍처 이미지의 인덱스와 플랫폼별 매니페스트, 별도 레지스트리 복제, 공급망 서명 정책은 해당 요구가 생긴 경우 추가로 검증한다. [GitHub Container Registry](https://docs.github.com/en/packages/working-with-a-github-packages-registry/working-with-the-container-registry) · [Kubernetes 이미지](https://kubernetes.io/docs/concepts/containers/images/)

### P20 · 신규 저장소 첫 셋업과 첫 PR에서 공통 품질 기준 적용

**가설.** 새 저장소와 새 개발·Guardrail 세션에서도 승인된 공통 기준과 저장소별 프로파일을 바탕으로 사용자의 개별 옵션 안내 없이 개발·검증 환경을 설정할 수 있다. 첫 셋업에서 적용한 필수 검사는 이후 PR에서도 실행 증거가 확인되어야 완료 조건을 충족한다.

**선행 조건.** 사용할 카탈로그 항목·문서 범위의 P25, P22의 기본 실행·문서 내장·역할 분리, P07·P08의 독립 검증과 P23의 공통 CI·설정 기준 대조를 먼저 통과한다. NPG에서 옮긴 규칙을 기본 동작으로 사용하는 범위는 P21의 해당 통과 결과도 필요하다. 카탈로그·프로파일·이미지·템플릿 버전을 고정한 뒤 비교한다. 준비물을 만드는 회차와 에이전트의 활용 효과를 재는 회차를 분리한다.

**고정 입력과 역할.** CI·테스트·린트 설정이 없는 최소 코드 골격으로 시작한다. Go 저장소와 Rust 저장소를 각각 사용한다. 실험 담당자가 스택별 필수·조건부·선택 검증, 정상 후보, 결함 후보, 기대 판정과 비교 예산을 미리 고정한다. 개발 에이전트는 첫 설정과 검증용 최소 테스트를 추가하고 첫 기능 PR을 만든다. Guardrail은 별도 세션·클론·권한으로 설정과 PR을 검토하고 검사를 재현한다. 두 역할에 프로젝트 목표·스택·승인된 기준과 정본에 대한 접근을 제공한다. 셔플 플래그, 누락 위치, 결함 주입 위치는 사용자 메시지로 알려주지 않는다.

| 비교군 | 제공하는 입력과 동작 | 확인할 차이 |
| --- | --- | --- |
| A · 기준 문서 | 승인된 공통·저장소별 기준을 자연어로 제공한다. 에이전트가 도구와 옵션을 찾아 설정한다. | 필요한 항목을 얼마나 스스로 찾고 적용하는가. |
| B · 기준과 카탈로그 | A에 버전이 고정된 카탈로그를 제공한다. 각 항목에 적용 조건, 찾는 결함, 검증 범위, 시간·환경 비용, 명령 예시와 근거를 담는다. | A 대비 누락, 탐색 비용과 불필요한 검사가 줄어드는가. |
| C · 카탈로그와 완료 판정 | B에 승인 기준을 실행 항목으로 연결한 프로파일과 증거 대조를 추가한다. 코디네이터가 셋업과 PR마다 필요한 항목을 계산한다. | Guardrail이나 CI가 필수 항목을 빠뜨린 회차에서도 완료가 차단되는가. |

비교군마다 동일한 모델·검증 이미지·도구·코드·승인 기준을 제공하고, 새 세션과 작업공간에서 시작한다. 정상 경로를 스택·비교군별 3회 반복한다. P20의 비교를 위해서만 A에서 이미지 내 카탈로그의 조회를 차단하고, 공통 정책 문서에는 동일하게 접근할 수 있게 한다. B와 C는 같은 이미지에 포함된 카탈로그를 읽는다. C의 프로파일은 A·B에도 제공한 기준을 실행 항목으로 표현한 버전이다. 후보 PR의 쓰기 범위 밖에 승인 프로파일과 판정 규칙을 둔다. 카탈로그와 이미지의 식별자를 기록한다.

| 시험 사례 | 수행 절차 | 기대 판정과 증거 |
| --- | --- | --- |
| 신규 셋업 → 정상 PR | 두 스택의 새 저장소에 필수 도구·테스트·린트와 CI를 연결한다. Guardrail이 셋업 후보의 실제 검사를 독립 실행한 뒤 첫 기능 PR에서도 새 SHA로 다시 실행한다. | 스택별 적용 필수 항목이 모두 통과하면 셋업 준비 완료와 PR 검증 완료가 각각 기록된다. 두 단계 모두 사용자의 개별 옵션 안내 0건. Go 전용 검사는 승인 범위에 따라 Rust에서 제외된다. |
| Go 테스트 순서 의존 | 첫 기능 PR에 앞 테스트가 남긴 상태에 뒤 테스트가 의존하는 결함을 넣는다. 고정한 Go 도구 체인에서 기본 순서 통과와 실패를 드러내는 셔플 seed를 실험 담당자가 사전에 확인한다. 같은 seed를 각 비교군의 재현 시험 입력으로 제공한다. C의 프로파일은 해당 변경에서 `go test -shuffle=<seed> -v ./...` 실행을 요구한다. | 기본 테스트의 성공만 제출하면 C의 완료가 차단된다. 셔플로 결함을 발견하고 같은 seed에서 재현한다. 상태 의존을 교정한 후보는 같은 seed에서 통과한다. 패키지, seed, 실행 명령과 원본 로그를 남긴다. [Go 테스트 옵션](https://pkg.go.dev/cmd/go) |
| 필수 설정·검사 누락 | 셋업 PR에서 필수 린트 설정을 제거한다. 별도 회차에서 첫 기능 PR의 필수 셔플을 빼고 일반 테스트의 성공만 제출하거나, 필수 테스트를 건너뛰거나, 이전 SHA의 성공 기록을 제출한다. | C에서 각 회차의 잘못된 준비 완료·PR 검증 완료는 0건이다. 누락 항목과 재검증 조건을 표시한다. 실행 증거가 빠지면 `INCONCLUSIVE`, 설정 위반이나 결함이 확인되면 `FAIL`로 기록한다. 교정하고 현재 SHA로 다시 실행하면 전진한다. |
| 조건부 검증과 프로파일 미등록 | 격리 환경의 카오스 시험을 요구하는 변경과 무관한 변경을 각각 제출한다. 필수 시험에 필요한 환경이 없는 회차와 승인 프로파일을 찾을 수 없는 새 스택 회차도 실행한다. | 필수 카오스 시험이 실행 불가하면 원인을 기록하고 완료를 보류한다. 무관한 변경에서는 승인 범위에 따라 해당 시험을 요구하지 않는다. 프로파일 미등록 회차는 어떤 기준의 승인이 필요한지 표시하고 준비 완료를 보류한다. |

**측정과 채택 기준.** 스택·비교군별로 적용 필수 항목 대비 실제 실행·통과·누락 수, 정상 후보 오차단 수, 결함 검출·재현 수, 관련 없는 검사 실행 수, 셋업과 첫 PR의 소요 시간, 사용자 질문·개입 수, 두 에이전트의 회차 전체 토큰을 기록한다. 문서 조회 결과를 포함한 모델 입력과 최종 출력까지 토큰을 합산한다. A→B의 카탈로그 이득은 결함 검출과 필수 검사 적용을 유지하거나 개선하면서 사전에 정한 비용 지표가 개선되는지로 판단한다. C는 정상 경로의 모든 회차에서 필수 항목을 모두 통과하고 사용자의 개별 옵션 안내 없이 전진해야 한다. 필수 근거가 빠진 회차의 잘못된 완료는 0건이어야 한다.

**보존할 증거.** 저장소·커밋 SHA·작업 ID·역할과 세션, 기준·카탈로그·프로파일 버전, 이미지 digest, 적용 항목과 선택·제외 사유, 실행 명령·seed·원본 로그, 셋업과 PR 각각의 완료 판정 및 사용자 개입 기록을 보존한다. 결과의 적용 범위는 시험한 Go·Rust 프로파일이다. 새 스택은 해당 프로파일과 같은 수용 시험으로 별도 확인한다.

### P21 · NPG 책임·정책의 이전 형태와 동작 보존

**가설.** 1.1절에서 보존·형태 변경한 지침·인계·정책을 맞는 형태로 옮기면 새 외부 쓰기 경계에서도 필요한 보호와 정상 진행을 유지할 수 있다. Notion 본문 쓰기 브로커·사건별 헬퍼를 그대로 이식하는 실험은 하지 않는다.

**채택 기준.** 보존하는 규칙은 고정 정상·위반 사례의 판정과 효과가 모두 맞아야 한다. 형태를 바꾼 규칙은 새 경계의 독립 기대값을 충족해야 한다. 정상 작업이 전진하고 다른 repo에 NPG 전용 제약을 과잉 적용하지 않아야 한다. 전달 비용 이득과 책임 이전의 기능 통과를 각각 기록한다. 운영 전환과 기존 actor의 정지는 P27의 별도 판정이다.

### P22 · 공통 개발·검증 이미지의 구조와 재현성

**가설.** 동일한 스택의 새 저장소와 새 컨테이너에서 승인된 이미지와 프로파일을 사용하면 공통 도구, 검사 명령과 필수 판정을 재현할 수 있다. 개발 에이전트와 Guardrail은 같은 이미지를 사용하면서도 작업공간과 권한을 분리할 수 있다. Go·Rust 전체 도구를 하나에 넣는 구성과 공통 기반 위에 언어별 파생 이미지를 두는 구성은 품질·재현성 조건을 먼저 충족한 뒤 운영 비용을 비교한다.

**선행 조건과 부분 통과.** T04의 고정 이미지 후보와 T05의 컨테이너 환경을 사용한다. 이미지에 넣은 문서·카탈로그 범위는 P25를 통과해야 한다. 먼저 문서 내장·조회, 도구·명령 재현, 역할별 공간·권한, 누락·비호환 거부를 확인한 결과를 `P22 기본 실행 통과`로 기록한다. 이 범위가 P08·P20·P21·P23·P24의 선행 증거이며, 통합·언어별 구성의 비용 비교는 별도 결과다. P20·P23·P24의 성공을 P22의 착수 조건으로 요구하지 않는다.

### P23 · GitHub Actions의 거짓 성공 방지

**가설.** 개발 에이전트가 워크플로를 등록하고 Guardrail이 검토하는 환경에서도, 의도적으로 실패하는 입력과 독립된 필수 판정을 사용하면 테스트 실패가 성공으로 가려지거나 필수 테스트가 실행되지 않은 PR의 병합을 막을 수 있다.

**선행 조건.** T04의 워크플로·프로파일 후보, P22 기본 실행 통과, P07의 역할·후보 SHA·검사 출처 대조, T03의 정상·실패 수집 대조와 T06의 독립 판정 경로, T05의 격리 GitHub 저장소·설정 조회/변경 자격을 준비한다. P07은 고정된 외부 CI로 먼저 시험할 수 있다. P23에서 검증된 공통 템플릿·설정 기준은 P20과 P24에 공급하고, 이 두 실험의 완료를 P23의 착수 조건으로 삼지 않는다.

#### 워크플로 등록과 검증 구조

| 단계 | 책임과 기준 |
| --- | --- |
| 개발 에이전트 · 구성 | 버전이 고정된 워크플로 템플릿과 저장소 프로파일을 사용한다. 필수 검사 ID, 실행 이벤트, 대상 SHA의 기준, 실행 이미지 digest, 테스트 명령과 보고 형식을 명시한다. P22 이미지의 검증 실행기로 구문과 필수 단계 연결을 사전 점검한다. |
| Guardrail · 독립 검증 | 개발과 분리된 작업공간·권한에서 워크플로와 호출 스크립트를 검토한다. 동일한 워크플로의 정상 입력과 **의도적으로 실패하는 테스트 입력**을 같은 GitHub Actions 이벤트, 필수 작업, 명령 및 환경으로 실행해 실패가 최종 판정까지 전달되는지 확인한다. |
| 코디네이터 · 필수 판정 | 후보 PR 밖에서 관리하는 실행기와 프로파일로 필수 검사를 실행하고, 그 실행기가 직접 수집한 증거를 사용한다. 승인 검사 ID, 실제 결과·테스트 수와 개별 판정, 워크플로·실행 ID·회차, 체크아웃 SHA를 대조한다. 등록 또는 검사 경로 변경 시 정상·실패 대조까지 통과한 워크플로 버전에 대해서만 필수 판정을 성공으로 발행한다. |
| GitHub · 병합 조건 | 실험 저장소의 보호 브랜치에서 독립 판정을 필수 검사로 등록한다. 성공 판정의 발행 권한을 후보 워크플로와 분리하고, 연결한 GitHub App을 검사 출처로 고정하는 경로를 시험한다. 후보 작성 권한에 보호 규칙 우회 권한을 부여하지 않는다. |

체크 화면의 결론, 테스트 프로세스 종료 코드, 필수 테스트 실행 증거를 각각 보존한다. `continue-on-error`가 적용되면 실패 단계의 `outcome`과 최종 `conclusion`이 달라질 수 있고, 건너뛴 작업은 GitHub에서 성공으로 보고될 수 있다. 워크플로 변경과 필수 검사 경로를 바꾸는 스크립트·템플릿·프로파일 변경에도 같은 검증을 적용한다. #### GitHub 저장소 설정 검증

공통 **GitHub 설정 기준**은 이미지에 문서로 넣고 저장소별 승인 값은 프로파일에서 읽는다. 첫 등록 후와 설정 변경 후에는 Guardrail이 GitHub에서 실제 값을 다시 읽는다. 보호 규칙이 둘 이상 적용되거나 조직에서 상속되는 경우, 병합 대상 브랜치에 적용되는 규칙을 대조한다. 코디네이터는 병합 직전에 필수 설정을 다시 확인한다. [GitHub ruleset과 상위 규칙 조회](https://docs.github.com/en/rest/repos/rules) · [GitHub Actions 권한 조회](https://docs.github.com/en/rest/actions/permissions)

| 검증 항목 | 승인 기준과 대조할 실제 설정 |
| --- | --- |
| 기본·대상 브랜치와 병합 방식 | 기본 브랜치, PR의 병합 대상, 허용된 병합 방식과 보호 규칙이 적용되는 브랜치 |
| 보호 규칙과 독립 검토 | 브랜치 보호 또는 활성 ruleset, PR·독립 승인 요구, 직접 푸시와 규칙 우회 허용 주체 |
| 필수 검사 | 정확한 검사 이름, 승인된 검사 발행 App, 필요한 브랜치에서 필수로 적용되는지 여부 |
| Actions 권한 | 허용된 Actions·재사용 워크플로 범위, `GITHUB_TOKEN`의 저장소 기본 권한, 워크플로·작업별 권한과 PR 작성·승인 허용 여부 |

개발 에이전트는 설정 기준을 제안하거나 이미 승인된 초기 설정을 지정된 권한으로 적용한다. Guardrail은 실제 설정과 통제 동작을 독립 검증한다. 필수 설정이 기준과 다르거나 읽을 수 없으면 불일치 또는 미확인으로 기록하고 코디네이터의 자동 병합을 보류한다. GitHub 자체의 병합 가능 상태와 코디네이터의 보류 판정은 각각 기록한다.

#### 실제 GitHub Actions와 저장소 설정에서 검증할 시나리오

격리한 GitHub 시험 저장소에서 승인 템플릿, 이미지 digest와 테스트 후보를 고정한다. 정상 후보와 결함 후보는 필수 테스트의 관측 결과가 달라지도록 준비한다. 결함 후보는 필수 테스트 명령 자체가 0이 아닌 코드로 종료하는 것을 독립 실행으로 먼저 확인한다. 결함 주입용 임시 단계의 실패를 본 테스트의 실패 증거로 사용하지 않는다. `|| true`처럼 셸에서 실패를 무시하는 경우를 포함해, 위반 사례는 다른 조건을 유지한 채 한 번에 하나씩 주입한다.

| 사례 | 시험 방법 | 기대 결과 |
| --- | --- | --- |
| 정상 후보와 실패 후보 | 승인 워크플로에서 정상 후보와 필수 테스트가 실패하는 후보를 각각 실행한다. 테스트 코드·입력 차이만으로 결과가 달라지게 한다. | 정상 후보는 필수 판정을 통과한다. 결함 후보는 테스트 단계와 최종 필수 판정이 실패한다. |
| 테스트 실패를 성공으로 바꾸는 워크플로 | 필수 단계의 `continue-on-error` 또는 실패를 흡수하는 셸 처리를 별도 회차에 넣고 같은 결함 후보를 실행한다. | 후보 워크플로가 성공으로 표시돼도 독립 판정에서 거부한다. 원래 테스트 종료 코드와 최종 체크 결론의 차이를 재현한다. |
| 필수 검사가 실행되지 않은 워크플로 | 조건식으로 필수 작업을 건너뛰거나, 테스트 선택 결과를 0건으로 만들거나, 필수 매트릭스 항목 하나를 누락시킨다. 선택 검사만 정책에 따라 제외되는 정상 사례도 넣는다. | 승인 목록의 필수 항목과 실행 증거가 일치해야 통과한다. 필수 항목이 빠지면 어떤 항목이 빠졌는지 표시하고 보류한다. 승인된 선택 검사 제외는 정상 통과한다. |
| 다른 SHA의 초록 체크 | 앞선 SHA의 성공을 남긴 뒤 새 커밋을 제출한다. 별도 회차에서는 워크플로가 이전 SHA를 체크아웃하도록 바꾼다. | 이전 후보 성공과 잘못 체크아웃한 결과로는 병합 조건을 충족하지 못한다. 프로파일이 PR head와 시험용 merge SHA 중 어느 쪽을 요구하는지 고정하고, 실제 체크아웃과 해당 PR·head·base의 관계를 확인한다. [PR 이벤트의 SHA 기준](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows#pull_request) |
| 동일 이름의 성공과 보호 규칙 | 후보 워크플로가 필수 검사와 같은 이름의 성공을 제출하거나, 후보가 필수 검사를 약화하는 변경을 제출한다. 정상 회차에서는 승인된 독립 출처에서 실제 검증 결과를 제출한다. | 후보가 만든 성공은 필수 독립 판정을 충족하지 못한다. 권한이 없는 계정의 보호 규칙 변경과 결함 후보의 시험 병합은 거부된다. 독립 판정이 성공한 정상 후보는 병합 가능하다. |
| 저장소 설정 불일치 | 시험 저장소에서 필수 검사 제거, 다른 브랜치에 보호 규칙 적용, 쓰기 권한 또는 우회 권한 확대를 각각 주입한다. 설정 조회가 실패하는 회차와 승인 설정을 복원한 회차도 둔다. | 불일치 또는 미확인 항목을 기록하고 자동 병합을 보류한다. GitHub가 병합 가능으로 표시한 경우에도 자동 병합 요청은 0건이다. 승인 설정을 복원한 뒤 다시 읽어 일치를 확인하면 정상 후보가 전진한다. |

**통과와 증거.** 필수 테스트 실패·누락·잘못된 SHA·승인되지 않은 출처나 필수 설정 불일치·미확인으로 인한 코디네이터의 잘못된 완료와 자동 병합 요청은 각 회차에서 0건이다. 승인 설정에서 GitHub는 결함 후보의 병합을 거부하고, 정상 및 승인된 선택 검사 제외 사례는 통과한다. 비교는 후보 워크플로의 결론을 그대로 본 판정과 독립 판정을 같은 실행 결과에 대조한다. 저장소·PR·workflow 경로와 버전·run/attempt ID·검사 출처·실제 SHA·원본 테스트 결과·설정 기준 버전과 조회값·코디네이터 판정·GitHub의 병합 가능 상태를 보존한다. 실제 Actions 실행이나 병합 조건을 확인할 수 없으면 해당 사례는 `INCONCLUSIVE`로 표시한다.

| 사례·회차 | 실제 테스트 실행·종료 코드 | Actions 결론 | 독립 판정 및 병합 조건 | 차이와 원본 증거 |
| --- | --- | --- | --- | --- |
| 정상 / 결함 대조 | — | — | — | — |
| 실패 무시 / 필수 검사 누락 | — | — | — | — |
| 잘못된 SHA / 같은 이름의 성공 | — | — | — | — |
| GitHub 저장소 설정 불일치·복구 | — | — | — | 승인 기준 버전, 항목별 기대값·실제값, 설정 조회 및 병합 가능 상태 |

`—`는 실측 전 빈칸이다. 검증 범위는 고정한 실패·우회 시나리오에 한정한다. 새 우회 사례를 발견하면 회귀 사례에 추가한다.

### P24 · 내장 정책으로 신규 저장소 설정·검증·수정 반복

**가설.** 사용자가 시험 저장소와 스택, 승인 범위를 지정해 시작을 한 번 요청하면 개발 에이전트가 이미지 내 문서를 읽고 셋업을 수행한다. Guardrail이 독립적으로 실제 설정과 CI의 동작을 검증하고, 코디네이터가 재현 근거를 개발 에이전트에 넘겨 수정·재검증을 이어간다. 사용자는 필수 옵션이나 수정 방법을 회차마다 알려줄 필요가 없다.

**시작 조건.** 새 저장소·새 세션과 승인된 P22 이미지, 저장소 프로파일, 격리된 GitHub 설정 권한을 사용한다. 정책 내용과 결함 위치는 시작 메시지에 추가하지 않는다. 시험 중에는 내장 공통 문서만으로 적용 지침을 찾을 수 있어야 한다. 정책에 없는 저장소별 값·예외의 승인 여부는 프로파일에서 확인한다.

P25의 해당 문서 범위, P22 기본 실행, P23의 사용할 CI·설정 검증, P20 C의 필수 기준 적용·누락 차단을 먼저 통과한다. 반복을 조율할 T06 실행본은 적용 범위의 P02~P08·P13 증거를 갖춰야 한다. P20 A→B의 토큰 절감이 아직 입증되지 않아도 기능상 선행 조건이 충족되면 P24는 진행할 수 있다. 문서 적용 대조에 쓰는 두 이미지도 바뀐 문서 범위의 P25와 P22 통과 증거를 각각 갖춘다.

| 단계 | 에이전트와 코디네이터의 동작 | 다음 단계에 필요한 증거 |
| --- | --- | --- |
| 1. 읽기·계획 | 개발 에이전트가 이미지의 시작 안내와 정책 색인을 읽는다. GitHub 설정, 워크플로, 테스트·린트에 적용되는 항목을 골라 실제 저장소 상태와 대조한다. | 이미지 digest, 문서 ID·버전·조항, 적용 대상과 계획한 변경 |

| 4. 수정·재검증 | 확인된 실패는 코디네이터가 해당 조항, 기대값·실제값, 재현 로그와 함께 개발 에이전트에 돌려보낸다. 개발 에이전트는 승인 범위의 문제를 수정한다. Guardrail은 새 커밋과 현재 설정에서 관련 검사를 다시 실행한다. | 회차별 변경·판정·근거와 새 후보의 검증 결과 |

**시험 사례.** 첫 셋업이 정상인 회차에서는 첫 검증 후 종료하는지 확인한다. 교정 회차에서는 잘못 연결된 필수 GitHub 검사와 테스트 실패를 성공으로 처리하는 워크플로를 차례로 노출해, 두 번의 수정·재검증이 추가 사용자 입력 없이 이어지는지 본다. 이 회차의 교정 한도는 3회로 설정한다. 별도 회차에서는 필수 정책 문서 누락, 승인 범위 밖의 설정 변경 필요, 같은 실패가 한도까지 반복되는 상황을 주입한다. 정상 완료된 저장소에 동일 조건으로 시작을 다시 요청해 불필요한 설정 쓰기가 없는지도 확인한다.

**문서 적용 대조.** 동일한 시작 메시지·도구·저장소 프로파일을 사용하고, 내장 문서의 승인 기준 한 항목만 다르게 한 두 시험 이미지를 비교한다. 바뀐 기준은 프로파일이나 시작 메시지에 중복해서 적지 않는다. Guardrail의 독립 기대값은 각 이미지 버전별로 미리 고정한다. 실제 설정·검사가 각 이미지 문서에 맞게 달라져야 문서 적용을 확인한 것으로 판정한다.

**통과와 증거.** 정상 및 교정 가능 회차는 사용자 추가 안내 0건으로 종료한다. 준비 완료 전 모든 필수 증거를 현재 후보와 실제 GitHub 설정에 다시 대조한다. 의도적 실패 입력은 요구한 경로에서 실패해야 한다. 보류 회차의 잘못된 완료와 승인 범위 밖 쓰기, 완료된 저장소 재실행의 불필요한 설정 쓰기는 각각 0건이다. 문서를 읽었다는 자기 보고와 실제 정책 적용을 구분할 수 있도록 시작부터 종료까지 조회·변경·시험 기록을 보존한다.

### P25 · 초기 정책 문서·카탈로그의 충실도와 정확성

**검증 질문.** 에이전트에게 제공하기 전에, 선언한 초기 범위의 자료가 빠짐없이 채워졌고 설명·옵션·적용 조건·확인 방법이 맞는지 확인한다. T02는 자료를 만드는 작업이고 P25는 그 자료의 준비 상태를 검증하는 실험이다. 에이전트가 실제로 잘 선택하고 적용하는지는 이후 P20·P21·P24에서 별도로 판정한다.

**선행 입력.** T01의 요구 기준·독립 기대 판정표, T02의 카탈로그·정책 문서 후보와 원본 대응표, T03의 필드·참조·실행 결과 대조 도구, 필요한 범위의 T05 환경을 고정한다. P22 이미지나 후보 코디네이터를 준비 검증의 필수 입력으로 삼지 않고, 외부의 고정 도구·절차로 먼저 시험한다.

| --- | --- | --- |

**진행 방법.** Go의 작은 범위에서 작성·직접 실행·독립 대조·교정을 먼저 반복해 항목 형식을 다듬는다. 이어 T01이 정한 초기 Go·Rust와 공통 정책 범위를 채운다. 사용하려는 필수 항목의 공백·오류를 교정하고 재검증한 뒤 통과 목록을 고정한다. 이후 P20·P24 평가 중에는 비교군에 제공한 버전을 바꾸지 않는다. 새 결함을 발견하면 원본 결과를 보존하고 교정본의 준비 검증부터 새 회차를 시작한다.

**통과와 증거.** 선언한 사용 범위의 요구 ID별 자료 연결률과 필수 필드 충족률은 각각 100%이고, 확인된 중대한 설명·적용·명령 오류가 0건이어야 한다. 여기서 중대한 오류는 검사 누락, 잘못된 통과, 권한 범위 오류 또는 정상 작업의 진행 불가를 만드는 오류다. 지정한 문서 오류 변형의 잘못된 준비 완료도 0건이어야 한다. 정상 대조·교정본은 통과해야 한다. 명령·관측을 확인하지 못한 항목은 `INCONCLUSIVE`, 범위에서 사전에 제외한 항목은 `N/A`로 남긴다. 후속 실험이 필수로 쓰는 항목에는 `PASS` 증거가 필요하다. 일부 범위만 통과했으면 그 항목·스택만 준비 완료로 표시한다.

### P26 · 실제 백로그의 산출과 자동화 충분성

**검증 질문.** 합성 예제에서 안전하게 멈추는 것뿐 아니라 실제 제품 작업을 승인 범위 안에서 사람의 재지시 없이 끝낼 수 있는가.

**선행 조건.** S1의 자기 repo 조율, 적용 범위의 P07·P08·P13·P21·P23, P28의 후속/정지 감지와 P12의 최소 보고·현황 이해도를 통과한다. T05에서 기존 개발자·예약 실행과 겹치지 않는 작업·브랜치·외부 효과 범위의 독점 권한을 확인한다. 전체 NPG 중단은 착수 조건이 아니다. 신규 셋업이 필요한 표본에는 해당 P20 C·P24도 요구한다.

**고정 표본.** NodeKit·Sori의 실제 백로그에서 기능 변경·결함 교정·계약/통합·실패 복구를 포함한 N건을 실행 전에 고정한다. 초기안은 repo별 6건, 합계 12건이며 정확한 목록·난도·수용 기준·제외 조건·완료율 목표·시간/토큰 예산은 T01에서 검토 후 확정한다. DF-01 같은 보고 필드 추가만으로 표본을 채우지 않는다. 기존 담당자가 진행 중인 작업을 중복 배정하지 않는다. 격리 fork/시험 저장소에서 수행하면 실제 코드·CI·수용 기준과 다른 점을 공개하고 결과를 `시험 범위 산출`로 표시한다. 제품 repo의 병합·인수 완료와 섞어 집계하지 않는다.

**절차.** 승인 작업 묶음을 한 번 제출한다. 코디네이터가 선후관계에 따라 개발→내부 검사→독립 검토→교정→병합→병합 SHA의 main CI→필수 산출물·후속 인수→보고를 이어간다. 작업 일부에는 실제 복구 가능한 장애를 정한 순서로 넣는다. 관련 없는 repo의 진행을 함께 관측한다. 사람의 초기 승인·작업 문서 작성과 실행 중 개입을 따로 기록한다.

**판정.** 잘못된 완료·권한 밖 효과 0건은 필수다. 여기에 실행 전에 고정한 무개입 완료율·처리 시간·비용·보류 한도를 각각 만족해야 `자동화 충분성`을 채택한다. 모든 작업 보류나 일부 쉬운 작업만 완료한 결과는 통과가 아니다. 각 표본의 정상 완료 여부를 독립 담당자가 코드·CI·산출물로 확인한다. 사후 표본 삭제나 난도 낮은 표본 교체를 하지 않는다. 정상 종결·실패·미해결·사람 결정 대기를 모두 최초 N건에 남기고 종료 시각을 고정한다. 사람이 처리한 종료·취소를 무개입 완료로 세지 않는다.

| 무개입 완료 수 / 최초 N건 | — | — | — |

**현재 상태.** 표본·완료율·예산은 미확정이고 실험은 미실행이다. 이 값이 없는 실행으로는 ‘충분히 자동화됐다’고 판정하지 않는다.

### P27 · NPG 전환·책임 종료·복귀

**검증 질문.** 기존 운영의 상태와 미결 외부 효과를 잃지 않고 책임을 옮기며, 같은 범위의 쓰기 소유자가 둘이 되는 기간과 보호 장치가 없는 기간을 피할 수 있는가.

**두 범위.** P27-R은 복제 상태·격리 자격으로 수행하는 전환 연습이다. S1·P21·P28·P12·P13의 해당 증거와 현재 상태 조사 도구를 준비한다. P27-L은 승인된 운영 전환 창에서 실제 actor·자격·스케줄을 대상으로 수행하는 판정이며, P27-R과 2단계의 P26·사용할 P23·최소 현황 검증 통과가 추가로 필요하다. 이 문서 업데이트는 실제 예약 중지나 전환을 실행하는 요청이 아니다.

| --- | --- | --- |
| 상태 조사 | 현재 설치 SHA·정책, 중앙/Operator/Guardrail/감시의 실행·소유권·lease, canonical journal·미결 요청, 관련 예약/서비스·트리거를 읽어 목록으로 고정한다. | 오래된 RELEASED나 저장소 기본 policy만으로 무소유를 판단하지 않는다. |

| 복귀 | 새 배정을 중지·권한 회수한 뒤 DB·GitHub·미결 요청·이미 진행된 외부 효과를 대조한다. 기존 실행본이 새 상태를 안전하게 인수할 수 있을 때만 재개한다. | 오래된 스냅샷으로 이미 반영된 효과를 지우거나 재실행하지 않는다. 자동 복귀가 불가능하면 범위와 필요한 처분을 남긴다. |

### P29 · Harness² 방식의 실행 지침 개선 가능성

**가설.** 고정된 실행 지침보다, 같은 사건에서 후보 지침을 비교하고 관측 차이로 조합하는 제한된 절차가 재개·보고의 정확성과 진행을 개선할 수 있다.

**선행 작업·구현.** R01의 T07, T08의 분리 자료·독립 판정, T03의 반복 실행·비용 계측, 사용할 P25 초기 문서 범위를 준비한다. 공식 demo/실행기를 연결할 수 있는지 먼저 시험하고, 불가하면 이유와 최소 어댑터 또는 방법 재구현을 별도 후보로 기록한다. 구현 범위는 후보 문서 생성→같은 사건의 비교 실행→행동 차이 기록→조합 문서 출력이다. 보호 정책은 편집 대상에서 제외한다.

**비교.** A는 현재 고정 지침, B는 Propose–Probe–Compose 1회, C는 B와 같은 총 생성·실행 예산에서 한 후보를 직접 수정·평가하는 단순 방법이다. B의 후보 수와 비교·조합 상한을 사전에 고정한다. B만 더 많은 재시도를 써서 좋아진 것인지 C로 구분한다. 원 방법의 정답 없는 내부 비교 점수와 Console의 독립 기대값을 모두 보존한다. 최종 채택은 독립 판정으로 한다.

**사례.** 결과 미확인과 미전송을 혼동하기 쉬운 재개 안내, 이전 SHA 승인만 남은 보고, 정상 완료, 정상적인 외부 대기를 사용한다. 작성용 사건과 다른 실패 계열·새 repo의 변형에서 평가한다. 더 그럴듯한 보고지만 실제 완료/미확인 사실을 왜곡하는 후보도 대조 입력으로 준다.

**통과·채택.** 동일 입력·버전에서 후보·probe·조합·결과를 재대조할 수 있으면 최소 구현 가능성의 근거가 된다. 정상 진행·보고 사실·승인 범위를 보존하고, 독립 평가에서 사전 품질/진행/비용 기준을 충족해야 도입 효과를 채택한다. 내부 점수만 오른 후보나 전부 보류하는 후보는 채택하지 않는다. 재사용 후보는 비교 실행기·패치/조합 기록·지침 어댑터다. 논문의 전체 재귀·도메인 벤치마크 재현이나 운영의 자동 자기 변경은 이 범위에 포함하지 않는다.

**결과.** 2.2절 공통 표에 후보 수·비교 횟수·내부/독립 점수 차이·조합 근거를 추가한다. 원본 코드 재사용/어댑터/방법 재구현 중 어떤 경로가 가능한지와 Rust 연동 수정량을 기록한다.

### P30 · Trace2Skill 방식의 개발 기록→재사용 스킬 생성 가능성

**가설.** 사람이 일일이 추가하지 않아도, 여러 성공·실패 기록에서 추출·통합한 절차가 고정 초기 카탈로그의 반복 누락을 줄이며 다른 repo의 같은 종류 작업에 적용될 수 있다.

**선행 작업·구현.** R02의 T07, T08의 정규화·비밀 제거·분리 자료, T03의 실행·계측, P25 초기 카탈로그를 준비한다. 개발·검토·복구 기록을 입력 계약으로 변환하는 코드, 기록별 개선 후보, 충돌 통합·출처 연결·스킬 디렉터리 출력을 최소 구현한다. 공개 spreadsheet 중심 실행과 Console 기록의 차이를 명시하고 필요한 입력·평가 어댑터를 별도 산출물로 남긴다.

**비교.** A는 고정 초기 카탈로그, B는 동일 기록을 매번 조회하는 방법, C는 같은 기록에서 생성·통합한 스킬을 제공하는 방법이다. B와 C의 원본 기록·대상 모델·도구·평가 예산은 같게 한다. 선택적으로 같은 예산의 순차 수정과 국소 후보 통합을 비교해 통합 자체의 기여를 분리한다. 생성에 쓰지 않은 작업·실패 계열·새 repo에서 평가한다.

**사례.** 옵션 누락, 실패를 성공으로 가린 CI, 현재 SHA 확인 누락, 자동 재개 실패의 반복 기록을 넣는다. 성공 기록과 실패 뒤 복구 기록을 구분한다. 상반된 도구 버전의 조언, 우연히 통과한 잘못된 절차, 승인 밖 우회를 제안하는 기록을 섞어 출처·적용 조건·충돌을 식별하는지 검사한다. 숨긴 최종 결함의 정답을 기록에 포함하지 않는다.

**통과·채택.** 원본 기록→국소 후보→통합 결과의 출처가 연결되고 실행 가능한 후보를 만들면 최소 구현 가능성을 기록한다. 생성 스킬은 별도 P25 검증 범위를 통과한 뒤에만 대상 에이전트에 제공한다. 최종 평가에서 필수 적용·결함 발견·정상 완료를 유지·개선하고, 기록 재조회 대비 비용을 포함한 사전 기준을 만족해야 도입 효과를 채택한다. 새 repo에 적용되지 않으면 확인한 repo 범위의 결과로 한정한다. 초기 자료를 자동으로 완전하게 만들었다고 해석하지 않는다.

**결과.** 공통 표와 P20 항목별 대조표에 기록 수·스킬 수·출처 연결률·충돌/오류·반려·교정 수, 새 repo의 실제 적용·실행 수를 더한다. 재사용 후보는 기록 정규화기·출처 매핑·후보 통합기·회귀 평가 자료다.

### P31 · SkillOpt 방식의 제한된 스킬 수정과 채택 가능성

**가설.** 고정 모델을 유지하고 스킬 문서의 변경 크기를 제한하며 별도 validation으로 채택하면, 무제한 자기 수정이나 고정 문서보다 안정적으로 개선할 수 있다.

**선행 작업·구현.** R03의 T07, T08의 작성/validation/최종 분리 자료와 독립 점수, T03의 사용량 계측, P25를 통과한 초기 스킬을 준비한다. 초기 스킬은 수작업 고정본으로 시작할 수 있고 P30의 통과를 필수로 요구하지 않는다. P30 산출물을 쓰는 추가 회차는 해당 버전의 준비 검증 증거를 요구한다. Console 실행·점수를 연결하는 어댑터, 제한된 add/delete/replace, 거부 후보 기록, validation 채택·기존본 복원을 최소 구현한다.

**비교.** A는 변경하지 않은 스킬, B는 같은 총 제안·실행 예산의 직접 수정, C는 변경 예산과 validation 채택을 갖춘 방법이다. 대상 모델·스킬 최초 버전·도구·권한을 고정한다. 수정 글자/토큰 상한·epoch·후보 수·재시도 예산을 먼저 정한다. validation은 후보 선택에 쓰고 최종 평가는 보고용으로만 사용한다.

**사례.** 실제 필수 적용이 빠지는 장황한 스킬을 개선하게 한다. 작성용 점수만 높이는 수정, 필수 조항 삭제로 짧아진 수정, 사용한 validation에 과적합한 수정, 변경 상한을 넘는 패치를 각각 대조한다. validation 실패·동점·정상 개선, 최적화 중단 후 재개와 기존본 복원도 확인한다.

**통과·채택.** 변경 한도·보호 조항·거부 기록·validation 채택 규칙이 지정대로 동작하고 올바른 기존본을 복원하면 최소 구현 가능성을 기록한다. validation 점수가 엄격히 좋아진 후보만 다음 독립 평가로 넘기며, 최종 품질·진행·전체 비용 기준도 만족해야 Console 도입 효과를 채택한다. 짧아졌다는 이유만으로 토큰 절감 성공이라 하지 않는다. 최적화 비용·거부 회차·검증 비용을 포함한 누적 회수 여부를 공개한다.

**결과.** 공통 표에 수정량·제안/채택/거부 수·validation/최종 점수·필수 조항 보존·복원 결과를 더한다. 재사용 후보는 문서 패치기·변경 한도 검사·후보 이력·평가 어댑터다. 모델 가중치 학습이나 제품 코드 자동 승격은 실험 범위가 아니다.

### P32 · SkillOps 방식의 계약·관계·유지보수 가능성

**가설.** 개별 문서가 맞는 것뿐 아니라 스킬 계약·버전·관계를 점검하면, 단순 목록 조회로 남는 중복·구버전·검증 공백·입출력 불일치를 줄일 수 있다.

**선행 작업·구현.** R04의 T07, T08의 정상/오류 라이브러리와 독립 기대 그래프, T03의 대조·계측, P25 초기 문서 범위를 준비한다. 카탈로그를 선행조건·동작·산출물·검증기·실패 모드 계약으로 변환하고, 의존·호환·중복·대안·계보 관계를 기록하는 최소 어댑터를 만든다. 관계 표현을 위해 그래프 DB를 필수로 도입하지 않는다. 고정 파일이나 기존 DB로 비교할 수 있다.

**비교.** A는 같은 스킬의 평면 목록·키워드 조회, B는 계약·관계 검증만 적용, C는 진단 뒤 merge/repair/retire/add-validator/add-adapter의 유지보수 후보까지 적용한다. 제공 문서와 작업·도구·예산을 맞추고 유지보수 전후의 정상 실행을 같은 입력으로 비교한다. 실행 중인 버전을 수정하지 않고 새 라이브러리 버전으로 평가한다.

**사례.** 중복 스킬, 잘못 연결된 버전, 필수 validator 누락, 출력/입력 형식 불일치, 선행조건 미충족, 순환 의존을 각각 주입한다. 이름이 비슷하지만 적용 범위가 다른 정상 스킬과 승인된 대안도 포함한다. 자동 통합·폐기가 정상 기능을 지우는지 대조한다. 필수 선행이 없으면 필요한 준비를 제시하고, 준비가 주어지면 정상 실행으로 이어져야 한다.

**통과·채택.** 계약·관계·버전·유지보수 전후 결과를 외부 기대값과 대조할 수 있으면 최소 구현 가능성을 기록한다. 지정 오류의 미탐·잘못된 연결·정상 기능 파괴·필수 검증 누락 완료는 0건이어야 하고 정상 대조는 진행해야 한다. 후보 복원과 출처를 보존하며, 평면 목록보다 사전에 정한 품질·탐색·유지 비용 기준을 개선해야 도입 효과를 채택한다. 구조 검사 통과만으로 스킬 내용의 정확성(P25)이나 실제 활용(P20)을 대체하지 않는다.

**결과.** 공통 표에 오류별 검출/주입 수·정상 보존·스킬/관계 수·유지보수 조치·준비 제안/실제 후속 진행·복원 결과를 더한다. 재사용 후보는 계약 스키마·관계 검사기·라이브러리 diff·이전 버전 복원·회귀 사례다.

### P33 · 결과 처분·코드 재사용·최종 스프린트 연결 검증

**가설.** 성공·실패·증거 부족이 섞인 보고에서도 결과와 도입 결정을 분리하고, 유효한 모듈만 재사용하면서 필수 목표의 누락 없이 실행 가능한 후속 스프린트를 만들 수 있다.

**선행 작업·구현.** T01의 필수/선택 요구·처분 권한·누적 예산과 T03·T09 후보를 준비한다. 외부 검증 담당자가 아래 모의 결과 묶음, 자산 버전·계약과 기대 처분·작업 목록을 먼저 고정한다. 후보 출력과 독립 기대값을 대조하며 후보가 자신의 변환 결과를 단독 승인하지 않는다. 첫 회차는 합성 입력으로 규칙을 시험하고, 실제 실험 보고가 생기면 해당 보고·처분·자산에 연결한 별도 회차를 수행한다. 모의 통과를 실제 연구의 성공이나 제품의 완성으로 보고하지 않는다.

| 시험 입력 | 기대 처분과 후속 스프린트 |
| --- | --- |
| 정상 채택·부분 채택·최소 실행만 PASS·효과/비용 미달이 혼재 | 입증된 범위만 채택하고 미달 후보를 편입 작업으로 발행하지 않는다. 부분 채택의 미충족 선행은 대기로 남긴다. |
| 관측 누락·환경 부족과 실제 기능 실패가 혼재 | INCONCLUSIVE와 FAIL을 구분한다. 보류의 담당·부족 근거·재개 조건을 남기고 조건 확보 후 관련 회차만 다시 연다. |
| 선택적 방법 기각과 필수 기능의 실패 | 선택적 방안은 종료할 수 있다. 필수 목표는 미해결로 남기고 대안/추가 실험을 먼저 배정한다. 필수 목표가 빠진 계획의 착수 가능 판정은 거부한다. |

**통과·증거.** 고정한 모든 사례에서 실험 판정·도입 결정·후속 ID·요구사항/자산/작업 대응이 독립 기대값과 일치해야 한다. 필수 목표 누락, 미채택 후보의 무근거 편입, 버전 불일치 증거 사용, 한도 초과 자동 재실행, 중복 작업과 승인 없는 스프린트 실행은 각 사례 0건이다. 정상 입력의 유효한 초안 생성과 재개는 성공해야 한다. 입력 보고·처분·자산 목록의 digest, 변환기 버전, 생성 문서의 버전·diff, 독립 판정과 반려 사유를 보존한다.

**재사용.** 결과 스키마·처분 대조기·누적 예산 검사·자산 검증·요구사항/작업 변환·문서 diff·회귀 사례를 재사용 후보로 남긴다. P33의 합성 입력 회차는 다른 P 실험의 완료를 기다리지 않고 실행할 수 있다. 실제 최종 스프린트 발행에는 5.6절의 대상 범위 실측 결과와 독립 검토가 필요하다.

**추가 회차 · v1.2 실행 번호와 진척 집계.** 76개 작업 장부와 분할된 P/S 참조를 합성 입력으로 준다. 정상 초기 0/76, 작업별 검수·실험 평가의 다른 결과, P12/P19/P20/P22/P23/P24/P26/P27/P28/P33의 부분 범위, S0~S3 중복 추가, P15 성공 집계, 같은 재시험의 중복 작업, 기준선 변경 없는 분모 수정, 근거 없는 동일 공수 가중률·예정일을 각각 대조한다. 미해결 필수 기능을 남긴 채 평가를 종료한 입력도 포함한다. 번호·분모·종류별 인수·기능/전환 상태·다음 작업이 독립 기대값과 일치하고, 범위 밖/중복 번호·필수 증거 없는 인수·과거 결과 덮어쓰기가 각 0건이어야 한다. 실제 연결 회차는 11-03에서 원본 보고·자산·장부 버전으로 다시 수행한다.

## 4. 도그푸딩 부트스트랩과 첫 스프린트

도그푸딩은 **코디네이터의 검증된 실행본이 그 코디네이터의 다음 변경을 실제로 조율하는 것**이다. 최초 실행본의 제작과 검증은 고정된 외부 절차가 맡는다. 이후에도 새 후보의 증거와 승격은 실행 중인 후보 밖에서 확인한다.

S0에 사용할 후보는 T06에서 만든다. 공통 개발·Guardrail 이미지는 해당 범위의 P25·P22를, 공통 CI와 GitHub 설정은 P23을 먼저 통과한 버전을 쓴다. 이러한 선행 증거를 확보하는 작업은 S0의 외부 부트스트랩에 포함한다. S0 완료를 그 선행 시험들의 착수 조건으로 요구하지 않는다. S0에 사용하는 문서·이미지·CI는 최소 적용 범위로 먼저 검증할 수 있으며, 모든 언어·제품·연구 범위의 준비가 끝나기를 기다릴 필요는 없다. S0 수용에는 P21의 사용할 책임 이전, P28의 최소 후속/외부 감시, P12의 최소 보고·현황 이해도 증거도 포함한다.

| 단계 | 실행 방법 | 다음 단계로 가는 조건 |
| --- | --- | --- |
| S0 · 씨앗 버전 | 테스트용 repo와 보호된 기준을 준비한다. 외부 CI와 별도 Guardrail로 Rust v0의 기동·문서 접수·배정·DB·체크포인트·보고·후속·외부 감시를 검증한다. | P02~P08·P13 및 사용할 P21·P28·P12의 최소 범위를 통과한다. 이미지 digest·설정·복귀 절차를 고정한다. 운영 NPG는 이 단계의 시험만으로 정지하지 않는다. |
| S1 · 자기 repo에서 한 건 | 고정 v0에 아래 스프린트 문서를 넣는다. 개발 에이전트와 Guardrail이 별도 작업공간에서 v1의 구현과 검토를 수행한다. v0는 스프린트를 조율한다. 새 후보를 GHCR에 게시하고 digest로 고정해 격리된 컨테이너 시험 환경에서 실행한다. Kubernetes에서의 검증은 S3에서 수행한다. | P17이 통과한다. v1의 필수 CI·독립 검토·수신 기록이 현재 문서·SHA·이미지에 연결된다. |
| S2 · 후보 전환과 다음 회차 | 별도 승격 권한자가 검증된 digest를 시험 환경에 지정한다. 한 회차에서 쓰기 권한을 가진 코디네이터를 하나로 유지한다. 문제가 발생하면 배정을 멈추고 검증된 직전 버전 또는 외부 절차로 복귀한 뒤 상태를 대조한다. | P18과 P19의 게시·digest 확인 조건을 통과한다. 승격·복귀 경로가 재현되고 현재 실행본이 다음 작업 한 건을 안전하게 인수한다. |
| S3 · Kubernetes에서 검증층 연결 | S1~S2의 역할 경계를 유지하고 코디네이터와 에이전트를 시험 클러스터로 옮긴다. 노드 관측기는 별도 배치한다. 코디네이터 제품 후보 Pod를 대상으로 P09·P10을 적용하고, 개발 에이전트 Pod의 정책 시험은 별도 회차로 실행한다. | 코드 검증과 실행 증거를 함께 요구한 P14와 GHCR digest를 고정한 Kubernetes 검증·승격 시험 P19가 통과한다. 적용 실패·관측 누락·정책 위반이 완료로 처리되는 건 0건이다. |

**S1 제출용 작업 문서 초안 · DF-01**

| 필드 | 값 |
| --- | --- |
| 목표 | 코디네이터의 운영 보고에 현재 적용 문서 버전과 검토 대상 SHA를 표시해 수신자가 어느 작업 결과인지 확인할 수 있게 한다. |
| 대상과 범위 | 코디네이터의 보고 생성 코드와 필요한 검증. 권한·승격 경로·공통 검증 기준의 변경은 별도 작업으로 분리한다. |
| 입력 | 승인된 DF-01 문서 v1, 고정 v0 digest, 테스트 repo의 기준 커밋, 승인 검사 프로파일, 테스트 수신기. |
| 수용 기준 | 정상 완료 보고에 문서 버전과 SHA가 실제 증거와 일치한다. 이전 SHA의 승인이나 증거가 빠진 후보에 대한 완료 보고 0건. 재시작 뒤 테스트 수신기 수신 1건. 현재 SHA의 필수 CI와 독립 Guardrail 승인 확인. |
| 증거 | 적용 문서·배정·복구 이력, 후보 PR과 SHA, CI 및 독립 판정, 기대 보고와 실제 수신 기록. |
| 종료 | v0가 시험 채널에서 완료를 보고한다. v1의 실행본 승격은 별도 절차에서 판정하고, 완료 보고와 별도 사건으로 남긴다. |

외부 실행 절차에는 고정 v0 시작, 후보 이미지 빌드와 실행, 장애 주입, 외부 DB·GitHub·수신기 대조, 종료·복귀 방법을 포함한다. S0의 첫 변경에서 환경별 명령과 권한을 고정하고, S1 입력에 버전을 적는다. 후보 코드는 쓰기 권한이 있는 릴리즈 실행기와 작업공간·자격 증명을 분리한다. DB 스키마가 달라지는 회차에는 직전 실행본 호환성 또는 별도 복구를 먼저 시험하고, 외부 요청과 보고를 대조한 뒤 쓰기를 재개한다. [GitHub Actions 보안 사용 지침](https://docs.github.com/en/actions/reference/security/secure-use)

### 5.3 재사용할 구현과 다음 작업

T03의 실행·증거 수집·대조·계측, T06의 배정·수정·재검증 연결은 공통 모듈로 구현하고 저장소·언어·정책 값은 버전이 있는 설정·문서로 분리한다. 문서 변형, 오류 주입과 고정 기대값은 회귀 검증 자산으로 보존한다. 각 실험 결과에 재사용할 모듈·버전, 통과한 범위, 운영 전 보완점과 다음 작업의 착수 조건을 연결한다. 초기 자료 준비와 검증을 다음 개발에서 재사용할 수 있도록 입력·출력·증거 형식도 함께 고정한다.

**모듈별 자산 목록.** 실험용 서버·오류 주입·고정 기대값은 제품 실행 모듈과 분리한다. 재사용 가능한 자산은 실행 코드, 설정·정책 문서, 이미지/워크플로 템플릿, 평가 자료·회귀 테스트로 구분한다. 공통 코드의 입력·출력·오류·설정 계약을 고정하고, repo·언어·자격·운영 주소를 공통 로직에 숨겨 넣지 않는다.

| 자산 ID·종류 | 경로·commit/digest·출처/이용 조건 | 입출력 계약·의존 버전 | 검증 범위·실행 증거 | 재사용 상태·대상 | 남은 보완·스프린트 작업 ID |
| --- | --- | --- | --- | --- | --- |
| — | — | — | — | — | — |

재사용 상태는 `후보/검증됨/편입 대기/편입됨/보존 전용`으로 표시한다. 검증됨에는 어느 범위의 증거인지 붙이고, 대상 repo·역할·설정·이미지로의 통합 검증은 별도 편입 작업으로 남긴다. 공개 원본 코드의 이용 조건과 의존성은 T07 결과에 연결하고, 직접 구현한 공통 모듈도 출처·버전과 검증 범위를 기록한다.

실험 방안이 기각돼도 독립적으로 유효한 계측기·실행기·오류 주입·회귀 사례는 재사용할 수 있다. 해당 모듈의 정상·실패 입력, 계약, 대상 환경에서 필요한 통합 검증이 근거다. 방안 기각만으로 모듈을 폐기하지 않고, 코드가 존재하거나 과거에 한 번 실행됐다는 이유만으로 검증됨으로 올리지 않는다. 목표 환경에서 권한·복구·성능 등 추가 검증이 필요한 범위는 운영 전 보완 작업으로 명시한다.

### 5.5 연구 방법의 착수·조합·편입 순서

1. **현재 기준 준비.** T01~T03·P25로 사람이 검증한 작은 초기 카탈로그와 독립 채점기를 먼저 고정한다. T05의 필요한 격리 환경을 준비한다.
2. **원본과 자료 준비.** T07은 R01~R04별로 실행 경로·어댑터·제약을 확인한다. T08은 실제 또는 표시된 모의 기록과 분리 평가 자료를 준비한다. 이 단계는 대체 핵심 구현과 독립적으로 진행할 수 있다.
3. **단독 가능성·효과 검증.** P29·P30·P31·P32를 각각 현재 기준과 비교한다. 권장 착수는 작은 계약 검사가 가능한 P32와 기록 자료를 쓰는 P30부터지만, 서로의 통과를 필수로 요구하지 않는다. 각 방법의 최소 실행과 효과 채택을 따로 판정한다.
4. **선택한 조합의 추가 회차.** 예를 들어 P30의 기록 기반 스킬 생성→P31의 제한된 수정→P32의 라이브러리 검증을 적용하는 조합과, P29의 실행 지침 개선을 추가한 조합을 새 설정으로 고정한다. 채택한 방법만 포함하고 각 단계의 버전·효과·비용을 남긴다. 단독 효과를 그대로 합산하지 않는다. 조합 실패는 다른 단독 통과를 지우지 않고 해당 조합을 보류한다.
5. **새 버전으로 재검증·편입.** 통과 후보는 P25[새 버전]부터 필요한 이미지·CI·새 repo 활용 회차로 이어간다. 운영 편입은 별도 검토·승격으로 판정하고, 미채택이면 현재 검증본을 계속 쓴다.

P29~P32 전체 통과를 NPG 대체나 초기 카탈로그 사용의 조건으로 걸지 않는다. 연구 실험에 배정할 예산과 도입 우선순위는 T01에서 정하고, 유효한 개선이 없거나 비용이 초과하면 보류·기각할 수 있다.

### 5.6 실험 보고에서 최종 개발 스프린트로 연결

최종 개발 스프린트는 대상 범위의 **요구사항 → 실험 증거 → 도입 결정 → 재사용 자산 → 남은 작업 → 수용 기준**을 연결한 버전 문서다. 4절의 S0~S3는 실험을 실행할 부트스트랩 경로이며, 이 절은 그 결과로 이후 제품 개발 범위를 확정하는 절차다. 모든 선택적 연구가 끝날 때까지 기다리지 않고, 승인된 목표 중 증거와 의존이 준비된 범위부터 문서화할 수 있다.

1. **판정 입력 고정.** T01 요구사항 기준, 대상 실험의 원본 결과·2.3절 처분표, 5.3절 자산 목록, 미해결·추가 실험 계획과 적용 문서/이미지 버전을 한 묶음으로 고정한다. 채택된 결과만 모으지 않고 대상 범위의 실패·중단·기각·보류도 포함한다.
2. **목표별 공백 대조.** 필수 목표마다 검증된 접근, 재사용 자산, 남은 구현 또는 선행 실험이 연결되는지 확인한다. 선택적 기각은 도입 범위에서 제외하고 이유를 남긴다. 필수 목표의 방법이 미정이면 대안/추가 실험을 앞단에 두고 해당 구현 작업은 조건 대기로 둔다.
3. **작업과 순서 작성.** 재사용 코드의 제품화·통합·회귀 검증, 새로 필요한 구현, 추가 실험·대안 검증을 서로 다른 작업으로 만든다. 선행 작업·담당 역할·입력 버전·수용 기준·증거·복귀 조건을 붙이고 누락·순환·중복을 검사한다. 보류/기각 후보를 편입 확정 작업으로 바꾸지 않는다.
4. **공수와 종료 목표 산정.** PoC에서 이미 끝낸 작업과 이후 남은 작업을 구분한다. 실측 시간·토큰·반복 횟수는 근거로 연결하고, 통합·추가 구현·재검증·전환 공수는 추정 범위와 가정을 밝힌다. 코드 재사용량을 이유로 추가 검증 비용을 0으로 두거나 준비 비용을 중복 합산하지 않는다. 근거가 부족한 항목은 일정 확정 대신 선행 조사로 둔다.
5. **독립 검토와 발행.** P33에서 검증한 변환기로 초안을 만들고, 독립 담당자가 원본 결과와 요구사항·작업 대응을 다시 대조한다. 초안 생성·독립 검토·승인·실행은 별도 상태로 기록한다. 승인 주체와 위임 범위에 따라 발행하고, 발행 이후 배정·인수·후속 처리는 P28의 계약을 따른다.

| 목표 ID·필수/선택 | 근거 실험·회차·처분 | 채택 범위·재사용 자산 버전 | 남은 제품화/신규 구현/추가 실험 | 스프린트 작업 ID·선행 | 수용 기준·검증 증거 |
| --- | --- | --- | --- | --- | --- |
| — | — | — | — | — | — |

스프린트 작업에는 위 대응표와 함께 담당 역할, 공수 범위·산정 근거, 착수 가능/조건 대기, 실패 시 처분·재개 조건을 기록한다. 보류 목록에는 원인·담당·재확인 기한·재개 신호를, 기각 목록에는 근거·유지할 자산·대체 여부를 남긴다. 예산·반복 한도는 원 요구사항과 연결해 후속 스프린트로 이월해도 추적한다.

**발행과 완료의 기준.** 필수 목표 누락, 근거 없는 채택/재사용, 미해결 선행 또는 순환이 있으면 해당 범위를 착수 가능으로 발행하지 않는다. 미해결의 조사·재시험 작업을 포함한 검토용 초안은 만들 수 있고, 의존하지 않는 준비된 범위는 별도 스프린트로 진행할 수 있다. 실험 묶음을 처분하고 보고한 것과 제품 목표를 달성한 것은 별도다. 후자는 필수 수용 기준의 실제 충족이 필요하다. 목표·기준 변경은 기존 위임 범위를 확인하고 별도 승인이 필요한 경우 그 결정과 버전을 남긴다.

**변경의 환류.** 새 실험 결과·정책·코드가 기존 처분을 바꾸면 원 보고와 이전 스프린트 버전을 보존한 채 영향받는 목표·자산·작업을 대조하고 새 문서 버전을 만든다. 실행 중 작업에는 P02의 문서 변경 대조를 적용하며 오래된 승인으로 계속 진행하지 않는다. 동일 입력·버전의 재변환은 같은 작업 ID를 재사용하고, 원본 변경 시 diff·재검증 범위를 제시한다. 결과 처분부터 최종 스프린트까지의 이 연결을 P33에서 별도로 검증한다.

### 5.7 실행 스프린트 목록의 적용

앞쪽 진척표와 9절은 T/P/S 계약을 실행·보고할 단위를 고정한다. 기존 5.2절은 기술 실험의 선행, 9절은 해당 범위의 구현·준비·검수 작업의 선행이다. 둘을 함께 적용하고 번호 순서만으로 선행 증거를 생략하지 않는다. 같은 T06 구현을 여러 기능 작업으로 나눠도 그 후보의 기동과 P 실험의 계약 PASS는 구분한다. 76개 작업의 검수 여부와 32개 실험 평가 종료·필수 기능/전환을 별도로 보고한다.

9절의 작업 선행은 기본 단일 실행의 준비 순서이며, 06의 C 기능 부분 통과, 07의 신규 셋업 표본, 10의 P30 후보 선택처럼 문장으로 표시한 조건부 범위는 별도 증거를 소비한다. 후보 제작→새 버전 준비 검증→그 후보의 효과 평가를 단계로 나눠 기존 실험 전체에 역방향 의존을 만들지 않는다. 작업/후보 버전이 바뀌면 P02·P33으로 영향받는 범위와 집계를 대조한다.

## 6. 독립 검토자에게 전달할 질문

1. **타당성.** 각 가설을 절차와 대조군으로 반증할 수 있는가? 같은 입력으로 다시 실행했을 때 판정이 일치하는가?
2. **논리.** 현재 문서·SHA·이미지·정책과 증거가 올바르게 연결되는가? GitHub 이벤트와 최종 상태, 관측과 차단, 완료와 전달, 컴파일러 검증과 업무 정책 검증이 각각 구분되는가?
3. **구현 이득.** 추가 층이 실제로 새 결함을 찾거나 위험을 줄이는가? Rust 자체의 이득과 eBPF 계측의 이득, 직접 관측기를 유지할 비용을 각각 비교할 수 있는가?
4. **반례.** 잘못된 통과나 영구 정지를 만들 수 있는 입력이 남는가? 중요도, 재현 절차, 기대값·실측값, 영향을 받는 실험 ID와 수정 제안을 남겨 달라.
5. **도그푸딩.** 씨앗 버전의 외부 검증과 자기 repo의 실제 변경을 구분할 수 있는가? 후보가 검사 설정·권한·승격을 스스로 바꾸는 경로가 남는가? GHCR에 게시한 후보와 실제 검증·롤아웃의 이미지가 동일한가?

6. **신규 저장소 적용.** 사용자가 세부 시험 옵션을 알려주지 않아도 새 에이전트가 첫 셋업과 첫 PR의 필수 기준을 적용하는가? 카탈로그가 선택 비용을 줄이는 효과와 완료 판정이 누락을 차단하는 효과를 각각 관측할 수 있는가?

7. **기존 정책 이전.** NPG의 지침 전달, 실제 인수, 코드 강제가 각각 검증되는가? 원본의 보호 동작과 정상 처리 경로가 보존되며, NPG 전용 제약이 승인된 저장소에만 적용되는가?

8. **공통 개발·검증 이미지.** 여러 저장소에서 같은 기준을 재현하면서 역할별 작업공간과 권한을 분리하는가? 통합 이미지와 언어별 파생 이미지의 비용을 같은 품질과 실행 조건으로 비교하는가?

9. **GitHub Actions 결과와 저장소 설정.** 같은 필수 테스트 경로의 정상·실패 대조를 실제 실행했는가? 실패 무시, 필수 증거 누락, 이전 SHA, 후보의 같은 이름 체크를 잡는가? 대상 브랜치에 승인 설정이 실제로 적용되어 있으며, 설정이 달라지면 자동 병합이 보류되는가?

10. **내장 정책을 사용하는 자동 셋업.** 한 번의 시작 요청으로 문서를 읽고, 설정하고, 독립적으로 시험하고, 발견한 문제를 수정·재검증하는가? 권한·근거·교정 한도를 넘는 경우 정확히 보류하는가?

11. **자료의 충실도와 선행 관계.** 카탈로그를 채우는 T02와 내용의 정확성·충실도를 검증하는 P25가 분리돼 있는가? 필수 목록과 기대값이 카탈로그 밖의 기준에 근거하는가? 각 후속 실험은 필요한 범위·버전의 선행 증거를 받고 시작하며, 의존관계에 순환이나 준비 부족을 활용 실패로 오인하는 경로가 없는가? 작성·준비 비용과 반복 사용의 비용을 함께 설명하는가?

12. **대체와 진행.** Notion 쓰기 제거와 책임 이전이 일관되는가? 실제 main CI·후속 인수·한도 해소 재개·timeout·외부 감시가 빠지지 않았는가? 모든 작업 보류가 자동화 충분성 통과로 처리되는 경로가 없는가?

13. **표본과 실제 전환.** P26의 분모·난도·사람 문서 작성/개입 비용이 적절한가? 시험 범위 산출과 제품 병합을 구분하며 P27-R을 실제 전환으로 오인하지 않는가? 기존 보호를 끄기 전에 새 경로·복귀가 준비되는가?

14. **네 연구의 가능성.** R01~R04의 원 방법·제공 코드·Console 적응·직접 재구현이 구분되는가? T07~T08→P29~P32→새 버전 준비 검증의 선행관계가 맞는가? 필요한 실행·인증·데이터 어댑터 공백을 가정으로 숨기지 않았는가?

15. **효과와 비용.** 고정 카탈로그 활용과 기록 기반 개선을 구분하는가? 동일 예산의 대조군, 숨긴 평가·출처, 후보 생성·거부·준비 비용을 포함한 결과표가 도입·보류를 판단하기에 충분한가? 개별 효과를 조합 효과로 잘못 더하지 않는가?

16. **결과 처분과 추가 실험.** PASS/FAIL/INCONCLUSIVE와 채택/보류/기각이 분리되는가? 의도적 결함의 차단을 실패로 오해하지 않는가? 필수 기능의 미해결, 선택적 방법의 기각, 부분 채택·조합 실패를 올바른 범위에 한정하는가? 추가 실험의 가설·담당·재개 조건·누적 상한이 있어 무한 반복과 영구 대기를 피하는가?

17. **코드 재사용.** 모듈별 경로·버전·출처·계약·검증 범위를 근거로 재사용 여부를 판단할 수 있는가? 기각된 방안의 유효한 공통 자산을 보존하면서, 확인하지 않은 코드를 편입 완료로 표시하는 경로를 막는가? 제품 실행 코드와 오류 주입·정답 자료의 경계가 유지되는가?

## 9. 실행 작업 목록과 인수 기준

이 절의 고정 목록이 실행·진척 집계의 단위다. 원 1~8절은 역할·계약·실험·의존·결과 처분의 상세 근거이며, 9절의 짧은 설명이 원 실험의 필수 사례나 기준을 생략하는 허가는 아니다. 한 원 실험이 여러 작업으로 나뉘면 필요한 모든 범위가 끝나야 그 실험의 평가 종료를 1건 인정한다. 5.2절 원 실험의 선행도 이번 작업이 쓰는 범위·버전에 적용한다.

**공통 담당:** 설계/준비/구현은 해당 개발 담당이 산출물을 만들고 독립 Guardrail/외부 담당이 인수한다. 검증은 독립 Guardrail 또는 외부 검증 실행기, 평가는 독립 평가 담당, 종합은 코디네이터/보고 작성 담당과 독립 검토 담당이 맡는다. 실제 주체·자격·작업공간·모델·검토 SHA는 01에서 고정하며, 작성자가 자기 결과를 단독 승인하지 않는다. 이 목록은 역할 배정의 계획이며 실제 세션을 기동한 기록이 아니다.

**각 작업의 장부:** 번호·상태·담당·입력 버전·실제 산출물 경로/commit·검수 증거·판정일·남은 공수·대기 원인/재개 조건을 유지한다. 초기 상태는 전부 미착수다. 아래 수량은 작업당 독립 인수 결과 한 건이며 테스트 건수·파일 수·프롬프트 수가 아니다. 작업 공수·기간은 전부 미산정이고, 01의 범위 고정 및 02의 실제 기록에서 근거를 얻어 별도 기준선으로 정한다.
