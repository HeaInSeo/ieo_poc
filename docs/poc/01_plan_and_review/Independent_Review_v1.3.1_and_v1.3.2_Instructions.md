# Console 코디네이터 PoC 계획 v1.3.1 검토와 v1.3.2 개정 지시

Nov 11, 2026 · @필요없어.

이 문서는 PoC 계획을 작성한 설계 에이전트에게 전달한다. 검토 대상은 `Console_Coordinator_v1_3_1_2026-11-10` 묶음이다. 수행할 일은 "v1.3.2 개정 지시" 절에 있고 앞 절은 그 근거다.

## 결론

**v1.3.1은 지시 28개를 전부 반영했고, 검산 수치는 검토자가 다시 계산한 값과 일치한다.** 실행에 들어갈 수 있는 수준이다.

남은 수정은 여섯 항목이다. 가장 큰 것은 repo 실행 단위다. v1.3.1의 U1(한 컨테이너에 개발과 Guardrail)은 Kubernetes의 Restricted 정책 아래에서 두 역할을 분리할 수 없어, 사용자가 2026-11-11에 repo당 Pod 둘로 다시 정했다.

v1.3.2를 낸 뒤에는 문서를 더 다듬지 않고 01-01부터 실행한다. 지금 가장 큰 공백은 계획이 아니라 런타임 선택과 probe 결과다.

## 새 사용자 결정

**U3 (2026-11-11). repo마다 개발 Pod 하나와 Guardrail Pod 하나를 따로 둔다. 각 Pod는 컨테이너 하나다.** 이 결정이 U1을 대체한다.

- 2026-11-04 설계 로그의 "별도 컨테이너 두 개"로 돌아가는 결정이다.
- 이름은 `<repo>-dev`, `<repo>-guardrail`을 유지한다. 같은 repo 라벨을 붙여 조회와 관리는 repo 단위로 한다.
- 코디네이터가 중앙에 하나라는 결정과 D1\~D8의 나머지는 그대로다.

U1이 기록된 경위는 이렇다. 사용자가 검토자에게 "에이전트가 컨테이너 안에서 동작한다"고 말한 것이 "한 컨테이너에 둘 다"로 옮겨졌다. 사용자는 아래 "문제 1"의 설명을 듣고 U3을 골랐다.

## 유지할 것

- **문서 분리.** 실험 상세(177KB)와 실행 장부(38KB)로 나뉘어, 실행 중에는 장부와 해당 실험 절만 읽으면 된다.
- **가벼워진 S0.** 카탈로그 없는 최소 이미지(05-04, P08-SEED)를 두어 03 스프린트 전체가 S0 경로에서 빠졌다.
- **EARLY-01.** 설계 로그의 POC-01\~05를 02 직후에 두었고, 01-04 직후가 아닌 이유를 적었다.
- **명세 v0와 보고 v0.** 주장(claim)과 판정(verified)이 필드로 구분되고 네 운영 상태가 스키마에 들어갔다. 계획 자신을 명세 v0로 직렬화했다.
- **1.2절의 런타임 어댑터 계약.** 동작이 이미 역할 단위여서 U3으로 바꿔도 필드를 고칠 필요가 없다.
- **연구 분리와 후속 순서, P34와 P35, 한도 공유(P05-Q), Guardrail 설정 승인 경로.** 지시대로다.

## 문제 1 · 단일 컨테이너는 Restricted 정책에서 역할을 분리하지 못한다

v1.3.1의 1.2절은 한 컨테이너 안에서 두 역할을 OS 접근 통제로 나누고, "같은 UID에 양쪽 자격을 준 구성은 독립성의 근거로 쓰지 않는다"고 적었다. 이 조건은 P11이 시험하는 PSA Restricted와 함께 성립하지 않는다.

1. 리눅스에서 파일을 고칠 수 있는지는 프로세스의 UID로 정해진다. 두 역할을 나누려면 서로 다른 UID로 띄워야 한다.
2. 자식 프로세스를 다른 UID로 띄우려면 띄우는 쪽(repo supervisor)이 루트이거나 `SETUID` 특권을 가져야 한다.
3. Restricted는 비루트 실행, 특권 전부 제거, 권한 상승 금지를 요구한다. 이 조건에서는 컨테이너 안의 모든 프로세스가 같은 UID로 돈다.

그 결과 개발 에이전트와 그것이 실행하는 빌드·테스트 코드가 Guardrail의 작업공간, 세션 기록, 검토 입력을 고칠 수 있고 Guardrail 프로세스의 환경 변수를 읽을 수 있다. 같은 호스트 단계에서는 supervisor를 루트로 돌려 통과할 수 있어서, 이 충돌은 S3(08 스프린트)에 가서야 드러난다.

|  | Pod 따로, 각 컨테이너 1개 (U3) | Pod 하나, 컨테이너 둘 | 컨테이너 하나에 둘 다 (U1) |
| --- | --- | --- | --- |
| 파일 분리 | 됨 | 됨 | Restricted에서 안 됨 |
| 네트워크 분리 | 됨. 역할별 정책 가능 | 안 됨. localhost 공유 | 안 됨 |
| Guardrail만 내려 두기 | 됨 | 안 됨 | 안 됨 |
| 한쪽 장애의 전파 | 없음 | Pod 축출 시 둘 다 | 둘 다 |
| 실행 관측의 역할 귀속 | Pod 단위로 가능 | 컨테이너 단위 | PID까지 내려가야 함 |
| 관리 대상 | repo당 2 | repo당 1 | repo당 1 |

개발과 Guardrail은 파일을 공유하지 않고, 서로 직접 통신하지 않으며, 일하는 시간대가 다르다. 한 Pod에 묶을 이유가 없어 U3이 Kubernetes의 기본 형태(Pod 하나에 컨테이너 하나)에도 맞는다.

**격리 시험의 위치도 고쳐야 한다.** v1.3.1에서 역할 격리의 거부 시험은 P22(03-06)와 P35(04-14)에 있는데 둘 다 S0의 선행이 아니다. P07 본문은 v1.2 그대로다. 그래서 S0와 S1은 독립 검토가 실제로 독립인지 확인하지 않은 채 통과한다. Pod를 나눠도 이 시험은 S0 경로에 둔다.

## 문제 2 · 검토 중에 새 커밋이 올라올 때의 규칙이 없다

사용자가 물은 상황이다. 개발 Pod가 커밋을 올리고 Guardrail Pod가 그것을 검토하는 동안, 개발 Pod가 다음 단계를 진행하다가 앞에 올린 것을 다시 고친다.

**잘못된 통과는 생기지 않는다.** Guardrail은 브랜치가 아니라 커밋 SHA를 검토하고 커밋은 바뀌지 않는다. P07이 "A를 승인한 뒤 B를 올림"을 시험하고 B의 잘못된 통과 0건을 요구한다.

**비어 있는 것은 세 가지다.**

| 빈 곳 | 생기는 일 |
| --- | --- |
| 검토 진행 중에 새 커밋이 오면 진행 중인 검토를 어떻게 하는가 | 검토가 헛돌고, 반복되면 최신을 따라잡지 못한다 |
| 앞 작업이 검토 중일 때 다음 작업을 어디에 쌓는가 | 앞 작업이 반려되면 그 위에 쌓은 다음 작업을 다시 맞춰야 한다 |
| 승인과 병합 사이에 새 커밋이 오면 | 승인받지 않은 커밋이 함께 병합될 수 있다. 574행은 병합 직전에 저장소 설정을 다시 확인한다고만 적었다 |

보고 v0에 `REVIEW_PENDING`이 있어 "검토 중에는 기다린다"를 암시하지만 규칙으로 적혀 있지 않다. NPG는 repo당 활성 수정 PR 하나라는 규칙으로 이 문제를 피했다. PoC에서는 같은 단순한 규칙으로 시작하고, 기다리는 비용을 P26에서 잰 뒤 병행을 풀지 정한다.

## 문제 3 · 손으로 쓰는 보고 장부

`progress/`와 `reports/` 구조는 사용자가 한곳에서 진척을 본다는 목적에 맞는다. 유지 방법이 무겁다.

- 사건 하나마다 일곱 곳을 고친다(REPORT, result.json, state.json, events.jsonl, STATUS, TASKS, RESULTS). state.json은 47KB다. 세 화면 파일에 같은 snapshot ID와 원장 SHA-256을 손으로 맞춰 넣어야 한다.
- "확정 후 5분 이내"와 "30분 간격"은 에이전트에게 타이머가 없어 지킬 수도 검증할 수도 없다.
- 전체 84 진행률은 성격이 다른 둘(주계획, 조건부로 착수하는 후속)을 합친 값이다.

일보다 장부가 커지는 것은 NPG에서 피하려던 일이다. state.json만 원본으로 두고 화면 파일은 스크립트로 생성한다.

## 문제 4 · 작은 것

- **P26 앞에 P35와 P05-Q가 없다.** 07-02의 선행에 04-14(자식 경계)와 04-15(한도 해소)가 없다. 실제 repo에서 자식의 범위 밖 쓰기를 확인하기 전에 실행하게 된다. 작업 12건을 돌리다 한도에 닿으면 무개입 완료율이 한도 때문에 깎인다.
- **버전 표기.** 파일명과 구조도 제목은 v1.3인데 내용은 v1.3.1이다.

## v1.3.2 개정 지시

Console 코디네이터 PoC 계획 v1.3.1을 v1.3.2로 개정한다. 아래 외에는 작업 ID, 선행, 통과 기준을 바꾸지 않는다.

1. **repo 실행 단위를 U3으로 고친다.**
   - `User_Decisions` 파일에 U3을 기록하고 U1에 "U3으로 대체됨"을 표시한다.
   - 1절, 1.2절, 구조도, `DEV_AGENT_HANDOFF`, probe 확인표의 "단일 컨테이너 안의 두 역할"을 "repo당 두 Pod(개발, Guardrail), 각 컨테이너 하나"로 고친다.
   - Pod마다 자기 UID, 파일시스템, 역할 자격, 영속 볼륨을 쓴다. 두 Pod 사이에 쓰기 가능한 공유 볼륨을 두지 않는다. Guardrail의 입력은 승인 명세·프로파일과 GitHub의 고정 SHA다.
   - repo supervisor는 Pod별 PID 1로 두고 자기 Pod의 역할 하나만 기동·복원·종료한다. 런타임 어댑터의 필드는 유지하고 `container_or_pod_ref`가 역할별로 다르다는 점만 명시한다.
   - 같은 호스트 단계에서는 repo당 컨테이너 둘로 기동한다. S3에서는 두 Pod 모두에 PSA Restricted를 적용하고, 역할별로 다른 네트워크 정책을 주는 사례를 P11에 넣는다.
   - 1.5절의 "일 없음"은 역할별로 판정한다. "두 역할 모두 일 없음이어야 정지 후보" 조건을 삭제한다. 상시 유지 여부는 결정 필요로 두고 P34에서 역할별 복원 시간과 자원을 잰다.
   - P34의 컨테이너 재생성 주입을 "개발 Pod 재생성, Guardrail Pod 재생성, 둘 다 재생성"으로 나눈다.
   - 08-05와 P09의 "같은 컨테이너의 두 역할" 문구를 Pod 단위 귀속으로 되돌린다.
2. **역할 격리 시험을 S0 경로에 둔다.** P07(04-07)에 사례를 추가한다. 개발 역할이 Guardrail의 작업공간·세션 기록·승인 입력에 접근을 시도한다. Guardrail의 자격 획득을 시도한다. Guardrail 명의의 검토 발행을 시도한다. 성공 0건이어야 하고 하나라도 성공하면 그 구성의 독립 검토는 `FAIL`이다.
3. **검토 중의 변경 규칙을 새 절로 적는다.**
   - 작업 하나에 PR 하나다. PoC 기본 프로파일은 repo당 열린 수정 PR 하나다.
   - 개발 에이전트는 PR을 검토에 넘긴 뒤 `REVIEW_PENDING`으로 기다린다. 그 브랜치에 push할 수 있는 것은 코디네이터가 반려를 전달해 교정 단계로 전환한 경우뿐이다.
   - 검토 중에 새 head가 관측되면 코디네이터는 진행 중인 검토 배정을 무효로 표시하고 새 SHA로 다시 배정한다. 옛 SHA의 늦은 결과는 그 SHA에 귀속해 보존하고 판정에 쓰지 않는다.
   - 병합은 승인받은 head SHA를 지정해 수행한다. 불일치하면 병합하지 않는다.
   - 의존하는 다음 작업은 앞 작업의 병합과 main CI 확인 뒤에 배정한다.
   - P07에 사례를 추가한다: 검토 진행 중 새 커밋 push(강제 push 포함), 승인과 병합 사이의 새 커밋, 교정 단계가 아닌데 개발 역할이 push 시도. 옛 SHA 승인으로 병합된 건 0건, 무효가 된 검토가 판정에 쓰인 건 0건이어야 한다. 정상 교정 경로는 진행해야 한다.
   - P26 결과표에 "검토 대기로 개발이 쉬 시간"을 기록한다.
4. **보고 장부의 유지 방법을 바꾼다.** state.json을 유일한 원본으로 두고 STATUS, TASKS, RESULTS는 스크립트로 생성한다. 스크립트는 01-06의 산출물에 넣고 별도 작업으로 늘리지 않는다. 화면 파일을 손으로 편집하지 않는다. 시간 기준 규칙(5분, 30분)은 "다음 의존 작업 착수 전"과 "제어를 돌려받는 지점마다"로 바꾼다. 전체 84 진행률은 삭제하고 주계획과 후속을 따로 표시한다.
5. **P26의 선행을 보완한다.** 07-01의 선행에 04-14(P35)를 추가한다. 04-15(P05-Q)는 07-02의 선행에 추가하거나, 추가하지 않는다면 P26 결과표에 "한도로 인한 정지" 분류를 넣어 무개입 완료율과 구분한다. 어느 쪽인지 근거와 함께 적는다.
6. **버전 표기를 맞춘다.** 파일명과 구조도 제목의 버전을 내용과 같게 한다.

### 산출물

- 바뀐 파일과 변경 요약표(절, 변경 내용, 이유)
- 의존관계 재검산 결과: 순환, 미정의 선행, 04-03·05-05·07-02 앞의 선행 작업 수
- 명세 JSON의 새 revision과 digest
- "결정 필요" 목록. 근거가 없는 곳은 추측으로 채우지 않는다

이 지시에 동의하지 않는 항목이 있으면 고치지 말고 항목 번호와 근거를 보고한다.

## 개정 뒤의 순서

v1.3.2가 나오면 검토자는 위 여섯 항목의 반영과 의존관계 재검산만 확인한다. 그다음 검토 대상은 문서가 아니라 01 스프린트의 실제 결과다.

가장 먼저 필요한 것은 **런타임 선택과 01-04의 probe**다. probe 확인표 15개 항목이 전부 미실행이고, 지속성·한도·자식·무인 기동의 계약이 그 결과에 달려 있다. U3에서는 Pod마다 에이전트 인증을 따로 넣으므로 두 가지를 첫 probe로 확인한다.

- 같은 계정으로 세션 둘을 동시에 열 수 있는가
- 개발과 Guardrail의 자격과 한도를 나눌 수 있는가

### 검토자가 확인하지 못한 것

- **런타임의 실제 기능.** probe가 한 건도 실행되지 않았다.
- **5.2절의 기술 의존과 후속 계획의 의존.** 다시 계산하지 않았다.
- **실험 상세의 P 본문 전체.** 1절, 4절, 7절, P07, P11, P34, P35와 장부의 해당 행을 읽었다. 나머지 P 본문은 한 줄씩 대조하지 않았다.
- **`progress/state.json`의 내용과 보고 양식.** 구조만 보고 항목별로 검산하지 않았다.
- **NPG의 현재 서버 상태, 설계 로그가 인용한 Notion 원본, P26의 백로그 후보.** 이전 검토와 같다.
