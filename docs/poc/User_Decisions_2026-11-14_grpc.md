# 사용자 결정 2026-11-14 · 내부 통신 gRPC 기준과 CNI 독립 검증

사용자 지시의 요지를 원문 표현대로 옮긴다. 이 결정을 계획에 연결한 내용은 [gRPC 내부 API 계획 v0](Plan_gRPC_Internal_API_v0.md)에 있다.

## 1. 현재 작업 흐름 유지

> 이번 지시는 gRPC 적용 방향과 검증 요구사항을 채택하는 결정입니다. 현재 작업을 중단하고 즉시 새 구현으로 전환하라는 뜻은 아닙니다.

- 02-04를 포함한 현재 승인된 작업은 기존 범위와 수용 기준에 따라 계속한다.
- 요구사항을 계획과 원장에 기록하고, 기존 구현으로 충족하는 부분과 추가 개발이 필요한 부분을 대조한다.
- API·실제 서비스 연결·Kubernetes 검증 작업의 의존관계에 맞춰 구현 시점을 배치한다. 이미 만들어진 기능을 중복 구현하지 않는다.
- 후속 변경을 쉽게 하기 위해 현재 코드에서 미리 분리해야 할 부분이 있다면 그 영향부터 확인한다.
- 기존 검수 완료 항목의 수용 기준을 소급 변경하거나 완료 판정을 취소하지 않는다. 추가 범위는 별도로 추적한다.
- 다음 정규 보고에 반영 위치와 실행 순서를 포함한다. 실제 차단 사유가 없으면 현재 작업을 계속한다.

## 2. 내부 통신은 gRPC 기준

> 향후 Kubernetes 배포와 기존 자체 서비스들의 gRPC 사용을 고려해, 코디네이터와 실행 관리 서비스 사이의 내부 API를 gRPC로 제공하는 방향을 반영하세요.

> 기존 배정·판정·권한·DB 로직을 재사용하고, HTTP와 gRPC에 같은 업무 규칙을 중복 구현하지 마세요. 기존 HTTP/JSON 계약과 시험을 유지하면서 gRPC 경로를 추가하세요.

계약에 명시할 것(사용자 원문 목록): 서비스·메시지 정의와 버전 호환 규칙, 인증과 역할별 권한, HTTP·gRPC 상태 코드의 대응 및 상세 오류 사유, 재시도 가능 여부와 멱등 처리, 요청 제한 시간과 취소 처리.

> Claude CLI 실행 방식과 GitHub·Notion의 외부 API 연결은 이번 통신 방식 변경 대상이 아닙니다.

## 3. 특정 CNI 확장 기능에 의존하지 않는 기본 경로

> “특정 CNI 확장 기능 없이도 gRPC의 서비스 발견·요청 분산·장애 복구를 제공하며, 환경별 확장 기능은 선택적으로 활용한다.”

- 기본·폴백 경로는 Headless Service와 클라이언트 측 분산을 우선 검토한다.
- 사용하는 Rust gRPC 라이브러리가 실제로 지원하는지 확인할 것: 여러 Pod 주소 발견, Pod 추가·삭제·교체에 따른 주소 목록 갱신, 사용 가능한 연결 사이의 RPC 분산, 연결 실패 감지와 재연결.
- 지원이 부족하면 독립적인 gRPC L7 프록시 구성을 대안으로 선택한다. 선택 근거와 필요한 구성요소를 기록하고, 여러 방식을 불필요하게 모두 구현하지 않는다.
- 폴백에서도 gRPC를 유지한다. 사용할 분산 경로와 필요한 설정은 배포 구성에 명시한다.

## 4. 기본 kind 환경에서 필수 시험

- Cilium을 설치하지 않은 kind 기본 네트워크, 멀티 노드, 시험용 gRPC 서버·클라이언트. 서버 응답에 Pod 식별자와 요청 ID를 남긴다.
- 필수 시험(사용자 원문 목록): 복제본 증가, Pod 삭제·교체, 롤링 업데이트, 긴 스트림 중단, 요청 재전송.
- 클라이언트와 채널을 재사용하는 조건에서 분산을 확인한다. 새 RPC의 분산과 기존 스트림의 복구는 별도 기준으로 시험하고, 기존 스트림이 다른 Pod로 자동 이동한다고 가정하지 않는다.

> 관측 시간·요청 수·허용 편차·복구 제한 시간과 실패 기준은 실행 전에 근거와 함께 정하세요. 결과를 보고 기준을 바꾸지 마세요.

- 초기 네트워크 시험은 시험용 서버·클라이언트로 하며 실제 Claude 호출은 필요 없다. 시험용 서버의 결과와 실제 코디네이터의 결과를 구분한다.

## 5. 제품 경로의 기존 규칙 재검증

gRPC 경로에서도 같은 업무 요청에 같은 판정과 DB 상태가 나오는지 확인한다. 공통 회귀 시험(사용자 원문 목록): 인증·역할 권한, 중복 배정 방지와 멱등 처리, 실패 시 트랜잭션 롤백, 옛 세대 결과 보존 및 현재 판정 제외, 연결 중단 후 재전송에 따른 중복 반영 방지.

> 연결 실패만 보고 작업 전체를 무조건 재실행하지 마세요. 전송 성공 여부와 서버의 실제 반영 여부가 다를 수 있는 상황을 포함하세요.

## 6. Cilium 경로는 추가 검증

- 호환되는 시험 환경이 있으면 별도 kind 구성에서 Cilium의 L7 분산 경로도 시험한다. 설치 여부만으로 판정하지 않고 활성화한 기능·설정과 실제 요청 분포를 확인한다. 기본 경로와 같은 기준을 적용한다.
- 불가능하면 이유와 필요한 조건을 기록하고 기본 kind 결과와 분리해 보고한다. Cilium 추가 시험의 미실행을 현재 승인된 작업의 차단 조건으로 확대하지 않는다.
- 기존 개발 클러스터와 운영 DB를 변경하지 않는 별도 시험 환경을 사용한다. 호스트 자원을 확인하고, 필요하면 기본 kind와 Cilium 구성을 순차 실행한다.

## 7. 검수와 보고

- 기존 독립 검토·필수 CI·승인 head 조건 병합·main CI 확인 절차를 유지한다. 진행 중인 검토·병합 단위에 이번 변경을 섞지 않고 독립된 작업과 PR로 진행한다.
- 추가 결제 금지와 기존 모델 호출 예산은 그대로다. 이번 요구사항을 이유로 예산을 확대하거나 자동 재시도를 추가하지 않는다.
- 준비 작업을 완료 수에 넣거나 기존 완료 수·분모를 바꾸지 않는다.

> kind에서 통과한 결과를 물리 서버 장애·실제 서버 간 네트워크 단절·운영 처리량 검증까지 완료한 것으로 표현하지 마세요.
