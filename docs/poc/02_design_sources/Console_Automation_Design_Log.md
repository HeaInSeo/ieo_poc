# Console 새 개발 운영 시스템 설계 논의

2026-11-04 · 논의 중

새 저장소에서 repo별 개발 담당자가 제품 개발을 이어가고, 커밋이 올라온 뒤 검토와 테스트 결과가 모이면 한 번에 보고하는 흐름을 설계한다. 중요한 결정과 검증 결과를 여기에 누적하고, 합의한 항목은 개발 스프린트의 작업과 수용 기준으로 옮긴다.

새 설계 제안은 적용 전제와 실패할 수 있는 사례를 먼저 확인한다. 문서 확인, 모의시험, 실제 환경 실증의 결과를 구분하고, 확인한 범위와 남은 조건을 기록한다.

## 자동 스프린트의 최종 목표

**사용자가 정한 목표.** 범위와 완료 기준이 확정된 스프린트 문서를 제출하면, repo 전담 에이전트가 적용한 문서 버전을 기록하고 선행조건이 충족된 작업을 자동으로 착수한다. 이후 구현, 내부 테스트·린트, 독립 적대적 검토, 필요한 교정과 재검증, 수용 판정, 사용자 완료 보고까지 이어진다. 기존 권한으로 처리할 수 있는 정상 경로와 복구 가능한 장애는 시스템이 이어서 처리하고, 범위·일정·권한의 결정이 필요한 예외는 영향과 선택지를 사람에게 보고한다.

**명세에서 완료 근거까지.** Spec Kit에서 영향을 받은 흐름을 적용한다. Notion의 설계 정본에서 목표와 수용 기준을 정하고, 스프린트 문서에는 요구사항과 작업을 연결한다. 작업마다 대상 repo, 선행조건, 검증 방법, 필수 산출물, 종료 조건을 명시한다. 실행 기록에서는 요구사항에서 작업과 적용 문서 버전, GitHub 커밋, 검사·검토 근거까지 따라갈 수 있어야 한다. [GitHub Spec Kit](https://github.com/github/spec-kit#spec-driven-development)

| 판정 | 필요한 근거 |
| --- | --- |
| 작업 완료 | 적용한 문서 버전의 필수 수용 기준이 충족됐다. 현재 대상 커밋에서 적용 프로파일의 필수 검사와 독립 검토를 통과했고, 작업 계약에서 요구한 실행·사용성 증거와 병합·산출물·인계가 확인됐다. 교정으로 커밋이 바뀌면 새 커밋의 검증 근거로 판정한다. |
| 스프린트 완료 | 모든 필수 목표가 작업 결과와 연결되고, 종료를 막는 미해결 항목이 0건이다. 승인된 범위 변경은 해당 스프린트 문서 버전과 결정 기록에 연결한다. |
| 완료 보고 | 확인된 목표와 결과, 필수 검사·독립 검토 근거, 승인된 잔여 사항을 사람이 읽을 수 있게 전달한다. 스프린트 판정과 보고의 대기·전달 확인·결과 미확인 상태는 각각 기록한다. |

**장애 뒤 재개.** 토큰 한도에 도달하기 전과 작업 단계의 경계에서 적용 문서 버전, 작업공간·커밋, 마지막으로 확인한 단계, 다음 행동, 미확인 외부 요청의 식별자를 보존한다. 토큰 소진이나 시스템 장애 뒤에는 같은 이름의 에이전트가 저장된 기록을 읽고 현재 권한·문서 버전·GitHub와 외부 상태를 대조한다. 이미 확인된 단계는 건너뛰고, 재개 조건을 충족하면 마지막 확인 지점에서 자동으로 이어간다. 외부 요청 결과를 확인할 수 없으면 해당 작업과 의존 작업을 보류한다. 별도 repo의 독립 작업은 계속 진행한다. 기존 Notion 복구 문서의 고정 HEAD, 남은 범위, 다음 행동을 남기는 방식을 근거로 삼는다. [Codex 컨텍스트 초과 복구](https://app.notion.com/p/3b286e6dd1d18170adf1c298c6af3f98)

**앞선 연구 검토의 반영 순서.** 자동 재개, 스프린트 문서의 실제 적용 확인, 한 작업의 전체 흐름 검증을 첫 종단 실증의 수용 기준으로 삼는다. 보고 문안과 작업 재개 안내를 개선하는 연구는 운영 밖에서 재현 사례를 확보한 뒤 별도 검토한다.

## 합의한 방향

- **새 저장소에서 설계한다.** 기존 `notion-projection-guard`의 운영 경험을 설계 근거로 삼는다. 기존 시스템의 복구와 새 시스템의 설계는 별개로 다룬다.
- **repo별 전담 개발 에이전트가 개발을 이어간다.** 독립 검토는 별도 역할이 맡는다. 개발 에이전트의 중간 보고는 사람이 읽는 진행 메시지로 유지하고, 자동화는 GitHub에 남은 결과를 관측한다. 개발 에이전트에게 별도 완료 메시지 전송을 요구하지 않는다.
- **중앙 감독과 큐 감독의 역할을 구분한다.** 주기적으로 상태를 확인하고 의미 있는 변화를 알리는 운영 방식은 유지할 가치가 있다. 새 설계에서는 코드 검토와 검증 흐름을 GitHub 결과에 연결하고, 주기 감시는 이벤트 누락, 검토 미착수, 보고 누락 같은 예외를 찾는 데 쓴다. 두 감독이 같은 상태를 중복 보고하는 부분은 줄인다.

## Rust 코디네이터와 상시 실행 모델

**사용자가 제시한 방향.** 새 서비스는 코디네이터(Coordinator)라고 부르고, Rust로 개발하는 방향이다. 코디네이터는 컨테이너의 PID 1로 상시 실행하며 종료되면 해당 컨테이너도 종료된다. 에이전트의 접속을 받고, 역할과 담당 repo를 확인해 작업을 배정하며 개발에서 독립 검토, 교정, 완료 보고로 이어지는 순서를 조율한다. 개발 에이전트와 Guardrail은 각각의 작업을 실행하고 결과를 제출한다. 코디네이터가 그 결과와 승인된 스프린트 문서를 대조해 다음 단계를 결정한다.

**초기 연결 제안.** 컨테이너 안에서 코디네이터 프로세스 하나를 상시 실행한다. 에이전트는 인증된 HTTP/JSON API를 통해 등록·재접속하고, 맡을 작업을 요청하고, 진행 및 결과를 제출한다. 같은 에이전트 이름이라도 실행 인스턴스가 바뀌면 구분한다. PostgreSQL에 작업과 실행 시도, 소유권, 마지막 검증 증거를 보존한다. 서버나 에이전트가 재시작하면 저장된 기록과 GitHub 등 외부 상태를 대조해 배정과 검토 인계를 이어간다. 연결 유지 방식과 라이브러리 조합은 PoC에서 확인한다. Rust의 상태 타입, Tokio, axum, SQLx가 첫 후보 구성이다. [Rust 상태 타입](https://doc.rust-lang.org/book/ch06-00-enums.html) · [Tokio 종료 처리](https://tokio.rs/tokio/topics/shutdown) · [axum HTTP 서버](https://docs.rs/axum/latest/axum/serve/index.html) · [SQLx 연결 풀](https://docs.rs/sqlx/latest/sqlx/struct.Pool.html)

**확인할 경계.** 연결이 끊기면 실행 시도와 외부 요청의 상태부터 대조한다. 배정은 DB에 확정한 뒤 응답하며, 응답을 잃은 에이전트가 다시 요청해도 기존 배정을 조회할 수 있어야 한다. 소유권이 교체된 뒤 예전 실행 인스턴스의 결과가 상태를 전진시키지 않도록 검사한다. 외부 요청 결과가 불확실한 작업은 기존 중단·대조 조건을 적용한다.

**PoC에서 확인할 항목.** 개발 에이전트가 작업을 받고 진행을 저장한 직후 코디네이터를 강제 종료한다. 코디네이터를 다시 띄워 에이전트가 재접속하면 같은 작업과 실행 시도를 찾아야 한다. 중복 배정과 완료 상태의 중복 반영은 각각 0건이어야 하고, 소유권 교체를 시험할 때 이전 실행의 뒤늦은 제출은 거부되어야 한다. 이 시험은 기존 PostgreSQL 기록 PoC 및 GitHub 독립 검토 실증과 연결해 첫 종단 실증의 재시작 사례로 쓴다.

## 기존 NPG의 역할과 안전하게 멈추는 조건

**소스 확인.** `notion-projection-guard`의 역할은 중앙 감독의 관측·조치 기록을 권한이 있는 Notion 구간에 안전하게 반영하는 것이다. README에는 수정 범위를 확인하지 않은 채 여러 페이지에 쓰기가 이어졌던 사고가 기록되어 있다. 현재 코드는 페이지별 원본과 수정 계획을 저장하고, 쓰기 직전 권한과 페이지 상태를 다시 확인한 뒤 승인된 요청을 한 번 호출한다. 쓰기 후에는 전체 본문과 보호 속성을 대조하고 검증 영수증을 저장해야 다음 페이지로 진행한다. 결과가 불확실하거나 대조가 실패하면 해당 배치를 멈추고, 정본 저널에서 미해결 상태를 유지해 새 배치도 차단한다. [README의 쓰기 계약](https://github.com/HeaInSeo/notion-projection-guard/blob/e5075affbc87ed650a755558b8491828e6783862/README.md#L257-L297) · [실행 흐름](https://github.com/HeaInSeo/notion-projection-guard/blob/e5075affbc87ed650a755558b8491828e6783862/runner.js#L188-L244) · [브로커의 배치 차단과 검증](https://github.com/HeaInSeo/notion-projection-guard/blob/e5075affbc87ed650a755558b8491828e6783862/broker.cjs#L1124-L1207)

**검증의 경계.** Notion이 마지막 조회와 쓰기 사이에 바뀔 수 있다. 쓰기 범위를 좁혀 영향을 제한하고 쓰기 후 대조로 이상을 발견해 후속 쓰기를 막는 구조다. 중단 상태에는 어느 단계까지 확인했는지와 원래 요청의 결과를 대조할 근거가 남는다. 요청이 외부에서 이미 반영됐을 수 있으므로 결과 미확인과 미전송을 구분한다. [쓰기 직전 확인과 호출](https://github.com/HeaInSeo/notion-projection-guard/blob/e5075affbc87ed650a755558b8491828e6783862/runner.js#L102-L135) · [단계별 중단과 복구 근거](https://github.com/HeaInSeo/notion-projection-guard/blob/e5075affbc87ed650a755558b8491828e6783862/broker.cjs#L541-L581)

**새 Console 설계에 적용할 제안.** 근거가 부족하면 영향을 받는 상태 전환과 외부 작업만 보류한다. 실패 원인, 마지막으로 확인한 단계, 재개에 필요한 증거를 기록하고, 같은 상태나 선행조건을 공유하는 작업까지 보류 범위에 포함한다. 독립적인 repo와 작업은 계속 진행할 수 있도록 차단 범위를 나눈다. 실행 기록 API의 DB 쓰기는 같은 사건 ID로 기존 처리 결과를 확인할 수 있게 설계한다. 외부 변경 요청은 결과가 불확실할 때 원래 요청과 실제 외부 상태를 대조한 뒤 재개한다. 이 원칙의 실제 적용과 차단 범위는 새 설계의 검증 항목으로 남긴다.

## 전담 에이전트의 개발 환경과 GitHub 정본

**현재 구현 범위.** repo마다 한 개발 에이전트가 지속적으로 개발을 맡는다. 개발 환경은 이미지로 정의하고, 담당 에이전트의 컨테이너는 **작업 사이의 대기 중에도 상시 실행**한다. 개발 환경을 보존하고, 에이전트가 컨텍스트 한계에 부딪힐 때 참고할 위키 문서와 도구를 그 환경에서 제공한다. 코드와 개발 결과는 GitHub에 저장한다.

**향후 검토할 Kubernetes 배치와 장애 복구.** Pod 배치는 이후 단계에서 검토한다. 컨테이너가 종료되면 kubelet이 재시작 정책에 따라 같은 Pod에서 다시 실행할 수 있다. Pod나 노드에 장애가 생기면 워크로드 컨트롤러가 대체 Pod를 만들 수 있다. [Kubernetes Pod 수명 주기](https://kubernetes.io/docs/concepts/workloads/pods/pod-lifecycle/)

다시 실행된 에이전트가 하던 일을 이어가려면 작업 파일과 재개에 필요한 맥락을 재시작 후에도 읽을 수 있게 보존해야 한다. 노드 장애 후 다른 노드에서 재개하려면 그 노드에서도 상태를 읽을 수 있어야 한다. 저장 방식, Pod를 관리할 워크로드 유형, 브랜치와 PR을 이어가는 규칙, Guardrail의 실행 환경은 별도 설계 항목이다. [Kubernetes 영속 볼륨](https://kubernetes.io/docs/concepts/storage/persistent-volumes/)

## Notion 설계 정본과 스프린트 작업 문서

기존 방식은 Notion에 정본·설계 문서와 작업 진행 기록을 함께 둔다. 새 방향에서도 설계 정본과 설계 문서는 Notion에 두고 그곳에서 갱신한다. 설계에서 도출한 스프린트 일정과 실행할 작업은 별도 문서로 개발 컨테이너에 전달하는 안을 검토한다.

| 구분 | 역할 |
| --- | --- |
| Notion | 정본과 설계 문서를 작성하고 갱신한다. |
| 스프린트 작업 문서 | 대상 repo, 스프린트 일정, 작업 ID·버전, 범위, 선행조건, 수용 기준, 구현에 필요한 설계 내용과 출처를 담는다. |
| GitHub | 코드, 커밋, PR, CI 결과를 보존한다. PR과 검증 결과를 적용한 작업 문서의 버전에 연결하는 방안을 검토한다. |
| 실행 DB | 작업 진행, 변경 이력, 예외, 사람에게 보고할 사항과 전달 상태를 기록한다. |

**운영 제안.** 개발 에이전트는 전달받은 작업 문서를 읽고 스프린트를 실행한다. 설계가 바뀌어 현재 작업의 범위나 수용 기준에 영향을 주면, 변경된 작업을 새 버전으로 전달한다. 이전 버전에서 수행한 작업과 검증 결과는 해당 버전에 귀속한다. 새 버전을 만들고 전달하는 책임과 진행 중 작업을 전환할 시점은 별도 논의한다.

**로컬 모의시험.** 임시 작업 문서의 수용 기준을 직접 읽어 Notion 조회 없이 1차 결과를 판정했다. 계약 테스트가 추가된 새 버전을 전달했을 때 이전 버전의 결과를 새 버전 완료로 인정하지 않았다. 출처 링크만 있고 수용 기준이 없는 문서는 판정할 수 없었다. 실제 컨테이너의 문서 전달과 진행 중 전환은 후속 실증 범위다.

## 스프린트 실행 기록과 보고

개발 에이전트가 작업 문서를 실행하면서 진행 상태, 변경 이력, 예외, 사람에게 보고할 사항을 DB에 기록한다. 작업 ID와 문서 버전에 실행을 연결하고, 구현·검증 결과는 해당 GitHub PR·커밋·CI를 참조한다. 작업 문서가 개정되면 어느 버전에서 변경이 발생했고 어떤 결과를 냈는지 추적할 수 있어야 한다.

| 기록 | 확인할 내용 |
| --- | --- |
| 작업 상태 | 담당 에이전트, 작업 ID와 문서 버전, 현재 단계, 마지막으로 확인한 결과 |
| 실행 이력 | 착수, 상태 전환, 예외 발생·해소, 일정·범위 변경, 변경 이유와 근거 |
| 사람에게 보고할 사항 | 연결된 실행 사건, 보고 이유, 발송 대기·발송 확인·결과 미확인 등 전달 상태 |

**저장과 보고 제안.** 보고가 필요한 변경은 작업 상태, 실행 이력, 보고 대기 항목을 한 DB 트랜잭션으로 저장한다. 보고 발송은 저장된 대기 항목을 읽어 별도로 진행한다. 같은 실행 사건의 재시도는 같은 식별자로 처리한다. 외부 발송 결과를 확인할 수 없을 때의 대조와 재시도 방식은 실제 전달 경로가 정해진 뒤 검증한다. 보고 대상으로 분류할 기준, 기록 주체, DB 제품은 별도 논의한다. [Transactional outbox](https://docs.aws.amazon.com/prescriptive-guidance/latest/cloud-design-patterns/transactional-outbox.html)

**로컬 모의시험.** SQLite에서 보고 대기 항목을 쓰기 직전에 실패를 주입하니 상태와 이력도 함께 롤백됐다. 같은 예외를 8개 실행이 동시에 기록했을 때 상태 전환, 예외 이력, 보고 대기 항목이 각각 한 번만 반영됐다. 시험 범위는 DB 기록까지다.

### 사람이 읽고 결정하는 운영 보고

**제안.** 첫 줄에서 어떤 작업에 무엇이 달라졌고, 지금 사람이 결정할 일이 있는지 알 수 있게 한다. 보고는 **결정 필요**와 **상태 변경**으로 구분한다. 같은 사건에서 새 증거나 영향 변화 없이 상태만 다시 조회했다면 실행 DB에 관측을 남긴다. 결정이 처음 필요해졌거나, 이미 보고한 사건의 영향 범위·재개 조건·결정 시한에 실질적인 변화가 생기면 다시 알린다.

| 보고 순서 | 담을 내용 |
| --- | --- |
| 한 줄 요약 | repo와 작업 또는 PR, 바뀐 상태, 사용자 결정 필요 여부 |
| 확인한 사실과 영향 | 마지막으로 확인한 단계, 보류된 작업과 계속할 수 있는 작업, 확인된 사실과 아직 확인할 수 없는 결과. 관측 시각에는 시간대를 표시한다. |
| 다음 행동 | 다음 조치를 맡은 사람이나 에이전트, 재개 조건 또는 다음 확인 시점. 다음 확인 시점과 해결 예상 시각을 구분한다. |
| 결정 요청 | 사용자가 정할 질문 한 가지, 선택지별 영향, 권고와 이유, 실제 결정 시한이 있을 때 그 시한과 지나면 생기는 일. 답이 없을 때 취하는 기본 조치와 승인 범위를 적는다. |
| 확인 근거 | 작업 문서 버전, PR·커밋, CI·리뷰, 사건 기록 중 판단을 뒷받침하는 링크와 식별자. 내부 상태 코드와 저널 정보는 여기에 둔다. |

완료라는 표현은 무엇이 끝났는지 밝혀 쓴다. 예를 들어 CI 통과, 현재 커밋에 대한 독립 검토 승인, 병합, 후속 작업 인수는 각각 따로 표시한다. 외부 요청의 반영 여부를 확인할 수 없으면 그 상태를 그대로 쓰고, 성공·실패·미전송과 구분한다. 결정 요청에는 현재 근거로 실행할 수 있는 선택지만 제시한다. 답변을 적용하기 전에 승인 대상과 근거가 여전히 유효한지 확인한다.

**과거 보고 재작성 예시.** Sori PR #48의 당시 보고는 전송 단계에서 멈췄고 외부 반영 결과가 미확인이며 사용자 결정이 필요 없다고 기록했다. 같은 내용을 아래처럼 읽히게 한다.

> **상태 변경 · Sori PR #48의 검토 인계 보류 · 사용자 결정 불필요**  
> 새 커밋의 CI는 통과했어. 검토 인계 중 멈췄고, 해당 요청이 외부에 반영됐는지는 아직 확인되지 않았어.  
> 담당 자동화는 원래 요청 결과를 대조한 뒤 인계를 재개할 수 있는지 판단해. 그때까지 이 요청은 다시 보내지 않아.

**검증 계획.** 보고만 읽은 사람이 아래 각 사례에서 끝난 단계, 모르는 사실, 영향을 받는 작업, 다음 행동과 사용자 결정 여부를 원본 증거와 일치하게 설명할 수 있어야 한다. 결정 요청 사례에서는 어떤 선택이 언제까지 필요하고 미응답 시 어떤 조치가 적용되는지도 맞혀야 한다.

| 시험 입력 | 기대하는 해석 또는 동작 |
| --- | --- |
| 현재 커밋의 CI 통과와 이전 커밋의 독립 승인 | CI 통과까지 확인했다. 현재 커밋의 독립 검토가 필요하다. |
| 외부 요청 응답 유실과 원래 요청 결과 미확인 | 해당 인계가 보류됐다. 담당자가 원래 요청을 대조하며 사용자가 재전송을 결정할 일은 없다. |
| 승인된 일정으로 진행할 수 없어 범위나 일정 결정이 필요함 | 결정할 질문, 선택지별 영향, 권고 이유와 미응답 시 조치를 알 수 있다. |
| 동일한 사건을 다시 관측함 | 새 증거나 영향 변화가 없으면 같은 알림이 추가로 발송되지 않는다. |

이 검증은 과거 사례를 바탕으로 보고 문안을 점검하는 단계부터 진행한다. 사람이 실제로 이해한 내용과 알림 발송·중복 억제 동작은 후속 시험에서 확인한다.

### 여러 repo의 운영 DB와 MCP 연결

**운영 DB 제안.** 여러 컨테이너에서 여러 repo의 상태를 동시에 기록하는 구성을 기준으로 PostgreSQL을 우선 검토한다. 작업 상태, 실행 이력, 보고 대기 항목을 같은 트랜잭션으로 저장할 수 있고, 서로 다른 작업의 행을 갱신하는 동안 행 단위로 잠글 수 있다. 로컬 SQLite WAL에서 repo A의 쓰기 트랜잭션을 유지한 채 repo B의 다른 행을 갱신하니 즉시 반환 모드에서 `SQLITE_BUSY`가 발생했고, A가 커밋한 뒤 B의 재시도는 성공했다. PostgreSQL의 동시성은 공식 문서로 확인했으며 운영 환경 실증은 남아 있다. [SQLite WAL](https://www.sqlite.org/wal.html) · [PostgreSQL 행 잠금](https://www.postgresql.org/docs/current/explicit-locking.html)

repo와 작업 사이의 의존 관계는 우선 관계형 테이블로 저장하고, 다단계 영향 범위는 재귀 쿼리로 조회하는 안을 검토한다. 여러 repo에 걸친 의존 경로 탐색이 주된 사용 사례가 되고 실제 조회에서 제약이 드러나면 그래프 DB를 검토한다. [PostgreSQL 재귀 쿼리](https://www.postgresql.org/docs/current/queries-with.html) · [Neo4j 가변 길이 경로](https://neo4j.com/docs/cypher-manual/current/patterns/variable-length-paths/)

**MCP 연결 제안.** 에이전트는 내부 MCP 서비스에 작업 상태 조회, 진행 보고, 예외 기록 도구를 호출한다. 서비스가 인증된 에이전트의 repo·작업 권한과 작업 문서 버전을 확인하고 DB 트랜잭션을 실행한다. 다른 컨테이너나 노드에서 연결할 때는 인증된 Streamable HTTP를 후보로 둔다. DB에 저장한 뒤 응답이 끊겨도, 같은 사건 ID로 재시도하면 기존 결과를 돌려주는 계약을 서버에서 적용한다. 향후 Kubernetes 배치 전에는 여러 repo 동시 기록, 다른 repo 쓰기 거부, 응답 유실 후 재시도, 오래된 작업 버전의 쓰기 거부를 실제 PostgreSQL과 선택한 연결 방식으로 실증한다. [MCP 전송 규격](https://modelcontextprotocol.io/specification/2025-11-25/basic/transports)

### 에이전트 연결 방식 비교

| 방식 | 이 설계에서 맡을 수 있는 역할 |
| --- | --- |
| HTTP API와 OpenAPI | 컨테이너, 운영 스크립트, 대시보드가 작업 상태 조회·진행 기록·예외 등록을 같은 인터페이스로 호출한다. OpenAPI는 HTTP 요청과 응답의 계약을 기술한다. [OpenAPI 규격](https://spec.openapis.org/oas/v3.1.1.html) |
| gRPC | 에이전트 런타임이나 내부 서비스가 `.proto`로 정의한 타입과 생성한 클라이언트를 사용해 같은 업무 기능을 호출한다. [gRPC 개요](https://grpc.io/docs/what-is-grpc/introduction/) |
| MCP | MCP를 지원하는 여러 에이전트 호스트가 업무 기능을 도구로 발견하고 호출한다. [MCP 도구 규격](https://modelcontextprotocol.io/specification/2025-11-25/server/tools) |
| A2A | 독립된 에이전트 사이에서 검토 요청, 장시간 작업 상태와 결과를 주고받는 데 적용할 수 있다. [A2A와 MCP](https://a2a-protocol.org/v1.0.1/topics/a2a-and-mcp/) |

**제안.** 호출자가 고정된 첫 구현에서는 HTTP/JSON API와 OpenAPI를 후보로 둔다. 여러 MCP 호스트에서 도구를 발견하고 호출해야 하는 경우에는 같은 실행 기록 서비스의 업무 기능을 MCP로 노출하는 방식을 검토한다. repo 권한, 작업 문서 버전, 사건 ID에 따른 재시도 처리는 실행 기록 서비스가 담당한다.

**로컬 모의시험.** 임시 HTTP/JSON 서비스가 SQLite에 사건을 저장한 직후 응답을 끊도록 했다. 동일한 사건 ID와 내용으로 다시 호출하니 성공 응답을 받았고 기록은 한 건이었다. 같은 ID로 다른 내용을 보내니 HTTP 409가 반환됐다. 시험은 일반 HTTP에서도 이 재시도 계약을 구현할 수 있음을 확인했다. PostgreSQL과 실제 에이전트의 연동은 아래 별도 PoC에서 검증한다.

## 별도 PoC · PostgreSQL과 개발 에이전트 연동

**목표.** 실제 개발 에이전트가 컨테이너에서 스프린트 작업 문서 한 건을 받아 작은 코드 변경과 테스트를 수행하고, 그 과정의 상태·이력·예외를 실행 기록 API를 통해 실제 PostgreSQL에 남기는지 확인한다. 현재 상태는 계획이며 실증 결과는 실행 후 기록한다.

**최소 구성.** 같은 호스트에 개발 에이전트 컨테이너 한 개, 실행 기록 서비스 한 개, PostgreSQL 한 개를 띄운다. 테스트용 repo A·B와 고정된 작업 문서를 사용한다. 실제 에이전트는 A를 담당하고, 별도 자격으로 실행하는 테스트 클라이언트가 B의 동시 쓰기를 재현한다. 연결 방식은 현재 제안에 따라 HTTP/JSON API와 간단한 OpenAPI 명세부터 시험한다. 호출 범위는 작업 조회, 진행 기록, 예외 등록으로 제한한다.

| 검증 항목 | 재현 방법과 통과 기준 |
| --- | --- |
| POC-01 실제 에이전트의 실행과 기록 | 에이전트가 작업 문서를 읽고 테스트 repo A에서 작은 변경과 테스트를 수행한다. API를 통해 착수와 검증 결과를 기록하고 상태를 다시 조회한다. 에이전트 실행 로그, API 응답, DB 기록에서 에이전트 ID·repo·작업 ID·문서 버전·테스트 결과가 일치해야 한다. |
| POC-02 트랜잭션과 롤백 | 보고 대상 예외를 등록하면 상태 전환, 예외 이력, 보고 대기 항목이 모두 한 번씩 저장되어야 한다. 보고 대기 항목 저장 직전에 실패를 주입하면 세 기록 모두 이전 상태를 유지해야 한다. |
| POC-03 응답 유실과 재시도 | PostgreSQL 커밋 직후 응답을 끊고 같은 사건 ID와 내용으로 재시도한다. 최초 처리 결과를 돌려주고 이력과 보고 대기 항목은 각각 한 건이어야 한다. 같은 ID에 다른 내용을 보내면 충돌로 거부하고 DB 기록을 그대로 유지해야 한다. |
| POC-04 여러 repo의 동시 쓰기 | repo A의 쓰기 트랜잭션을 의도적으로 열어 둔 상태에서 독립된 repo B의 작업을 갱신한다. B의 쓰기가 A의 잠금 해제 전에 커밋되고, A까지 커밋한 뒤 양쪽 상태와 이력이 각 repo에 한 건씩 남아야 한다. |
| POC-05 repo 권한과 문서 버전 | A 자격으로 B에 쓰기를 시도하고, A의 작업 문서를 v2로 전환한 뒤 v1에 대한 새 사건을 보낸다. 두 요청 모두 거부되고 상태·이력·보고 대기 항목의 변화가 0건이어야 한다. 같은 조건에서 A의 v2에 대한 정상 요청은 성공해야 한다. |

**완료 기준.** POC-01~05의 재현 절차와 실제 결과를 남긴다. 에이전트 실행 로그, API 응답, DB 조회 결과를 작업 ID와 사건 ID로 연결해 검토할 수 있어야 한다. 미통과 항목은 원인과 재시험 조건을 기록하고, 전체 통과 후 운영 스프린트의 수용 기준으로 옮긴다.

PoC는 단일 호스트의 테스트 환경에서 보고 대기 항목 저장까지 확인한다. MCP 연동은 필요할 때 같은 검증 시나리오를 별도로 적용한다. Kubernetes 배치, 실제 알림 발송, GitHub CI·Guardrail 승인 연동은 각 실증 범위에서 다룬다.

## 개발 에이전트와 Guardrail의 컨테이너 배치

개발 에이전트와 Guardrail을 모두 컨테이너에서 실행한다. repo 전담 개발 에이전트의 컨테이너는 작업 사이에도 상시 실행한다.

**제안.** 첫 실증은 같은 호스트의 별도 컨테이너 두 개에서 진행한다. 개발 에이전트는 기존 작업공간에서 코드를 작성하고 GitHub에 푸시한다. Guardrail은 자기 작업공간에 PR의 대상 커밋 SHA를 받아 검토와 테스트를 수행한다. 개발 작업공간과 검토 작업공간을 분리하면 개발 중인 파일이 바뀌어도 Guardrail이 같은 커밋을 기준으로 판정할 수 있다.

GitHub의 개발 주체와 검토 주체를 구분한다. Guardrail은 검토한 SHA를 지정해 PR 리뷰를 남긴다. 리뷰를 진행하는 동안 PR에 새 커밋이 올라오면 기존 판정은 검토했던 커밋에 귀속한다. 컨테이너 분리는 작업공간과 자격 증명에 적용하고, 컨테이너 배치 방식과 Guardrail의 상시 실행 여부, repo별 또는 공용 운영 여부는 추가 논의한다. [GitHub PR 리뷰 API](https://docs.github.com/en/rest/pulls/reviews#create-a-review-for-a-pull-request)

## 에이전트 이름과 장애 복구

개발 에이전트와 Guardrail에는 사람이 역할과 담당 범위를 알아볼 수 있는 고정 이름을 부여한다. 운영자는 그 이름으로 상태를 확인하고 장애가 발생한 에이전트를 다시 실행할 수 있어야 한다. 예를 들어 두 역할을 Sori 전용으로 배치할 경우 `sori-dev`와 `sori-guardrail`처럼 이름을 붙일 수 있다. 실제 이름은 배치 방식에 맞춰 정한다.

이름과 역할, 담당 repo 또는 담당 범위, 실행 설정, 작업공간과 재개 기록의 연결은 컨테이너 수명과 분리해 보존한다. 장애 후 같은 이름으로 다시 실행하면 같은 에이전트의 작업공간과 재개 기록을 찾아 마지막으로 저장된 지점부터 이어간다.

**복구 실증 기준.** 개발과 검토 각각에서 에이전트 실행을 중단시킨 뒤 기존 이름으로 다시 실행한다. 같은 역할과 담당 범위로 돌아오고, 중단 전에 저장한 작업과 검토 대상을 올바르게 이어가는지 확인한다.

## Guardrail의 공통 이미지와 repo별 검증 설정

Guardrail은 repo의 린트와 테스트 환경을 설정하고 계속 개선하는 역할도 맡는다. 공통 베이스라인을 이미지에 담아 에이전트가 같은 출발점에서 검증을 시작하도록 한다. repo에 연결된 이름으로 컨테이너를 실행할 때 해당 repo의 검증 설정을 적용한다.

| 구분 | 담는 내용 |
| --- | --- |
| 공통 베이스 이미지 | 검증 실행기, 공통 도구와 버전, 공통으로 적용할 기본값 |
| repo별 검증 설정 | 사용할 린트 규칙, 실행할 테스트와 명령, 테스트 데이터나 서비스 같은 선행조건 |
| repo별 파생 이미지 | 공통 이미지에 없는 SDK, 시스템 패키지, 추가 검증 도구가 필요한 경우에 사용하는 확장 방법 |

**운영 제안.** repo별 설정과 파생 이미지의 빌드 정의를 Git에서 버전 관리한다. Guardrail이 repo의 특성에 맞게 검증 설정을 개선하면 변경 이력으로 검토할 수 있게 남긴다. 설정 변경의 채택 절차와 공통 기준의 적용 범위는 별도 논의한다. [Dockerfile의 베이스 이미지 설정](https://docs.docker.com/reference/dockerfile/#from)

에이전트의 고정 이름에 실행 이미지의 digest와 검증 설정의 버전을 연결해 보존한다. 같은 이름으로 장애를 복구할 때 같은 도구와 린트·테스트 규칙을 불러올 수 있고, 공통 이미지 업데이트와 repo별 설정 변경도 각각 추적할 수 있다. 복구 실증에서는 동일한 버전을 사용해 적용되는 도구 버전과 검증 명령이 재생성 전후에 일치하는지 확인한다. [Docker 이미지 버전 고정](https://docs.docker.com/build/building/best-practices/#pin-base-image-versions)

### 베이스 이미지와 repo별 설정의 검증

**문서 확인.** 이미지 digest를 고정하면 같은 이미지 버전을 지정할 수 있다. 검증을 재현하려면 repo별 설정 버전과 결과에 영향을 주는 외부 테스트 데이터·서비스도 식별해야 한다. [Docker 이미지 버전 고정](https://docs.docker.com/build/building/best-practices/#pin-base-image-versions)

**로컬 반례.** 임시 Git repo에서 후보 커밋에 계약 테스트 실패를 넣고, 같은 커밋의 설정에서는 그 테스트를 실행 목록에서 뺐다. 동일한 후보 코드를 검사했을 때 후보 설정은 단위 테스트만 실행해 PASS였고, 기존 승인 설정은 계약 테스트까지 실행해 FAIL이었다. 이미지 버전을 맞춰도 실행할 검사 목록을 어디서 읽는지에 따라 판정이 달라진다.

**보완 제안.** 제품 PR에는 검토 시작 시 확정한 승인 설정을 적용한다. Guardrail이 제안한 설정 개선은 별도 변경으로 검토해 승인된 뒤 적용하는 흐름을 검토한다. 현재 검증 범위는 공식 문서와 로컬 반례까지다. 실제 컨테이너에서는 재생성 뒤 같은 도구와 검사를 불러오는지, 후보 PR이 필수 검사 목록을 바꿔도 승인된 검사가 실행되는지 확인한다.

## GitHub에서 검증 완료를 판단하는 방법

이 절의 `GitHub 코드 검증 완료`는 현재 PR 커밋에 대해 필수 테스트·린트 등 CI가 통과하고, 지정된 독립 검토자의 유효한 승인이 확인된 상태를 뜻한다. 커밋 푸시, CI 종료, 리뷰 제출은 현재 상태를 다시 읽는 계기로 사용한다. 새 커밋이 올라오면 이전 커밋의 결과는 그 커밋에 귀속한다. 리뷰가 늦게 도착하거나 취소돼도 현재 PR 상태를 기준으로 판단한다.

| 단계 | 확인할 증거 | 처리 |
| --- | --- | --- |
| PR 커밋 갱신 | 현재 PR의 head SHA | 이 커밋을 검증 대상으로 삼는다. |
| 필수 CI 통과 | 대상 커밋에 적용되는 필수 테스트·린트 결과 | 해당 커밋의 독립 검토를 시작할 수 있는지 확인한다. |
| 독립 검토 완료 | 지정 검토자의 승인 상태와 리뷰의 `commit_id` | 필수 CI도 통과했으면 코드 검증 결과를 한 건으로 묶어 기록한다. |
| 정기 대조 | GitHub의 현재 상태와 검토·보고 처리 기록 | 빠진 단계만 이어서 처리한다. |

## Kubernetes에서 실행 증거를 더하는 검증층

**사용자가 제시한 목표.** 사람이 설계하고 스프린트를 제출하면 쿠버네티스에서 전담 에이전트가 개발·교정·검증을 계속하고, 완료 기준을 충족했을 때 최종 결과를 보고한다. 현재의 CI와 독립 코드 리뷰에 더해 요구사항·설계 오류, 보안·정책 위반, 실제 사용성까지 필요한 범위에서 확인한다. 사용자가 Rust를 고려한 이유에는 Linux eBPF로 실행 행동을 별도 증거로 확인하고, 필요한 관측기를 Rust로 확장할 가능성이 있다. 코디네이터 자체의 메모리 안전성은 별도의 기술 검토 항목이다.

| 검증층 | 증거와 판정 |
| --- | --- |
| 요구사항·설계 | 구현 전 독립 적대적 검토로 모순, 권한 경계, 실패 경로, 시험할 수 없는 수용 기준을 확인한다. |
| 코드와 검사 | 현재 커밋의 필수 CI·린트와 승인 프로파일을 대조한다. 독립 Guardrail이 고정 SHA에서 재현 절차, 기대값과 실측값, 심각도와 원본 증거를 남긴다. |
| 배포·권한 정책 | Kubernetes 입장 제어는 실제 Pod 명세에 적용한다. 사용자·업무 권한은 애플리케이션이 제공하는 인터페이스에서 허용·거부 결과를 검증한다. |
| Kubernetes 실행 | 개발 에이전트 Pod와 제품 후보 Pod를 따로 식별한다. 지정한 커널 지점에서 실제 프로세스 실행, 파일 접근, 네트워크 연결 시도 등을 관측해 승인 정책과 대조한다. |
| 사용성 | 자동화는 대표 과업과 실행 증거를 준비한다. 사람의 평가가 필요한 기준에는 실제 과업 성공, 혼동, 오류 후 복구를 기록한다. |

**역할과 권한.** 코디네이터는 문서·검사·리뷰·실행 증거를 대조한다. BPF 프로그램을 로드하는 권한은 별도 노드 관측기에 두고, 개발 에이전트와 코디네이터에는 맡은 역할에 필요한 권한만 부여하는 구성을 검토한다. 첫 실증은 Tetragon을 후보로 검토한다. Rust 기반 Aya는 기존 관측기를 설정해도 필요한 커널 증거를 얻기 어려울 때 해당 공백을 대상으로 비교한다. Rust로 코디네이터를 구현했을 때의 이득과, eBPF 계측을 더했을 때의 이득은 독립적으로 판정한다. [Tetragon TracingPolicy](https://tetragon.io/docs/concepts/tracing-policy/) · [Aya](https://aya-rs.dev/book/)

**판정 규칙 제안.** 작업 문서가 실행 보안 검증을 필수로 지정하면 적용 정책, 관측 대상, 유효한 관측 구간과 원자료를 증거에 연결한다. 금지 행위를 관측하면 정책에 따라 실패로 기록한다. 정책 적용이나 관측 범위를 확인할 수 없으면 미검증으로 둔다. 탐지와 차단은 각각 시험하며, 차단을 요구하는 경우 시험용 수신기에서 연결 수락 여부도 대조한다. 이 결과는 고정한 시나리오와 관측 범위에 귀속된다. [Tetragon 정책 집행 예시](https://tetragon.io/docs/getting-started/enforcement/)

## 도그푸딩으로 코디네이터를 구현하고 검증하는 순서

1. **씨앗 버전.** 외부 GitHub Actions와 독립 Guardrail로 최소 Rust 코디네이터 v0를 만든다. PID 1 기동, 문서 접수, 개발·검토 배정, 외부 DB 기록, 장애 후 복구, 시험 보고를 검증하고 실행 이미지와 검사 프로파일을 고정한다.
2. **자기 repo에서 실제 작업 한 건.** 검증된 v0에 자기 repo의 첫 작업 문서를 제출한다. 개발 에이전트가 변경을 구현하고 독립 Guardrail이 새 후보의 SHA를 검토한다. 첫 작업 후보는 보고서에 적용한 문서 버전과 검토 대상 SHA를 드러내는 변경이다.
3. **별도 판정과 복귀.** 검증 기준과 배포 권한은 후보가 쓰지 못하는 영역에 둔다. 외부 승격 절차가 검증된 후보의 digest를 지정한다. 후보가 필수 검사를 빼거나 자기 승격을 시도하는 반례와, 실패 뒤 이전 버전 또는 외부 절차로 복귀해 상태를 대조하는 절차를 실증한다.
4. **Kubernetes에서 검증층 적용.** 이전 단계의 역할 분리를 유지하면서 코디네이터 제품 후보 Pod와 개발 에이전트 Pod의 실행 검증을 각기 재현한다. 실행 증거를 요구한 스프린트에서 증거가 빠지면 완료 판정이 보류되는지 확인한다.

**GHCR 이미지 경로.** 제한된 게시 작업이 고정한 Git SHA에서 나온 OCI 후보를 실증용 GHCR 패키지에 올린다. Git SHA·빌드 실행 ID·GHCR 매니페스트 digest를 연결하고, 검증용 Pod와 승인된 롤아웃은 같은 digest를 사용한다. 후보 실행 환경의 권한, 패키지 게시 권한, 배포 승인 권한을 구분한다. 태그가 가리키는 이미지가 바뀌거나 게시·pull이 실패하면 P19의 반례로 검증한다. [GitHub Container Registry](https://docs.github.com/en/packages/working-with-a-github-packages-registry/working-with-the-container-registry) · [Kubernetes 이미지](https://kubernetes.io/docs/concepts/containers/images/)

독립 검토용 `Console_Coordinator_PoC_Validation_Plan.md`에는 위 검증층과 기존 PostgreSQL·GitHub·재시작 시험을 연결한 P01~P19, 단계별 판정, 자기 repo에 제출할 첫 작업 DF-01을 담았다. 전체 역할과 증거 흐름은 `Console_Coordinator_Architecture.png`에 정리했다. 실제 PoC 결과와 구현 언어·관측기의 이득은 실행 증거로 별도 기록한다.

## 첫 실증에서 확인할 항목

**관측한 사례.** Sori PR #48을 확인한 회차에는 `b26246e4`의 검사 13개가 모두 통과했다. GitHub에 남은 Codex 코멘트 리뷰는 이전 커밋 `cf4485d9`에 대한 것이었고, 현재 커밋에 대한 Guardrail의 `PASS v59`는 Notion에서 확인됐다. 당시 개발 서버의 GitHub CLI 계정은 PR 작성자와 같은 `HeaInSeo`였다. Guardrail이 작성자와 구분되는 GitHub 검토 주체로 승인할 수 있는지가 실증의 선행조건이다. [Sori PR #48](https://github.com/HeaInSeo/sori/pull/48) · [Codex 리뷰](https://github.com/HeaInSeo/sori/pull/48#pullrequestreview-5691645127) · [Guardrail 판정](https://app.notion.com/p/3f586e6dd1d181cd9f5bdcdab6290de7)

**모의시험.** CI와 별도 검토자의 승인이 어느 순서로 들어와도 두 조건이 충족된 뒤 보고 대기열에 한 건이 등록됐다. 같은 입력을 8개 실행이 동시에 처리한 경우에도 대기열 등록은 한 건이었다. 이 결과의 검증 범위는 대기열 등록까지다.

**실제 시험의 수용 기준.** 테스트 PR 하나에서 작성자와 다른 지정 검토 주체가 현재 커밋을 승인한다. GitHub에서 필수 CI와 리뷰를 함께 확인한 뒤 시험용 코드 검증 알림이 한 번 도착해야 한다. 같은 이벤트를 반복 처리해도 추가 알림은 0건이어야 한다. 현재 커밋의 유효한 승인 없이 CI만 통과했거나 이전 커밋의 리뷰만 있는 경우에도 검증 완료 알림은 0건이어야 한다.

| 계획과 실행 기록 | 별도 스프린트 작업 문서를 컨테이너에 전달하고 실행 상태를 DB에 기록하는 방향이다. 문서 발행·전달과 DB 기록 책임, 보고 기준을 정한다. |
| 실행 방식 개선 | Harness², SkillOpt, Trace2Skill, SkillOps를 참고해 실행 기록으로 반복 실패를 찾고 같은 사례를 다시 돌려 개선을 검증하는 방식을 검토한다. 통합 범위와 도입 시점은 이후 스프린트 논의에서 정한다. [Harness²](https://github.com/google-research/harness2) · [SkillOpt](https://github.com/microsoft/SkillOpt) · [Trace2Skill](https://github.com/Qwen-Applications/Trace2Skill) · [SkillOps](https://github.com/Hik289/SkillOps) |
