# 사용자 결정 2026-11-17 · 02-05 예산 (나)의 예비 회차 강제 방식

02-05 예산 이름·상한 코드 PR 구현 중에 나온 질문에 대한 사용자의 답을 옮긴다. 근거는 [사용자 결정 2026-11-15](User_Decisions_2026-11-15_0205-x08.md) §2.1의 멈춤 규칙이다: “예비 1회는 실행 환경 결함으로 실패한 개발 회차(R1 또는 R2)를 원인 보고 뒤 한 번 다시 할 때만 쓰고, 다른 목적에는 쓰지 않음. G1이 실패하면 다시 하지 않고 보고.” 코드는 실패가 실행 환경 결함인지와 원인 보고가 있었는지를 스스로 판단할 수 없다.

## 1. 질문과 답

| 선택지 | 내용 |
| --- | --- |
| (가) 횟수만 | 역할 몫으로 개발 ≤3회, Guardrail ≤1회, 총 4회만 강제. 세 번째 개발 회차가 정당한 예비인지는 사람의 운영 규칙 |
| **(나) 횟수 + 명시적 예비 표식 — 사용자 답** | 세 번째 개발 회차는 예비 표식(사유 + 대체할 이전 시도 id)이 있고, 그 이전 시도가 이 예산의 실패한 개발 회차로 기록돼 있을 때만 허용. 표식이 없으면 개발 2회에서 멈춤. 표식·사유를 원장에 기록 |
| (다) 횟수 + 사유만 있는 표식 | (나)에서 대체할 시도 id를 요구하지 않음 |

## 2. 반영

- 숫자는 2026-11-15 결정 그대로다: 총 4회(계획 3 + 개발 전용 예비 1), 회당 600초, 합계 2,400초, 과금 토큰 200,000, cache_read 2,000,000, 역할 몫 개발 3회·1,800초·150,000·1,500,000 / Guardrail 1회·600초·50,000·500,000, 추가 청구 USD 0.
- 개발 역할의 세 번째 회차는 호출에 예비 표식(사유, 대체할 이전 시도 id)이 있어야 한다. 대체할 시도는 이 예산의 이전 개발 회차이고 기록이 실패(`stop_required` 또는 성공이 아닌 결과)여야 한다. 표식이 없거나 조건이 맞지 않으면 거부한다. 기록을 읽을 수 없거나 모호하면 거부한다.
- 예비는 한 번뿐이다. Guardrail에는 예비가 없다(G1은 다시 하지 않는다).
- “실행 환경 결함”과 “원인 보고 뒤”라는 판단은 표식을 붙이는 사람의 몫으로 남는다. 코드는 표식이 있고 실패한 개발 회차를 대체한다는 것만 확인한다. 표식과 사유는 원장 기록에 남는다.
- 이 결정은 실제 모델 호출을 승인하지 않는다. 02-05 실제 회차는 단계 8의 남은 전제(재배치, 읽기 전용 바인딩 대조 등) 뒤에만 한다. 02-04 예비 5회 미사용, 02-04·X-02·01-04 예산 전용 금지는 그대로다.

## 3. 구현에서 정한 해석(개발자, 사용자에게 보고)

- **예비는 “실패한 계획 회차 다음의 회차”다.** 결정은 예비가 R1 또는 R2를 다시 하는 것이라고 한다. R1이 실패하면 그 `stop_required` 기록이 R2를 막으므로 예비가 두 번째 개발 회차가 될 수 있어야 한다. 규칙: 예비가 아닌 개발 회차 최대 2회 + 실패한 개발 회차를 대체하는 예비 1회. 개발 회차는 어느 순서든 합계 3회다.
- **예비 표식은 그 표식이 가리키는 실패 회차에 대한 사람의 판단이다.** 표식이 가리키는 실패 회차의 `stop_required` 기록은 그 호출과 이후 호출을 더는 막지 않는다. 다른 `stop_required` 기록은 계속 막고, 미계측 실패 회차는 계속 예산을 멈춘다(0으로 세지 않음). 예비가 있는 예산에서만 생기므로 02-04 동작은 바뀌지 않는다.
