# 사용자 결정 2026-11-17 · 02-05 예산 (나)의 예비 회차 강제 방식

02-05 예산 이름·상한 코드 PR 구현 중에 나온 질문에 대한 사용자의 답을 옮긴다. 근거는 [사용자 결정 2026-11-15](User_Decisions_2026-11-15_0205-x08.md) §2.1의 멈춤 규칙이다: “예비 1회는 실행 환경 결함으로 실패한 개발 회차(R1 또는 R2)를 원인 보고 뒤 한 번 다시 할 때만 쓰고, 다른 목적에는 쓰지 않음. G1이 실패하면 다시 하지 않고 보고.” 코드는 실패가 실행 환경 결함인지와 원인 보고가 있었는지를 스스로 판단할 수 없다.

## 1. 질문과 답

| 선택지 | 내용 |
| --- | --- |
| (가) 횟수만 | 역할 몫으로 개발 ≤3회, Guardrail ≤1회, 총 4회만 강제. 세 번째 개발 회차가 정당한 예비인지는 사람의 운영 규칙 |
| **(나) 횟수 + 명시적 예비 표식 — 사용자 답** | 세 번째 개발 회차는 예비 표식(사유 + 대체할 이전 시도 id)이 있고, 그 이전 시도가 이 예산의 실패한 개발 회차로 기록돼 있을 때만 허용. 표식이 없으면 개발 2회에서 멈춤. 표식·사유를 원장에 기록 |
| (다) 횟수 + 사유만 있는 표식 | (나)에서 대체할 시도 id를 요구하지 않음 |

## 2. 반영

- 숫자는 2026-11-15 결정 그대로다: 총 4회(계획 3 + 개발 전용 예비 1), 회당 600초, 합계 2,400초, 과금 토큰 200,000, cache_read 2,000,000, 역할 몫 개발 3회·1,800초·150,000·1,500,000 / Guardrail 1회·600초·50,000·500,000, 추가 청구 USD 0.
- 개발 역할은 예비 표식 없이 최대 2회 실행한다. 예비 1회는 호출에 예비 표식(사유, 대체할 이전 시도 id, 원인 보고·근거 참조)이 있어야 하고 실패한 개발 계획 회차를 대체한다(R1이 실패하면 예비가 두 번째, R2가 표식 없는 세 번째 회차가 될 수 있다). 대체할 시도는 이 예산의 이전 개발 회차로 원장에 기록이 하나뿐이어야 하고, 그 유효 기록(정정 반영)이 실패(`stop_required` 또는 성공이 아닌 결과)여야 한다. 표식은 `kind=user`인 사람 운영 주체만 붙이며(인증된 사람 자격의 deliverAssignment로만, 인증 신원이 없는 호스트 호출자 ieo-role-call은 거부), 원장에 승인자와 승인 시각을 함께 남긴다. 표식이 없거나 조건이 맞지 않거나 기록을 읽을 수 없거나 모호하면 거부한다. (§4의 사용자 확인으로 정정한 문구. 처음 문구는 “개발 역할의 세 번째 회차는 호출에 예비 표식이 있어야 한다”였다)
- 예비는 한 번뿐이다. Guardrail에는 예비가 없다(G1은 다시 하지 않는다).
- “실행 환경 결함”과 “원인 보고 뒤”라는 판단은 표식을 붙이는 사람의 몫으로 남는다. 코드는 표식이 있고 실패한 개발 회차를 대체한다는 것만 확인한다. 표식과 사유는 원장 기록에 남는다.
- 이 결정은 실제 모델 호출을 승인하지 않는다. 02-05 실제 회차는 단계 8의 남은 전제(재배치, 읽기 전용 바인딩 대조 등) 뒤에만 한다. 02-04 예비 5회 미사용, 02-04·X-02·01-04 예산 전용 금지는 그대로다.

## 3. 구현에서 정한 해석(개발자, 사용자에게 보고)

- **예비는 “실패한 계획 회차 다음의 회차”다.** 결정은 예비가 R1 또는 R2를 다시 하는 것이라고 한다. R1이 실패하면 그 `stop_required` 기록이 R2를 막으므로 예비가 두 번째 개발 회차가 될 수 있어야 한다. 규칙: 예비가 아닌 개발 회차 최대 2회 + 실패한 개발 회차를 대체하는 예비 1회. 개발 회차는 어느 순서든 합계 3회다.
- **예비 표식은 그 표식이 가리키는 실패 회차에 대한 사람의 판단이다.** 표식이 가리키는 실패 회차의 `stop_required` 기록은 그 호출과 이후 호출을 더는 막지 않는다. 다른 `stop_required` 기록은 계속 막고, 미계측 실패 회차는 계속 예산을 멈춘다(0으로 세지 않음). 예비가 있는 예산에서만 생기므로 02-04 동작은 바뀌지 않는다.
- 근거와 시험: [02-05 예산 보고](reports/tasks/02-05/budget-0205-20261117/REPORT.md) §1·§7.

## 4. 해석 확인(사용자 결정 2026-11-17, 두 번째 답)

독립 검토(PR #81 검토 b38e8df)가 §3의 두 해석을 단계 8 전에 사용자에게 확인하라고 권했다. 사용자는 두 해석 ①·②를 승인하고 다음 조건을 붙였다(사용자 지시 그대로).

### 4.1 예비 회차의 순서
- 표식 없는 개발 계획 회차는 최대 2회, 예비는 최대 1회다.
- 예비는 실패한 R1 또는 R2를 대체하는 재시험이며, 반드시 개발 세 번째 호출일 필요는 없다.
- R1 실패 시에는 ‘R1 실패 → 예비로 R1 재시험 → 정상 완료 후 R2’가 가능하다.
- 개발 총 3회·Guardrail 1회·전체 4회와 기존 시간·토큰·금액 상한은 유지한다. G1 실패의 재시도는 허용하지 않는다.

### 4.2 예비 표식과 사람 승인
- 표식은 `kind=user`인 사람 운영 주체만 붙일 수 있다.
- 같은 예산의 실패한 개발 계획 회차 ID, 예비 사용 사유, 원인 보고·근거 참조, 승인자와 승인 시각을 원장에 기록한다.
- 사유 문자열이 있다는 것만으로 실행 환경 결함이 입증됐다고 처리하지 않는다. 실제 예비 사용 시 사람이 원인과 근거를 확인해야 한다.

### 4.3 정지 해제 범위
- 예비 표식은 지정한 실패 회차의 해당 사유로 생긴 `stop_required`만 해제한다.
- 미계측 사용량, 원장 불일치, 상한 도달, 추가 과금·비허용 한도 신호, 미확정 외부 효과 등 별도의 차단 조건은 유지한다.
- 원래 실패 기록과 사용량은 보존하고 승인·예비 사용 기록을 추가한다. 사용량 초기화나 0 처리로 해제하지 않는다.
- 예비 표식은 한 번만 소비하며, 중복 요청으로 추가 실행이 생기면 안 된다. 예비 자체가 실패하면 다시 멈추고 보고한다.

### 4.4 검증과 진행
- R1 실패 후 두 번째 호출에 예비를 사용하고 세 번째에 R2를 실행하는 경로, R2 실패 후 예비를 사용하는 경로를 모두 시험한다.
- 사람 이외의 표식, 다른 예산·역할·정상 회차를 가리키는 표식, 표식 재사용과 다른 차단 조건 우회를 거부하는 시험을 포함한다.
- 결정문 §2와 계약·코드·보고서를 일치시키고, 기존 독립 검토·CI·승인 head 병합·main CI 확인·원장 갱신 절차를 잇는다.

### 4.5 범위
이번 답은 예비 사용 규칙과 구현을 승인하는 것이다. 실제 실패가 발생했을 때 필요한 건별 사람의 예비 승인까지 미리 부여한 것으로 처리하지 않는다. 추가 청구 USD 0과 02-04 예비 5회 미사용 조건도 유지한다.
