# 개발 에이전트 인계·진척·실험 보고 지시

2026-11-12 KST · v1.3.3 · 이 파일을 실행 장부와 함께 개발 에이전트에게 전달한다.

## 1. 이 작업의 범위와 첫 응답

PoC 주계획 **73개 작업/31개 실험**, 후속 **12개 작업/5개 개선 후보**를 원 ID·선행·검수 조건대로 수행한다. 주계획과 조건부 후속의 진행률은 따로 표시하며 합산 진행률은 제공하지 않는다. U3의 repo당 개발 Pod·Guardrail Pod 둘(각 컨테이너 하나), 중앙 단일 활성 코디네이터를 유지한다. 같은 호스트 단계는 컨테이너 둘이고 각 supervisor는 자기 역할만 제어한다. 이번 기준선 변경은 P36 한 작업/실험만 추가한다. 기존 ID는 유지한다.

**다음은 첫 작업부터 지켜야 하는 운영 지시다. 자동 보고 기능을 먼저 개발해야 이 지시를 적용하는 것이 아니다.** 현재 개발 에이전트가 state.json만 진행 원본으로 갱신하고 제공된 scripts/render_progress.py로 화면을 만든 뒤 같은 개발 대화에 링크와 요약을 반환한다. STATUS/TASKS/RESULTS는 손편집하지 않는다. 이후 구현한 보고 기능이 이 역할을 넘겨받아도 경로와 의미를 유지한다.

시작 전에 묶음의 현재 계획·명세와 `scripts/`, `progress/`, `reports/`를 실제 작업 repo의 **`docs/poc/`** 아래 같은 상대 구조로 둔다. 실제 repo가 아직 미정이면 현재 개발 호스트의 PoC 작업 루트에 같은 `docs/poc/`를 먼저 두고 준비 작업을 보고한다. 01에서 repo를 확정해 옮길 때 기존 STATUS에 새 위치 안내를 남기고 같은 대화에 링크 변경을 알린다. 보고 서비스를 먼저 개발하거나 원격 repo 생성을 기다려야 초기 보고를 하는 구조로 만들지 않는다. 테스트 대상 NodeKit/Sori의 별도 배정과 혼동하지 않는다. 논문/PDF 등 원문은 기존 승인된 참고 위치를 사용할 수 있으나 실제 열리는 링크를 인덱스에 남긴다. 원문·로그 전부를 제품 소스 브랜치에 자동 커밋하라는 지시가 아니다.

개발 에이전트의 **첫 응답**에는 적용 계획 v1.3.3, 실제 `docs/poc` 절대 경로, 사용자가 열 수 있는 **STATUS.md의 고정 링크**, 주계획 0/73·후속 0/12, 다음 01-01, 결정 필요/미확정 항목을 쓴다. 공유 작업공간의 파일 열람 기능이나 기존 승인된 산출물 전달 경로로 실제 링크를 확인한다. 단순 서버 내부 경로를 사용자에게 읽을 수 있는 링크라고 주장하지 않는다. 사용자의 읽음 ACK를 다음 작업의 선행으로 요구하지 않는다.

이 압축파일은 전달 시점의 초기 스냅샷이다. 실제 진행은 **개발 호스트의 고정 STATUS 링크**에서 본다. 이미 내려받은 ZIP이 자동 갱신되는 것으로 설명하지 않는다. 개발 호스트/대화가 파일 공개를 지원하지 않으면 동일 개발 대화의 텍스트 요약과 기존 승인된 첨부 경로로 최신 보고를 제공하고 `REPORT_VISIBILITY_UNKNOWN`을 기록한다. 새 서비스/예약이나 외부 메시지 채널을 임의로 만들지 않는다.

## 2. 고정 파일 위치와 읽는 순서

모든 아래 경로는 실제 repo 루트 기준이다. 묶음 안에서는 `docs/poc/`를 제외한 같은 상대 경로를 사용한다.

| 위치 | 역할과 독자 |
| --- | --- |
| `docs/poc/progress/STATUS.md` | 사용자의 시작점. 주계획·후속의 별도 수량, 현재 작업, 최근 결과, 막힌 이유, 다음 행동, 필요한 결정, 상세 링크 |
| `docs/poc/progress/TASKS.md` | 주계획 73개와 후속 12개 전수 작업 상태·최근 결과 보고 링크 |
| `docs/poc/progress/RESULTS.md` | 주계획 31개 실험과 후속 5개 후보의 모든 회차/비교/채택 처분 인덱스 |
| `docs/poc/progress/state.json` | 위 화면을 만드는 진행 원장. 작업 ID·상태·증거·회차·시각·snapshot_id의 원본 |
| `docs/poc/progress/events.jsonl` | state.json의 events에서 생성한 변경 이력. 손편집하지 않으며 단순 재조회로 완료 수를 늘리지 않음 |
| `docs/poc/progress/RESUME.md` | state.json의 resume에서 생성한 마지막 확인 지점·작업공간·SHA·미확인 외부 효과·다음 행동 |
| `docs/poc/reports/tasks/<task_id>/<run_id>/REPORT.md` | 설계·준비·구현·검수 작업 결과. 코드/PR/원본 검증과 연결 |
| `docs/poc/reports/experiments/<experiment_id>/<run_id>/REPORT.md` | 실험별 회차의 가설·환경·기대/실측·판정·비용·채택/보류/기각 |
| 같은 회차의 `result.json`, `evidence/` | 구조화 결과와 원본 로그/수치/스크린샷 등 필요한 증거. 자격 증명·비밀 값 제외 |
| `docs/poc/reports/templates/` | 작업/실험/중단·재개/대화 요약 양식 |

`run_id`는 회차 시작 시 한 번 정한 고유 ID다. ID를 바꾸어 같은 시도를 새 성과로 세지 않는다. 완료한 보고/원본은 덮어쓰지 않고 교정본·재시험에 새 run_id/revision과 이전 참조를 붙인다. 작업 보고가 실험 보고를 사용하면 링크로 연결하고 로그/비용을 중복 계산하지 않는다. 같은 분자의 결과가 여러 파일에 있다고 완료 수를 늘리지 않는다.

원장의 `latest_report`와 파일 증거 참조는 **docs/poc 루트 기준 상대 경로**(예: `reports/tasks/01-01/<run_id>/REPORT.md`)다. progress 아래 Markdown에서는 `../reports/...`로 링크한다. 절대 경로·상위 경로 이탈·아직 생성하지 않은 파일을 정상 최신 보고 링크로 기록하지 않는다. 외부 PR/CI 증거는 원본 URL과 대상 SHA/실행 ID를 함께 보존한다.

## 3. 갱신·전달 시점

| 사건 | 반드시 할 일 |
| --- | --- |
| 작업 착수/단계 전환 | 원장에 현재 작업·역할·단계·최근 실제 관측 시각을 기록하고 STATUS를 갱신한다. 의도한 착수와 실제 첫 행동을 구분한다. |
| 구현 산출물 또는 실험 회차 종료 | 먼저 REPORT/result/원본 증거를 저장한다. 원장과 인덱스를 갱신한 뒤 같은 개발 대화에 결과·파일 링크를 반환한다. 다음 의존 작업을 시작하기 전에 마친다. |
| FAIL/INCONCLUSIVE·보류·사용자 결정 | 원인·영향·다음 담당·재개 조건을 즉시 기록하고 같은 대화에 알린다. 변화 없는 같은 대기는 중복 알림을 만들지 않는다. |
| 작업 중 오래 걸리는 실행 | 실제 제어를 돌려받는 지점에서 최근 관측을 기록한다. 제어를 돌려받는 지점마다 원장을 갱신하고 생성기를 실행한다. 도구가 장시간 응답하지 않으면 마지막 관측 시각과 `관측 지연`을 표시하고 성공으로 추정하지 않는다. 별도 예약을 만드는 뜻이 아니다. |
| 의도적인 종료·컨텍스트 교체 | 중단 전에 원장의 resume을 작성하고 생성기를 실행해 현재 인덱스와 연결한다. |
| 강제 종료·네트워크/프로세스 장애 뒤 재개 | RESUME·원장·실제 파일/GitHub/미확인 외부 요청을 대조한 뒤 작업을 이어간다. 빠진 보고/인덱스부터 복구하고 이미 수행한 외부 변경을 재발행하지 않는다. |

일반 결과는 **다음 의존 작업 착수 전**에 반영하고 **제어를 돌려받는 지점마다** 마지막 실제 관측과 전달 상태를 갱신한다. 강제 종료 중 즉시 알림을 보장했다고 쓰지 않는다. 자동 보고가 구현되기 전에는 현재 개발 에이전트가 원장 갱신과 생성기 실행을 맡고, 관측 지연은 다음 응답에 명시한다. 구현 후에는 기존 보고 v0/outbox 계약과 같은 의미로 전환한다.

**채널은 현재 개발 대화/작업 스레드와 공유 파일이다.** Slack·이메일·Notion 발송이나 새 자동화를 추가하지 않는다. 보고 저장과 대화 전달은 별도 상태(`pending/sent/unknown`)로 기록한다. 응답 유실은 보고 미저장·실험 실패와 구분하고 기존 보고 ID로 확인한다. 실제 수신을 확인하지 못하면 `unknown`을 유지한다.

## 4. 상태와 진행률 계산

작업 상태는 기존 일곱 가지를 사용한다: 미착수·준비됨·진행·검수 중·검수 완료·조건 대기·종료 미충족. **증거와 요구된 독립 검수 없는 완료 주장은 검수 완료에 포함하지 않는다.** 원 작업이 재검증을 요구하면 관련 수용 근거의 유효성을 갱신하고 과거 버전 결과는 남긴다.

| 지표 | 계산·주의 |
| --- | --- |
| 주계획 | 검수 완료 수 / 73. 상태별 작업 수의 합은 73 |
| 후속 | 검수 완료 수 / 12. 상태별 작업 수의 합은 12 |
| 실험 평가 종료 | 주계획 종료/31, 후속 후보 종료/5. 성공·실패·판정 불가와 채택 처분을 별도 표시 |
| 필수 기능/전환 | S0/S1/S2/S3·P26·P27-L의 실제 증거를 개별 표시. 실험 평가 종료 수와 합치지 않음 |

유효하게 평가하고 기각한 선택적 방법은 평가 작업을 종료할 수 있다. 실패한 필수 검증을 보고했다는 사실은 해당 작업 검수 완료가 아니다. 다른 repo/언어/회차·재실험·S0~S3를 새 작업으로 더하지 않는다. 기준선을 바꿀 때만 원/변경 분모·요구·근거를 함께 기록한다. 보류 중인 과업을 삭제해 진행률을 높이지 않는다.

## 5. 각 결과에서 바로 확인할 내용

보고에는 계획·작업/실험·회차·현재 단계, 적용 명세/카탈로그/프로파일/모델·도구 버전, 커밋 SHA·이미지 digest, 실행 환경/권한, 가설과 검증 방법, 독립 기대값·실측값·수치/분모·PASS/FAIL/INCONCLUSIVE, 코드/PR/로그 링크, 시간·부모/자식 전체 토큰·사람 개입, 남은 문제·다음 행동을 남긴다. 모의/실제·작성/validation/최종 평가를 구분한다. 해당 없음/미계측에는 이유를 쓰고 0으로 대체하지 않는다.

평가/FAIL/INCONCLUSIVE는 채택·부분 채택·보류·기각, 필요한 추가 실험/대안·누적 한도·재개/종료 조건과 재사용할 모듈의 경로/SHA/검증 범위를 적는다. 검증 PASS는 원본 증거·독립 확인 링크로 충분하다. 아직 얻지 않은 결과는 `미실행`, 관측 불충분은 `INCONCLUSIVE`로 남긴다. 프로세스 종료나 에이전트의 자기 평가만으로 코디네이터가 판정한 PASS로 쓰지 않는다.

## 6. 저장·갱신·복원 순서

이 원장은 PoC를 개발하는 작업의 진척/보고를 위한 것이다. 제품 코디네이터의 배정·사건·판정 정본은 계획 1.1/1.5절의 외부 DB이며, 이 보완으로 state.json에 이전하는 것이 아니다.

1. 회차의 원본 로그·명령·SHA·실측을 불변 증거로 보존한다. REPORT/result.json은 해당 회차 증거이며 작업/진행 상태의 별도 원장으로 편집하지 않는다. 같은 사실을 여러 보고에 수작업 전사할 필요 없이 한 회차 보고를 참조한다.
2. 한 reporting owner가 `progress/state.json`의 작업·실험 runs·events·resume·전달 상태를 갱신한다. Guardrail의 원본 판정은 수정하지 않고 참조한다. 임시 파일 작성 후 교체하고 구버전을 보존한다. 보고 ref는 docs/poc 기준 상대 경로이며 미생성 경로를 최신 링크로 기록하지 않는다.
3. docs/poc에서 `python3 scripts/render_progress.py`를 실행한다. STATUS/TASKS/RESULTS, events.jsonl, RESUME.md는 이 스크립트가 같은 snapshot_id/실제 원장 SHA-256으로 생성한다. 개별 화면을 손편집하지 않는다. `--check`는 재생성 예상값과 저장된 화면이 같은지 확인한다. 생성 중 끊기면 원장으로 다시 실행하며 혼합 snapshot을 최신 완료로 해석하지 않는다.
4. 다음 의존 작업 착수 전과 제어를 돌려받는 지점마다 같은 대화에 결과/링크를 보낸다. 파일 저장과 전달은 별도다. 전달 상태를 원장에 바꾸면 다시 생성한다. 불확실한 수신을 sent로 올리지 않는다.

생성기는 01-06의 기존 산출물에 포함되며 이 묶음에도 초기 도구를 제공했다. 첫 응답부터 실행할 수 있지만 현장 경로·권한/증거·정상/실패 입력의 검수는 01-06에서 한다. 제공 사실을 새 작업/검수 완료로 세지 않는다. 전체 보고 서버를 먼저 구현하지 않는다. 소스 변경 PR과 보고 산출물을 구분해 보고 갱신으로 검토 중 head를 바꾸지 않는다.

원장의 `experiments[].runs[]`는 `run_id`, `revision`, `observed_at`, `verdict`, `latest_report`, `evidence`와 필요한 `expected`, `observed`, `cost`, `adoption`, `unresolved`, `next_action`을 담는다. 같은 회차의 후속 revision은 원 참조를 남긴다. 작업 최신 보고·모든 실험 회차·미해결이 화면에서 빠지지 않아야 한다. 검수 완료는 `verification_level=verified`와 실제 증거 참조가 있는 경우만 기록하며 생성기가 독립 검수/실제 실행을 대신하지 않는다. 초기 원장은 전부 미실행이다.

**검토와 push:** 작업 하나에 PR 하나, repo당 열린 수정 PR 하나다. 검토 제출 뒤 개발은 REVIEW_PENDING으로 기다린다. 반려를 받은 교정 단계에서만 push한다. 새 head를 관측한 코디네이터는 이전 검토 배정을 무효화하고 새 SHA에 재배정한다. 옛 결과는 보존하되 현재 판정에 쓰지 않는다. 병합 요청은 승인 head SHA의 서버 측 조건을 지정하고 불일치 시 병합하지 않는다. 의존하는 다음 작업은 병합과 병합 SHA의 main CI 뒤에 배정한다. P07의 역할 격리/경쟁 시험은 S0 전에 통과해야 한다. P26에는 검토 대기 때문에 개발이 쉰 시간과 한도로 인한 정지 건수/시간을 따로 기록한다.

## 7. 중단과 다음 에이전트의 재개

원장의 resume에는 마지막 검증 단계, 코드/worktree/branch/SHA, 현재 명세·이미지·프로파일, 실행 중인 명령/CI/검토와 식별자, 미확인 외부 효과, 저장된 보고, 아직 갱신 못 한 인덱스, 다음 담당/명령·재개 조건을 남긴다. 비밀 값은 넣지 않는다. 다음 에이전트는 오래된 대화 요약 대신 이 기록과 현재 외부 상태를 대조한다. 승인 범위 안의 정상 재개마다 사용자에게 다시 지시를 요구하지 않는다.

## 9. 이번 리뷰의 실행 순서

01-01부터 수행하고 01-02에서 공식 근거의 런타임 비교표와 권고안을 낸 뒤 사용자 선택을 받는다. 선택을 관측하지 않고 승인으로 기록하지 않는다. 01-04는 동시 두 세션과 자격/한도 분리 두 probe부터 실행한다. 하나라도 불가/관측 불가이면 이후 준비·제품 작업을 진행하지 말고 원 로그·영향·대안을 보고한다. [개정 v1.3.3-A1](Amendment_v1.3.3-A1.md) 이후 진행/중단은 판정표 A1-GATE-01-04를 따른다: 한도 공유 확인은 지원 구성으로 기록하고 진행하며, 동시 실행 불가·역할 자격 격리 실패/미확인·한도 구조 관측 불가는 중단이다. 01 스프린트 종료 시 산출물과 원본 probe를 독립 검토에 전달한다.
