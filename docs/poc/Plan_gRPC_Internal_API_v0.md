## 1. 범위

- **대상**: 코디네이터와 실행 관리 서비스(역할 Pod의 supervisor) 사이의 내부 API. 지금은 HTTP/JSON(`contracts/ieo-api-v0.openapi.yaml`, `crates/ieo-coord`)이다.
- **대상 아님**: Claude CLI 실행 방식(supervisor가 같은 컨테이너에서 프로세스로 실행), GitHub·Notion 외부 API 연결.
- **유지**: 기존 HTTP/JSON 계약과 시험. gRPC는 경로를 **추가**한다.
- **gRPC 표면(초안, X-03에서 확정)**: supervisor가 코디네이터에 하는 호출(배정 조회·인수, 체크포인트·세대·순번 보고, 증거·결과 제출, 세션 상태)과 그에 필요한 기존 작업(배정·증거·판정 조회). 사람·등록자용 작업(명세 등록·의미 검토·Notion 가져오기·예외 승인)은 HTTP/JSON에 둔다.
- **새 작업의 HTTP 형태**: 02-05에서 새로 생기는 작업도 작업 표에 한 번만 정의한다. 두 전송이 같은 표로 보내므로 업무 규칙은 하나다. HTTP/JSON 형태를 함께 둘지는 X-03에서 작업마다 정한다. 기본은 함께 두는 것이다(기존 HTTP 시험 체계로 규칙을 검증할 수 있게).

| 롤백 | 요청 단위 트랜잭션 | 같음(같은 `handle`) |

## 3. 미리 분리할 부분과 영향(구현 전에 확인)

- **확인한 사실(코드 읽기)**: `api::handle`은 이미 전송과 무관하다. `http.rs`(약 100줄)는 tiny_http 요청을 `Req`로 바꾸고 `Resp`를 응답으로 옮기는 얇은 어댑터다. 업무 규칙은 HTTP 헤더·소켓을 보지 않는다.
- **gRPC 어댑터가 똑같이 해야 하는 `http.rs`·`handle`의 전송 쪽 동작**: 본문 1 MiB 상한(넘으면 400 `SCHEMA_VIOLATION`), 작업자별 DB 재연결(실패하면 500), 인증 없이 트랜잭션 밖에서 답하는 `/v0/health`. 이 동작을 gRPC에서 어떻게 표현할지(메시지 크기 상한·`UNAVAILABLE`·health 서비스) X-03에 적는다.
- **분리 후보(X-04 첫 단계, 동작 변경 없음)**:
  1. `handle` 안의 경로 일치(method + path 조각)를 **작업 표**(`Operation` 열거)로 뽑는다. HTTP와 gRPC가 같은 표로 보내게 하여 두 경로가 갈라지지 않게 한다. 기존 HTTP 시험이 그대로 통과해야 한다.
  2. 상태 코드는 지금 HTTP 숫자(`u16`)다. 내부 표현은 그대로 두고 gRPC 어댑터에 대응표만 둔다. 업무 규칙 쪽을 바꾸지 않는다.
- **런타임**: 지금은 동기(tiny_http, postgres 동기 클라이언트, 작업자 스레드마다 DB 연결 하나)다. Rust gRPC 서버(후보 tonic)는 비동기(tokio)다. 동기 `handle`을 `spawn_blocking` 또는 별도 작업자 풀에서 부르면 규칙은 그대로 쓸 수 있다. 같은 바이너리에 둘지 별도 바이너리로 둘지는 X-04 설계에서 정한다.
- **02-04 영향**: supervisor가 코디네이터에 체크포인트 digest·순번을 보고하는 부분이 생기면, 호출을 `CoordinatorClient` 같은 경계 뒤에 둔다. 02-04는 기존 HTTP로 진행하고, gRPC 전환은 X-04·02-05에서 한다. 02-04의 수용 기준은 바꾸지 않는다.

## 4. 계약에 명시할 것(X-03)

`contracts/ieo-internal-v0.proto`(가칭)와 설명 문서로 정한다.

1. **서비스·메시지와 버전 호환**: 패키지 `ieo.internal.v0`. 필드 번호를 다시 쓰지 않는다. 필드를 지우면 `reserved`로 막는다. 호환되지 않는 변경은 새 패키지(`v1`)로 한다. 기존 OpenAPI 0.8 계약과 같은 업무 의미를 쓴다.
2. **인증과 역할별 권한**: metadata Bearer 토큰. HTTP와 같은 `Credentials`·범위 표를 쓴다. 에이전트 자격의 금지 범위도 같다.
3. **상태 코드 대응과 상세 오류 사유**: 400→INVALID_ARGUMENT, 401→UNAUTHENTICATED, 403→PERMISSION_DENIED, 404→NOT_FOUND, 409→ABORTED(동시성·CAS) 또는 ALREADY_EXISTS·FAILED_PRECONDITION(내용 충돌·선행 조건), 422→FAILED_PRECONDITION, 500→INTERNAL, 503→UNAVAILABLE. 구체 대응은 기존 `code`(예: `OWNERSHIP_CONFLICT`, `IMPORT_GATED`)마다 표로 고정한다. 상세 사유는 같은 `code`·`rejections[]`를 오류 메시지 상세로 보낸다.
4. **재시도 가능 여부와 멱등**: 작업마다 재시도 가능 여부를 표로 정한다. 상태를 바꾸는 작업은 멱등 키나 (assignment_id, generation) 같은 식별자 없이는 재시도하지 않는다. 연결 실패만으로 재실행하지 않는다. 같은 키로 재조회해 서버의 실제 반영 여부를 먼저 확인한다(사용자 결정 §5).
5. **제한 시간과 취소**: 클라이언트 deadline을 서버가 지킨다. 트랜잭션 커밋 전에 취소되면 롤백한다. 커밋 뒤에 연결이 끊기면 반영된 상태다. 클라이언트는 같은 키로 재조회해 결과를 얻는다. 서버 쪽 최대 처리 시간도 정한다.
6. **긴 스트림(필요한 작업만)**: 스트림의 각 항목에 순번을 붙인다. 끊기면 클라이언트가 마지막으로 받은 순번부터 다시 연다. 이미 연 스트림이 다른 Pod로 옮겨 간다고 가정하지 않는다.

## 5. 서비스 발견·분산·장애 복구(X-05 설계, 원칙)

> “특정 CNI 확장 기능 없이도 gRPC의 서비스 발견·요청 분산·장애 복구를 제공하며, 환경별 확장 기능은 선택적으로 활용한다.”

- **기본·폴백 경로(우선 검토)**: Kubernetes Headless Service(Pod별 A 레코드) + 클라이언트 측 분산.
- **확인할 라이브러리 지원(아직 확인 안 함, X-05 시작 때 정확한 버전의 소스·문서와 실험으로 확인)**:
  - 여러 Pod 주소 발견 — 후보: Headless Service DNS를 주기적으로 조회해 주소 집합을 만든다.
  - Pod 추가·삭제·교체에 따른 주소 목록 갱신 — 후보: tonic `Channel::balance_channel`이 받는 추가/삭제 변경 통지.
  - 사용 가능한 연결 사이의 RPC 분산 — 후보: tower의 balance(P2C).
  - 연결 실패 감지와 재연결 — 후보: 연결 재시도와 HTTP/2 keepalive 설정.
- **대안**: 위 지원이 부족하면 독립 gRPC L7 프록시(예: Envoy) 하나를 고른다. 선택 근거와 필요한 구성요소를 기록한다. 여러 방식을 모두 구현하지 않는다. 폴백에서도 gRPC를 유지한다.
- 사용한 분산 경로와 설정은 배포 구성에 적는다.
- **Cilium(X-07)**: 별도 kind 구성의 추가 검증이다. 미실행이어도 다른 작업을 막지 않는다.

## 7. 검증 기준을 미리 정하는 규칙(X-05·X-06)

- 관측 시간, 요청 수, 허용 편차, 복구 제한 시간, 실패 기준은 실행 **전에** 근거와 함께 커밋한다(예: `docs/poc/reports/extra/X-05/criteria.md`). 결과를 본 뒤 바꾸지 않는다.
- 새 RPC의 분산과 기존 스트림의 복구는 따로 판정한다. 클라이언트·채널을 재사용하는 조건에서 분산을 본다.
- 서버 응답에 Pod 식별자와 요청 ID를 남긴다. 시험용 서버의 결과와 실제 코디네이터의 결과를 구분해 보고한다.
- 기존 개발 클러스터와 운영 DB를 쓰지 않는다. 호스트 자원을 확인하고, 필요하면 기본 kind와 Cilium 구성을 순차로 실행한다.

## 8. 표현의 한계

kind에서 통과한 결과는 물리 서버 장애, 실제 서버 간 네트워크 단절, 운영 처리량 검증을 뜻하지 않는다. 보고에 실제 다중 서버 환경으로 남긴 검증을 따로 적는다.
