# Opt-in Codex trial adapter

This isolated adapter is based on #106 merge `9e220a4d49b0db9d26d46422a20a4f1c811256b0`. The local App Server 0.169.1 schema and the existing mock/role-readiness evidence informed the implementation. Verification ran only against a fake executable over stdio.

## Launcher interface

The external caller invokes `adapter.py --delivery-id ID --attempt-id ID --cwd DIR --state DIR --codex ABSOLUTE_BINARY --model PINNED_MODEL --enable-trial`. It supplies one newline-terminated JSON string, an exact `{"prompt":"..."}` object, or one text block in the existing Claude user envelope on stdin. The adapter relays the text through the Codex protocol. The state directory must already exist, have mode 0700 and be owned by the execution UID. The launcher supplies the isolated `HOME` and `CODEX_HOME`; all other inherited variables are stripped when starting the child. The caller must pin the binary and trusted configuration, confine the filesystem and egress, and protect this durable state across attempts. The opt-in flag is a launcher interlock, not a substitute for caller approval.

The adapter runs initialize/config/account checks, asks for a fresh ephemeral read-only thread with the pinned model, and rechecks the thread's effective settings. Only a ChatGPT account type is accepted, read without token refresh. The fixed RPC sequence sends one `turn/start` after synchronizing the durable intent to disk. The per-delivery lock blocks concurrent reuse. An existing complete, partial, or unknown intent prevents launching another child for that ID. The existing caller must enforce its shared assignment/budget lock and one authorized delivery across distinct IDs.

For a matching successful `turn/completed`, stdout is exactly one JSON line of type `ieo_codex_trial_receipt` with delivery_id, attempt_id, thread_id, turn_id, result and auth. `usage` is absent because token notifications do not establish final usage. Treat absence as unmeasured, never as zero. A receipt establishes an observed completed turn, while repository effects and independent usage remain the caller's evidence obligations. Failed/ambiguous operations return nonzero and no receipt. An already stored receipt stays in state for separate reconciliation, never via re-execution.

Post-intent parsed events are retained in `STATE/DELIVERY/events.jsonl`. `state.json` records intent, observed status, IDs and the last matching cumulative snapshot on completion. Early start notifications cannot bind the RPC without a matching ACK. Regressing counters, mismatched identifiers, unexpected server requests and failed turns block a receipt. Diagnostic stderr never carries provider payloads. No Claude-compatible stream or synthesized billing row is generated.

## Integrated supervisor candidate

The isolated development role recognizes an administrator-controlled executable named `codex-trial-bridge` in its read-only role configuration directory. The supervisor requires a pinned checkpoint, central coordinator, a fresh read-only development session, a 120-second-or-shorter guard window and matching, unexpired trial approval for the assignment generation, head, checkpoint and model. It reserves the isolated role once before starting the bridge. The bridge uses the caller's existing output collection; the shared ledger records the admitted delivery ID, associated thread/turn, and completed result. Observed counters are separate from authoritative final usage. Missing final usage is unmeasured and the trial stops.

The same adapter's `--preflight-only` mode checks its effective config, ChatGPT account and limits without creating a thread or turn. An isolated read-only bind mount of the designated host subscription passed this query. Actual role provisioning, account-bound no-extra-charge admission and final provider usage assurance remain pending. The existing caller's admission evidence is Claude-specific; reuse of a Claude rate-limit event for Codex would be invalid. No execution approval file was installed.

## Pre-dispatch subscription gate

The caller checks the isolated role's bearer-authenticated `GET /v0/role/codex-preflight` while holding the shared ledger reservation, before writing an in-flight marker or posting a run. It checks the assignment and generation, head and checkpoint pin, runtime and expiry. The role repeats the checks before acceptance. Claude's observation is kept on the Claude path. The trial still uses shared and per-role budget arithmetic.

The trial approval file must bind the assigned subscription credential digest and applicable quota bucket. Role setup must supply the evidence for disabled auto-reload, blocked paid paths and blocked API fallback before installing approval. The gate rejects an unexpected local Codex config, a changed credential, an expired approval, an unavailable bucket, and nonzero or unknown credits. A quota response cannot itself verify paid-path controls. Do not populate the approval attestations from the mock fixtures or from the user's zero-credit balance alone.

## Dispatch fence and immutable credential

After the slow role preflight, the coordinator checks stop and the monotonic delivery deadline again. The caller checks it before creating the in-flight marker, and the HTTP transport repeats it after loading the adapter token and serializing the body, immediately before invoking the POST. If the fence closes there, the caller clears the marker and records a local `not_called` outcome. A rejection received over HTTP remains a remote refusal. The coordinator records the hash of the actual POST body, including the pinned approval digest, for later read-only reconciliation.

The GET preflight returns the digest of the approval it checked. The role requires that same digest on POST and again at launch. The adapter receives `--auth-sha256`, `--approval`, `--approval-sha256`, and `--authorization-expires-unix`. It checks the approval before launching the child and again at the turn write. In the assigned role it requires an exact read-only file mount of `auth.json` in a read-only credential home, a non-symlink inode protected by Linux fs-verity (x86-64/aarch64), and the approved byte digest. A read-only alias alone cannot prevent writes to the backing inode. The verifier measures fs-verity and hashes from the opened file descriptor. It never provisions verity, rewrites the source, or copies authentication into a new file. It rechecks the credential before the turn. The trusted launcher still owns the mount namespace and binary; this does not defend against privileged remount or prove a real assigned home is provisioned.

The effective authorization end is the earlier of central approval expiration and 300 seconds after the administrator's billing observation. Missing, future, or expired observations and false attestations are refused. This candidate uses a five-minute local maximum age; it cannot establish USD 0 enforcement or rule out a credit change after a lookup. The existing read-only lookup does not establish an fs-verity-protected assigned credential mount.

The plan in `a3feef9` and the evidence boundary in `fe59c09` govern live execution. Internal provider request counts and 4,000 billable / 20,000 cache-read tokens are observations; they are not provider-side caps or deductions from a single turn. These fixes do not change shared budget arithmetic or make observed usage final.

## Required prior evidence for trial admission

Authorized preflight and launch require a centrally reviewed, read-only role record `codex-trial-prerequisites.json`. The same central approval used for dispatch pins its SHA-256 as `prerequisites_sha256`. Install the adapter and its sibling `prerequisites.py` together. The supervisor checks the pin before preflight and launch. The bridge checks and parses the two pinned files before starting Codex and repeats the check immediately before writing `turn/start`. An unbound `--preflight-only` diagnostic has no dispatch authority and emits no authorization expiry or workspace binding.

The review schema is `ieo.codex-trial-prerequisites/v1`. Its `scope` must exactly match the approval's assignment ID/generation, target SHA, checkpoint SHA-256, model, quota `limit_id`, auth SHA-256, Codex workspace UUID, and approved Claude account/quota-group/window IDs. The bridge sets `forced_chatgpt_workspace_id` to that UUID and checks the runtime's effective setting. A profile whose workspace cannot be verified and pinned remains ineligible.

| Review entry | Required state and evidence |
| --- | --- |
| `workspace_credit_spend` | `verified_blocked`, source `workspace_admin_policy`, proof SHA-256, observation time and enforcement end. Obtain an enforceable workspace policy for blocking credit spend, including paid reset or credit consumption. A zero balance, auto-reload OFF, or RPC field showing unspent capacity cannot establish this control. |
| `concurrent_credit_changes` | `verified_excluded`, source `account_wide_enforced_freeze`, proof SHA-256, observation time and enforcement end. Establish a control covering other sessions, account owners and automation that can change credits or paid state. A pair of read snapshots cannot rule out concurrent writes. |
| `claude_quota` | `naturally_exhausted`, source `operator_usage_screen`, proof SHA-256, observation and reset UTC time, `limit_kind=included_subscription`, `extra_usage=disabled`. Observe the approved Claude account and applicable window after natural exhaustion. Establish UTC reset, operator and evidence, and repeat after reset. |

The five-minute freshness limit applies to every observation. The authorized start must leave the entire 120-second guarded local window before Claude reset and before the two enforcement periods end. The bridge returns the tightened expiry through role preflight; the coordinator uses it at its POST fence, then the role and the adapter recheck it. Local process termination does not prove the provider stopped by reset.

The central approver must inspect the original evidence before publishing the digests; the runtime validates the scope, freshness and integrity of these attestations and cannot establish the external controls by itself. No production approval or prerequisite record was created. The observed personal subscription balance and lack of a separate switch have not established an enforceable workspace policy or account-wide freeze. The existing Claude screen and query results are historical observations and cannot replace a fresh approved record. Leave these conditions unverified and the trial in `WAITING_FOR_PREREQUISITE` until the real evidence exists.
